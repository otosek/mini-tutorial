Ten tutorial to ściąga governance tożsamości i kont w AWS: jak grupujesz konta, jak narzucasz twarde limity z góry, jak działają polityki IAM i jak logujesz ludzi (IDC / Directory) oraz budujesz landing zone (Control Tower). Nie obejmuje EC2, S3 ani Lamdy poza miejscami, gdzie polityka ich dotyczy.

1. AWS Organizations

Po co: jedna organizacja zamiast luźnych kont e-mailowych. Management account (dawniej master) tworzy / zaprasza member accounts, układa je w drzewo OU (Organizational Units), centralizuje billing (consolidated billing) i jest punktem zaczepienia dla SCP, CloudTrail org, Config aggregators i Control Tower.

Management vs member

Management — tylko governance, billing, rzadko workload. Workload (prod/dev) = member accounts. Root użytkownika managementu to krytyczny sekret.

OU (Organizational Units)

Foldery kont: np. Security, Infrastructure, Sandbox, Workloads/Prod, Workloads/NonProd. Polityki org przypinasz do OU — dziedziczą je wszystkie konta poniżej.

Root
├── Security OU          (Log Archive, Audit)
├── Infrastructure OU    (Shared networking, CI)
├── Sandbox OU
└── Workloads OU
    ├── Prod OU
    └── NonProd OU

Przykład użycia: nowe konto aplikacji = automatycznie w Workloads/NonProd, dostaje SCP „zakaz regionów spoza eu-central-1” i tagi z cost center, bez ręcznego klikania w każdym koncie.

Pułapka: trzymanie produkcji w management account. Awaria lub kompromitacja tego konta = cała organizacja.

2. Organization Policies

Po co: twarde reguły na poziomie organizacji — obowiązują niezależnie od tego, co administrator member account ustawi w IAM. To nie zastępuje IAM; to górny sufit uprawnień i konfiguracji.

TypPo coPrzykład
SCP (Service Control Policy)Maksymalny zakres API, które konto / OU w ogóle może wywołać (identity-based i tak muszą pozwolić)Deny ec2:* poza eu-central-1; Deny usuwania CloudTrail
RCP (Resource Control Policy)Ogranicza, kto może dostać dostęp do zasobów konta (np. tylko principal z tej org)Zakaz publicznych bucketów / ról trust spoza organizacji
Declarative policiesWymuszenie konfiguracji usług (np. ustawienia EC2/VPC) bez skryptów w każdym koncieJednolita konfiguracja w całej OU
Tag policiesWymuszanie / walidacja kluczy tagówCostCenter, Owner obowiązkowe
Backup policiesCentralne plany AWS BackupCodzienny backup RDS w Prod OU
AI opt-out / Chatbot / etc.Zgody i limity usług AI / komunikacyjnych na poziomie orgOpt-out z użycia danych do trenowania modeli
 
// SCP — tylko Europa Centralna (uproszczony szkic)
{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "DenyOutsideFrankfurt",
    "Effect": "Deny",
    "NotAction": ["iam:*", "organizations:*", "sts:*", "support:*"],
    "Resource": "*",
    "Condition": {
      "StringNotEquals": { "aws:RequestedRegion": "eu-central-1" }
    }
  }]
}
SCP ≠ grant. SCP może tylko ograniczać (efektywne uprawnienie = IAM ∩ SCP). Puste / zbyt ostre SCP potrafi odciąć Cię od konta — zawsze zostaw ścieżkę awaryjną dla ról admina / break-glass i testuj na Sandbox OU.

3. IAM — advanced policy (identity-based)

Po co: klasyczna polityka przypięta do usera, grupy lub roli (identity). „Advanced” to nie osobny produkt — to wzorce poza prostym Action + Resource: *: warunki, zmienne polityki, permissions boundaries, session policies.

MechanizmPo co
Condition keysaws:SourceIp, aws:PrincipalTag, aws:RequestedRegion, s3:prefix — dostęp tylko gdy kontekst się zgadza
Policy variables${aws:username}, ${aws:PrincipalTag/team} — jedna polityka, wielu użytkowników
Permissions boundaryMaksymalny zestaw uprawnień, jaki rola/user w ogóle może mieć — nawet jeśli ktoś doklei AdministratorAccess
Session policyDodatkowe zawężenie przy AssumeRole / federacji (np. CI dostaje tylko deploy do jednego środowiska)
ABAC (atrybuty)Uprawnienia po tagach principal ↔ resource zamiast setek ról per zespół
 
// Identity policy — developer widzi tylko swój prefiks w S3
{
  "Effect": "Allow",
  "Action": ["s3:GetObject", "s3:PutObject"],
  "Resource": "arn:aws:s3:::app-artifacts/${aws:PrincipalTag/team}/*"
}

// Permissions boundary — nawet admin team nie wyjdzie poza ten sufit
{
  "Effect": "Allow",
  "Action": ["s3:*", "ecr:*", "logs:*", "cloudwatch:*"],
  "Resource": "*"
}

Przykład: rola CI/CD ma boundary bez iam:CreateUser; pipeline może deployować do ECS, ale nie utworzy backdoora IAM nawet przy błędnej polityce w pipeline.

4. IAM — resource-based policy

Po co: polityka wisząca na zasobie (S3 bucket policy, SQS queue policy, KMS key policy, Lambda resource policy, ECR, Secrets Manager, API Gateway…). Decyduje, który principal (z tego lub innego konta) może wywołać akcję na tym zasobie. Niezbędna do cross-account i do „publicznego” dostępu (zwykle go unikasz).

Identity-basedResource-based
„Co ja (rola) wolę robić?”„Kto wolno do mnie (zasobu)?”
Na user/group/roleNa bucket / kolejka / klucz / funkcja…
Cross-account: zwykle + trust / resource policyCzęsto jedyny sposób na dostęp z innego konta bez kopiowania identity policy
 
// S3 bucket policy — tylko rola z konta CI w tej samej org
{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "AllowOrgCI",
    "Effect": "Allow",
    "Principal": { "AWS": "arn:aws:iam::111122223333:role/github-actions" },
    "Action": ["s3:GetObject", "s3:PutObject"],
    "Resource": "arn:aws:s3:::release-artifacts/*",
    "Condition": {
      "StringEquals": { "aws:PrincipalOrgID": "o-xxxxxxxxxx" }
    }
  }]
}
Pułapka: "Principal": "*" + Allow na S3/SQS bez twardego Condition = publiczny dostęp. Łącz z Block Public Access i SCP/RCP.

KMS: key policy jest wyjątkowa — bez wpisu w key policy nawet admin IAM może nie użyć klucza. Zawsze zaplanuj root konta + role aplikacyjne w key policy.

5. IAM policy evaluation logic

Po co: zrozumieć, dlaczego AccessDenied mimo „Allow w konsoli”. AWS składa decyzję z wielu warstw; kolejność i Deny mają znaczenie.

1. Domyślnie DENY (implicit deny)
2. SCP / RCP (org) — Deny tu = koniec (nie da się „przebić” IAM Allow)
3. Resource-based / identity-based / permissions boundary / session /
   VPC endpoint policy / SCP Allow-list…
4. Jawny DENY w którejkolwiek obowiązującej polityce wygrywa z Allow
5. Dopiero gdy jest Allow i brak Deny → ALLOW

Uproszczony model same-account vs cross-account:

  • To samo konto: wystarczy Allow w identity lub (dla wielu usług) w resource policy — szczegóły zależą od usługi; przy S3 często obie warstwy patrzą na siebie.
  • Cross-account: zwykle potrzebujesz Allow po stronie identity w koncie A oraz Allow w resource policy / trust w koncie B.
// Dlaczego jest AccessDenied?
// - SCP z Deny na s3:DeleteBucket  →  IAM AdministratorAccess nie pomoże
// - Boundary bez s3:PutObject      →  doklejona polityka Put i tak nie działa
// - Brak Principal w bucket policy przy cross-account
// - Condition aws:SourceVpce nie spełniony (ruch nie z VPC endpoint)

Narzędzia: IAM Policy Simulator, Access Analyzer (external access), CloudTrail errorCode=AccessDenied + encode’owany powód w nowszych odpowiedziach API.

6. AWS IAM Identity Center

Po co: (dawniej AWS SSO) centralne logowanie ludzi do wielu kont Organizations — jeden portal, Permission Sets mapowane na role IAM w member accounts. Zastępuje ręczne IAM users per konto i klasyczne „zakładanie usera w każdym koncie”.

Permission Set

Szablon uprawnień (np. DeveloperAccess, ReadOnly). Identity Center tworzy z niego rolę w wybranych kontach i przypisuje grupy użytkowników.

Źródło tożsamości

Wbudowany katalog IDC, albo zewnętrzny IdP: Microsoft Entra ID, Okta, Ping, Google — SAML/SCIM. Ludzie logują się firmowym SSO, nie osobnym hasłem AWS.

Przykład: grupa Entra aws-developers → Permission Set z PowerUser (bez IAM) → konta w OU NonProd. Prod tylko grupa aws-prod-ops + MFA wymuszony w IdP.

IAM usersIdentity Center
Per konto, długie access keyJedno SSO, krótkie sesje CLI (aws sso login)
Trudny offboardingOffboarding = wyłączenie w IdP / grupie
OK dla break-glass wyjątkówDefault dla ludzi i większości automatyzacji ludzkich
Pułapka: mylenie Identity Center (ludzie → konta AWS) z Cognito (klienci aplikacji). To inne problemy.

7. AWS Directory Services

Po co: managed katalogi (Active Directory / LDAP-like) w AWS — gdy aplikacje lub workstationy potrzebują AD, a nie chcesz stawiać DC na EC2 od zera. Łączy się z IAM Identity Center, WorkSpaces, RDS SQL Server (Windows auth), EC2 domain-join.

OpcjaPo co
AWS Managed Microsoft ADPełne managed AD w VPC — grupy, GPO (ograniczone), trust do on-prem AD; WorkSpaces, RDS, EC2
AD ConnectorProxy do istniejącego on-prem AD — bez kopiowania haseł do chmury; logowanie WorkSpaces / EC2 do korporacyjnego AD
Simple ADTani Samba-compatible katalog — małe środowiska, ograniczone funkcje; rzadziej wybierany do nowych wdrożeń

Przykład: firma ma AD on-prem; WorkSpaces w AWS mają się logować tymi samymi kontami → AD Connector w VPC z linią Direct Connect / VPN do DC. Identity Center federuje się do Entra, a niekoniecznie do Directory Service — Directory to raczej Windows/legacy app world.

Kiedy Directory, kiedy IDC: ludzie do konsoli/CLI AWS → Identity Center (+ Entra). Domain-join Windows, GPO, NTLM/Kerberos dla appów → Directory Service. Często obu używasz równolegle.

8. AWS Control Tower

Po co: gotowa landing zone na Organizations — automatycznie zakłada strukturę OU (Security, Sandbox…), konta Log Archive i Audit, obowiązkowy CloudTrail/Config, guardrails (SCP + Config rules) i Account Factory do provisioningu nowych kont „z szablonu”.

Guardrails

Mandatory / strongly recommended / elective — np. zakaz otwartego SSH 0.0.0.0/0, wymuszenie szyfrowania, zakaz usuwania logów. Część to SCP, część detekcja Config.

Account Factory

Nowe konto z nazwą, OU, emailem — od razu pod guardrails i baseline. Wersja „Account Factory for Terraform” (AFT) dla IaC.

AFT / Customizations

Control Tower ustawia fundament; dalej Customizations for Control Tower (CfCT) albo AFT dokładają role, VPC, pipeline per konto.

Przykład ścieżki: włącz Control Tower w regionie home → powstają Security OU + shared accounts → definiujesz Additional OU Workloads → Account Factory tworzy app-payments-prod → SCP z org + guardrails CT blokują publiczne S3 zanim zespół zdąży „na chwilę otworzyć”.

Sam Organizations + SCPControl Tower

Typowe błędy

  • Workload w management account. Management tylko do org/billing/CT.
  • Traktowanie SCP jak grantu. SCP nie daje uprawnień — tylko je obcina.
  • SCP bez ścieżki break-glass. Możesz zamknąć sobie konsolę; testuj na Sandbox.
  • Publiczny Principal * w resource policy. Zwłaszcza S3/SQS/SNS — łącz z Block Public Access.
  • Cross-account tylko identity Allow. Bez resource/trust policy w drugim koncie będzie AccessDenied.
  • Ignorowanie permissions boundary. Delegujesz tworzenie ról → bez boundary = eskalacja do admina.
  • IAM users z długimi access key dla ludzi. Default = Identity Center + krótkie sesje.
  • Mylenie Cognito z Identity Center. Klienci app vs pracownicy AWS.
  • Directory Service „bo SSO”. Do logowania ludzi w AWS wystarczy IDC + Entra; AD tylko gdy naprawdę potrzebujesz domeny Windows.
  • Control Tower bez decyzji o regionie home i OU. Późniejsza przebudowa landing zone jest bolesna — zaprojektuj drzewo OU pod guardrails na starcie.
  • Deny w jednej warstwie, debug tylko w IAM policy. Patrz SCP → boundary → session → resource → identity (evaluation logic).
