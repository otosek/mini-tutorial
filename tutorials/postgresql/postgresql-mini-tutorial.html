Podstawy

PostgreSQL — relacyjna baza open source z rozbudowanym SQL, typami JSON, full-text, rozszerzeniami. MVCC — czytający nie blokują piszących (w przeciwieństwie do lock-heavy modeli).

CREATE TABLE authors (
    id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    first_name  text NOT NULL,
    last_name   text NOT NULL,
    email       text NOT NULL UNIQUE,
    metadata    jsonb NOT NULL DEFAULT '{}',
    tags        text[] DEFAULT '{}',
    created_at  timestamptz NOT NULL DEFAULT now()
);

UPSERT — ON CONFLICT

UPSERT = INSERT, a gdy wiersz już istnieje (konflikt unikalności) → UPDATE zamiast błędu. W Postgresie przez ON CONFLICT … DO UPDATE (inaczej niż MERGE w Oracle/SQL Server, choć PG 15+ ma też MERGE).

  • ON CONFLICT (email) — kolumna/kolumny z UNIQUE lub PRIMARY KEY
  • EXCLUDED — pseudo-tabela z wierszem, który próbowałeś wstawić
  • DO NOTHING — pomiń duplikat bez aktualizacji
INSERT INTO authors (email, first_name, last_name)
VALUES ('a@ex.com', 'Anna', 'Nowak')
ON CONFLICT (email) DO UPDATE
    SET first_name = EXCLUDED.first_name,
        last_name  = EXCLUDED.last_name,
        updated_at = now()
WHERE authors.updated_at < EXCLUDED.updated_at;  -- opcjonalnie: aktualizuj tylko gdy nowsze

UPSERT + CTE (WITH)

CTE (WITH) definiuje tymczasowy wynik zapytania — czytelny staging przed INSERT/UPSERT. Przydatne przy imporcie wielu wierszy, deduplikacji lub transformacji danych w jednym statement (atomowo).

-- Batch UPSERT: dane w CTE → INSERT z ON CONFLICT
WITH incoming AS (
    SELECT * FROM (VALUES
        ('a@ex.com', 'Anna', 'Nowak'),
        ('b@ex.com', 'Jan',  'Kowalski')
    ) AS v(email, first_name, last_name)
),
deduped AS (
    SELECT DISTINCT ON (email) email, first_name, last_name
    FROM incoming
    ORDER BY email
)
INSERT INTO authors (email, first_name, last_name)
SELECT email, first_name, last_name FROM deduped
ON CONFLICT (email) DO UPDATE
    SET first_name = EXCLUDED.first_name,
        last_name  = EXCLUDED.last_name;

CTE + RETURNING (poniżej): wynik UPSERT w jednym zapytaniu — bez osobnego SELECT po imporcie.

WITH upserted AS (
    INSERT INTO authors (email, first_name, last_name)
    VALUES ('a@ex.com', 'Anna', 'Nowak')
    ON CONFLICT (email) DO UPDATE
        SET first_name = EXCLUDED.first_name
    RETURNING id, email, (xmax = 0) AS inserted  -- true = nowy wiersz
)
SELECT * FROM upserted;
CTE — kiedy używać

Czytelność (zamiast zagnieżdżonych subquery), wielokrotne odwołanie do tego samego zbioru, pipeline transformacji przed UPSERT. WITH RECURSIVE — osobno: hierarchie (patrz sekcja „Inne featury”).

Window functions

Funkcje okienkowe liczą coś po wierszach, ale nie grupują wyniku jak GROUP BY — każdy wiersz zostaje, dostaje kolumnę z agregatem „w oknie”.

SkładniaZnaczenie
OVER ()Cała partycja (wszystkie wiersze)
PARTITION BY colOsobne okna per grupa (np. per autor)
ORDER BY colKolejność w oknie — ważne dla ROW_NUMBER, LAG
ROWS/RANGE BETWEEN …Ruchome okno (np. suma z ostatnich 7 dni)
FunkcjaPo co
ROW_NUMBER()Numer wiersza w partycji (unikalny)
RANK() / DENSE_RANK()Pozycja z remisami (RANK ma luki)
LAG(col) / LEAD(col)Poprzedni / następny wiersz w oknie
SUM() OVERSuma bieżąca, % całości bez GROUP BY
 
-- Numer wiersza per nazwisko
SELECT first_name, last_name,
       ROW_NUMBER() OVER (PARTITION BY last_name ORDER BY created_at) AS rn
FROM authors;

-- Top 1 tytuł per autor (bez LATERAL — filtr na rn = 1 w zewnętrznym query)
SELECT * FROM (
    SELECT t.*,
           ROW_NUMBER() OVER (PARTITION BY author_id ORDER BY created_at DESC) AS rn
    FROM titles t
) x WHERE rn = 1;

-- Porównanie z poprzednim miesiącem (LAG)
SELECT date_trunc('month', created_at) AS month,
       count(*) AS cnt,
       LAG(count(*)) OVER (ORDER BY date_trunc('month', created_at)) AS prev_cnt
FROM authors
GROUP BY date_trunc('month', created_at);

RETURNING

RETURNING zwraca wiersze dotknięte przez INSERT / UPDATE / DELETE — bez drugiego round-trip SELECT. W Spring/JPA często zastępuje @GeneratedValue + osobne odpytanie o ID.

OperacjaTypowe użycie
INSERT … RETURNINGNowe id, created_at, defaults z DB
UPDATE … RETURNINGLista zmienionych wierszy + nowe wartości
DELETE … RETURNINGArchiwizacja / audit — co usunięto
UPSERT … RETURNINGID po konflikcie — insert i update w jednej odpowiedzi
 
-- INSERT — od razu id do aplikacji
INSERT INTO authors (first_name, last_name, email)
VALUES ('Jan', 'Kowalski', 'j@ex.com')
RETURNING id, created_at;

-- UPDATE — ile i które wiersze
UPDATE authors SET metadata = metadata || '{"verified": true}'
WHERE email LIKE '%@ex.com'
RETURNING id, email;

-- DELETE z audytem
DELETE FROM authors WHERE deleted_at IS NOT NULL
RETURNING id, email, deleted_at;

-- UPSERT + RETURNING (sync cache / event po zapisie)
INSERT INTO authors (email, first_name, last_name)
VALUES ('a@ex.com', 'Anna', 'Nowak')
ON CONFLICT (email) DO UPDATE SET first_name = EXCLUDED.first_name
RETURNING id, email, xmax = 0 AS was_inserted;
Pułapka: RETURNING a trigger

RETURNING zwraca wiersz po triggerach BEFORE/AFTER — widzisz wartości już zmodyfikowane w DB (np. updated_at z triggera).

JSONB i operatory strzałkowe

json — tekst, zachowuje whitespace. jsonb — zparsowany, binarny, wolniejszy insert, szybsze query i indeksy. W prod: prawie zawsze jsonb.

Operatory strzałkowe

OperatorZwracaPrzykład

->>text (wartość skalarna)metadata->>'city'
#>jsonb po ścieżce tablicowejmetadata#>'{address,city}'
#>>text po ścieżcemetadata#>>'{address,city}'

<@czy jest zawarty wodwrotność @>

-- Przykład danych
-- metadata: {"address": {"city": "Kraków", "zip": "30-001"}, "vip": true}

SELECT
    metadata->'address'->>'city'           AS city,      -- "Kraków"
    metadata#>>'{address,city}'           AS city2,     -- to samo
    metadata @> '{"vip": true}'            AS is_vip,    -- true
    metadata ? 'phone'                     AS has_phone  -- false
FROM authors;

-- Aktualizacja zagnieżdżonego pola
UPDATE authors
SET metadata = jsonb_set(metadata, '{address,city}', '"Warszawa"')
WHERE id = '...';

-- jsonb_path (PG 12+) — SQL/JSON path
SELECT * FROM authors
WHERE metadata @? '$.address.city ? (@ == "Kraków")';

Indeks na JSONB

-- GIN na całym jsonb — @>, ?, ?|, ?&
CREATE INDEX idx_authors_metadata ON authors USING GIN (metadata);

-- Indeks na konkretną ścieżkę (expression index)
CREATE INDEX idx_authors_city ON authors ((metadata->'address'->>'city'));

Checklist optymalizacji

  1. WHERE / JOIN na kolumnach z indeksem
  2. SELECT * — unikaj; tylko potrzebne kolumny (Index Only Scan)
  3. ANALYZE — statystyki aktualne (autovacuum/analyze)
  4. N+1 — batch / JOIN zamiast pętli w aplikacji
  5. LIKE '%foo%' — nie użyje B-tree; rozważ pg_trgm GIN
  6. Funkcja na kolumnie — WHERE lower(email) = … psuje indeks → expression index lub generated column
  7. Limit — paginacja przez keyset (WHERE id > last) zamiast OFFSET 100000

VACUUM i bloat

MVCC zostawia martwe wiersze — VACUUM czyści, AUTOVACUUM domyślnie włączony. Długie transakcje blokują vacuum → rosnąca tabela mimo DELETE.

Inne ciekawe featury

Arrays

WHERE 'sql' = ANY(tags), array_agg(title), unnest. GIN indeks na array.

Full-Text Search (tsvector / tsquery)

to_tsvector('polish', body) @@ to_tsquery('polish', 'autor & książka') — GIN indeks na tsvector.

LATERAL

Subquery z dostępem do poprzedniego FROM — „top N per group” elegancko.

SELECT a.*, t.latest_title
FROM authors a
CROSS JOIN LATERAL (
    SELECT title AS latest_title FROM titles
    WHERE author_id = a.id ORDER BY created_at DESC LIMIT 1
) t;
Materialized views

Cache wyniku zapytania — REFRESH MATERIALIZED VIEW CONCURRENTLY dla read-heavy index.

Row-Level Security (RLS)

Polityki per wiersz — multi-tenant w jednej tabeli: CREATE POLICY … USING (tenant_id = current_setting('app.tenant')).

Advisory locks

pg_advisory_lock(id) — mutex aplikacyjny bez tabeli lock — joby, migracje.

Extensions

pg_trgm (podobne stringi), pgcrypto, postgis (geo), citext (case-insensitive text).

LISTEN / NOTIFY

Lekki pub/sub wewnątrz PG — event do aplikacji bez kolejki zewnętrznej (ograniczone skalowanie).

Partitioning (deklaratywne)

Tabela partycjonowana po dacie/kluczu — prune partycji w query planie.

Common Table Expressions — RECURSIVE

Hierarchie — drzewo kategorii, org chart.

Generated columns (STORED)

Kolumna wyliczana z innych — indeksowalna, spójna z JSON extract.

Typowe błędy

  1. timestamp bez strefy — błędy przy DST i wielu regionach
  2. JSON zamiast JSONB „bo prostsze” — brak indeksów, wolniejsze filtry
  3. -> zamiast ->> w WHERE — porównujesz jsonb z text
  4. Brak indeksu na FK — wolne JOIN i DELETE parent
  5. OFFSET paginacja na dużych offsetach — keyset pagination
  6. SELECT * + ORM bez lazy/eager świadomości — N+1
  7. Zbyt wiele indeksów — spowalnia INSERT/UPDATE
  8. Brak indeksu UNIQUE pod ON CONFLICT (col) — UPSERT fail w runtime
  9. Window: WHERE rn = 1 bez subquery — alias z OVER niedostępny w WHERE tego samego poziomu
  10. RETURNING pominięte — aplikacja robi drugi SELECT po INSERT (zbędny round-trip)
  11. Ignorowanie EXPLAIN — „wolno” bez diagnozy planu
