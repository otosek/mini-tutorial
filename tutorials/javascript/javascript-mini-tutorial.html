Część 1 — Historia i „wars”

1.1 Skąd się wziął JavaScript

JavaScript powstał w Netscape (1995) jako język skryptowy w przeglądarce. Standardyzacja przez ECMA → nazwa formalna ECMAScript (ES). Przez lata każda przeglądarka implementowała JS inaczej — stąd legenda o „dniach, w których IE psuł layout”.

1.2 Browser Wars i problem kompatybilności

Lata 90.–2000.: wojna Netscape vs Internet Explorer. Różne API DOM, różne błędy w JS. Firmy pisały if (document.all) { /* IE */ } albo używały bibliotek (jQuery — 2006) żeby ukryć różnice.

ES3 (1999) — długo „zamrożony” standard, na którym opierał się cały web 2.0. ES4 — porzucony (zbyt ambitny). Przez ~10 lat prawie brak nowości w samym języku.

1.3 ES5 (2009) — pierwsza stabilna modernizacja

  • strict mode — "use strict"
  • JSON.parse / JSON.stringify
  • Metody tablic: forEach, map, filter, reduce
  • Object.defineProperty — fundament późniejszego Reacta (reaktywność Vue 2)

ES5 to nadal „stary JS” w głowach wielu osób — funkcje function, var, callbacki zamiast Promise.

1.4 ES6 / ES2015 — „nowy JavaScript”

Przełom: let/const, klasy, moduły import/export, strzałki, Promises, template literals, destructuring. Od 2015 standard ECMAScript dostaje roczną edycję (ES2016, ES2017… ES2024) zamiast wielkich skoków co dekadę.

EraProblemRozwiązanie dziś

Część 2 — ES6 (2015) — przełom

2.1 let, const zamiast var

// ES5 — function scope, hoisting, można nadpisać
var count = 1
var count = 2  // OK (źle)

// ES6+ — block scope
let items = []
const API_URL = '/api/authors'
// const API_URL = '...'  // błąd — nie nadpisujesz stałych

const nie znaczy „głęboko niemutowalny” — tablica pod const może mieć push, ale nie możesz przypisać nowej tablicy do tej samej zmiennej.

2.2 Strzałkowe funkcje, template literals, destructuring

// template literal
const msg = `Author: ${author.firstName} ${author.lastName}`

// destructuring
const { id, email } = user
const [first, ...rest] = tags

// spread
const merged = { ...defaults, ...overrides }
const allTags = [...existing, 'new']

2.3 Klasy — syntactic sugar nad prototypami

class AuthorService {
  constructor(api) {
    this.api = api
  }

  async findById(id) {
    return this.api.get(`/authors/${id}`)
  }
}

Pod spodem nadal prototypy — class to czytelniejsza składnia, nie nowy model obiektowy jak w Javie.

Część 3 — Domknięcia (closures)

3.1 Co to jest domknięcie

Funkcja „pamięta” zmienne z zewnętrznego zakresu (lexical scope), nawet gdy ten zakres już się skończył. To fundament modułów, prywatnych zmiennych i wielu wzorców w JS.

function createCounter() {
  let count = 0           // „prywatne” — z zewnątrz niedostępne
  return {
  increment() { count++ },
  getCount() { return count }
  }
}

const counter = createCounter()
counter.increment()
counter.getCount()  // 1

3.2 Domknięcia w praktyce biznesowej

Gdzie spotkasz closures
  • React hooks — useEffect „widzi” props/state z renderu, w którym powstał
  • Event handlery — funkcja w addEventListener trzyma kontekst z momentu rejestracji
  • Factory / DI — serwis zamknięty na konfigurację (baseUrl, token)
  • Debouncing — setTimeout wewnątrz funkcji pamięta ostatni timer

3.3 Pułapka: pętla var + setTimeout

// ES5 bug — wszystkie wypiszą 3
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 100)
}

// fix: let (block scope) lub IIFE
for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 100)  // 0, 1, 2
}

Część 4 — this i strzałkowe funkcje

4.1 this zależy od wywołania

Kontekstthis
Zwykła funkcja f()undefined (strict) lub global
Metoda obj.f()obj
new F()nowy obiekt
call / apply / bindjawnie podany obiekt
Strzałka () =>this z otaczającego zakresu (lexical)
 
const service = {
  name: 'Authors',
  load() {
    // strzałka — this = service (z metody load)
    setTimeout(() => console.log(this.name), 0)
  }
}

Pułapka: strzałki nie mają własnego this — nie używaj ich jako metod obiektu, jeśli potrzebujesz dynamicznego this (np. w handlerze kliknięcia na prototypie).

Część 5 — Asynchroniczność: Promises i async/await

5.1 Ewolucja: callback → Promise → async/await

// callback (ES5) — zagnieżdżanie
getAuthor(id, (err, author) => {
  if (err) return handle(err)
  getBooks(author.id, (err2, books) => { /* ... */ })
})

// Promise (ES2015)
getAuthor(id)
  .then(author => getBooks(author.id))
  .then(books => render(books))
  .catch(handle)

// async/await (ES2017) — składnia synchroniczna
async function showAuthor(id) {
  try {
    const author = await getAuthor(id)
    const books = await getBooks(author.id)
    render(books)
  } catch (err) {
    handle(err)
  }
}

5.2 Stany Promise

pending → fulfilled (wartość) lub rejected (błąd). Łańcuch .then zwraca nowy Promise. Promise.all — czeka na wszystkie; Promise.allSettled — zbiera wyniki nawet przy błędach; Promise.race — pierwszy kończy.

const [user, settings] = await Promise.all([
  fetchUser(id),
  fetchSettings(id)
])

const results = await Promise.allSettled([
  fetch('/api/a'),
  fetch('/api/b')  // może fail — reszta i tak wraca
])

5.3 fetch — standard w przeglądarce i Node

const res = await fetch('/api/authors', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ firstName: 'Anna' })
})
if (!res.ok) throw new Error(`HTTP ${res.status}`)
const author = await res.json()

fetch nie rzuca przy 404/500 — sprawdzaj res.ok. W React + TanStack Query logika fetch często siedzi w queryFn.

Część 6 — Event loop

6.1 Jednowątkowy JS + kolejka zadań

JavaScript w przeglądarce/Node ma jeden wątek na wykonanie kodu. Operacje I/O (sieć, timer, plik) deleguje do środowiska; wynik wraca przez callback queue (task queue) i microtask queue (Promises).

console.log('1')
setTimeout(() => console.log('2'), 0)
Promise.resolve().then(() => console.log('3'))
console.log('4')
// kolejność: 1, 4, 3, 2
// microtasks (Promise) przed macrotasks (setTimeout)

6.2 Dlaczego to ważne w aplikacjach

  • Długi sync kod blokuje UI (freeze przeglądarki)
  • await oddaje kontrolę — inne microtaski mogą wejść między krokami
  • Web Workers / worker_threads (Node) — ciężkie obliczenia poza głównym wątkiem

8.2 Map, Set, WeakMap

Map — klucze dowolnego typu, kolejność wstawiania. Set — unikalne wartości. WeakMap — klucze tylko obiekty, GC może posprzątać — cache metadanych DOM bez wycieków pamięci.

9.2 Czego unikać w nowym kodzie

  • var, function tylko dlatego że „tak zawsze było”
  • Callbacki zamiast Promise/async tam, gdzie API to wspiera
  • CommonJS w zielonym polu frontendu (ESM + bundler)
  • Mutowanie stanu React — preferuj spread, toSorted, immutable patterns
  • == — używaj === (porównanie bez koercji typów)

9.3 JavaScript vs TypeScript

W korporacjach i większych aplikacjach dominuje TypeScript — ten sam runtime JS, typy tylko przy kompilacji. Czysty JS nadal w skryptach, małych narzędziach, legacy i fragmentach bez build step. Znasz nowoczesny JS → TS to dodatek składni, nie inny język.

Część 10 — Typowe błędy

  1. Mylenie == i === — 0 == false jest true; używaj ===.
  2. this w callbacku — zgubione w zwykłej funkcji; strzałka lub bind.
  3. Closure w pętli z var — wszystkie iteracje widzą tę samą wartość.
  4. Brak catch przy async — nieobsłużony rejection = cichy błąd lub crash w Node.
  5. await w pętli zamiast Promise.all — sekwencyjne requesty 10× wolniejsze niż równoległe (gdy nie muszą być po kolei).
  6. Mutacja obiektu ze stanu React — state.push(x) nie triggeruje re-render; nowa referencja.
  7. JSON.parse bez try/catch — zły payload z API wywala cały handler.
  8. || zamiast ?? — wartość 0 lub '' zostaje zastąpiona domyślną.
  9. Zakładanie że fetch rzuca na 404 — trzeba sprawdzić response.ok.
  10. Import ścieżek bez rozszerzenia w Node ESM — wymaga pełnych ścieżek lub bundlera z resolverem.
