Część 1 — Błędny startup: socket vs actuator

Problem: tcpSocket probe pokazuje OK gdy port się otworzy, ale aplikacja Spring Boot jest gotowa dopiero kilkanaście sekund później. Ruch płynie do niegotowego Poda.

Czas Wydarzenie tcpSocket Ruch actuator Ruch
0s JVM startuje FAIL — FAIL —
2s Tomcat binduje port 8080 OK Pod w endpoints FAIL Brak ruchu
4s Flyway migracje DB OK Ruch → 503 FAIL Brak ruchu
8s Hibernate SessionFactory OK 503, timeout FAIL Brak ruchu
12s Connection pool, @PostConstruct OK 503 FAIL Brak ruchu
18s Spring Context GOTOWY OK OK OK Pod w endpoints

Konsekwencje przy 100 req/s:

  • tcpSocket: ~16s fałszywego OK = ~1600 błędów przy każdym restarcie
  • /actuator/health/readiness: 0 błędów

Część 2 — Błędny shutdown

Problem: Przy wyłączaniu Poda tcpSocket pokazuje OK aż do zamknięcia portu — K8s kieruje ruch do umierającego Poda.

Czas Wydarzenie tcpSocket Błędy actuator Błędy
0s K8s wysyła SIGTERM OK — FAIL —
1s Graceful shutdown trwa OK 503 FAIL —
3s Connection pool zamykany OK DB errors FAIL —
5s Tomcat zamyka socket FAIL Conn refused FAIL —

Konsekwencje: tcpSocket = ~500 błędów, actuator = 0 błędów.

Część 3 — Graceful shutdown w Spring Boot

Problem: Bez server.shutdown=graceful Spring ucina aktywne requesty natychmiast przy SIGTERM.

Czas Wydarzenie Z graceful Bez graceful
0s SIGTERM Czeka na aktywne req Zamyka natychmiast
0.5s Aktywne requesty Dokańcza Connection reset
2s Zakończenie 0 błędów ~200 błędów + ucięte TX

Konfiguracja

server:
  shutdown: graceful

spring:
  lifecycle:
    timeout-per-shutdown-phase: 30s

Część 4 — PreStop hook i race condition

Problem: K8s robi dwie rzeczy równolegle przy delete Pod:

  1. Wysyła SIGTERM do kontenera (~50ms)
  2. Usuwa Pod z Service endpoints (propagacja 1-2s)

SIGTERM dociera szybciej niż propagacja endpoints. Przez 1-2s ruch wciąż płynie do zamykającego się Poda.

Bez preStop: ~100-200 błędów przy każdym shutdown (nawet z graceful shutdown włączonym).

Rozwiązanie — preStop hook

spec:
  containers:
  - name: app
    lifecycle:
      preStop:
        exec:
          command: ["sleep", "3"]

sleep 3 daje czas na propagację endpoints. Dopiero potem SIGTERM dociera do aplikacji.

BłądDlaczego źleRozwiązanie

-Xmx = limit RAM Brak miejsca na native memory → OOMKill Zostaw 25% na metaspace, stacks
Brak ExitOnOutOfMemoryError JVM wisi po OOM Dodaj flagę

JAVA_TOOL_OPTIONS — wszystkie flagi w jednym miejscu

env:
  - name: JAVA_TOOL_OPTIONS
    value: >-
      -XX:MaxRAMPercentage=75
      -XX:InitialRAMPercentage=50
      -XX:+ExitOnOutOfMemoryError
      -XX:+UseG1GC
Tip: requests.memory = limits.memory dla JVM. Inaczej JVM alokuje heap na podstawie requests, a potem OOMKill.

Część 7 — Kompletna konfiguracja

application.yml

server:
  shutdown: graceful

spring:
  lifecycle:
    timeout-per-shutdown-phase: 30s

management:
  endpoints:
    web:
      exposure:
        include: health
  endpoint:
    health:
      probes:
        enabled: true
      group:
        readiness:
          include: readinessState, db
        liveness:
          include: livenessState

Deployment

spec:
  containers:
  - name: app
    image: myregistry/app:1.2.0
    ports:
    - containerPort: 8080
    env:
    - name: JAVA_TOOL_OPTIONS
      value: >-
        -XX:MaxRAMPercentage=75
        -XX:+ExitOnOutOfMemoryError
    resources:
      requests:
        memory: "1Gi"
        cpu: "500m"
      limits:
        memory: "1Gi"
        cpu: "1000m"
    startupProbe:
      httpGet:
        path: /actuator/health/liveness
        port: 8080
      failureThreshold: 30
      periodSeconds: 2
    livenessProbe:
      httpGet:
        path: /actuator/health/liveness
        port: 8080
      periodSeconds: 10
    readinessProbe:
      httpGet:
        path: /actuator/health/readiness
        port: 8080
      periodSeconds: 5
    lifecycle:
      preStop:
        exec:
          command: ["sleep", "3"]

Część 8 — Typowe błędy

  1. tcpSocket zamiast httpGet — port otwarty ≠ aplikacja gotowa
  2. Brak graceful shutdown — requesty ucięte przy SIGTERM
  3. Brak preStop hook — race condition, błędy przez 1-2s
  4. Hardcoded -Xmx — ignoruje limity kontenera
  5. -Xmx = limit RAM — brak miejsca na native memory → OOMKill
  6. 1 replika — restart = 100% downtime, readiness bezużyteczna
  7. Liveness sprawdza DB — pad DB = restart loop wszystkich Podów
  8. Brak startupProbe — liveness zabija wolno startującą aplikację
  9. requests ≠ limits dla memory — JVM alokuje za dużo → OOMKill
  10. Duży heap (16GB+) — długie pauzy GC, gorsza latencja
