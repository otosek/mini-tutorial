Część 1 — Fundamenty

1.1 Co to jest Kubernetes

Kubernetes (K8s) to platforma do orkiestracji kontenerów — automatycznie deployuje, skaluje, restartuje i balansuje obciążenie aplikacji w klastrze maszyn. Nie budujesz kontenerów (to robi Docker); K8s decyduje gdzie i jak je uruchomić.

1.2 Jaki problem rozwiązuje

Bez orkiestracji: ręczne deploye na VM, brak auto-healingu, skalowanie „ręką”, rolling update = downtime. K8s daje deklaratywny model („chcę 3 repliki tego image”) i control plane, który dąży do desired state.

1.3 Kluczowe pojęcia w jednym zdaniu

Pod = najmniejsza jednostka (1+ kontenerów). Deployment = zarządza replikami Podów. Service = stały adres sieciowy do Podów. Namespace = logiczna izolacja zasobów.

Część 2 — Architektura klastra

KomponentRola
Control planeMózg klastra — API server, scheduler, controller manager, etcd
Node (worker)Maszyna uruchamiająca Pody — kubelet + kube-proxy + runtime (containerd)
API serverJedyny punkt wejścia — kubectl i kontrolery rozmawiają z nim
etcdBaza key-value — przechowuje stan klastra (desired + actual)
SchedulerPrzypisuje nowe Pody do Node'ów (zasoby, affinity, taints)
Controller managerPętle kontrolne — Deployment, ReplicaSet, Node controller itd.
kubeletAgent na Node — uruchamia kontenery, raportuje stan do API

Desired state vs actual state: piszesz YAML (desired) → kontrolery obserwują różnice → naprawiają (np. Pod umarł → nowy Pod).

Część 3 — Pod i workloady

Pod

Grupa 1+ kontenerów współdzielących network namespace i storage volumes. Krótko żyjący — ma unikalny IP, ale IP się zmienia przy restarcie. Rzadko tworzysz Poda bezpośrednio.

apiVersion: v1
kind: Pod
metadata:
  name: nginx
spec:
  containers:
  - name: nginx
    image: nginx:1.25
    ports:
    - containerPort: 80

Deployment

Najczęstszy workload — utrzymuje N replik Podów, robi rolling update i rollback. Zarządza ReplicaSetem pod spodem.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: authors-api
spec:
  replicas: 3
  selector:
    matchLabels:
      app: authors-api
  template:
    metadata:
      labels:
        app: authors-api
    spec:
      containers:
      - name: api
        image: myregistry/authors-api:1.2.0
        ports:
        - containerPort: 8080

Inne workloady — kiedy który

TypKiedy
DeploymentStateless app — API, frontend, worker bez lokalnego stanu
StatefulSetStabilna tożsamość (pod-0, pod-1), persistent storage — DB, Kafka
DaemonSetPo jednym Podzie na każdym Node — log agent, monitoring
Job / CronJobJednorazowe / cykliczne zadania — migracje, batch

Labels i selectors

Labels — pary klucz/wartość na obiektach (app: authors-api). Selectors — jak Service i Deployment znajdują swoje Pody. Bez poprawnych labeli Service nie routuje ruchu — klasyczny bug.

Część 4 — Networking

4.1 Service — stały adres do dynamicznych Podów

TypDostępUżycie
ClusterIPTylko wewnątrz klastra (domyślny)Komunikacja między serwisami
NodePortPort na każdym Node (30000–32767)Dev, prosty dostęp z zewnątrz
LoadBalancerZewnętrzny LB od cloud provideraProd — publiczny endpoint
HeadlessClusterIP: NoneStatefulSet — bezpośredni DNS per Pod
 
apiVersion: v1
kind: Service
metadata:
  name: authors-api
spec:
  selector:
    app: authors-api
  ports:
  - port: 80
    targetPort: 8080
  type: ClusterIP

4.2 Ingress — HTTP routing z zewnątrz

Ingress to reguły routingu (host, path → Service). Sam w sobie nie ma IP — wymaga Ingress Controller (nginx, traefik, AWS ALB). TLS termination często tutaj.

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: authors
spec:
  rules:
  - host: authors.example.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: authors-api
            port:
              number: 80

4.3 DNS w klastrze

Service authors-api w namespace default → DNS: authors-api.default.svc.cluster.local. Pody mogą się wołać po nazwie Service bez znać IP.

Część 5 — Config, Secrets, Storage

5.1 ConfigMap i Secret

ConfigMap — dane niesekretne (config files, env). Secret — wrażliwe (hasła, tokeny) — base64 w etcd (nie szyfrowanie!), w prod używaj encryption at rest + external secret store.

# Inject jako env
env:
- name: DATABASE_URL
  valueFrom:
    secretKeyRef:
      name: db-credentials
      key: url

5.2 PersistentVolume (PV) i PVC

PV — zasób storage w klastrze. PVC — request na storage przez Pod. Dynamic provisioning tworzy PV automatycznie (np. EBS, Azure Disk). Pod + emptyDir = dane giną przy restarcie Pod.

Część 6 — Probes, resources, skalowanie

6.1 Health probes

ProbeCel
livenessProbeApp żyje? Nie → restart kontenera
readinessProbeApp gotowa na ruch? Nie → wyciągnięcie z Service endpoints
startupProbeWolny start — blokuje liveness do pierwszego sukcesu

Pułapka: liveness woła endpoint zależny od DB — DB padnie → restart wszystkich Podów w pętli.

6.2 Requests i limits

resources:
  requests:
    memory: "256Mi"
    cpu: "250m"      # 0.25 rdzenia
  limits:
    memory: "512Mi"
    cpu: "500m"

requests — scheduler używa do placementu. limits — max; przekroczenie memory → OOMKill; CPU → throttling.

6.3 HPA — Horizontal Pod Autoscaler

Skaluje liczbę replik Deploymentu na podstawie CPU, memory lub custom metrics. Wymaga metrics-server (CPU/memory) lub Prometheus adapter (custom).

6.4 Rolling update i rollback

kubectl rollout status deployment/authors-api
kubectl rollout undo deployment/authors-api

Strategia domyślna: maxUnavailable / maxSurge — zero-downtime deploy przy poprawnej readiness probe.

Część 7 — kubectl — najważniejsze komendy

# Kontekst i namespace
kubectl config current-context
kubectl get ns
kubectl -n production get pods

# Deploy i debug
kubectl apply -f deployment.yaml
kubectl get pods -w
kubectl describe pod <name>          # Events — pierwsze co czytasz przy CrashLoop
kubectl logs <pod> [-f] [-c container]
kubectl exec -it <pod> -- /bin/sh

# Skalowanie i rollout
kubectl scale deployment/authors-api --replicas=5
kubectl rollout history deployment/authors-api

# Szybki pod tymczasowy
kubectl run curl --rm -it --image=curlimages/curl -- sh

Imperative vs declarative: na prod preferuj apply -f (GitOps) zamiast kubectl run/create ad hoc.

Część 8 — Najczęstsze błędy

  1. Brak resource requests — scheduler nie wie gdzie posadzić; noisy neighbor
  2. limits memory = requests — brak headroom → OOMKill przy spike
  3. Liveness = readiness ten sam endpoint — restart zamiast tylko wyłączenia z LB
  4. latest tag image — niedeterministyczny deploy, brak rollbacku
  5. Brak label selector match — Service nie routuje do Podów
  6. Stan w emptyDir / lokalnym dysku — utrata danych przy restarcie
  7. Secrets w YAML w Git — wyciek; użyj Sealed Secrets / Vault
  8. Deploy bez readiness probe — ruch idzie na niedostartowany Pod
  9. Ignorowanie describe pod Events — ImagePullBackOff, CrashLoop widoczne od razu
  10. Jeden namespace na wszystko — brak izolacji dev/staging/prod

Pytania rekrutacyjne — krótkie odpowiedzi

Junior / Mid

1. Co to jest Kubernetes?

Platforma orkiestracji kontenerów — deploy, skalowanie, self-healing, networking.

2. Co to jest Pod?

Najmniejsza jednostka — 1+ kontenery, wspólny network i volumes; efemeryczny IP.

3. Pod vs Deployment?

Pod — jednostka runtime. Deployment — kontroler utrzymujący N replik Podów + rolling update.

4. Co to jest Service?

Stały endpoint (ClusterIP/DNS) do dynamicznie zmieniających się Podów.

5. ClusterIP vs NodePort vs LoadBalancer?

ClusterIP — wewnątrz klastra. NodePort — port na Node. LoadBalancer — zewnętrzny LB cloud.

6. Co to jest Ingress?

Reguły HTTP routingu (host/path → Service); wymaga Ingress Controller.

7. Co to jest namespace?

Logiczna izolacja zasobów w klastrze — dev, staging, prod.

8. ConfigMap vs Secret?

ConfigMap — config niesekretny. Secret — dane wrażliwe (base64, nie szyfrowanie).

9. liveness vs readiness?

Liveness — żyje? (restart). Readiness — gotowy na ruch? (endpoint Service).

10. requests vs limits?

Requests — rezerwacja dla schedulera. Limits — max; przekroczenie memory → OOMKill.

11. Co to jest etcd?

Baza key-value przechowująca stan klastra — desired i actual state.

12. Rola kubelet?

Agent na Node — uruchamia kontenery, zgłasza stan do API server.

13. Co to jest ReplicaSet?

Utrzymuje stałą liczbę replik Podów; Deployment zarządza ReplicaSetem.

14. Jak sprawdzić logi Poda?

kubectl logs <pod> [-f]

15. Co to ImagePullBackOff?

Nie można pobrać image — zła nazwa, brak credentials, registry down.

Mid / Senior

16. Desired state vs actual state?

YAML deklaruje desired; kontrolery ciągle naprawiają actual do zgodności.

17. Deployment vs StatefulSet?

Deployment — stateless, losowe nazwy Podów. StatefulSet — stabilna tożsamość, ordered deploy, PVC per Pod.

18. Co to taint i toleration?

Taint na Node — „nie schedule'uj tu”. Toleration na Pod — „mogę tu wejść”. Dedicated nodes.

19. Affinity / anti-affinity?

Reguły schedulera — np. Pody razem na tym samym Node (affinity) lub rozłożone (anti-affinity).

20. HPA — jak działa?

Obserwuje metryki (CPU/memory/custom) → skaluje replicas Deploymentu w min/max range.

21. Rolling update — maxSurge / maxUnavailable?

Ile dodatkowych Podów podczas update / ile może być niedostępnych — kontrola zero-downtime.

22. PV vs PVC?

PV — zasób storage. PVC — claim/request; Pod mountuje PVC, nie PV bezpośrednio.

23. Headless Service — po co?

ClusterIP: None — DNS zwraca IP każdego Poda; dla StatefulSet, peer discovery.

24. CNI — co robi?

Plugin sieciowy — przydziela IP Podom, routing między Node'ami (Calico, Flannel, Cilium).

25. RBAC w K8s?

Role/ClusterRole + RoleBinding — kto (ServiceAccount/user) może co na jakich zasobach.

26. ServiceAccount — po co?

Tożsamość Poda w klastrze — do RBAC i auth do API (np. sidecar, operator).

27. GitOps — idea?

Git = source of truth; Argo CD / Flux synchronizuje cluster state z repo (declarative).

28. Helm — po co?

Package manager — charty z templatami, values per env, wersjonowane release.

29. Pod Disruption Budget (PDB)?

Min dostępnych replik podczas voluntary disruption (node drain, cluster upgrade).

30. Sidecar pattern?

Dodatkowy kontener w Pod — proxy (Envoy), log shipper, config reloader obok app.

Pułapki / tricky

31. Czy Pod IP jest stały?

Nie — zmienia się przy restarcie; używaj Service DNS.

32. Czy Secret jest szyfrowany domyślnie?

Nie — base64 w etcd; w prod włącz encryption at rest + external secrets.

33. Restart Deployment = nowy Pod?

Tak — nowe Pody, nowe IP; stan lokalny ginie (bez PVC).

34. Czy kubectl delete pod kasuje Deployment?

Nie — Deployment tworzy nowy Pod (self-healing).

35. Liveness sprawdza DB — problem?

Tak — pad DB → wszystkie Pody restartowane w pętli; DB sprawdzaj w readiness.

36. latest tag — problem?

Tak — imagePullPolicy: Always, niedeterministyczny deploy, trudny rollback.

37. Czy jeden kontener = jeden Pod zawsze?

Nie — sidecary w tym samym Pod; ale Pod to granica skalowania i sieci.

38. Scheduler vs kubelet?

Scheduler — wybiera Node. Kubelet — uruchamia kontenery na wybranym Node.

39. CrashLoopBackOff — pierwsze kroki?

kubectl logs, describe pod Events, sprawdź command/args, env, probes.

40. K8s vs Docker Compose?

Compose — dev, jedna maszyna. K8s — prod cluster, self-healing, skalowanie, networking multi-node.
