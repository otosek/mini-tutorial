Część 1 — Błędny startup: socket vs actuator ⭐

Problem: tcpSocket probe pokazuje OK gdy port się otworzy, ale aplikacja Spring Boot jest gotowa dopiero kilkanaście sekund później. Ruch płynie do niegotowego Poda.

Czas Wydarzenie tcpSocket Ruch (tcpSocket) actuator Ruch (actuator)
0s JVM startuje ❌ FAIL — ❌ FAIL —
2s Tomcat binduje port 8080 ✅ OK Pod w endpoints ❌ FAIL Brak ruchu
4s Flyway migracje DB ✅ OK 🔴 Ruch → 503 ❌ FAIL Brak ruchu
8s Hibernate SessionFactory ✅ OK 🔴 503, timeout ❌ FAIL Brak ruchu
12s Connection pool, @PostConstruct ✅ OK 🔴 503 ❌ FAIL Brak ruchu
18s Spring Context GOTOWY ✅ OK ✅ OK ✅ OK Pod w endpoints

Konsekwencje:

  • tcpSocket: ~16s fałszywego OK = ~320 błędów przy każdym restarcie
  • /actuator/health/readiness: 0 błędów

Część 2 — Błędny shutdown ⭐

Problem: Przy wyłączaniu Poda tcpSocket pokazuje OK aż do zamknięcia portu — K8s kieruje ruch do umierającego Poda.

Czas Wydarzenie tcpSocket Błędy (tcpSocket) actuator Błędy (actuator)
0s K8s wysyła SIGTERM ✅ OK — ❌ FAIL —
1s Graceful shutdown trwa ✅ OK 🔴 503 ❌ FAIL —
3s Connection pool zamykany ✅ OK 🔴 DB errors ❌ FAIL —
5s Tomcat zamyka socket ❌ FAIL 🔴 Conn refused ❌ FAIL —

Konsekwencje:

  • tcpSocket: ~100 błędów
  • actuator: 0 błędów

Część 3 — Graceful shutdown w Spring Boot ⭐

Problem: Bez server.shutdown=graceful Spring ucina aktywne requesty natychmiast przy SIGTERM.

Czas Wydarzenie Z graceful ✅ Bez graceful ❌
0s SIGTERM Czeka na aktywne req 🔴 Zamyka natychmiast
0.5s Aktywne requesty Dokańcza 🔴 Connection reset
2s Zakończenie 🟢 0 błędów 🔴 ~40 błędów + ucięte TX

Konsekwencje:

  • Z graceful: 0 błędów
  • Bez graceful: ~40 błędów + ucięte transakcje

Konfiguracja

server:
  shutdown: graceful

spring:
  lifecycle:
    timeout-per-shutdown-phase: 25s

Część 4 — PreStop hook i race condition

Problem: K8s robi dwie rzeczy równolegle przy delete Pod:

  1. Wysyła SIGTERM do kontenera (~50ms)
  2. Usuwa Pod z Service endpoints (propagacja 1-2s)

SIGTERM dociera szybciej niż propagacja endpoints. Przez 1-2s ruch wciąż płynie do zamykającego się Poda.

⚠️ UWAGA: Bez preStop: ~20-40 błędów przy każdym shutdown (nawet z graceful shutdown włączonym).

Konsekwencje:

  • Bez preStop: ~20-40 błędów
  • Z preStop: 0 błędów

Rozwiązanie — preStop hook

spec:
  containers:
  - name: app
    lifecycle:
      preStop:
        exec:
          command: ["sleep", "3"]

sleep 3 daje czas na propagację endpoints. Dopiero potem SIGTERM dociera do aplikacji.

Część 5 — Java w kontenerach: dobre praktyki

Zalecane parametry JVM

ParametrOpisStatus
-XX:MaxRAMPercentage=75Heap = 75% RAM konteneraZalecane
-XX:InitialRAMPercentage=50Początkowy heapOpcjonalne
-XX:+ExitOnOutOfMemoryErrorZabij JVM przy OOM — K8s zrestartujeZalecane
-XX:+UseG1GCG1 — domyślny od Java 9Domyślne

Częste błędy

BłądDlaczego źleRozwiązanie
-Xmx2g (hardcoded) Ignoruje limity kontenera MaxRAMPercentage=75
-Xmx = limit RAM Brak miejsca na native memory → OOMKill Zostaw 25% na metaspace, stacks
Brak ExitOnOutOfMemoryError JVM wisi po OOM Dodaj flagę

JAVA_TOOL_OPTIONS — wszystkie flagi w jednym miejscu

env:
  - name: JAVA_TOOL_OPTIONS
    value: >-
      -XX:MaxRAMPercentage=75
      -XX:InitialRAMPercentage=50
      -XX:+ExitOnOutOfMemoryError
      -XX:+UseG1GC

💡 TIP: requests.memory = limits.memory dla JVM. Inaczej JVM alokuje heap na podstawie requests, a potem OOMKill.

Część 6 — CPU podczas startu Spring Boot

Problem: Spring Boot podczas startu zużywa znacznie więcej CPU niż w runtime — Hibernate, Flyway, inicjalizacja kontekstu, kompilacja JIT. Jeśli Kubernetes dławi CPU, start trwa znacznie dłużej.

Objawy dławienia CPU

  • Metryki CPU przez dłuższy czas na górnej granicy (blisko limits.cpu)
  • Start aplikacji trwa 2-3× dłużej niż lokalnie
  • kubectl top pod pokazuje CPU na 100% limitu przez cały startup

Rozwiązanie 1 — usuń limits.cpu (Burstable QoS)

Ustaw tylko requests.cpu, bez limits.cpu. Aplikacja może użyć więcej CPU jeśli jest dostępny na nodzie.

resources:
  requests:
    memory: "1Gi"
    cpu: "1"
  limits:
    memory: "1Gi"
    # brak limits.cpu — aplikacja może "burst"

Rozwiązanie 2 — Kube Startup CPU Boost

Kontroler od Google, który automatycznie zwiększa CPU podczas startu i przywraca oryginalne wartości po gotowości poda (in-place, bez restartu).

Wymagania:

  • Kubernetes 1.33+ lub starszy z feature gate InPlacePodVerticalScaling
  • Zainstalowany kontroler: helm install kube-startup-cpu-boost
apiVersion: autoscaling.x-k8s.io/v1alpha1
kind: StartupCPUBoost
metadata:
  name: spring-app-boost
  namespace: demo
spec:
  selector:
    matchExpressions:
    - key: app.kubernetes.io/name
      operator: In
      values: ["spring-app"]
  resourcePolicy:
    containerPolicies:
    - containerName: spring-app
      percentageIncrease:
        value: 50
  durationPolicy:
    podCondition:
      type: Ready
      status: "True"

Powyższa konfiguracja zwiększa CPU o 50% podczas startu. Po osiągnięciu stanu Ready (readinessProbe OK) przywraca oryginalne wartości.

Część 7 — Dlaczego skalować aplikacje Java

Jedna instancja to anty-pattern. Java w dużych kontenerach działa gorzej niż w wielu małych.

readinessProbe bezużytecznaRuch nie ma gdzie iść

Część 8 — Kompletna konfiguracja

application.yml

server:
  shutdown: graceful

spring:
  lifecycle:
    timeout-per-shutdown-phase: 25s

management:
  endpoints:
    web:
      exposure:
        include: health
  endpoint:
    health:
      probes:
        enabled: true
      group:
        readiness:
          include: readinessState, db
        liveness:
          include: livenessState

Deployment

spec:
  containers:
  - name: app
    image: myregistry/app:1.2.0
    ports:
    - containerPort: 8080
    env:
    - name: JAVA_TOOL_OPTIONS
      value: >-
        -XX:MaxRAMPercentage=75
        -XX:+ExitOnOutOfMemoryError
    resources:
      requests:
        memory: "1Gi"
        cpu: "1"
      limits:
        memory: "1Gi"
    startupProbe:
      httpGet:
        path: /actuator/health/liveness
        port: 8080
      failureThreshold: 30
      periodSeconds: 2
    livenessProbe:
      httpGet:
        path: /actuator/health/liveness
        port: 8080
      periodSeconds: 10
    readinessProbe:
      httpGet:
        path: /actuator/health/readiness
        port: 8080
      periodSeconds: 5
    lifecycle:
      preStop:
        exec:
          command: ["sleep", "3"]

Część 9 — Typowe błędy ⭐

  1. tcpSocket zamiast httpGet — port otwarty ≠ aplikacja gotowa
  2. Brak graceful shutdown — requesty ucięte przy SIGTERM
  3. Brak preStop hook — race condition, błędy przez 1-2s
  4. Hardcoded -Xmx — ignoruje limity kontenera
  5. -Xmx = limit RAM — brak miejsca na native memory → OOMKill
  6. 1 replika — restart = 100% downtime, readiness bezużyteczna
  7. Liveness sprawdza DB — pad DB = restart loop wszystkich Podów
  8. Brak startupProbe — liveness zabija wolno startującą aplikację
  9. requests ≠ limits dla memory — JVM alokuje za dużo → OOMKill
  10. Duży heap (16GB+) — długie pauzy GC, gorsza latencja
  11. limits.cpu zbyt niski — dławienie CPU podczas startu, 2-3× dłuższy startup
