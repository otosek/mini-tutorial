Część 1 — AOT w ekosystemie Java

Java domyślnie = interpretacja + JIT (C1/C2 w HotSpot). Start aplikacji wymaga: wczytania klas, weryfikacji, linkowania, dopiero potem kompilacji gorących metod. To daje wysoki peak throughput, ale **wolny cold start** i długi warmup.

PodejścieKiedy pracaRuntime
JIT (HotSpot)w trakcie działaniapełny JVM, adaptacja
Leyden AOT cachetraining run + build cachepełny JVM, JIT nadal działa
Graal Native Imagebuild timenatywny binary, minimalny runtime

Część 2 — Project Leyden i JEP 483

Project Leyden (OpenJDK) — poprawa startup, warmup i footprint przez przenoszenie pracy z runtime do wcześniejszej fazy. Cel długoterminowy: AOT w ramach JVM jako alternatywa dla pełnej natywizacji GraalVM — bez rezygnacji z dynamiczności Javy.

JEP 483 (JDK 24, dostarczony): Ahead-of-Time Class Loading & Linking. Rozszerza CDS — klasy zapisane nie tylko sparsowane, ale w stanie loaded + linked (rozwiązane referencje, zweryfikowany bytecode, lambda forms).

Efekt (Spring PetClinic, orientacyjnie)

~40% szybszy start, ~21k klas gotowych od bootu — bez zmian w kodzie źródłowym. Klasy spoza cache nadal ładują się normalnie (open world).

Część 3 — Workflow AOT cache

Typowy pipeline (JDK 24+; w 25+ uproszczony przez JEP 514):

# 1. Training run — nagranie klas użytych przez aplikację
java -XX:AOTMode=record -XX:AOTConfiguration=app.aotconfig \
  -jar authors-api.jar

# 2. Utworzenie cache z konfiguracji
java -XX:AOTMode=create -XX:AOTConfiguration=app.aotconfig \
  -XX:AOTCache=app.aot -jar authors-api.jar

# 3. Produkcja — start z cache
java -XX:AOTCache=app.aot -jar authors-api.jar

Training run powinien **realnie wykonać** ścieżki startowe aplikacji (health check, główne endpointy, inicjalizacja Spring). Cache jest **specyficzny dla wersji JDK, classpath i często buildu** aplikacji.

# Wyłączenie linkowania przy tworzeniu (debug porównawczy)
java -XX:AOTMode=create -XX:-AOTClassLinking ...

CDS → AppCDS → AOT cache

CDS/AppCDS oszczędzają parse; Leyden oszczędza też **load i link** — najdrożniejsze fazy przy starcie dużej aplikacji (Spring Boot).

Część 6 — GraalVM

GraalVM to ekosystem Oracle — nie jedna rzecz:

SkładnikOpis
Graal compilerZaawansowany kompilator JIT (plugin do HotSpot od JDK 17+ jako opcja)
Native ImageAOT: bytecode → natywny executable (native-image)
TruffleFramework do implementacji języków na Graal (Polyglot)
libgraalGraal JIT skompilowany do natywnego — szybszy start samego kompilatora

Native Image — workflow

# Spring Boot 3+ (Maven)
./mvnw -Pnative native:compile

# lub bezpośrednio
native-image -jar authors-api.jar

# wynik: pojedynczy binary, bez zainstalowanego JDK na hoście

Closed-world assumption: kompilator zakłada, że w runtime nie pojawią się nowe klasy poza tym, co widać w build time. Reflection, dynamic proxies, JNI, classpath plugins — wymagają konfiguracji (reflect-config.json, reachability metadata). Spring AOT + GraalVM metadata pomagają w Spring Boot 3.

# Przykład konfiguracji reflection (Graal)
{
  "name": "com.example.Author",
  "allDeclaredFields": true,
  "allDeclaredMethods": true
}

Rekrutacyjna one-liner

Leyden = szybszy start **w normalnym JVM**. Graal Native Image = **inny sposób deployu** (binary), nie „szybszy HotSpot”.

Kiedy co wybrać

ScenariuszRekomendacja
Spring Boot monolit / mikroserwis na K8s (długo żyje)Leyden AOT cache + normalny JVM
Serverless, scale-to-zero, CLIGraal Native Image
Dużo reflection, dynamiczne pluginyLeyden lub JVM; Native Image tylko z metadata

Minimalny obraz kontenera, brak JDKNative Image

Typowe błędy

  1. Training run bez realnego ruchu — cache nie zawiera klas z endpointów używanych dopiero w prod
  2. Cache z innej wersji JAR/JDK — invalidacja lub brak korzyści, czasem błędy
  3. Myślenie, że Leyden = Native Image — nadal potrzebujesz JVM na hoście
  4. Native Image bez Spring AOT — reflection w Hibernate/Spring failuje w runtime
  5. Pomijanie native-image-agent — brak metadata dla reflection
  6. Benchmark tylko cold start bez peak throughput — Native Image może przegrać po rozgrzaniu JVM
  7. Graal JIT vs Native Image — to różne produkty; „używamy Graal” ≠ native binary
  8. Brak regeneracji cache po upgrade Spring/Java — stare cache bezużyteczne
  9. Closed-world w Leyden — nie dotyczy; klasy spoza cache ładują się JIT-em normalnie
  10. Deploy Native Image bez testów integracyjnych na binary — inne zachowanie GC, stack traces, JFR

Pytania rekrutacyjne — krótkie odpowiedzi

Junior / Mid

1. Co to Project Leyden?

Inicjatywa OpenJDK: szybszy start, warmup i mniejszy footprint przez AOT w ramach HotSpot JVM.

2. Co wprowadza JEP 483?

Ahead-of-time class loading and linking — cache klas w stanie loaded+linked (JDK 24).

3. Czym różni się AOT cache od AppCDS?

AppCDS cache'uje sparsowane klasy; JEP 483 także loaded i linked state.

4. Co to GraalVM Native Image?

AOT kompilacja Javy do natywnego executable — bez pełnego JDK w runtime.

5. JIT vs AOT — krótko?

JIT kompiluje w runtime (adaptacja); AOT przed uruchomieniem (szybszy start, mniej dynamiki).

6. Czy Leyden wymaga zmian w kodzie?

Nie — poza krokiem training/create cache w pipeline.

7. Co to training run w Leyden?

Uruchomienie aplikacji z -XX:AOTMode=record — JVM zapisuje, które klasy załadować do cache.

8. Closed-world assumption — kto?

Graal Native Image — wszystkie klasy muszą być znane/rejestrowane w build time.

9. Czy po Leyden nadal działa JIT?

Tak — pełny HotSpot JIT; cache tylko przyspiesza start ładowania klas.

10. Dla kogo Native Image?

Serverless, CLI, edge, kontenery z twardym limitem pamięci i cold start.

11. Co to CDS?

Class Data Sharing — współdzielenie metadanych klas między procesami JVM.

12. Plik AOT cache?

Typowo .aot — wynik -XX:AOTMode=create.

13. Graal compiler vs Native Image?

Graal compiler = JIT w JVM; Native Image = AOT do binary — różne narzędzia.

14. Spring Boot 3 + Graal?

Profil native, Spring AOT przetwarza bean definitions pod closed world.

15. Dlaczego wolny start Spring Boot?

Tysiące klas, classpath scanning, auto-config, JIT dopiero po starcie — Leyden atakuje fazę ładowania.

Mid / Senior

16. Open world (Leyden) vs closed world (Graal)?

Leyden: klasy spoza cache ładują się normalnie. Graal: nieznane klasy/reflection bez config = fail.

17. JEP 515 — AOT method profiling?

Profil metod z training run w cache — szybszy JIT warmup (JDK 25).

18. JEP 516 — GC-agnostic cache?

Cache działa z różnymi GC (np. ZGC); baseline cache w JDK 26.

19. Kiedy invalidować AOT cache?

Zmiana JDK, JAR, classpath, znacząca zmiana kodu/dependencies.

20. native-image-agent — po co?

Nagrywa reflection, JNI, resources w trakcie testów → generuje config JSON.

21. Peak throughput: JVM vs Native Image?

Po długim warmup HotSpot JIT często szybszy; Native Image stabilny ale niższy ceiling.

22. CRaC / Coordinated Restore — relacja do Leyden?

CRaC = snapshot JVM w punkcie; Leyden = cache klas bez pełnego snapshotu — komplementarne pomysły na start.

23. -XX:AOTClassLinking wyłączone?

Tworzy cache bez linkowania — mniejszy zysk, debug różnicy load vs link.

24. Substrate VM?

Minimalny runtime Graal Native Image (GC, wątki) — nie pełny HotSpot.

25. PGO w Native Image?

Profile-guided optimization — profile z JVM wstrzykiwane do drugiego buildu native.

26. Leyden a reflection?

Pełne wsparcie — reflection działa; po prostu klasy mogły nie trafić do cache.

27. Docker: distroless + Leyden vs Native?

Leyden: obraz z JRE + cache. Native: obraz tylko z binary — mniejszy, bez JVM.

28. libgraal?

Graal JIT jako natywna biblioteka — szybszy start kompilatora w HotSpot z -XX:+UseJVMCICompiler.

29. Dlaczego build Native Image trwa długo?

Pełna analiza reachability, AOT kompilacja całego closure, generowanie metadanych.

30. Kierunek Leyden po JEP 483?

AOT code compilation — bytecode→native w cache; dalsze skracanie warmup.

Pułapki

31. „Leyden zastępuje GraalVM”?

Nie — konkurencja/komplementarność; Leyden w OpenJDK, Graal Native Image osobny produkt Oracle.

32. Cache z dev na prod?

Ryzykowne — różny classpath, profile Spring; generuj cache per artefakt w CI.

33. Native Image + dynamic Class.forName(userInput)?

Closed world — klasa musi być w metadata; inaczej ClassNotFoundException w runtime.

34. Leyden bez training — czy coś działa?

JDK 26+ baseline cache częściowo pomaga; pełny zysk wymaga app-specific training.

35. Metryka tylko time-to-first-byte?

Native wygrywa; dodaj p95 throughput po 10 min — JVM może wygrać.

36. Graal JIT domyślnie w JDK 21?

Nie domyślnie w każdej dystrybucji — opcja w niektórych buildach (np. Oracle, custom).

37. Hibernate + Native Image?

Wymaga extensywnej konfiguracji entity/reflection — dlatego Spring AOT + metadata critical.

38. AOT cache a modular JPMS?

Cache zależy od module path — zmiana modułów wymaga regeneracji.

39. Debugging Native Image vs JVM?

Native: gdb, mniej typowych narzędzi Java; stack trace inny; JFR ograniczone.

40. Decyzja architekta: authors API na K8s HPA?

Długowieczne pody → Leyden + JVM. Scale-to-zero / serverless → rozważ Native Image. Hybryda: Leyden teraz, Native dla wybranych mikroserwisów.
