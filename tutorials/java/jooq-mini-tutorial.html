Fundamenty — co to jest jOOQ

jOOQ (Java Object Oriented Querying) to biblioteka, która mapuje SQL na typowany DSL w Javie. Zamiast składać zapytania z łańcuchów znaków albo polegać na abstrakcji ORM, piszesz SQL — ale kompilator pilnuje nazw tabel, kolumn i typów.

Po co w ogóle jOOQ? Bo w wielu systemach SQL jest prawdą: raporty, agregacje, window functions, UPSERT, CTE — to nie jest „szczegół implementacji”, tylko rdzeń logiki. Hibernate ukrywa SQL kosztem niespodzianek (N+1, lazy loading, nieoptymalne zapytania). Czysty JDBC daje kontrolę, ale bez bezpieczeństwa typów i z dużą ilością boilerplate. jOOQ łączy oba światy: pełna kontrola nad SQL + compile-time safety.

Filozofia jOOQ: „SQL first”. Biblioteka nie udaje, że baza to obiektowa graf encji — generuje i wykonuje prawdziwe zapytania SQL, znane z dokumentacji Postgresa, MySQL czy Oracle.

jOOQ ≠ ORM

Nie zarządza cyklem życia encji, nie ma lazy loading ani cache pierwszego poziomu. To query builder + executor. Mapowanie obiektowo-relacyjne (1:N, dziedziczenie) zostaw Hibernate — jOOQ bierze na siebie zapytania, gdzie SQL ma znaczenie.

Kiedy jOOQ, kiedy Hibernate, kiedy JDBC

Po co wybierać narzędzie świadomie? W stacku Java często masz wszystkie trzy opcje naraz. Zły wybór = miesiące walki z N+1 albo setkami linii JDBC. Reguła praktyczna: Hibernate do CRUD i prostych relacji, jOOQ do zapytań, gdzie SQL jest złożony lub krytyczny, JDBC / JdbcClient gdy potrzebujesz absolutnego minimum zależności.

W praktyce korporacyjnej często spotkasz hybrydę: Hibernate do zapisu encji domenowych, jOOQ do odczytów (CQRS-light), raportów i batchy. Spring Boot wspiera oba bez konfliktu — wspólny DataSource.

Pułapka: „zamienimy cały Hibernate na jOOQ”

jOOQ nie zastąpi zarządzania relacjami obiektowymi ani dirty checking. Przepisanie całego modelu domenowego na jOOQ rzadko się opłaca — chyba że domena jest płaska i query-centric.

Konfiguracja i generowanie kodu

Po co code generator? Ręczne definiowanie "author"."id" w stringach to ten sam problem co JDBC — literówka wykryta dopiero na produkcji. Generator czyta rzeczywisty schemat (tabele, kolumny, klucze, enumy Postgresa) i tworzy klasy Tables.AUTHOR.ID. Zmiana nazwy kolumny w migracji Flyway → przebudujesz projekt → kompilator wskaże wszystkie miejsca do poprawy.

Zależności (Maven)

<dependency>
    <groupId>org.jooq</groupId>
    <artifactId>jooq</artifactId>
</dependency>

jOOQ Codegen (build time)

Plugin Maven/Gradle łączy się z bazą (lub z pliku DDL) i generuje pakiet, np. com.example.db:

// Wygenerowane — NIE edytuj ręcznie
public class Tables {
    public static final Author AUTHOR = Author.AUTHOR;
    public static final Title TITLE = Title.TITLE;
}

public class Author extends TableImpl<AuthorRecord> {
    public final TableField<AuthorRecord, UUID> ID = createField(...);
    public final TableField<AuthorRecord, String> EMAIL = createField(...);
}

Migracja zmienia schemat → codegen w CI (lub lokalnie) → commit wygenerowanych klas. Bez tego drift między kodem a bazą wraca przez boczne drzwi. Alternatywa: codegen z URL testcontainers w pipeline.

DSL i type-safe SQL

Po co DSL zamiast stringów? Zapytanie budujesz jak zdanie: select().from().where().fetch(). IDE podpowiada kolumny, a typy filtrów (UUID, String, LocalDateTime) muszą się zgadzać. Porównanie AUTHOR.ID.eq(uuid) nie skompiluje się z String — JDBC pozwoliłby i wywalił się w runtime. 
import static com.example.db.Tables.*;

// SELECT first_name, email FROM author WHERE id = ?
List<AuthorRecord> rows = dsl
    .select(AUTHOR.FIRST_NAME, AUTHOR.EMAIL)
    .from(AUTHOR)
    .where(AUTHOR.ID.eq(authorId))
    .fetchInto(AUTHOR);  // mapowanie na record tabeli

// Lub na własne DTO
List<AuthorDto> dtos = dsl
    .select(AUTHOR.FIRST_NAME, AUTHOR.EMAIL)
    .from(AUTHOR)
    .where(AUTHOR.EMAIL.like("%@example.com"))
    .fetchInto(AuthorDto.class);

JOIN — czytelny jak SQL

Result<Record3<String, String, String>> result = dsl
    .select(AUTHOR.FIRST_NAME, AUTHOR.LAST_NAME, TITLE.TITLE_)
    .from(AUTHOR)
    .join(TITLE).on(TITLE.AUTHOR_ID.eq(AUTHOR.ID))
    .where(AUTHOR.CREATED_AT.gt(LocalDateTime.now().minusYears(1)))
    .fetch();

Warunki dynamiczne (filtry opcjonalne)

Typowy case: endpoint z parametrami query — część filtrów pusta. jOOQ pozwala składać Condition bez konkatenacji SQL:

Condition condition = DSL.trueCondition();
if (email != null)   condition = condition.and(AUTHOR.EMAIL.eq(email));
if (namePrefix != null) condition = condition.and(AUTHOR.LAST_NAME.startsWith(namePrefix));

return dsl.selectFrom(AUTHOR).where(condition).fetch();
Po co Condition zamiast StringBuilder? Parametry są bindowane (PreparedStatement) — ochrona przed SQL injection. Logika AND/OR jest jawna. Testujesz filtry jednostkowo bez parsowania stringów.

Plain SQL, gdy DSL nie wystarcza

// fragment zapytania poza DSL — nadal z bindingiem
Field<BigDecimal> rank = DSL.field("rank() OVER (ORDER BY score DESC)", BigDecimal.class);

dsl.select(AUTHOR.FIRST_NAME, rank)
   .from(AUTHOR)
   .fetch();

CRUD, JOIN, warunki dynamiczne

Po co osobna sekcja CRUD? Składnia insert/update/delete w jOOQ różni się od SELECT i ma własne wzorce: returning(), onConflict(), set() z wyrażeniami SQL. Zrozumienie ich pozwala pisać repozytoria bez powrotu do JDBC.

INSERT

AuthorRecord record = dsl.newRecord(AUTHOR);
record.setEmail("anna@ex.com");
record.setFirstName("Anna");
record.store();  // INSERT + ustawia wygenerowane ID jeśli jest

// Lub fluent:
UUID newId = dsl.insertInto(AUTHOR)
    .set(AUTHOR.EMAIL, "jan@ex.com")
    .set(AUTHOR.FIRST_NAME, "Jan")
    .returning(AUTHOR.ID)
    .fetchOne()
    .getId();

UPDATE i DELETE

dsl.update(AUTHOR)
   .set(AUTHOR.FIRST_NAME, "Anna Maria")
   .where(AUTHOR.ID.eq(authorId))
   .execute();

dsl.deleteFrom(TITLE)
   .where(TITLE.AUTHOR_ID.eq(authorId))
   .execute();

Paginacja

dsl.selectFrom(AUTHOR)
   .orderBy(AUTHOR.CREATED_AT.desc())
   .limit(pageSize)
   .offset(page * pageSize)
   .fetch();
Metoda fetchPo co
fetch()Lista wszystkich wierszy
fetchOne()Dokładnie jeden — wyjątek jeśli 0 lub >1
fetchOptional()Optional<Record> — brak = empty
fetchSingle()Jeden wiersz, jedna kolumna — np. COUNT
fetchLazy()Stream z kursorem — duże zestawy bez ładowania do pamięci

Batch, UPSERT, transakcje

Po co batch i UPSERT w jOOQ? Import tysięcy wierszy pojedynczym INSERT-em to wąskie gardło. Batch grupuje operacje w jednej transzy. UPSERT (ON CONFLICT w Postgresie) eliminuje race condition „najpierw SELECT, potem INSERT lub UPDATE”. jOOQ generuje dialekt-specyficzny SQL — nie musisz pamiętać składni Oracle vs Postgres.

Batch insert

dsl.batch(
    dsl.insertInto(AUTHOR, AUTHOR.EMAIL, AUTHOR.FIRST_NAME)
       .values("a@ex.com", "Anna"),
    dsl.insertInto(AUTHOR, AUTHOR.EMAIL, AUTHOR.FIRST_NAME)
       .values("b@ex.com", "Bogdan")
).execute();

// Lub batch z wieloma VALUES w pętli
List<Query> queries = emails.stream()
    .map(e -> dsl.insertInto(AUTHOR, AUTHOR.EMAIL).values(e))
    .toList();
dsl.batch(queries).execute();

UPSERT (Postgres)

dsl.insertInto(AUTHOR)
   .set(AUTHOR.EMAIL, "anna@ex.com")
   .set(AUTHOR.FIRST_NAME, "Anna")
   .onConflict(AUTHOR.EMAIL)
   .doUpdate()
   .set(AUTHOR.FIRST_NAME, "Anna Updated")
   .execute();

Transakcje

dsl.transaction(configuration -> {
    DSLContext tx = DSL.using(configuration);
    tx.insertInto(AUTHOR)...execute();
    tx.insertInto(TITLE)...execute();
    // rollback automatyczny przy unchecked exception
});
Po co dsl.transaction() a nie @Transactional? W kodzie bibliotecznym lub batch job bez Springa — lambda transaction jest samowystarczalna. W Springu i tak używasz @Transactional — jOOQ podłącza się do tej samej transakcji przez ConnectionProvider.

Spring Boot

Po co starter jOOQ? Spring Boot auto-konfiguruje DSLContext z istniejącego DataSource — ten sam pool co Hibernate. Nie duplikujesz konfiguracji połączenia. Wstrzykujesz DSLContext do serwisów tak jak JdbcTemplate. 
// build.gradle / pom.xml
// org.springframework.boot:spring-boot-starter-jooq

@Service
@RequiredArgsConstructor
public class AuthorQueryService {
    private final DSLContext dsl;

    public List<AuthorDto> findByDomain(String domain) {
        return dsl.select(AUTHOR.FIRST_NAME, AUTHOR.EMAIL)
                  .from(AUTHOR)
                  .where(AUTHOR.EMAIL.like("%@" + domain))
                  .fetchInto(AuthorDto.class);
    }
}

Konfiguracja własna DSLContext

Multi-tenancy, custom ExecuteListener (logowanie SQL, metryki), Settings (np. withRenderFormatted(true) w dev) — bean DefaultConfiguration + DefaultDSLContext.

Zaawansowane scenariusze

CTE (WITH)

Po co CTE w jOOQ? Złożone raporty czytelniejsze jako pipeline: najpierw CTE z agregatem, potem SELECT z CTE. jOOQ wspiera zagnieżdżone with() — to nadal jeden statement SQL, atomowy w transakcji. 
var recent = name("recent_authors").as(
    select(AUTHOR.ID, AUTHOR.EMAIL)
    .from(AUTHOR)
    .where(AUTHOR.CREATED_AT.gt(LocalDateTime.now().minusMonths(1)))
);

dsl.with(recent)
   .select(count())
   .from(recent)
   .fetchSingle(0, int.class);

Stored procedures i funkcje

// Wywołanie funkcji Postgres
BigDecimal result = dsl.select(
    DSL.function("calculate_royalty", BigDecimal.class, AUTHOR.ID)
).from(AUTHOR).where(...).fetchSingle(...);

Multi-schema / multi-tenancy

Osobny DSLContext z Settings ustawiającym renderSchema lub mapowanie schema("tenant_123").table("author") — izolacja tenantów bez zmiany kodu zapytań.

Reactive (R2DBC)

jOOQ jest synchroniczny (JDBC). Dla WebFlux użyj R2DBC z własnym query layer lub trzymaj jOOQ w blokującym wątku (Schedulers.boundedElastic()). To świadomy kompromis — type-safety vs pełna reaktywność.

Typowe błędy

  1. Brak codegen po migracji — kod kompiluje się ze starymi kolumnami; błędy w runtime na prod.
  2. fetchOne() gdy wyników jest 0 lub wiele — użyj fetchOptional() albo fetchOneInto() z świadomością kontraktu.
  3. N+1 w pętli — jOOQ nie chroni przed zapytaniem w pętli tak jak świadomy JOIN; batch fetch albo jeden SELECT z IN.
  4. String concatenation w where() — .where("email = '" + email + "'") omija typowanie i otwiera SQL injection; używaj AUTHOR.EMAIL.eq(email).
  5. Ignorowanie dialektu — onConflict działa inaczej w MySQL (onDuplicateKeyUpdate); testuj na docelowej bazie.
  6. Ładowanie gigantycznego fetch() — milion wierszy do listy; użyj fetchLazy() lub LIMIT + kursor.
  7. Edycja wygenerowanych klas — zmiany znikną przy następnym codegen; logika do osobnych serwisów/repozytoriów.
  8. Mieszanie odpowiedzialności z Hibernate — ta sama encja zarządzana przez Session i jednocześnie UPDATE przez jOOQ bez entityManager.flush() → niespójny stan cache.
  9. Brak indeksów pod zapytania jOOQ — jOOQ generuje optymalny SQL, ale plan wykonania zależy od DBA; EXPLAIN nadal twoja odpowiedzialność.
  10. Open Source vs Commercial — dialekty Oracle, SQL Server w pełni w wersji commercial; Postgres/MySQL w open source — sprawdź licencję przed wyborem.
