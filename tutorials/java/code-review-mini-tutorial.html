0. Po co review — i w jakiej kolejności

Code review to nie „czy kod wygląda ładnie”. To decyzja: czy ten diff może wejść na main bez ryzyka dla produktu, zespołu i utrzymania. Ty jako reviewer chronisz jakość — nie egocentrycznie „swój styl”, tylko wspólne standardy i intencję ticketu.

CI (build + testy + analiza statyczna)
        ↓
LLM / bot (wstępny review diffu)
        ↓
Ty — mały, wartościowy obszar:
  1. Czy robi to, o co prosiło zadanie?
  2. Czy struktura i granice mają sens?
  3. Czy konwencje Java / projektu są OK?
  4. Czy testy dowodzą zachowania?
  5. Czy nie ma ryzyka (bezpieczeństwo, dane, regresja)?

Im więcej złapie CI i LLM, tym mniej czasu marnujesz na formatowanie i oczywiste null-checki — zostaje myślenie o domenie, API i regresjach.

1. Najpierw maszyny — potem człowiek

Nie otwieraj diffu „na świeżo”, jeśli CI jest czerwone albo bot jeszcze nie napisał. Wyjątek: awaria CI niezwiązana z PR — wtedy napisz to w komentarzu i kontynuuj tylko warstwę, którą maszyny nie pokryją.

Analiza statyczna (musi być zielona)

Pułapka: komentowanie w PR rzeczy, które Checkstyle i tak zablokuje. To szum. Poproś autora o poprawę CI albo popraw regułę w repo — nie rób z siebie lintera.

LLM jako pierwszy reviewer

Bot (Copilot, Cursor Bugbot, CodeRabbit, własny prompt na diff) dostaje opis ticketu + diff i odpowiada na checklistę. Ty czytasz jego znaleziska i weryfikujesz — nie kopiujesz ślepo.

  • Czy bot zrozumiał wymaganie (nie tylko pliki)?
  • Które uwagi bot są fałszywie pozytywne (ignoruj i nie powtarzaj)?
  • Czego bot nie widzi: kontekst domeny, ukryte kontrakty, decyzje produktowe?
  • Czy w diffie są miejsca oznaczone przez bota jako „ryzykowne” — te czytasz w pierwszej kolejności?
Kluczyk: prompt dla LLM: „Jesteś reviewerem Java/Spring. Ticket: … Diff poniżej. Zwróć tylko: (1) niezgodność z wymaganiem, (2) regresje, (3) brakujące testy, (4) problemy bezpieczeństwa. Bez uwag o formatowaniu.”

2. Zgodność z zadaniem

Zanim wejdziesz w klasy — otwórz ticket / opis PR / AC. Diff bez kontekstu łatwo „poprawić” w złą stronę.

  • Czy PR realizuje to zadanie, a nie „przy okazji” trzy inne refaktory?
  • Czy acceptance criteria są pokryte (happy path + wymienione edge case’y)?
  • Czy scope jest mały? Olbrzymi PR = poproś o split albo reviewuj warstwami (API → domena → infra).
  • Czy opis PR mówi dlaczego, nie tylko co? Brak opisu = request changes na opis, nie na kod.
  • Czy są breaking changes API / migracje DB — i czy są udokumentowane?
  • Czy feature flag / rollback jest przemyślany przy ryzykownym wdrożeniu?
// Źle w komentarzu:
"To powinno być inaczej zrobione."

// Dobrze:
"AC-3: przy braku autora API ma zwrócić 404.
Tu zwracamy 200 z pustym body — czy to świadoma zmiana kontraktu?"
Pułapka: approve’owanie „ładnego” kodu, który nie spełnia AC. Estetyka nie zastępuje zgodności z wymaganiem.

3. Klasy, pakiety, granice

Patrzysz na to, gdzie żyje kod i czy zależności nie płyną pod prąd.

  • Czy nowe klasy siedzą w właściwym pakiecie (domena / application / adapter), a nie w „util” / „helper”?
  • Czy jedna klasa = jedna odpowiedzialność? God-class w PR = czerwona flaga.
  • Czy warstwa web nie woła bezpośrednio JDBC/JPA omijając serwis (jeśli projekt tego zabrania)?
  • Czy nie ma cyklicznych zależności między pakietami?
  • Czy publiczne API (kontrolery, eventy) nie wycieka encjami JPA / szczegółami persystencji?
  • Czy nazwy klas i metod mówią o domenie (cancelOrder), a nie o technice (processData)?

4. Konwencje i idiomy Java

Tu nie grebisz o spacje — o idiomy zespołu i języka. Zakładasz, że Spotless już przeszedł.

  • Nazewnictwo: klasy PascalCase, metody/pola camelCase, stałe UPPER_SNAKE, pakiety małe litery.
  • Optional jako zwrotka — nie jako pole encji / parametr wszędzie.
  • Immutability tam, gdzie ma sens: record, final fields, unmodifiable kolekcje na granicach.
  • Obsługa błędów: wyjątki domenowe vs 500; nie łykać wyjątków pustym catch.
  • Zasoby: try-with-resources; brak wycieków streamów / połączeń.
  • Equals/hashCode/toString — spójne, zwłaszcza przy encjach (zwykle po ID biznesowym, nie po całej grafie).
  • Streamy: czytelność > „spryt”; side-effecty w forEach = zapytaj.
  • Wątki / współbieżność: czy stan współdzielony jest bezpieczny? Virtual threads ≠ magiczna poprawa wszystkiego.
  • Spring: scope beanów, transakcje transakcji (@Transactional na public methods, self-invocation), Lazy vs N+1.
// Review: zapytaj o transakcję i N+1
@Transactional(readOnly = true)
public List<OrderDto> findAll() {
  return orderRepository.findAll().stream()   // lines?
      .map(orderMapper::toDto)                // getItems() w mapperze?
      .toList();
}

5. Testy — czy są i czy dowodzą

Brak testów przy logice biznesowej = niemal zawsze request changes (chyba że PR to czysty config / wygenerowany kod i zespół ma inną politykę).

  • Czy dla nowej ścieżki jest test, który padnie, gdy usuniesz implementację? (nie „coverage theatre”)
  • Nazwy: shouldRejectCancel_whenOrderAlreadyShipped > test1.
  • Arrange–Act–Assert / Given–When–Then — czytelny układ.
  • Czy testują zachowanie, a nie prywatne metody / wewnętrzny stan?
  • Czy edge case’y z ticketu mają osobne scenariusze?
  • Mocki: czy mockowane jest tylko zewnętrze (repo, HTTP)? Nadmiar mocków = test kruchy.
  • Testy integracyjne / @SpringBootTest — czy nie są zbędnie wolne i czy mają jasny zakres?
  • Czy flaky (losowe sleepy, zależność od kolejności, czas systemowy bez clocka)?
  • Czy assert mówi co sprawdzamy (assertThat(status).isEqualTo(404)), a nie tylko „nie rzuciło”?
Słaby testCo powiedzieć
Tylko verify(service).method()„Brak asercji wyniku — co ma być prawdziwe po wywołaniu?”
Thread.sleep(500)„Zamień na Awaitility / synchroniczny test / fake clock.”
Kopiuj-wklej 5 prawie identycznych testów„Parameterized test albo jedna tabela przykładów.”
Test „przechodzi” bez asercji„To nie jest test — to smoke bez kontraktu.”

6. Bezpieczeństwo, dane, operacje

  • Autoryzacja: czy endpoint sprawdza uprawnienia, nie tylko „jest zalogowany”?
  • IDOR: czy user A może po ID dociągnąć zasób usera B?
  • Input: walidacja (@Valid), limity rozmiaru, brak SQL/JPQL sklejanych ze stringa.
  • Sekrety: hasła, tokeny, connection stringi — nie w logach, nie w repo, nie w wyjątku.
  • PII w logach — maskowanie.
  • Migracje DB: czy odwracalne / bezpieczne online (locki, backfill)?
  • Timeouty, retry, idempotencja przy wywołaniach zewnętrznych.
  • Obserwowalność: czy da się zdebugować produkcję (korelacje, sensowne logi błędów)?

7. Jak pisać komentarze w PR

ZamiastNapisz
„Źle.”Co jest nie tak + dlaczego + propozycja lub pytanie.
„Ja bym zrobił X.”„X zmniejsza ryzyko Y, bo… — co myślisz?” (preferencja ≠ blocker)
Ściana tekstu na 20 liniiJeden problem = jeden wątek; link do docs/ADR.
Tylko nitpickiOznacz nit: / opcjonalne: vs blocking:

Severities (ustal z zespołem):

  • blocking — musi wejść przed merge (bug, bezpieczeństwo, brak AC, brak testu krytycznego).
  • should — mocna sugestia; merge możliwy po dyskusji.
  • nit — styl / naming; nie blokuj samego PR za nitpicki, jeśli CI i tak egzekwuje styl.
  • question — nie wiesz; autor wyjaśnia lub poprawia.
  • praise — konkretna dobra decyzja (uczy zespół, co powielać).
Kluczyk: kończ review podsumowaniem: „Blocking: 2 (test cancel + IDOR). Reszta nity. Po poprawkach LGTM.” Autor wie, co jest bramką.

8. Tipsy i kluczyki

Czytaj diff jak użytkownik API

Najpierw publiczne wejścia (kontroler, event, metoda publiczna), potem w dół. Nie zaczynaj od prywatnego helpera.

Diff „od końca”

Czasem otwórz najpierw testy — mówią, jakie zachowanie autor obiecuje. Potem sprawdź, czy produkcja to spełnia.

Reguła 30–60 minut

Po godzinie jakość review spada. Duży PR → sesje albo split. Lepiej dwa krótkie review niż jedno „zmęczone approve”.

Szukaj tego, czego nie ma

Brak walidacji, brak rollbacku, brak testu negatywnego, brak indeksu przy nowym zapytaniu — review to też lista nieobecności.

Jedno pytanie > pięć opinii

„Jaki jest kontrakt przy null?” zmusza autora do myślenia. „Zrób Optional” to narzucanie stylu.

Sprawdź migracje i feature flags osobno

Kod aplikacji może być OK, a deploy zabije produkcję lockiem na tabeli. Deploy path = część review.

Chwal konkret

„Dobry test na race przy double-cancel” > „fajny PR”. Wzmacnia dobre wzorce.

Nie reviewuj tego, czego nie rozumiesz w domenie

Napisz: „Nie znam reguły X — proszę o potwierdzenie od @osoby-domenowej.” Cisza + approve = ryzyko.

Mini-checklist przed „Approve”:
[ ] CI zielone (lub znany false alarm)
[ ] Bot/LLM przejrzany, false-positive odfiltrowane
[ ] AC z ticketu spełnione
[ ] Brak wycieku encji / sekretów
[ ] Testy dowodzą nowych ścieżek
[ ] Blocking komentarze rozwiązane lub uzgodnione
[ ] Wiesz, jak to się wdroży / cofnie

Typowe błędy (Twoje — jako reviewera)

  • Robienie z siebie Checkstyle. Format i importy = CI. Ty = zachowanie i ryzyko.
  • Approve przy czerwonym pipeline „bo kod wygląda OK”. Merge gate istnieje po coś.
  • Ignorowanie opisu ticketu. Piękny kod obok AC to nadal zły PR.
  • Blokowanie za gust. Preferencje oznaczaj jako nit; blocking tylko dla ryzyka / standardu zespołu.
  • Review w głowie bez komentarzy. Jeśli coś jest niejasne i milczysz — nikt się nie nauczy.
  • Ściana 40 komentarzy bez priorytetu. Autor nie wie, co jest bramką. Używaj severity + summary.
  • Bike-shedding nazw przez godzinę. Nazwa ma być jasna; nie idealna według Twojego thesaurusu.
  • Pomijanie testów, bo „autor zwykle pisze dobre”. Każdy PR osobno.
  • Rubber-stamp (LGTM bez czytania). Twój approve = Twoja odpowiedzialność przy incydencie.
  • Toksyczny ton. Atakuj kod i decyzję, nie osobę. „Ten catch ukrywa błąd” ≠ „nie umiesz Javy”.
  • Powtarzanie fałszywych alarmów LLM. Weryfikuj bota; inaczej uczysz zespół ignorować review.
  • Nieskończone ping-pongi. Po 2–3 rundach zrób sync 15 min — szybciej niż kolejny esej w GitHubie.
