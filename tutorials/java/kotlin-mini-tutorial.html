Fundamenty

Kotlin to język na JVM (JetBrains, 2016) — 100% interoperacyjny z Javą: wywołujesz biblioteki Java z Kotlina i vice versa. Kompiluje się do bytecode jak Java. Na Androidzie Kotlin jest domyślny; w backendie (Spring) obok Javy.

Kotlin nie zastępuje Javy 1:1 — część „magii” to składnia i bezpieczeństwo typów w compile-time. Java 25 (LTS) nadal jest referencją na JVM; wiele pomysłów Kotlina trafiła do Javy (records, sealed, pattern matching), ale Kotlin wciąż ma unikalne cechy (extensions, coroutines, null w typach).

Null i typy

Nullable types

Co robi: Typ z ? jawno oznacza, że wartość może być null. Bez ? — compile error przy przypisaniu null.

Kotlin 
var name: String = "Anna"
var nick: String? = null
// nick.length — błąd kompilacji; użyj safe call lub check
Java 25

Jak w Javie: Brak nullable w typie — Optional, adnotacje (@Nullable), lub konwencja. Records i pattern matching nie rozwiązują null w sygnaturze.

String name = "Anna";
String nick = null; // legalne — NPE w runtime

Optional<String> nickOpt = Optional.empty();
nickOpt.orElse("default");

Safe call ?. i Elvis ?:

Co robi: ?. zwraca null zamiast NPE; ?: to wartość domyślna gdy null.

Kotlin 
val len = nick?.length          // Int? — null jeśli nick null
val label = nick ?: "anonymous"
Java 25

Jak w Javie: Optional.map, lub pattern matching z null w switch (J21+).

Integer len = nick != null ? nick.length() : null;

String label = nick != null ? nick : "anonymous";
// lub
String label2 = Optional.ofNullable(nick).orElse("anonymous");

!! (not-null assertion)

Co robi: Wymusza „to nie jest null” — NPE w runtime jak w Javie. Unikaj w produkcji.

Kotlin 
val s = nick!!  // NPE jeśli nick == null
Java 25 
String s = nick; // po ręcznym sprawdzeniu lub świadomym ryzyku NPE

Smart cast

Co robi: Po sprawdzeniu typu/null kompilator „wie”, że zmienna jest bezpieczna — bez jawnego cast.

Kotlin 
if (x is String) {
    println(x.length)  // x już String
}
Java 25

Jak w Javie: Pattern matching instanceof (od J16) — ten sam pomysł.

if (x instanceof String s) {
    System.out.println(s.length());
}

Klasy i dane

Data class

Co robi: Jedna linija — equals, hashCode, toString, copy, komponenty destrukturyzacji.

Kotlin 
data class Author(val id: String, val name: String)

val a = Author("1", "Anna")
val b = a.copy(name = "Jan")
val (id, name) = a
Java 25

Jak w Javie: record (od J16) + record patterns w switch (J21+).

record Author(String id, String name) {}

var a = new Author("1", "Anna");
// brak copy() — nowy record lub ręcznie
var b = new Author(a.id(), "Jan");

switch (a) {
    case Author(var id, var name) -> ...
}

Sealed class / interface

Co robi: Zamknięta hierarchia — znane podtypy w compile-time; idealne z when.

Kotlin 
sealed interface Result
data class Ok(val data: String) : Result
data class Err(val msg: String) : Result
Java 25

Jak w Javie: sealed + permits (od J17) — prawie identyczny model.

sealed interface Result permits Ok, Err {}
record Ok(String data) implements Result {}
record Err(String msg) implements Result {}

Properties (val / var)

Co robi: Pole + getter (+ setter dla var) bez boilerplate; val = tylko odczyt.

Kotlin 
class User(val id: String, var email: String)
// user.id — wywołuje getId() w bytecode
Java 25

Jak w Javie: Record dla immutable DTO; Lombok @Getter; lub ręczne gettery/settery.

record User(String id, String email) {} // immutable

// mutable — klasa z polami + get/set lub Lombok

Object (singleton) i companion object

Co robi: object = jedna instancja (singleton). companion object = statyczne metody/pola jak w Javie, ale z interfejsami i extensions.

Kotlin 
object Config { val apiUrl = "https://api" }

class Factory {
    companion object {
        fun create() = Factory()
    }
}
Java 25 
// Singleton — enum lub holder pattern
enum Config { INSTANCE;
    String apiUrl() { return "https://api"; }
}

class Factory {
    static Factory create() { return new Factory(); }
}

Primary constructor

Co robi: Parametry konstruktora w nagłówku klasy — mniej kodu niż Java bean.

Kotlin 
class Service(private val repo: Repo) {
    fun run() = repo.findAll()
}
Java 25 
class Service {
    private final Repo repo;
    Service(Repo repo) { this.repo = repo; }
    void run() { repo.findAll(); }
}
// lub record jeśli tylko dane

Funkcje i rozszerzenia

Extension functions

Co robi: „Metoda” na istniejącym typie bez dziedziczenia — compile-time sugar, statyczna funkcja z receiverem.

Kotlin 
fun String.isEmail(): Boolean =
    contains("@") && contains(".")

"user@mail.com".isEmail()
Java 25

Jak w Javie: Statyczna metoda util (StringUtils), lub wrapper — brak extensions w języku.

class StringExt {
    static boolean isEmail(String s) {
        return s.contains("@") && s.contains(".");
    }
}

Default parameters i named arguments

Co robi: Domyślne wartości parametrów; wywołanie z nazwami — czytelne API bez builderów.

Kotlin 
fun greet(name: String, polite: Boolean = true) = ...
greet("Anna", polite = false)
Java 25

Jak w Javie: Overloady metod, builder pattern, lub record z opcjonalnymi polami + Optional.

void greet(String name) { greet(name, true); }
void greet(String name, boolean polite) { ... }

Top-level functions

Co robi: Funkcje poza klasą — plik staje się modułem procedur (jak w Go).

Kotlin 
// utils.kt
fun parseId(raw: String): Long = raw.toLong()
Java 25

Jak w Javie: Klasa util ze statycznymi metodami; od J9 — można mieć wiele klas w jednym pliku tylko przez inner/nested — top-level to zawsze klasa.

// Utils.java
public final class Utils {
    public static long parseId(String raw) { ... }
}

Inline functions + reified generics

Co robi: inline wstawia bytecode na miejsce wywołania (zero overhead lambdy). reified T — typ generyczny dostępny w runtime (np. gson.fromJson<List<Author>>()).

Kotlin 
inline fun <reified T> Gson.fromJson(json: String): T =
    fromJson(json, object : TypeToken<T>() {}.type)
Java 25

Jak w Javie: Brak reified — przekazuj Type, Class<T>, lub MethodHandle. Inline — optymalizacja JIT, nie składnia.

<T> T fromJson(Gson gson, String json, Class<T> type) {
    return gson.fromJson(json, type);
}

Składnia i wyrażenia

when (wyrażenie)

Co robi: Switch zwracający wartość; gałęzie bez break; wzorce typów, wyrażenia warunkowe.

Kotlin 
val label = when (result) {
    is Ok -> result.data
    is Err -> "error: ${result.msg}"
    else -> "unknown"
}
Java 25

Jak w Javie: Switch expression + pattern matching (J21+).

String label = switch (result) {
    case Ok(var data) -> data;
    case Err(var msg) -> "error: " + msg;
    default -> "unknown";
};

String templates

Co robi: "Hello $name" i "${expr}" — interpolacja w compile-time gdzie możliwe.

Kotlin 
val msg = "User $name has ${orders.size} orders"
Java 25

Jak w Javie: String.format, String.join, text blocks (J15+) — string templates w preview w starszych wersjach; w 25 nadal głównie format/concat.

String msg = String.format("User %s has %d orders", name, orders.size());
// lub "User " + name + " has " + orders.size() + " orders"

Scope functions: let, run, apply, also, with

Co robi: Krótkie bloki na obiekcie — transformacja, konfiguracja, side-effect. Różnią się receiverem (it vs this) i zwrotem.

Kotlin 
val id = raw?.let { parseId(it) }
val user = User().apply { email = "a@b.c" }
also { log.info("created {}", it) }
Java 25

Jak w Javie: Optional.map, try-with-resources, lub lambdy na builderze — brak jednego standardu.

Long id = raw != null ? parseId(raw) : null;

var user = new User();
user.setEmail("a@b.c");
log.info("created {}", user);

Delegated properties (by)

Co robi: Lazy init, observable, mapowanie — logika get/set w delegacie.

Kotlin 
val heavy by lazy { computeHeavy() }
var name by Delegates.observable("") { _, old, new ->
    println("$old -> $new")
}
Java 25

Jak w Javie: Holder pattern, Supplier + volatile, lub framework (Spring @Lazy).

private volatile Object heavy;
Object getHeavy() {
    if (heavy == null) heavy = computeHeavy();
    return heavy;
}

Kolekcje i API

Immutable vs mutable collections

Co robi: Osobne typy: List (read-only interfejs) vs MutableList — jawna mutability w API.

Kotlin 
val readOnly: List<String> = listOf("a")
val mutable: MutableList<String> = mutableListOf("a")
Java 25

Jak w Javie: List.of() — niemutowalna; new ArrayList<>() — mutowalna. Brak rozróżnienia w typie interfejsu — konwencja lub UnmodifiableList.

List<String> readOnly = List.of("a");
List<String> mutable = new ArrayList<>(List.of("a"));

Collection operators

Co robi: map, filter, flatMap, groupBy jako metody na kolekcji — jak LINQ, bez Stream API.

Kotlin 
authors.filter { it.active }.map { it.name }
Java 25

Jak w Javie: Stream API (od J8) — deklaratywnie, ale przez .stream().

authors.stream()
    .filter(a -> a.isActive())
    .map(Author::getName)
    .toList();

Współbieżność

Coroutines

Co robi: Lekkie „wątky” w bibliotece (kotlinx.coroutines) — suspend, strukturalna współbieżność, cancellation, async/await w składni. Główna przewaga Kotlina na I/O.

Kotlin 
suspend fun fetchAuthors(): List<Author> =
    withContext(Dispatchers.IO) { repo.loadAll() }

val authors = async { fetchAuthors() }
Java 25

Jak w Javie: Virtual Threads (J21+) — synchroniczny styl bez callbacków; Structured Concurrency (StructuredTaskScope, preview w 25). Brak suspend w języku — CompletableFuture lub czysty sync na virtual thread.

try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
    Subtask<List<Author>> t = scope.fork(() -> repo.loadAll());
    scope.join();
    var authors = t.get();
}
// lub prościej na virtual thread:
try (var ex = Executors.newVirtualThreadPerTaskExecutor()) {
    ex.submit(() -> repo.loadAll()).get();
}

Flow (cold stream)

Co robi: Asynchroniczny strumień wartości z backpressure — odpowiednik Rx bez pełnego Rx; flow { emit() }, operatory jak w kolekcjach.

Kotlin 
fun events(): Flow<Event> = flow {
    while (true) emit(readEvent())
}
Java 25

Jak w Javie: Reactive Streams (Project Reactor, RxJava), Stream (synchroniczny), lub async generatorów — brak w standard library.

Flux<Event> events = Flux.create(sink -> {
    while (!sink.isCancelled()) sink.next(readEvent());
});

Kotlin vs Java 25 — co się zbliżyło

Java 25 nie „kopiuje” całego Kotlina, ale wiele luk zamyka:

Kiedy Kotlin: Android, multiplatform (KMP), team preferuje składnię, coroutines/Flow w całym stacku. Kiedy Java 25: ekosystem czysto JVM/Spring bez Kotlina, rekordy + virtual threads wystarczą, zero dodatkowego runtime (coroutines lib).

Typowe błędy

  • Platform types z Javy — String! z Javy w Kotlinie to „unknown nullability” — traktuj jak nullable w API.
  • !! zamiast safe call — wraca NPE; w Javie też, ale w Kotlinie wygląda „bezpiecznie”.
  • Extension ukrywa metodę — extension nie nadpisuje metody klasy; kolejność importów ma znaczenie.
  • data class z mutowalnymi polami — copy shallow; mutowalny var w data class psuje immutability.
  • Coroutine na Main bez Dispatchers — blokujesz UI / event loop.
  • GlobalScope — brak structured concurrency; wycieki i trudny cancellation.
  • Mylenie runBlocking z produkcją — tylko testy / main; w serwisie użyj scope z lifecycle.
  • Java: Optional w polach encji — antywzorzec; Optional tylko w return type API.
  • Java: ignorowanie virtual threads przy migracji z Kotlina — nie 1:1 z coroutines, ale podobny model I/O.
  • Mieszanie stylów w jednym module — half Kotlin half Java beans bez records/data class — boilerplate wraca.
