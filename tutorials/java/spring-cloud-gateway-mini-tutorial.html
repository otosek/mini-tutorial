Część 0 — Fundamenty

Spring Cloud Gateway (SCG) to reverse proxy i API gateway dla mikroserwisów w ekosystemie Spring. Stoi na Spring WebFlux i Project Reactor (Netty) — model reaktywny, nie servletowy Tomcat.

Jedno wejście HTTP(S) dla klientów (SPA, mobile, partnerzy). Gateway routuje żądanie do właściwego serwisu wewnętrznego, dodaje/usuwa nagłówki, waliduje JWT, limituje RPS, łączy się z circuit breakerem — zanim ruch trafi do Spring Boota za nim.

Klient → Spring Cloud Gateway (predicates + filters) │ ├─ /api/auth/** → auth-service:8081 ├─ /api/orders/** → order-service:8082 └─ /api/authors/** → author-service:8083
vsRóżnica
Zuul 1Servlet, blocking — EOL; nie startuj nowego projektu na Zuul
Nginx / Envoy / KongLżejsze, język konfiguracji inny; SCG gdy cały stack to Spring i chcesz filtry w Javie
AWS API GatewayManaged, integracja z Cognito/Lambda; SCG na ECS/EKS/VM gdy logika routingu w kodzie
Spring MVC + @ControllerTo nie gateway — to aplikacja. SCG to osobny proces na porcie 8080/443
Predykat + filtr

Predicate — czy trasa pasuje (Path, Method, Header, Cookie, After). Filter — co zrobić z żądaniem/odpowiedzią (StripPrefix, AddRequestHeader, Retry, CircuitBreaker). Trasa = lista predykatów (AND) + lista filtrów (kolejność ma znaczenie).

1. Kiedy używać / kiedy nie

Bierz SCGOlej SCG
Wiele serwisów Spring Boot, jeden publiczny host (api.example.com) Jeden monolit — wystarczy Spring Security + reverse proxy nginx
Centralna walidacja JWT / OAuth2 na brzegu Publiczne API tylko przez AWS API Gateway + Lambda — SCG redundantny
Filtry w Javie (tenant z Host, correlation-id, custom auth) Prosty path-based routing bez logiki — nginx/ALB tańszy operacyjnie
Integracja z Resilience4j, Micrometer, Spring Cloud Discovery Team nie chce WebFlux — utrzymanie reaktywnego gateway wymaga znajomości Reactor
BFF (Backend for Frontend) — agregacja kilku wywołań w jednym filtrze GraphQL gateway (Apollo Router) jako główny punkt wejścia — SCG tylko pod spodem
Pułapka: SCG nie zastępuje WAF, DDoS protection ani mTLS między serwisami. To warstwa aplikacyjna — przed nią i tak stawiasz CloudFront/ALB/nginx.

2. Routing

Starter: spring-cloud-starter-gateway (wersja z BOM Spring Cloud, np. 2024.0.x przy Boot 3.4). Nie dodawaj spring-boot-starter-web — koliduje z WebFlux.

spring:
  cloud:
    gateway:
      routes:
        - id: authors
          uri: http://localhost:8082
          predicates:
            - Path=/api/authors/**
          filters:
            - StripPrefix=1    # /api/authors/1 → /authors/1 na backendzie
        - id: orders
          uri: lb://order-service   # wymaga discovery (Eureka / K8s)
          predicates:
            - Path=/api/orders/**
            - Method=GET,POST

Programowo — RouteLocator bean (wygodne przy testach i dynamicznym routingu):

@Bean
RouteLocator routes(RouteLocatorBuilder b) {
  return b.routes()
      .route("authors", r -> r
          .path("/api/authors/**")
          .filters(f -> f.stripPrefix(1))
          .uri("http://author-service:8082"))
      .build();
}
PredykatPrzykład
Path/api/**, ant-style
MethodGET,POST
HeaderX-Api-Version, v2
Host*.tenant.app.com — multi-tenancy po subdomenie
Queryversion, beta
WeightCanary — 90% na v1, 10% na v2

StripPrefix vs RewritePath: StripPrefix=1 usuwa pierwszy segment ścieżki. RewritePath=/api/(?<segment>.*), /$\{segment} — pełna kontrola regexem. Błędny prefix = 404 na backendzie mimo „zielonego” gateway.

3. Filtry — wbudowane i własne

GatewayFilter — na trasę. GlobalFilter — na każde żądanie (kolejność przez getOrder(), niższa liczba = wcześniej).

@Component
class CorrelationIdFilter implements GlobalFilter, Ordered {
  @Override
  public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
    String id = exchange.getRequest().getHeaders()
        .getFirst("X-Correlation-Id");
    if (id == null) id = UUID.randomUUID().toString();
    String finalId = id;
    ServerHttpRequest req = exchange.getRequest().mutate()
        .header("X-Correlation-Id", finalId)
        .build();
    exchange.getResponse().getHeaders().add("X-Correlation-Id", finalId);
    return chain.filter(exchange.mutate().request(req).build());
  }
  @Override public int getOrder() { return -1; }
}
FiltrPo co
AddRequestHeader / RemoveRequestHeaderNagłówki wewnętrzne; usuń X-Tenant-Id z internetu
RetryPonów przy 502/503 (ostrożnie z POST)
RequestRateLimiterToken bucket (Redis — spring-boot-starter-data-redis-reactive)
CircuitBreakerResilience4j — fallback URI albo forward
RequestSizeOdrzuć zbyt duży body
RedirectToHTTP 302 — migracje URL
GlobalFilter a bezpieczeństwo nagłówków

Klient nie może ustawiać zaufanych nagłówków (X-Tenant-Id, X-User-Id). Gateway je usuwa na wejściu i ustawia po walidacji JWT — inaczej podmiana tenanta.

4. Bezpieczeństwo

Typowy układ: spring-boot-starter-oauth2-resource-server na gateway + JWT z Cognito/Keycloak. Mikroserwisy za gatewayem ufają nagłówkom wewnętrznym tylko w sieci prywatnej (mTLS / security group) albo weryfikują JWT ponownie.

@Configuration
@EnableWebFluxSecurity
class SecurityConfig {
  @Bean
  SecurityWebFilterChain springSecurity(ServerHttpSecurity http) {
    return http
        .csrf(ServerHttpSecurity.CsrfSpec::disable)
        .authorizeExchange(ex -> ex
            .pathMatchers("/actuator/health").permitAll()
            .pathMatchers("/api/public/**").permitAll()
            .anyExchange().authenticated())
        .oauth2ResourceServer(o -> o.jwt(Customizer.withDefaults()))
        .build();
  }
}

Mapowanie claimów JWT na nagłówek dla downstream:

@Bean
GlobalFilter jwtToHeaders() {
  return (exchange, chain) -> exchange.getPrincipal()
      .cast(JwtAuthenticationToken.class)
      .flatMap(auth -> {
        String sub = auth.getToken().getSubject();
        var req = exchange.getRequest().mutate()
            .header("X-User-Id", sub)
            .build();
        return chain.filter(exchange.mutate().request(req).build());
      })
      .switchIfEmpty(chain.filter(exchange));
}

CORS — konfiguruj na gateway (jeden punkt), nie powielaj na każdym serwisie:

spring.cloud.gateway.globalcors:
  cors-configurations:
    '[/**]':
      allowedOrigins: "https://app.example.com"
      allowedMethods: GET,POST,PUT,DELETE,OPTIONS
      allowedHeaders: "*"
      allowCredentials: true
Walidacja JWT na gateway + brak auth na serwisach w tej samej VPC = każdy kto trafi do portu serwisu omija gateway. Sieć musi blokować ruch z zewnątrz do portów aplikacji.

5. Odporność, timeouty, rate limit

Filtr CircuitBreaker wymaga Resilience4j (jak w tutorialu Resilience4j):

filters:
  - name: CircuitBreaker
    args:
      name: orderServiceCb
      fallbackUri: forward:/fallback/orders

Timeout HTTP do backendu — spring.cloud.gateway.httpclient.connect-timeout i response-timeout (Duration). Bez timeoutu wolny downstream zatyka połączenia Netty.

RequestRateLimiter — klucz per IP, per JWT sub albo per API key:

@Bean
KeyResolver userKeyResolver() {
  return exchange -> exchange.getPrincipal()
      .map(p -> p.getName())
      .defaultIfEmpty(
          exchange.getRequest().getRemoteAddress().getAddress().getHostAddress());
}

Redis jako magazyn tokenów — bez Redis filtr nie wstanie. Dla prostego rate limitu na edge czasem wystarczy AWS WAF / API Gateway usage plan.

6. Service discovery i Kubernetes

uri: lb://order-service — Spring Cloud LoadBalancer wybiera instancję z rejestru (Eureka, Consul) albo z K8s (spring-cloud-starter-kubernetes-client).

ŚrodowiskoPraktyka
KubernetesIngress (nginx/ALB) → SCG Deployment → Service ClusterIP mikroserwisów; albo SCG jako Ingress Controller (rzadziej)
ECS / VMSCG + Eureka/Consul albo statyczna lista URI w config
LokalnieBez discovery — http://localhost:808x per route

Actuator: /actuator/gateway/routes — lista tras (zabezpiecz w prod). spring.cloud.gateway.discovery.locator.enabled=true — auto-trasy z Eureka (/service-id/**) — wygodne na dev, na prod zwykle explicit routes.

Metryki: Micrometer + spring.cloud.gateway.metrics.enabled=true — tagi routeId, status, latency. Trace: propagacja przez Observation / OpenTelemetry — jeden trace przez gateway i downstream.

Typowe błędy

  1. spring-boot-starter-web + Gateway. Dwa konteksty servlet + reactive — konflikt beanów, dziwne 404. Tylko WebFlux.
  2. StripPrefix źle policzony. Backend oczekuje /authors, gateway wysyła /api/authors — 404. Sprawdź /actuator/gateway/routes.
  3. Blokujący kod w filtrze. jdbcTemplate.query na wątku Netty blokuje event loop. Użyj reaktywnego klienta albo subscribeOn(boundedElastic).
  4. Brak timeoutu response. Jedna wisząca instancja backendu trzyma połączenia — wyczerpanie pooli.
  5. Retry na POST z side-effectem. Podwójne zamówienie. Retry tylko na GET/HEAD albo z idempotency key.
  6. Zaufanie nagłówkom z klienta. X-Tenant-Id ustawione w Postmanie — eskalacja uprawnień. Usuń na wejściu, ustaw po JWT.
  7. CORS na każdym serwisie inaczej. Preflight pada na gateway — jedna globalna konfiguracja CORS.
  8. Circuit breaker bez fallback. Open = 503 bez treści; zdefiniuj fallbackUri lub cached response.
  9. Logowanie pełnego body. PII i hasła w logach gateway — filtr ModifyRequestBody tylko gdy trzeba, z redakcją.
  10. SCG jako jedyny load balancer bez health check. Routujesz na martwą instancję — włącz LB health probe albo K8s readiness.
