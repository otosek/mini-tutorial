Część 0 — Fundamenty

Resilience4j 2.x Lekka biblioteka odporności dla Javy — następca Netflix Hystrix. Nie wymaga osobnego wątku ani serwera; wzorce jako małe, komponowalne moduły z funkcjonalnym API (Vavr-style Try opcjonalnie).

Typowy use case: wołanie niestabilnego API, bazy lub zewnętrznego serwisu — ograniczasz kaskadę awarii, dajesz downstreamowi czas na recovery i chronisz własne zasoby (wątki, pamięć, CPU).

Request → RateLimiter → Bulkhead → CircuitBreaker → Retry → TimeLimiter → downstream
                ↑              ↑              ↑           ↑
           limit RPS      izolacja      open = fail-fast  ponów błąd
                          wątków/połączeń

Pułapka: Resilience4j nie zastępuje dobrego timeoutu HTTP klienta (RestClient, WebClient) — to osobna warstwa. Łącz oba.

Część 2 — Circuit Breaker

2.1 Stany

StanZachowanie
CLOSEDNormalne wołania; liczy błędy w sliding window
OPENNatychmiast CallNotPermittedException — bez wołania downstream
HALF_OPENTestowe wołania (np. 3); sukces → CLOSED, błąd → OPEN
DISABLED / FORCED_OPENRęczne wyłączenie lub wymuszenie open (maintenance)

2.2 Konfiguracja (programowo)

CircuitBreakerConfig config = CircuitBreakerConfig.custom()
    .failureRateThreshold(50)              // % błędów → open
    .slowCallRateThreshold(50)             // % wolnych wołań → open
    .slowCallDurationThreshold(Duration.ofSeconds(2))
    .waitDurationInOpenState(Duration.ofSeconds(30))
    .permittedNumberOfCallsInHalfOpenState(3)
    .slidingWindowType(SlidingWindowType.COUNT_BASED)
    .slidingWindowSize(10)
    .minimumNumberOfCalls(5)               // zanim ocenisz failure rate
    .recordExceptions(IOException.class, TimeoutException.class)
    .ignoreExceptions(BusinessException.class)
    .build();

CircuitBreaker cb = CircuitBreaker.of("paymentApi", config);

2.3 Użycie

Supplier<Payment> decorated = CircuitBreaker
    .decorateSupplier(cb, () -> paymentClient.charge(order));

try {
    Payment p = decorated.get();
} catch (CallNotPermittedException e) {
    return fallback(order);  // CB open — nie dzwonisz do API
}
Pułapka: failureRateThreshold liczy się z okna — przy małym slidingWindowSize i niskim ruchu jeden błąd może otworzyć breaker (albo odwrotnie: duże okno = wolna reakcja). Dostosuj minimumNumberOfCalls.

Część 3 — Retry, Bulkhead, Rate/Time Limiter

3.1 Retry

RetryConfig retryConfig = RetryConfig.custom()
    .maxAttempts(3)
    .waitDuration(Duration.ofMillis(500))
    .intervalFunction(IntervalFunction.ofExponentialBackoff(500, 2))
    .retryOnException(e -> e instanceof IOException)
    .retryOnResult(response -> response.getStatus() == 503)
    .build();

Retry retry = Retry.of("paymentApi", retryConfig);

Supplier<Payment> withRetry = Retry.decorateSupplier(retry, decorated);

Retry po circuit breakerze w łańcuchu — inaczej ponawiasz wołania do padającego serwisu zamiast fail-fast.

3.2 Bulkhead

TypMechanizmUwagi
Semaphore (default)Licznik równoległych wołań w tym samym wątkuLekki; OK na virtual threads
Thread poolOsobna pula wątków dla wywołańIzolacja CPU; nie mnoż pul na virtual threads bez potrzeby
 
Bulkhead bulkhead = Bulkhead.of("paymentApi",
    BulkheadConfig.custom().maxConcurrentCalls(25).build());

Supplier<Payment> isolated = Bulkhead.decorateSupplier(bulkhead, withRetry);

3.3 Rate Limiter

RateLimiter limiter = RateLimiter.of("externalApi",
    RateLimiterConfig.custom()
        .limitForPeriod(100)
        .limitRefreshPeriod(Duration.ofSeconds(1))
        .timeoutDuration(Duration.ofMillis(200))  // czekaj max 200 ms na permit
        .build());

3.4 Time Limiter

TimeLimiter timeLimiter = TimeLimiter.of(Duration.ofSeconds(3));

Callable<Payment> futureCall = TimeLimiter.decorateFutureSupplier(
    timeLimiter, () -> CompletableFuture.supplyAsync(() -> client.charge(order)));

Na blokującym kodzie z virtual threads często wystarczy timeout w kliencie HTTP; TimeLimiter ma sens przy CompletableFuture / async.

Część 4 — Spring Boot

4.1 Adnotacje (AOP)

@Service
public class PaymentService {

    @CircuitBreaker(name = "paymentApi", fallbackMethod = "chargeFallback")
    @Retry(name = "paymentApi")
    @Bulkhead(name = "paymentApi")
  public Payment charge(Order order) {
        return client.charge(order);
    }

    private Payment chargeFallback(Order order, Exception ex) {
        return Payment.pending(order.getId());
    }
}

application.yml:

resilience4j.circuitbreaker:
  instances:
    paymentApi:
      slidingWindowSize: 20
      failureRateThreshold: 50
      waitDurationInOpenState: 30s
      registerHealthIndicator: true

resilience4j.retry:
  instances:
    paymentApi:
      maxAttempts: 3
      waitDuration: 500ms
      enableExponentialBackoff: true
      exponentialBackoffMultiplier: 2

resilience4j.bulkhead:
  instances:
    paymentApi:
      maxConcurrentCalls: 25

Część 5 — Dekoratory i kolejność

Pełny łańcuch jednym wywołaniem:

Supplier<Payment> supplier = () -> client.charge(order);

supplier = RateLimiter.decorateSupplier(rateLimiter, supplier);
supplier = Bulkhead.decorateSupplier(bulkhead, supplier);
supplier = CircuitBreaker.decorateSupplier(circuitBreaker, supplier);
supplier = Retry.decorateSupplier(retry, supplier);

Payment result = supplier.get();

Albo Decorators.ofSupplier(supplier):

Supplier<Payment> decorated = Decorators.ofSupplier(() -> client.charge(order))
    .withRateLimiter(rateLimiter)
    .withBulkhead(bulkhead)
    .withCircuitBreaker(circuitBreaker)
    .withRetry(retry)
    .decorate();
Kolejność (zewnętrzny → wewnętrzny)Dlaczego
RateLimiter → Bulkhead → CircuitBreaker → RetryNajpierw limit RPS i wątków; CB fail-fast przed retry; retry tylko gdy CB closed
Retry wewnątrz CBBłędy z retry liczą się do failure rate — CB widzi realny stan downstream
Pułapka: Retry na zewnątrz circuit breakera — każda próba to osobne wołanie przy OPEN; dostajesz lawinę wyjątków zamiast jednego fail-fast.

Część 6 — Metryki i observability

Resilience4j integruje się z Micrometer — tagi name instancji, stan CB, liczniki wywołań, failure rate, slow calls.

// programowo — rejestracja eventów
cb.getEventPublisher()
    .onStateTransition(e -> log.warn("CB {}: {} -> {}",
        e.getCircuitBreakerName(),
        e.getStateTransition().getFromState(),
        e.getStateTransition().getToState()));
Metryka (przykład)Znaczenie
resilience4j.circuitbreaker.callskind: successful, failed, not_permitted
resilience4j.circuitbreaker.state0=closed, 1=open, 2=half_open, …
resilience4j.retry.callsretry_without_success, retry_with_success
resilience4j.bulkhead.available_concurrent_callsIle slotów zostało

Alertuj na: długi stan OPEN, wysoki not_permitted, bulkhead rejections, retry storms. Dashboard per instancja (paymentApi, inventoryApi).

Kiedy Resilience4j

Pełny zestaw wzorców, metryki Micrometer, dojrzały ekosystem — typowy wybór w microservices na Spring Boot 3.

Kiedy Spring 7 retry

Proste ponawianie metod bez CB/bulkhead — mniej zależności; nie zastępuje circuit breakera przy kaskadach awarii.

Kiedy service mesh (Istio, Linkerd)

Retry/timeout na poziomie sidecar — polityki per deployment; R4j nadal sensowny w aplikacji na logikę biznesową (fallback, które błędy retryować).

Typowe błędy

  1. Brak fallbacku przy OPEN — użytkownik dostaje 500 zamiast degradacji (cache, domyślna odpowiedź, kolejka).
  2. Retry na zewnątrz circuit breakera — lawina wołań do padającego serwisu; zła kolejność dekoratorów.
  3. Retry na błędy nienaprawialne — 400, 404, BusinessException — marnujesz czas i obciążasz downstream (ignoreExceptions).
  4. Jeden globalny CB na całą aplikację — awaria jednego endpointu otwiera breaker dla wszystkich; osobna instancja per downstream / operacja.
  5. Zbyt agresywny failure rate — minimumNumberOfCalls=1 + małe okno = flaky breaker przy sporadycznym ruchu.
  6. Bulkhead thread pool × virtual threads — niepotrzebna pula platform threads; preferuj semaphore bulkhead na Loom.
  7. Brak timeoutu HTTP — TimeLimiter/CB nie zastąpią connectTimeout/readTimeout w kliencie.
  8. Fallback wywołuje ten sam downstream — fallback musi być tańszy (cache, statyczna odpowiedź, inny serwis).
  9. Ignorowanie metryk not_permitted — użytkownicy widzą błędy, a Ty nie wiesz, że CB jest open od godziny.
  10. Testy bez symulacji open — unit testy z CircuitBreakerRegistry + wymuszenie stanu (transitionToOpenState()) sprawdzają fallback.
