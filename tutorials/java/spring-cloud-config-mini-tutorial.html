Część 0 — Fundamenty

Spring Cloud Config to serwer centralizujący konfigurację aplikacji (properties/YAML) poza JAR-em. Aplikacje (klienci) przy starcie i na żądanie pobierają ustawienia z serwera — jedna zmiana w repo Git propaguje się na wiele instancji bez przebudowy obrazu.

Git repo (config/) order-service.yml order-service-prod.yml application.yml │ ▼ Config Server (:8888) │ ├─ GET /order-service/default ├─ GET /order-service/prod └─ POST /actuator/bus-refresh (opcjonalnie) │ ▼ order-service, author-service, …

Konwencja nazw plików: {application}-{profile}.yml. application.yml — wspólne dla wszystkich. Profil prod + aplikacja order-service → merge application.yml + application-prod.yml + order-service.yml + order-service-prod.yml (późniejsze nadpisują wcześniejsze).

Server vs Client

Config Server — osobna aplikacja Spring Boot (@EnableConfigServer). Config Client — każda mikroaplikacja z spring-cloud-starter-config + spring.config.import=optional:configserver: (Boot 2.4+).

1. Kiedy używać / kiedy nie

Bierz Config ServerOlej Config Server
Wiele serwisów Spring, wspólne i per-serwis properties w Git K8s + ConfigMap/Secret per Deployment — wystarczy mount/env
Audyt zmian configu przez historię Git AWS — Parameter Store / Secrets Manager + spring.config.import (patrz Spring Cloud AWS)
Refresh bez restartu (/actuator/refresh, Spring Cloud Bus) 12-factor: config tylko ze zmiennych środowiskowych — bez dodatkowego serwera
HashiCorp Vault jako backend zamiast Git Jeden monolit, jeden plik application.yml w repo
Config Server to kolejny komponent SPOF i do zabezpieczenia. Na K8s często prościej: Helm values + Sealed Secrets zamiast osobnego serwera configu.

2. Config Server

Starter: spring-cloud-config-server. Minimum:

@SpringBootApplication
@EnableConfigServer
public class ConfigServerApplication {
  public static void main(String[] args) {
    SpringApplication.run(ConfigServerApplication.class, args);
  }
}
spring:
  application:
    name: config-server
  cloud:
    config:
      server:
        git:
          uri: https://github.com/org/config-repo
          default-label: main
          search-paths: '{application}'
          clone-on-start: true
server:
  port: 8888

Endpointy REST (uproszczone):

URLZwraca
/{name}/{profile}JSON z property sources
/{name}/{profile}/{label}Konkretna gałąź/tag Git
/{name}-{profile}.ymlYAML plain text

name = spring.application.name klienta. profile = spring.profiles.active (np. prod).

Inne backendy

BackendUżycie
Git (GitHub, GitLab, Bitbucket)Domyślny — wersjonowanie, PR na zmiany configu
VaultSekrety dynamiczne, rotacja — spring.cloud.config.server.vault
JDBCLegacy — tabela PROPERTIES; rzadko w nowych systemach
CompositeGit + Vault — nie-sekrety w Git, hasła w Vault

Bezpieczeństwo serwera: Spring Security + HTTP Basic / OAuth2. Klienci muszą się uwierzytelnić. W prod nie wystawiaj :8888 na internet bez TLS i auth.

3. Config Client

Starter: spring-cloud-starter-config. Boot 2.4+ — Config Data API:

spring:
  application:
    name: order-service
  profiles:
    active: prod
  config:
    import: "optional:configserver:https://config.example.com:8888"
  cloud:
    config:
      username: ${CONFIG_USER}
      password: ${CONFIG_PASS}
      fail-fast: true   # nie startuj bez config servera (prod)

Kolejność ładowania (uproszczone): application.yml w JAR → import config server → zmienne środowiskowe (najwyższy priorytet w Boot).

optional: — przy local dev bez serwera aplikacja wstaje na lokalnym YAML. Na prod usuń optional: albo użyj profilu — inaczej cicho jedziesz na starym configu z JAR.

Bootstrap (stary model, Boot < 2.4): osobny bootstrap.yml + spring-cloud-starter-bootstrap. W nowych projektach — tylko spring.config.import.

4. Refresh, Bus i szyfrowanie

@RefreshScope

Bean przeładowywany po refresh bez restartu JVM:

@RefreshScope
@ConfigurationProperties(prefix = "feature")
public class FeatureFlags {
  private boolean newCheckout;
  // getter/setter
}

Wywołanie: POST /actuator/refresh (włącz endpoint) — przeładowuje tylko @RefreshScope beany. Reszta aplikacji (connection pool, cache) — bez zmian.

Spring Cloud Bus

Kafka/RabbitMQ — jeden /actuator/busrefresh na jednej instancji propaguje refresh na wszystkie mikroserwisy. Wymaga spring-cloud-starter-bus-amqp lub kafka. Szczegóły: tutorial Bus.

Szyfrowanie wartości w Git

spring:
  datasource:
    password: '{cipher}AQA...'

Config Server z encrypt.key (symetryczny) lub Vault — deszyfruje przy serwowaniu klientowi. Klucz szyfrowania nigdy w tym samym repo co ciphertext. W 2025+ częściej: sekrety w Vault/Secrets Manager, Git tylko na nie-wrażliwe flagi.

5. Alternatywy — kiedy co wybrać

RozwiązaniePlusyMinusy
Spring Cloud Config + GitZNany stack Spring, audyt GitOsobny serwer, refresh wymaga Actuator/Bus
K8s ConfigMap + SecretNatywne, bez extra serwisuBrak centralnego repo dla wszystkich serwisów; rotacja ręczna
AWS Parameter Store / Secrets ManagerManaged, IAM, bez serweraVendor lock-in AWS; import przy starcie
Helm + GitOps (Argo CD)Config jako manifesty K8sZmiana = deploy, nie live refresh
Env vars / 12-factorProstota, przenośnośćDużo zmiennych przy wielu serwisach

Hybryda korporacyjna: nie-sekrety w Config Server (Git), hasła w Vault; albo Config Server z composite Git+Vault.

Typowe błędy

  1. Hasła w plain text w Git. Repo configu wyciekło = prod skompromitowany. Cipher lub Vault/Secrets Manager.
  2. optional:configserver: na prod. Serwer padł — aplikacja startuje na domyślnym JAR bez alarmu.
  3. Zła nazwa pliku. orderservice.yml zamiast order-service.yml — klient nie dostaje właściwego pliku.
  4. Refresh bez @RefreshScope. /actuator/refresh nic nie zmienia w już utworzonych beanach.
  5. Refresh connection pool / URL DB. @RefreshScope na DataSource — zamknięcie starych połączeń w trakcie ruchu. Często wymaga restartu rolling.
  6. Config Server bez HA. Jedna instancja — awaria blokuje start wszystkich klientów z fail-fast: true.
  7. Brak auth na Config Server. Każdy w sieci czyta prod secrets z /order-service/prod.
  8. Mieszanie bootstrap + import. Dwa mechanizmy — nieprzewidywalna kolejność property sources.
  9. Git search-paths źle ustawione. Puste odpowiedzi — pliki w podkatalogu, serwer szuka w root.
  10. Config Server „bo Spring Cloud” na K8s. Podwójna warstwa (ConfigMap + Config Server) bez korzyści — YAGNI.
