Część 0 — Fundamenty

Service discovery — mechanizm, dzięki któremu klient (Feign, Gateway, RestClient) wie, gdzie są instancje serwisu order-service bez hardcodowanego IP. Rejestr przechowuje listę host:port + metadane; klient pyta rejestr i wybiera instancję przez load balancer.

order-service (3 repliki) → rejestracja → Eureka / Consul / K8s API ↑ author-service (Feign) → LoadBalancer → wybór instancji order-service

Spring Cloud LoadBalancer (SC LB) zastąpił Netflix Ribbon (usunięty). Działa z dowolnym DiscoveryClient — Eureka, Consul, Kubernetes. URI lb://order-service w Gateway/Feign/RestClient aktywuje SC LB.

Discovery vs DNS

W K8s często wystarczy DNS (order-service.default.svc.cluster.local) + Service — kube-proxy/load balancer routuje. Osobny Eureka na K8s to zwykle zbędna warstwa. Discovery Spring ma sens na VM/ECS bez natywnego rejestru albo gdy chcesz ten sam model lokalnie i na prod.

2. Spring Cloud LoadBalancer

Starter: spring-cloud-starter-loadbalancer (często tranzytywnie z OpenFeign/Gateway). Bez discovery — statyczne instancje:

spring:
  cloud:
    discovery:
      client:
        simple:
          instances:
            order-service:
              - uri: http://localhost:8081
              - uri: http://localhost:8082

Programowe wywołanie:

@Autowired LoadBalancerClient lb;

URI uri = lb.choose("order-service").getUri();
// np. http://192.168.1.10:8081

Algorytm domyślny: RoundRobinLoadBalancer. Własny:

@Bean
ReactorLoadBalancer<ServiceInstance> customLb(
    Environment env, LoadBalancerClientFactory factory) {
  String name = env.getProperty(LoadBalancerClientFactory.PROPERTY_NAME);
  return new RoundRobinLoadBalancer(
      factory.getLazyProvider(name, ServiceInstanceListSupplier.class), name);
}
IntegracjaSkładnia
OpenFeign@FeignClient(name = "order-service") — bez url
Gatewayuri: lb://order-service
RestClient / @LoadBalanced@LoadBalanced RestClient.Builder → http://order-service/api
WebClient@LoadBalanced WebClient.Builder
 
@Bean
@LoadBalanced
RestClient.Builder restClientBuilder() {
  return RestClient.builder();
}

// GET http://order-service/orders/1  → LB wybiera instancję

Sticky sessions: domyślnie brak — każde żądanie może trafić na inną replikę. Sesja HTTP wymaga sticky LB (Ingress annotation) albo stateless JWT.

3. Netflix Eureka

Serwer Eureka — rejestr instancji. Klient na każdej aplikacji — rejestracja przy starcie, heartbeat co ~30 s, wyrejestrowanie przy shutdown.

# eureka-server
spring:
  application.name: eureka-server
eureka:
  client:
    register-with-eureka: false
    fetch-registry: false
server.port: 8761

# order-service (klient)
eureka:
  client:
    service-url:
      defaultZone: http://localhost:8761/eureka/
  instance:
    prefer-ip-address: true

Starter serwera: spring-cloud-starter-netflix-eureka-server. Klienta: spring-cloud-starter-netflix-eureka-client + @EnableDiscoveryClient (opcjonalne w nowszych wersjach — auto-config).

PojęcieZnaczenie
register-with-eurekaTa aplikacja rejestruje siebie
fetch-registryPobiera listę innych serwisów (potrzebne Feign/Gateway)
lease-renewal-intervalHeartbeat — za długi = opóźnione wykrycie padu
self-preservationSerwer nie usuwa instancji przy masowej utracie heartbeatów (split-brain protection)

HA Eureka: minimum 2 węzły serwera, defaultZone wskazuje oba. Pojedynczy Eureka Server to SPOF.

Status w 2025+: Netflix Eureka w maintenance mode, ale nadal używany w brownfield. Nowe greenfield na K8s — raczej bez Eureka.

4. HashiCorp Consul

Discovery + health checks + KV (config light). Starter: spring-cloud-starter-consul-discovery.

spring:
  cloud:
    consul:
      host: localhost
      port: 8500
      discovery:
        service-name: ${spring.application.name}
        health-check-path: /actuator/health
        health-check-interval: 10s
        prefer-ip-address: true

Consul odpytuje /actuator/health — instancja unhealthy znika z routingu szybciej niż przy samym braku heartbeatu Eureka (zależy od konfiguracji).

Multi-DC: Consul ma first-class wsparcie centrów danych — Eureka wymaga osobnej architektury peerów per region.

5. Kubernetes discovery

Starter: spring-cloud-starter-kubernetes-client (Fabric8 client) lub kubernetes-fabric8-discovery. Discovery czyta Endpoints/Service z API K8s.

spring:
  cloud:
    kubernetes:
      discovery:
        all-namespaces: false
      reload:
        enabled: true
        mode: event   # odśwież listę instancji przy zmianie Endpoints

spring.application.name powinno odpowiadać nazwie Kubernetes Service (np. order-service). Feign/Gateway z lb://order-service → Endpoints tego Service.

PodejścieOpis
DNS K8shttp://order-service bez SC — najprostsze w pure K8s
SC K8s discoveryTen sam kod co z Eureka (lb://), lista instancji z API
Ingress onlyRuch zewnętrzny przez Ingress; wewnątrz mesh DNS

Spring Cloud Kubernetes Config — ConfigMap/Secret jako property source (alternatywa dla Config Server — patrz tutorial Config).

6. Health, graceful shutdown, metadane

Actuator /actuator/health — Eureka/Consul oznaczają instancję DOWN gdy health nie przechodzi. Włącz probe w K8s:

livenessProbe:
  httpGet: { path: /actuator/health/liveness, port: 8080 }
readinessProbe:
  httpGet: { path: /actuator/health/readiness, port: 8080 }

Graceful shutdown: server.shutdown=graceful + spring.lifecycle.timeout-per-shutdown-phase — dokończ żądania przed wyrejestrowaniem. Bez tego LB wysyła ruch na padającą instancję.

Metadane instancji (Eureka/Consul) — wersja, strefa, canary:

eureka:
  instance:
    metadata-map:
      version: "2.1"
      zone: "eu-central-1a"

LoadBalancer może filtrować po metadanych (własny ServiceInstanceListSupplier) — np. tylko version=2.1 dla canary.

Typowe błędy

  1. lb:// bez startera LoadBalancer ani discovery. „No instances available for order-service” — dodaj klienta discovery lub simple instances.
  2. Eureka na K8s „dla zasady”. Dodatkowy stateful set, split brain, podwójna prawda o instancjach — użyj Service K8s.
  3. spring.application.name ≠ nazwa w Feign/Gateway. orders vs order-service — brak match w rejestrze.
  4. Rejestracja przed readiness. Ruch trafia na instancję, która jeszcze nie wstaje — opóźnij rejestrację (eureka.client.initial-instance-info-replication-interval-seconds) albo readiness probe.
  5. Jeden Eureka Server na prod. Awaria = brak discovery dla całego klastra.
  6. prefer-hostname w Docker/K8s bez DNS. Klient nie resolvuje hostname kontenera — prefer-ip-address: true.
  7. Self-preservation Eureka w incydencie. Serwer trzyma martwe instancje — wyłącz świadomie albo napraw sieć między klientem a serwerem.
  8. Session affinity bez sticky. Round-robin + sesja w pamięci = losowe wylogowania.
  9. Consul health check na złym porcie/path. Instancja zawsze unhealthy — 0 instancji w LB.
  10. Discovery w testach bez mocka. IT wymaga Eureka/Consul — użyj simple.instances albo Testcontainers Consul.
