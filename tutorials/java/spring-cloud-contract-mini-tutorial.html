Część 0 — Fundamenty

Test kontraktowy sprawdza, że dwa serwisy zgadzają się co do kształtu komunikacji (HTTP albo messaging) — bez stawiania całego środowiska. Spring Cloud Contract (SCC): jeden plik kontraktu (YAML / Groovy DSL) daje testy po stronie producenta i stuby WireMock po stronie konsumenta.

To nie jest OpenAPI (dokumentacja/schemat API) ani E2E (prawdziwa sieć, auth, infra). Schemat mówi „jakie pola mogą być”; kontrakt mówi „przy tym requeście dostaniesz ten status, te nagłówki i taki body”.

CDC (consumer-driven contracts)

Konsument opisuje, czego potrzebuje. Producent musi to spełnić — inaczej CI pada. W SCC kontrakty często leżą w repo producenta (łatwiejszy verifier): to hybryda, nie czysty CDC.

Część 1 — Jak działa

kontrakt YAML/Groovy (zwykle src/test/resources/contracts/) │ ├─ producer CI: Contract Verifier │ testy vs prawdziwy controller (MockMvc / WebTestClient) │ PASS → publikacja *-stubs.jar (Nexus / Artifactory) │ └─ consumer CI: Stub Runner WireMock ze stubów, bez żywego producenta

Producer: plugin (spring-cloud-contract-maven-plugin / Gradle) + spring-cloud-starter-contract-verifier. Generuje testy RestAssured z kontraktu. Klasa bazowa (baseClassForTests) ma @SpringBootTest i setup — bez niej verifier nie wie, jak odpalić aplikację.

Consumer: spring-cloud-starter-contract-stub-runner + @AutoConfigureStubRunner(ids = "g:a:+:stubs:port"). stubsMode: REMOTE (repo), LOCAL (m2), CLASSPATH (JAR na teście).

Konwencja CDC: katalogi per konsument — contracts/order-service/shouldReturnAuthor.yaml. Jeden producer, wielu konsumentów, różne oczekiwania.

Messaging

Ten sam mechanizm dla Kafka / Spring Cloud Stream: kontrakt opisuje wiadomość zamiast HTTP. Stub Runner podaje wiadomość na kanał; verifier sprawdza, że producer ją emituje. Nie myl z Testcontainers na prawdziwym brokerze.

Zależności — Maven i Gradle

Producer (author-service)

<!-- pom.xml — wersja z BOM Spring Cloud -->
<dependency>
  <groupId>org.springframework.cloud</groupId>
  <artifactId>spring-cloud-starter-contract-verifier</artifactId>
  <scope>test</scope>
</dependency>

<plugin>
  <groupId>org.springframework.cloud</groupId>
  <artifactId>spring-cloud-contract-maven-plugin</artifactId>
  <extensions>true</extensions>
  <configuration>
    <baseClassForTests>com.acme.author.contract.BaseContractTest</baseClassForTests>
  </configuration>
  <executions>
    <execution>
      <goals><goal>generateTests</goal></goals>
    </execution>
  </executions>
</plugin>
// Gradle (Kotlin DSL) — producer
plugins { id("org.springframework.cloud.contract") version "4.2.0" }
dependencies {
  testImplementation("org.springframework.cloud:spring-cloud-starter-contract-verifier")
}
contracts {
  testFramework.set(org.springframework.cloud.contract.verifier.config.TestFramework.JUNIT5)
  baseClassForTests.set("com.acme.author.contract.BaseContractTest")
}

Groovy DSL — ten sam kontrakt, więcej kontroli

// contracts/checkout-bff/shouldReturnAuthorWhenExists.groovy
import org.springframework.cloud.contract.spec.Contract

Contract.make {
  name 'shouldReturnAuthorWhenExists'
  request {
    method GET()
    url '/authors/1'
    headers { accept(applicationJson()) }
  }
  response {
    status OK()
    headers { contentType(applicationJson()) }
    body(
      id: fromRequest().path(2),
      name: 'Lem'
    )
    bodyMatchers {
      jsonPath('$.id', byRegex('[0-9]+'))
      jsonPath('$.name', byEquality())
    }
  }
}

Dynamiczne wartości — consumer vs producer

id: $(consumer(regex('[0-9]+')), producer(1))
name: $(consumer('Lem'), producer(regex(nonBlank())))
createdAt: $(consumer('2024-01-01T00:00:00Z'), producer(iso8601WithOffset()))

Echo z URL: fromRequest().path(2) dla /authors/{id} — stub zwraca id z requestu, verifier nie wymusza stałej 1.

Producer — verifier i klasa bazowa

Plugin generuje klasy typu ContractVerifierTest (RestAssured). Ty dostarczasz klasę bazową — kontekst Spring i dane testowe.

@SpringBootTest(webEnvironment = WebEnvironment.RANDOM_PORT)
public abstract class BaseContractTest {

  @Autowired protected AuthorRepository repository;

  @BeforeEach
  void seed() {
    repository.deleteAll();
    repository.save(new Author(1L, "Lem"));
  }
}

Wariant lżejszy — tylko warstwa web (szybsze testy kontraktu):

@ExtendWith(SpringExtension.class)
@WebMvcTest(AuthorController.class)
public abstract class BaseContractTest {

  @Autowired MockMvc mockMvc;
  @MockBean AuthorService authorService;

  @BeforeEach
  void stubService() {
    when(authorService.find(1L)).thenReturn(new AuthorDto(1L, "Lem"));
  }

Wygenerowany test (uproszczony — nie edytuj ręcznie):

// target/generated-test-sources/.../shouldReturnAuthorWhenExistsTest.java
@Test
void validate_shouldReturnAuthorWhenExists() {
  given()
      .header("Accept", "application/json")
    .when()
      .get("/authors/1")
    .then()
      .statusCode(200)
      .body("id", equalTo(1))
      .body("name", equalTo("Lem"));
}

Publikacja stubów (Maven): plugin w fazie verify buduje author-service-1.0.0-stubs.jar i wypycha do Nexus/Artifactory razem z artefaktem aplikacji.

Consumer — Stub Runner

Testujesz własnego klienta HTTP (RestTemplate, WebClient, Feign), nie mapowania WireMock ręcznie.

@SpringBootTest
@AutoConfigureStubRunner(
    ids = "com.acme:author-service:1.0.0:stubs:8081",
    stubsMode = StubRunnerProperties.StubsMode.REMOTE,
    repositoryUrl = "https://nexus.acme/repository/maven-releases")
class AuthorClientContractIT {

  @Autowired AuthorClient client;

  @Test void fetchesAuthor() {
    Author a = client.getById(1L);
    assertThat(a.name()).isEqualTo("Lem");
  }

  @Test void missingAuthor() {
    assertThatThrownBy(() -> client.getById(404L))
        .isInstanceOf(AuthorNotFoundException.class);
  }
}

WebClient z adresem stubu (gdy nie używasz discovery):

@TestConfiguration
static class StubTarget {
  @Bean
  @Primary
  WebClient authorWebClient(@Value("${stubrunner.runningstubs.author-service.port}") int port) {
    return WebClient.builder()
        .baseUrl("http://localhost:" + port)
        .build();
  }
}

Feign: ustaw url na port ze Stub Runner albo użyj @AutoConfigureStubRunner z stubsPerConsumer() gdy wiele producerów.

Messaging (Kafka / Spring Cloud Stream)

// contracts/order-service/shouldEmitOrderCreated.groovy
Contract.make {
  label 'order_created'
  input {
    triggeredBy('placeOrder()')
  }
  outputMessage {
    sentTo('orderCreated-out-0')
    body([
      orderId: $(consumer(anyUuid()), producer('11111111-1111-1111-1111-111111111111')),
      amount: 99.00
    ])
    headers {
      header('contentType', applicationJson())
    }
  }
}

Producer — klasa bazowa z triggerem:

public abstract class MessagingContractBase {
  @Autowired OrderService orderService;

  public void placeOrder() {
    orderService.place(new PlaceOrderCommand("SKU-1", 1));
  }
}

Consumer — Stub Runner wstrzykuje wiadomość; testujesz listener:

@SpringBootTest
@AutoConfigureStubRunner(ids = "com.acme:order-service:1.0.0:stubs:0")
class OrderCreatedListenerIT {
  @Autowired TestOrderSink sink;

  @Test void handlesEvent() {
    await().atMost(5, SECONDS).untilAsserted(() ->
        assertThat(sink.received()).extracting(OrderEvent::amount).contains(99.00));
  }
}

Kiedy stosować / kiedy nie

Scenariusze „tak”: order-service woła author-service po REST; checkout startuje przed gotowym API autorów — piszesz kontrakt GET /authors/{id}, instalujesz stuby; zmiana pola w JSON bez wersji API łamie CI u producenta zanim wdrożysz. Scenariusze „nie”: jeden moduł w monolicie — wystarczy test integracyjny; publiczne API dla setek partnerów — OpenAPI + polityka wersji, SCC tylko dla wybranych integracji wewnętrznych.

StosujNie stosuj
Mikroserwisy, niezależny deploy, różne zespoły Monolit / jeden zespół / zawsze ten sam pipeline
Konsument startuje, zanim producer jest gotowy (stuby) Publiczne API dla nieznanych klientów → OpenAPI + wersje
Łapanie breaking change w CI taniej niż E2E na env Test logiki biznesowej producenta (to unit / IT)
Kontrakt HTTP i messaging między bounded contextami UI, OAuth redirect, timeouty, retry, mTLS, prawdziwy SSL
Stabilny, wąski kontrakt (kilka endpointów, które ktoś realnie woła) „Pokryj całe API kontraktami” zamiast dokumentacji

Pułapka: SCC nie dowodzi, że serwisy ze sobą gadają na produkcji. Dowodzi, że producer spełnia kontrakt, a konsument umie czytać stub z tego kontraktu. Sieć, auth, schemat DB, kolejki — osobne testy.

Typowe błędy

  1. Kontrakt = kopia DTO — asercja wszystkich pól wewnętrznych; łamie się przy każdej refaktoryzacji. Kontraktuj to, co konsument czyta.
  2. Tylko happy path — brak 400/404/409. Konsument obsłuży błąd „na oko”, stub milczy.
  3. Stuby niepublikowane / zła wersja — consumer na 1.2.0-stubs, producer już zdeployował 1.3.0. CI zielone, prod czerwone.
  4. Za luźny regex — byRegex('.*') na body: verifier zawsze przechodzi, stub przyjmuje śmieci.
  5. Za sztywny JSON — dokładne porównanie całego body z UUID/timestampem. Użyj matchers + pary consumer/producer.
  6. Kontrakty tylko u konsumenta — producer nigdy ich nie weryfikuje. To dokumentacja, nie test.
  7. SCC zamiast E2E — nie łapie timeoutów, retry, kolejności wiadomości, uprawnień, DNS.
  8. Nagłówki poza kontraktem — Content-Type, correlation-id, Idempotency-Key. Stub nie wymaga, produkcja odrzuca.
  9. Nakładające się stuby bez priority — WireMock bierze pierwszy match; testy flakują.
  10. Verifier bez klasy bazowej / bez stubów serwisów — generowany test pada na NPE w serwisie, nie na kontrakcie.

Ciekawostki — krótkie odpowiedzi

Junior / Mid

1. Czym test kontraktowy różni się od E2E?

Kontrakt sprawdza zgodność interfejsu na stubach/generowanych testach, bez żywego drugiego serwisu. E2E stawia prawdziwe instancje i sieć.

2. Co z jednego kontraktu dostaje producer, a co consumer?

Producer: wygenerowane testy (verifier) przeciwko prawdziwej aplikacji. Consumer: stuby WireMock (Stub Runner) do testów klienta.

3. Gdzie trzymać kontrakty?

Najczęściej repo producenta (src/test/resources/contracts/), ewentualnie osobne repo kontraktów. Muszą być wejściem do CI producenta.

4. SCC vs OpenAPI?

OpenAPI opisuje API (dokumentacja, codegen). SCC weryfikuje zachowanie i publikuje stuby. Można je łączyć; samo YAML OpenAPI nie odpala testów producenta.

5. Po co *-stubs.jar?

Artefakt ze mappingami WireMock. Consumer ściąga go z repozytorium zamiast odpalać producenta.

Pułapki

6. Kontrakty w repo producenta — to jeszcze CDC?

Czysty CDC: konsument proponuje kontrakt. Lokalizacja w producerze to wygoda narzędzia. Jeśli zespół producenta pisze kontrakty „pod siebie”, to producer-driven — CDC tylko z nazwy.

7. Zielony kontrakt = można deployować niezależnie?

Nie. Masz zgodność kształtu wiadomości. Brakuje auth, schematu DB, kompatybilności wstecznej wielu wersji naraz, SLO. Deploy nadal wymaga wersjonowania i monitoringu.

8. Dlaczego para consumer() / producer()?

Stub musi zwrócić konkret (konsument). Verifier musi asercjować wzorzec albo wynik metody (producer, np. UUID z DB). Jedna wartość psuje jedną ze stron.

9. SCC vs Pact?

Pact jest wielojęzykowy: consumer nagrywa interaction, producer weryfikuje pact file. SCC jest JVM/Spring: kontrakt zwykle u producenta, stuby jako JAR. SCC umie importować Pact; to nie to samo narzędzie.

10. Czy SCC testuje Kafkę „naprawdę”?

Nie. Testuje kontrakt wiadomości (payload, destynacja, trigger). Broker, offsety, poison pill, idempotentny consumer — Testcontainers / IT.

11. Consumer na stubach + (latest), producer jeszcze nie opublikował — co się dzieje?

Stub Runner nie znajdzie artefaktu albo weźmie starą wersję z m2. „Latest” bez gated publikacji stubów to fałszywe bezpieczeństwo; pinuj wersję albo publikuj stuby w tym samym buildzie co producenta.

12. Verifier przechodzi, a na prodzie 415 / 401. Dlaczego?

Kontrakt nie obejmował Content-Type albo trailing slash. Verifier często stoi na MockMvc / standaloneSetup bez filtrów Spring Security i bez API gateway — 401/415 na prodzie w teście nie istnieją. Kontrakt ≠ pełny request na bramce.
