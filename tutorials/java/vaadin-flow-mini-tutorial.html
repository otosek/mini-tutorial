0. Co to jest Vaadin Flow

Vaadin Flow to framework do budowy aplikacji webowych w czystej Javie. Widoki, komponenty i logika UI żyją na serwerze; przeglądarka dostaje HTML/CSS i komunikuje się z serwerem przez WebSocket / HTTP — bez ręcznego REST-u i bez osobnego projektu React/Angular.

Jedno zdanie: piszesz UI jak Swing/Wicket, a użytkownik dostaje nowoczesną SPA w przeglądarce. Zespół Java może prowadzić feature od bazy do ekranu w jednym języku i jednym IDE.

Stack typowy: Spring Boot (DI, Security, Data) + Vaadin Flow (UI) + JPA/Hibernate + PostgreSQL.
Licencja: open source (Apache 2) + komponenty/wsparcie komercyjne Vaadin (LTS do 15 lat na major).

1. Model działania — server-driven UI

Przeglądarka                    Serwer (JVM)
┌──────────────┐               ┌─────────────────────────┐
│ HTML + CSS   │◄── diff UI ───│ Drzewo komponentów      │
│ (client eng) │               │ (Button, Grid, Form…)   │
│              │── event ─────►│ Listenery w Javie       │
│              │               │ Session = stan UI       │
└──────────────┘               │ + Application Services  │
                               └─────────────────────────┘
  • Stan UI siedzi w sesji HTTP na serwerze — każde kliknięcie to event → Java → aktualizacja drzewa → patch do przeglądarki.
  • Brak osobnego API tylko na potrzeby ekranu — serwisy wołasz bezpośrednio z widoku (przez warstwę application service).
  • Routing deklaratywny: @Route("orders"), layouty @Layout / RouterLayout.
  • Komponenty Vaadin (Grid, FormLayout, ComboBox, Dialog…) + własne lit-based / React embedded gdy trzeba.
Konsekwencja modelu: serwer jest stateful względem UI. Każda otwarta karta przeglądarki trzyma drzewo komponentów w pamięci JVM. To nie jest „stateless REST za CDN” — skalowanie wygląda inaczej niż przy React + API.

Zespół głównie JavaZero drugiej technologii UI; review i hiring w jednym stacku

3. Kiedy nie zalecane

SytuacjaDlaczego Flow boli
Publiczny marketing / SEOContent musi być w HTML dla crawlerów; Flow to SPA server-driven — słabe pod SEO. Osobna strona (SSR/SSG) albo Hilla/React
Bardzo wysoki ruch anonimowySesja UI na usera × tysiące równoległych = pamięć i sticky sessions
Offline-first / PWA z bogatą logiką offlineModel wymaga serwera; offline to nie natywna siła Flow
Zespół frontend (React/Vue) silniejszy niż Java UIBędą walczyć z idiomami; lepszy Hilla albo React + API
Mikroserwisy z wieloma klientami UIFlow wiąże UI z jedną appką JVM; mobile/partnerzy i tak potrzebują API
Pixel-perfect, mocno animowany UX konsumenckiDa się, ale koszt customizacji i round-tripów jest wyższy niż w czystym kliencie
Ekstremalnie niskie latency UI (gry, edytory real-time)Każda interakcja może iść na serwer — nie ten tool
Wymóg „zero stanu na serwerze” (FaaS pure)Sesja UI nie pasuje do bezstanowych Lambd bez ciężkiej gimnastyki
Pułapka: wybór Flow „bo Java”, gdy produkt to sklep publiczny z SEO i 100k anonimowych sesji dziennie. Da się to postawić — ale płacisz sesjami, sticky LB i limitem skalowania, którego React+CDN nie ma.

4. Architektura — jak budować

ui/          @Route, layouts, komponenty — TYLKO prezentacja
application/ Application Services — transakcje, security, use-case
domain/      encje, reguły (opcjonalnie bogaty model)
infra/       JPA, REST out, kolejki

Widok ──► ApplicationService ──► Repository / Port
   ✗ nie wołaj repozytorium wprost z @Route
   ✗ serwis nie zależy od Button / Grid
Application Service (stateless)

Jeden use-case / spójna grupa metod. Otwiera transakcję, waliduje wejście, egzekwuje @PreAuthorize, zwraca DTO lub (przy prostym CRUD) encję. Nie trzyma stanu UI.

Widok = cienki

Składa komponenty, binduje dane, woła serwis. Bez SQL, bez reguł biznesowych w listenerze przycisku.

DTO vs encja w UI

Prosty formularz 1:1 z tabelą → encja OK. Złożony ekran / kilka agregatów → DTO. Lazy load poza transakcją w serwisie = klasyczny LazyInitializationException w Gridzie.

@Route("orders")
@PermitAll
public class OrderListView extends VerticalLayout {

  public OrderListView(OrderService orders) {
    Grid<OrderSummary> grid = new Grid<>(OrderSummary.class, false);
    grid.addColumn(OrderSummary::number).setHeader("Numer");
    grid.setItems(query ->
        orders.findPage(query.getOffset(), query.getLimit()).stream());
    add(grid);
  }
}

@Service
public class OrderService {
  @PreAuthorize("hasAuthority('ORDER_READ')")
  @Transactional(readOnly = true)
  public List<OrderSummary> findPage(int offset, int limit) { ... }
}

5. Dobre praktyki i wytyczne

Widoki i nawigacja

  • Dane ładuj w AfterNavigationObserver / BeforeEnter, nie w konstruktorze (framework może tworzyć widok wcześniej).
  • Cleanup (subskrypcje, broadcaster) w onDetach — inaczej wyciek pamięci sesji.
  • Parametry trasy: @Route("orders/:id") + BeforeEnterEvent, nie ręczne parsowanie URL.
  • Layout wspólny (MainLayout) na nawigację i bezpieczeństwo menu — nie kopiuj sidebara.

Dane w Grid / Combo

  • Duże zbiory: CallbackDataProvider / lazy z paginacją w serwisie — nigdy findAll() do pamięci.
  • Filtrowanie i sortowanie po stronie bazy, nie streamem po 100k obiektów w JVM.
  • Binder<T> + Bean Validation — błędy pól w UI, reguły krytyczne i tak w serwisie.

Styl i temat

  • CSS w motywie (frontend/themes/...), nie setki getStyle().set(...) w Javie.
  • Lumo / własny theme; spójne tokeny (kolory, spacing) zamiast magicznych pikseli.
  • Dostępność: natywne komponenty Vaadin są dobre z pudełka — nie psuj ich własnym HTML-em bez ARIA.

Kod i moduły

  • Większa appka → multi-modul Maven/Gradle: ui zależy od application, nigdy odwrotnie.
  • Constructor injection; unikaj @Autowired na polach w widokach testowalnych.
  • Nie pakuj logiki domenowej do listenerów addClickListener.

Push / tło

  • Aktualizacje z wątku tła: ui.access(() -> { ... }) — inaczej wyjątek wątku UI.
  • Włącz @Push świadomie; bez pusha i tak działa request-response.
  • Broadcast między sesjami: ostrożnie z silnymi referencjami do UI — zawsze słabe / unregister w detach.

6. Wydajność i sesja

TematWytyczna
Pamięć sesjiMierz heap per aktywna sesja UI; trzymaj widoki lekkie, nie cache'uj całych list w polach widoku
Timeout sesjiUstaw realistyczny (np. 30 min); komunikuj wygaśnięcie użytkownikowi
Sticky sessionsPrzy wielu nodach: sticky LB albo replikacja sesji (kosztowna) — planuj od dnia 1
HeartbeatDomyślny heartbeat utrzymuje sesję; poznaj konfigurację przy proxy/timeoutach
PayloadNie odświeżaj całego layoutu — aktualizuj konkretne komponenty
WątkiCiężka praca poza requestem UI (executor); wynik wraca przez ui.access
Kluczyk: zanim wrzucisz Flow za auto-scalingiem „jak REST”, narysuj ścieżkę sesji. Bez sticky lub shared session użytkownik dostanie błędy po przełączeniu poda.

7. Bezpieczeństwo

  • UI ≠ security. Ukryty przycisk to UX. Prawdziwa ochrona: @PreAuthorize / method security na application service.
  • Vaadin + Spring Security — ścieżki /VAADIN/**, login view, VaadinWebSecurity (w nowszych starterach).
  • Waliduj w serwisie nawet jeśli Binder sprawdził formularz — UI da się ominąć (inne wejście, job, API).
  • Nie wystawiaj encji z leniwymi kolekcjami poza kontrolą — ryzyko nadmiarowych danych w sesji i błędów.
  • CSRF / origin — framework chroni kanał Vaadin; własne endpointy REST i tak zabezpiecz osobno.
@Service
public class OrderService {
  @PreAuthorize("hasAuthority('ORDER_CANCEL')")
  @Transactional
  public void cancel(OrderId id, String reason) {
    // reguły domenowe — niezależnie od tego, czy Button był widoczny
  }

Da się osadzać widoki React w Flow punktowo — gdy 90% aplikacji to formy biznesowe, a jeden ekran wymaga ciężkiego klienta. Nie odwrotnie: nie buduj całego produktu w Flow „z wyspami”, jeśli rdzeń to interakcja kliencka.

9. Must-know

  1. Flow = UI w Javie, stan na serwerze — świadoma decyzja o sesji i skalowaniu.
  2. Celuj w back-office / narzędzia wewnętrzne, nie w sklep z SEO.
  3. Widok cienki → Application Service → domena/infra; nigdy repo w @Route.
  4. Security w serwisie (@PreAuthorize), nie w widoczności przycisku.
  5. Lazy data w Gridzie; zero findAll() na produkcji.
  6. Ładowanie danych po nawigacji; cleanup w onDetach.
  7. CSS w theme, nie w getStyle() wszędzie.
  8. Wątki tła tylko przez ui.access.
  9. Od dnia 1: plan na sticky sessions albo architekturę sesji.
  10. Gdy zespół to frontendowcy albo produkt publiczny — rozważ Hilla / React, nie „Flow na siłę”.

Typowe błędy

  • Logika biznesowa w addClickListener. Niewytypowalna, niechroniona method security, nie do użycia z joba.
  • Wołanie repository z widoku. Omija warstwę transakcji i autoryzacji; wiąże UI z JPA.
  • findAll() do Grida. Pierwszy tenant z 200k wierszy kładzie sesję i heap.
  • Ładowanie w konstruktorze widoku. Zbyt wcześnie / wielokrotnie; użyj cyklu nawigacji.
  • Brak onDetach przy broadcasterze. Sesja trzyma UI → wyciek pamięci aż do restartu.
  • Aktualizacja UI z wątku tła bez ui.access. Losowe wyjątki i uszkodzony stan.
  • Security tylko przez ukrycie menu. Znajomość URL / inne wejście omija „ochronę”.
  • Encja z lazy collection w sesji UI poza transakcją. LazyInitializationException przy scrollu Grida.
  • Stylowanie wyłącznie getStyle(). Niemożliwy theme, konflikt z design systemem.
  • Wdrożenie multi-node bez sticky. Użytkownik skacze między podami → „Session expired” w kółko.
  • Flow na landing page z SEO. Zły tool; osobny site albo inny stack.
  • Traktowanie Flow jak React (masowy stan w kliencie). Walczysz z modelem zamiast z nim pracować — albo wybierasz Hilla.
