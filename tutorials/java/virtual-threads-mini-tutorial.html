Część 1 — Fundamenty

1.1 Co to są Virtual Threads

Virtual thread (wątek wirtualny) to lekki wątek zarządzany przez JVM, a nie przez system operacyjny. Od Java 21 są standardem (Project Loom). API wygląda jak zwykły Thread, ale koszt utworzenia i blokady I/O jest orders of magnitude niższy niż u platform thread.

1.2 Jaki problem rozwiązują

Platform thread = 1:1 z wątkiem OS. Każdy zajmuje ~1 MB stosu, tworzenie i przełączanie kontekstu jest drogie. Model „thread pool + N wątków” nie skaluje się do dziesiątek tysięcy równoczesnych połączeń (HTTP, DB, socket). Virtual threads pozwalają napisać prosty kod synchroniczny (jak zawsze) i mimo to obsłużyć ogromną liczbę równoległych zadań I/O-bound.

1.3 Ważna zasada

Virtual threads to nie szybsze CPU — to tańsze oczekiwanie. Nie zastępują parallelStream() ani wątków do obliczeń. Zastępują sztuczne limity pooli przy zadaniach, które głównie czekają.

Część 3 — Jak to działa pod spodem

3.1 Carrier threads (wątki nośne)

JVM utrzymuje małą pulę platform threads (domyślnie ≈ liczba rdzeni). To carriers. Virtual thread wykonuje kod na carrierze; gdy trafia na blokujące I/O, JVM go odpina (unmount) — carrier dostaje inny virtual thread. Po I/O virtual thread wraca na wolny carrier.

3.2 Continuations

Pod spodem Loom używa continuations — możliwość wstrzymania i wznowienia wykonania bez blokowania OS thread. To umożliwia „parkowanie” virtual thread przy read(), sleep(), LockSupport.park() itd.

3.3 Scheduler

Domyślny scheduler to ForkJoinPool w trybie work-stealing (VirtualThreadScheduler). Nie musisz go konfigurować na start — ważne, żeby wiedzieć: carriers ≠ twoja stara pula biznesowa; to osobna infrastruktura JVM.

Część 4 — Tworzenie i API

4.1 Sposoby utworzenia

// 1. Skrót
Thread.startVirtualThread(() -> doWork());

// 2. Builder (zalecany — nazwa, handler wyjątków)
Thread.ofVirtual()
    .name("worker-", 0)
    .uncaughtExceptionHandler((t, e) -> log.error("fail", e))
    .start(() -> doWork());

// 3. Executor — jeden virtual thread na zadanie (najczęstszy w serwisach)
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    executor.submit(() -> doWork());
}

4.2 Czego NIE robić

// ŹLE — pool virtual threads (antywzorzec!)
Executors.newFixedThreadPool(200, Thread.ofVirtual().factory());

// DOBRZE — jeden virtual thread na zadanie
Executors.newVirtualThreadPerTaskExecutor();

Pula virtual threads nie ma sensu — są tak tanie, że tworzysz nowy na każde zadanie. Limitowanie sztucznie odtwarza problem platform threads.

4.3 Thread.ofPlatform() vs Thread.ofVirtual()

Od Java 21 oba buildery są w API. Explicit: platform thread gdy potrzebujesz prawdziwego OS thread (np. pin native code, specyficzne wymagania). Reszta — virtual.

Część 5 — Kiedy używać / kiedy nie

5.1 Używaj — I/O-bound

  • Serwer HTTP — request = virtual thread (Tomcat 10.1+, Spring Boot 3.2+)
  • Wiele równoległych wywołań HTTP/DB/gRPC
  • Kod synchroniczny zamiast callbacków / reactive stacku
  • Wysoka liczba równoczesnych sesji czekających na sieć

5.2 Nie używaj (lub ostrożnie) — CPU-bound

  • Ciężkie obliczenia, kompresja, kryptografia — użyj ExecutorService z platform threads lub parallelStream z limitem
  • Kod z masą synchronized na hot path — pinning (patrz część 6)
  • Biblioteki thread-local heavy bez refaktoru

5.3 Złota reguła

„Virtual thread per task” dla I/O. „Platform thread pool” (mały, = rdzenie) dla CPU. Nie mieszaj modeli bez powodu.

Część 6 — Pinning

6.1 Co to jest

Pinning — virtual thread nie może się odpinać od carrier w trakcie blokady, więc carrier jest zajęty jak stary platform thread. Tracisz korzyść Loom.

6.2 Kiedy występuje

PrzyczynaSzczegóły
synchronizedBlokada w synchronized method/block — pin do JDK 24; potem częściowo łagodzone
Native code / JNIKod natywny może pinować carrier
Niektóre operacje w starych bibliotekachStare drivery, legacy locki

6.3 Jak wykryć

// JVM flag
-Djdk.tracePinnedThreads=full   // log przy pinowaniu
-Djdk.tracePinnedThreads=short

6.4 Jak naprawić

  • Zamień synchronized na ReentrantLock — nie pinuje (używa LockSupport)
  • Aktualizuj biblioteki (JDBC drivers, connection pool — nowsze wersje Loom-aware)
  • Unikaj długich sekcji synchronized w kodzie na virtual threads

Część 7 — ThreadLocal, ScopedValue, Structured Concurrency

7.1 ThreadLocal

Virtual threads mają własny ThreadLocal, ale przy milionach wątków — problem pamięci. Każdy ThreadLocal × milion wątków = dużo RAM. Unikaj ThreadLocal na hot path; preferuj przekazywanie kontekstu explicite.

7.2 ScopedValue (zamiennik ThreadLocal)

ScopedValue — immutable kontekst wiązany z zakresem (ScopedValue.where(...).run(...)). Lepszy dla virtual threads: dzielony, tanie dziedziczenie w structured concurrency. W Java 21+ w preview/incubator — warto znać kierunek.

7.3 Structured Concurrency (JEP 462 — Java 21+ preview, stabilizacja w kolejnych wersjach)

try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
    Subtask<String> user = scope.fork(() -> fetchUser(id));
    Subtask<List<Order>> orders = scope.fork(() -> fetchOrders(id));
    scope.join();
    scope.throwIfFailed();
    return combine(user.get(), orders.get());
}

Grupuje powiązane virtual threads w hierarchię — anulowanie rodzica = anulowanie dzieci. Lepsze zarządzanie cyklem życia niż „gołe” submit().

Część 8 — Integracja (Spring, JDBC, HTTP)

8.1 Spring Boot 3.2+

# application.properties
spring.threads.virtual.enabled=true

Włącza virtual threads dla Tomcat (request handling) i @Async (jeśli skonfigurowane). Prosty sposób na przetestowanie Loom w istniejącej aplikacji.

8.2 JDBC / connection pool

Blokujące Connection jest OK na virtual thread — wątek się odpnie, carrier robi co innego. Upewnij się, że pool (HikariCP) ma sensowny maximumPoolSize — to limit połączeń DB, nie wątków. Virtual threads ≠ nieskończone połączenia do bazy.

8.3 Reactive (WebFlux) vs Virtual threads

WebFlux — non-blocking end-to-end, mniej wątków, bardziej złożony kod. Virtual threads — blocking code, prostszy mental model. Dla typowego Spring MVC + JDBC virtual threads często wystarczą bez przepisywania na reactive.

Część 9 — Najczęstsze błędy na początku

  1. Pula virtual threads — newFixedThreadPool + virtual factory — antywzorzec
  2. Oczekiwanie szybszego CPU — Loom nie przyspiesza obliczeń
  3. Ignorowanie pinningu — synchronized w bibliotece blokuje skalowanie
  4. ThreadLocal everywhere — wyciek pamięci przy masie wątków
  5. Brak limitu na DB pool — 100k virtual threads × 1 query = zalanie bazy
  6. ThreadLocal z mutable state — trudne bugi przy migracji z platform pool
  7. Mieszanie modeli — część kodu reactive, część virtual — chaos
  8. ForkJoinPool.commonPool() dla I/O — to pool CPU, nie do blokującego I/O
  9. Zakładanie, że thread.getName() = stały carrier — virtual thread może skakać między carriers
  10. Brak monitorowania — metryki: liczba virtual threads, pinned threads, carrier utilization

Pytania rekrutacyjne — krótkie odpowiedzi

Junior / Mid

1. Co to jest virtual thread?

Lekki wątek JVM mapowany na małą pulę platform threads — tani w tworzeniu i przy blokadzie I/O.

2. Od której wersji Java?

Java 21 — final feature (Project Loom).

3. Virtual vs platform thread?

Platform = 1:1 z OS, drogi. Virtual = M:N na carriers, tani, do I/O-bound.

4. Jak utworzyć virtual thread?

Thread.startVirtualThread(), Thread.ofVirtual().start(), Executors.newVirtualThreadPerTaskExecutor().

5. Czy virtual threads przyspieszają CPU?

Nie — przyspieszają skalowanie zadań I/O-bound, nie obliczenia.

6. Co to jest carrier thread?

Platform thread z puli JVM, na którym chwilowo wykonuje się virtual thread.

7. Dlaczego nie robić puli virtual threads?

Są tak tanie, że sztuczne limitowanie odtwarza problem starych pooli.

8. thread.isVirtual() — po co?

Sprawdzenie, czy bieżący wątek jest virtual czy platform.

9. Kiedy używać virtual threads?

Wiele równoczesnych zadań I/O — HTTP, DB, socket, czekanie na sieć.

10. Co to jest pinning?

Virtual thread nie może się odpinać od carrier — carrier zablokowany jak platform thread.

11. Co powoduje pinning?

synchronized, native code, niektóre stare biblioteki.

12. Jak uniknąć pinningu w lockach?

Użyj ReentrantLock zamiast synchronized.

13. Czy blocking JDBC jest OK na virtual thread?

Tak — wątek się odpnie; carrier robi co innego. Limit to pool połączeń DB, nie wątki.

14. Spring Boot — jak włączyć?

spring.threads.virtual.enabled=true (Boot 3.2+).

15. Virtual threads vs reactive (WebFlux)?

Virtual = prosty blocking code, dużo wątków. Reactive = non-blocking, mało wątków, wyższa złożoność.

Mid / Senior

16. Jak działa unmount przy I/O?

JVM parkuje continuation virtual thread; carrier bierze inny. Po I/O — mount na wolnym carrierze.

17. Domyślny scheduler virtual threads?

ForkJoinPool work-stealing — liczba carriers ≈ rdzenie CPU (domyślnie).

18. -Djdk.tracePinnedThreads — po co?

Diagnostyka — log stack trace gdy virtual thread jest pinowany.

19. ThreadLocal + virtual threads — problem?

Miliony wątków × ThreadLocal = duża pamięć; preferuj ScopedValue lub explicit context.

20. Co to jest ScopedValue?

Immutable kontekst wiązany ze scope — bezpieczniejszy zamiennik ThreadLocal dla Loom.

21. Structured Concurrency — idea?

Hierarchia zadań: anulowanie/shutdown rodzica = dzieci. StructuredTaskScope.

22. Czy CompletableFuture.supplyAsync() używa virtual threads?

Domyślnie nie — używa ForkJoinPool.commonPool(). Trzeba podać własny executor.

23. Jak podać virtual executor do supplyAsync?

supplyAsync(task, Executors.newVirtualThreadPerTaskExecutor()).

24. HikariCP + virtual threads — na co uważać?

maximumPoolSize limituje połączenia DB — virtual threads mogą czekać w kolejce poola.

25. Tomcat z virtual threads?

Tomcat 10.1+ — VirtualThreadExecutor; jeden virtual thread na request zamiast platform pool.

26. Czy parallelStream() korzysta z virtual threads?

Nie — używa ForkJoinPool.commonPool() (platform). Osobne modele.

27. Migracja z FixedThreadPool(200) — co zamiast?

newVirtualThreadPerTaskExecutor() — bez sztywnego limitu 200; ewentualnie semafory na zasoby zewnętrzne.

28. Semaphore vs thread pool limit?

Semaphore limituje dostęp do zasobu (DB, API); virtual threads mogą czekać tanio bez blokowania carriers (jeśli bez pin).

29. Continuation — co to?

Mechanizm Loom: wstrzymanie/wznowienie wykonania bez blokowania OS thread.

30. Monitoring virtual threads w produkcji?

JFR events (jdk.VirtualThread*), Micrometer, liczba pinned threads, queue HikariCP.

Pułapki / tricky

31. Czy każdy virtual thread = osobny OS thread?

Nie — wiele virtual na małej liczbie carriers.

32. Czy synchronized zawsze pinuje?

W praktyce tak (JDK 21–24); JDK pracuje nad redukcją. Bezpieczniej ReentrantLock.

33. Czy więcej virtual threads = więcej połączeń DB?

Nie automatycznie — limituje connection pool, nie liczba wątków.

34. Czy virtual thread może zmienić carrier w trakcie?

Tak — między mount/unmount; nie zakładaj affinity do OS thread.

35. Thread.sleep() na virtual thread?

OK — wątek się odpnie, carrier wolny.

36. Czy Loom zastępuje reactive programming?

Nie w pełni — reactive nadal lepsze gdy cały stack non-blocking; Loom upraszcza blocking MVC.

37. InheritedThreadLocal + virtual threads?

Działa, ale koszt pamięci przy masowej skali — unikaj lub używaj ScopedValue.

38. Czy Object.wait() pinuje?

Tak — jak synchronized; trzyma monitor i carrier.

39. ExecutorService z virtual threads — shutdown?

Try-with-resources (AutoCloseable) lub shutdown() + awaitTermination — jak zwykły executor.

40. Project Loom vs „green threads” sprzed lat?

Podobna idea (lekki wątek), ale Loom integruje z OS I/O (blocking syscalls), carriers i istniejącym API Thread — nie green threads Javy 1.1.
