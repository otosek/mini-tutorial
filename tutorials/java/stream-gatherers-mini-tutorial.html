Część 1 — Fundamenty

1.1 Co to są Stream Gatherers

Stream Gatherers rozszerzają Stream API (Java 8) o własne operacje pośrednie — tak jak Collector rozszerza operacje terminalne przez collect(), tak Gatherer rozszerza pośrednie przez gather().

Historycznie: JEP 461 (Java 22 preview), JEP 473 (Java 23 preview), JEP 485 — finalizacja w Java 24 bez zmian API.

import java.util.stream.Gatherers;
import java.util.stream.Stream;

Stream.of(1, 2, 3, 4, 5)
    .gather(Gatherers.windowFixed(2))
    .forEach(System.out::println);
// [1, 2]
// [3, 4]
// [5]

1.2 Po co, skoro mamy map/filter/reduce?

Brakowało w JDK operacji takich jak okna (windowing), prefix scan, wielu wyników z jednego elementu w kontrolowany sposób albo współbieżne mapowanie z zachowaniem kolejności. Wcześniej: własne Spliterator, biblioteki (Guava), albo obejścia z collect + ponowne streamowanie.

Część 2 — Gatherer vs Collector vs map/filter

OperacjaWejście → wyjścieMoment
mappośrednia1 → 1lazy, element po elemencie
flatMappośrednia1 → Nlazy
Gathererpośrednia (gather)1→1, 1→N, N→1, N→Nlazy, ze stanem
Collectorterminalna (collect)stream → jeden wynikzużywa stream
Interfejs Gatherer<T, A, R>

T — typ elementu wejściowego · A — stan wewnętrzny (akumulator) · R — typ elementu wyjściowego downstream. Trzy fazy: initializer (stan początkowy), integrator (element + stan → emit?), finisher (flush na końcu).

fold to gatherer many-to-one w pipeline — emituje jeden wynik dopiero na końcu strumienia (albo przy finisherze). To nie to samo co reduce terminalne — wynik fold może iść dalej w pipeline.

Część 3 — Wbudowane gatherery (Gatherers)

GathererTypOpis
fold(initial, folder)many-to-oneAkumulacja do jednego wyniku na końcu
scan(initial, scanner)one-to-onePrefix scan — emit po każdym elemencie (bieżąca suma)
windowFixed(size)many-to-manyNie nakładające się listy po N elementów
windowSliding(size)many-to-manyOkno przesuwne o 1 element
mapConcurrent(n, mapper)one-to-oneMapowanie współbieżne (virtual threads), kolejność zachowana

scan — bieżąca suma

Stream.of(1, 2, 3, 4)
    .gather(Gatherers.scan(() -> 0, (acc, x) -> acc + x))
    .toList();
// [1, 3, 6, 10]

windowFixed — batchowanie ID autorów

List<Long> authorIds = List.of(1L, 2L, 3L, 4L, 5L);

authorIds.stream()
    .gather(Gatherers.windowFixed(2))
    .map(batch -> authorRepository.findAllById(batch))  // 1 query na 2 ID
    .flatMap(List::stream)
    .toList();

windowSliding — średnia krocząca

Stream.of(10, 20, 30, 40)
    .gather(Gatherers.windowSliding(3))
    .map(window -> window.stream().mapToInt(i -> i).average().orElse(0))
    .toList();
// [20.0, 30.0]  → okna [10,20,30], [20,30,40]

fold — pośrednia agregacja

// Łączy wszystkie tytuły w jeden string — wynik idzie dalej w pipeline
Stream.of("Dune", "Solaris", "Hyperion")
    .gather(Gatherers.fold(
        () -> new StringBuilder(),
        (sb, title) -> sb.append(title).append("; ")))
    .map(StringBuilder::toString)
    .findFirst();

Część 4 — mapConcurrent i virtual threads

Gatherers.mapConcurrent(maxConcurrency, mapper) uruchamia mapper równolegle (domyślnie na virtual threads), ale **emituje wyniki w kolejności wejścia** — inaczej niż parallelStream(), które optymalizuje CPU i nie gwarantuje kolejności.

// Pobierz szczegóły autorów z zewnętrznego API — max 10 równolegle
List<Author> authors = authorIds.stream()
    .gather(Gatherers.mapConcurrent(10, id ->
        restClient.get()
            .uri("/authors/{id}", id)
            .retrieve()
            .body(Author.class)))
    .toList();
mapConcurrent vs parallelStream

parallelStream — ForkJoinPool, CPU-bound, brak gwarancji kolejności. mapConcurrent — I/O-bound, limit współbieżności, kolejność encounter order zachowana. Idealne przy HTTP/DB z wieloma niezależnymi callami.

Część 5 — Własny gatherer

Fabryki: Gatherer.ofSequential(...) (sekwencyjny), Gatherer.of(...) (może wspierać równoległość z combinerem). Prosty gatherer: emit co drugi element.

Gatherer<Integer, ?, Integer> everySecond = Gatherer.ofSequential(
    () -> new boolean[] { true },                    // stan: czy emitować
    (state, element, downstream) -> {
      if (state[0]) {
        downstream.push(element);
      }
      state[0] = !state[0];
      return true;  // kontynuuj
    }
);

Stream.of(1, 2, 3, 4, 5, 6)
    .gather(everySecond)
    .toList();  // [1, 3, 5]

Integrator zwraca false, gdy chce przerwać przetwarzanie (jak short-circuit). finisher emituje resztkę stanu (np. niepełne okno).

Część 6 — Kompozycja gathererów

gatherer1.andThen(gatherer2) — pierwszy przetwarza, drugi dostaje jego output jako input. Przydatne: scan + fold, window + map.

var pipeline = Gatherers.<Integer>scan(() -> 0, Integer::sum)
    .andThen(Gatherers.fold(() -> 0, Integer::sum));

Stream.of(1, 2, 3).gather(pipeline).toList();
// scan: [1,3,6] → fold: [10]

Typowe błędy

  1. Myślenie, że gatherer = collector — gatherer to operacja pośrednia, stream dalej płynie
  2. mapConcurrent bez limitu — przy tysiącach ID zaljesz API/DB; ustaw maxConcurrency świadomie
  3. windowFixed na nieskończonym streamie bez backpressure — pamięć rośnie jeśli downstream wolny
  4. Mutowalny stan w integratorze współdzielony między wątkami — przy custom gathererze używaj ofSequential albo poprawnego combiner
  5. Oczekiwanie wielu wyników z fold w środku pipeline — fold emituje dopiero na końcu (many-to-one)
  6. Zamiana scan ↔ reduce — scan emituje każdy krok; reduce terminalny daje jeden wynik
  7. parallelStream + gather — zachowanie zależy od encounter order; testuj na małych danych
  8. Java 21 bez flagi preview — gatherery standardowe od Java 24; w 22–23 wymagały --enable-preview
  9. windowSliding na dużym oknie + długi stream — każde okno to nowa lista — koszt pamięci O(n×size)
  10. Brak obsługi pustego streamu w custom finisher — finisher musi poprawnie flushować resztkę stanu

Pytania rekrutacyjne — krótkie odpowiedzi

Junior / Mid

1. Co to Stream Gatherers?

API (Java 24) do własnych operacji pośrednich na streamach przez Stream.gather(Gatherer).

2. Który JEP finalizuje gatherery?

JEP 485 w Java 24 (preview: JEP 461 w 22, JEP 473 w 23).

3. Czym różni się gather od collect?

gather — operacja pośrednia (lazy), wynik dalej w pipeline. collect — terminalna, kończy stream.

4. Co robi Gatherers.scan?

Prefix scan — po każdym elemencie emituje bieżącą akumulację (np. sumy częściowe).

5. Co robi Gatherers.windowFixed(3)?

Grupuje elementy w listy po 3; ostatnie okno może być krótsze.

6. windowFixed vs windowSliding?

Fixed — okna rozłączne. Sliding — nakładające się, przesuwane o 1 element.

7. Przykład wyniku windowSliding(2) na [1,2,3]?

[[1,2], [2,3]]

8. Co robi Gatherers.fold?

Many-to-one — akumuluje wszystkie elementy do jednego wyniku emitowanego na końcu.

9. Czym jest mapConcurrent?

Mapowanie elementów współbieżnie z limitem; kolejność wyjścia = kolejność wejścia.

10. Gdzie jest klasa Gatherers?

java.util.stream.Gatherers

11. Czy gatherery wymagają Java 24?

Standard od 24. W 22–23 były preview z --enable-preview.

12. scan vs reduce terminalny?

scan emituje każdy krok pośredni w streamie; reduce daje jeden końcowy wynik i kończy pipeline.

13. Po co batchowanie windowFixed przy DB?

Grupuje ID do paczek — mniej round-tripów (IN (...), bulk API).

14. Czy gatherer może emitować więcej niż jeden element na input?

Tak — many-to-many (np. okna). flatMap też, ale gatherer ma kontrolowany stan.

15. Co to integrator w Gatherer?

Funkcja wołana per element: aktualizuje stan, opcjonalnie emituje downstream, zwraca czy kontynuować.

Mid / Senior

16. Typy transformacji gatherera (1→1, 1→N, N→1, N→N)?

scan/mapConcurrent = 1→1; window* = many-to-many; fold = many-to-one; flatMap-like custom = 1→N.

17. mapConcurrent vs parallelStream().map()?

mapConcurrent: virtual threads, limit concurrency, zachowana kolejność, I/O. parallelStream: ForkJoinPool, CPU, bez gwarancji kolejności.

18. Jak skomponować dwa gatherery?

g1.andThen(g2) — output g1 jest inputem g2.

19. Gatherer.ofSequential vs Gatherer.of?

Sequential — bez combiner, jeden wątek. of — może wspierać równoległe przetwarzanie z łączeniem stanu.

20. Kiedy fold jako pośredni zamiast collect?

Gdy zagregowany wynik ma iść dalej w pipeline (np. jeden string → dalsze map/filter), nie kończyć streamu.

21. Czy gatherer jest lazy?

Tak — jak inne operacje pośrednie; wykonanie przy terminal operation.

22. Co robi finisher gatherera?

Flush stanu po ostatnim elemencie — np. emit niepełnego okna, końcowa agregacja fold.

23. Integrator zwraca false — efekt?

Przerwanie przetwarzania (short-circuit w gathererze).

24. mapConcurrent(10, f) — co oznacza 10?

Maksymalna liczba równoległych wywołań f (współbieżność).

25. Czy gatherery działają na parallel stream?

Tak, ale semantyka encounter order zależy od gatherera; wiele jest sekwencyjnych ze względu na stan.

26. Analogia Gatherer : Stream jak Collector : ?

Collector rozszerza operacje terminalne; Gatherer — operacje pośrednie.

27. Przykład użycia scan w analityce?

Bieżąca suma salda, licznik running count, cumulative distribution w czasie rzeczywistym.

28. Dlaczego nie flatMap do okien?

flatMap nie ma wbudowanego stanu okna; gatherer enkapsuluje stan i granice okien czysto.

29. Custom gatherer — thread safety?

Stan per pipeline / per sub-stream; mutacja tylko w integratorze; przy równoległości — combiner lub sequential.

30. Gatherers a reactive streams?

Osobne modele; gatherery synchronizują się ze Stream API. Dla backpressure używaj reactive; gatherery dla batch w pamięci.

Pułapki

31. fold w środku pipeline — ile elementów downstream dostaniesz po 100 input?

Jeden (many-to-one) — dopiero po przetworzeniu całego upstream (finisher).

32. mapConcurrent z concurrency=1000 i wolnym API?

1000 równoległych calli — ryzyko timeoutów, rate limit, wyczerpanie pooli; semaphore po stronie klienta nadal potrzebny.

33. windowSliding(100) na streamie 1M elementów — pamięć?

~1M list po ~100 elementów — bardzo drogie; rozważ stream processing lub mniejsze okna/inne algorytmy.

34. Czy gather zastępuje Spliterator?

Dla wielu przypadków tak (czytelniej); Spliterator nadal nisko-poziomowy dla źródeł danych.

35. scan z mutowalnym akumulatorem (ArrayList)?

Emitujesz referencję do tego samego obiektu — downstream może zmutować; lepiej emitować kopie/immutable.

36. Java 22 preview — flaga kompilacji?

--enable-preview + target 22; od Java 24 standard bez preview.

37. fold + andThen + scan — kolejność?

Najpierw scan na input, potem fold na output scan — kolejność andThen ma znaczenie.

38. Czy mapConcurrent używa platform czy virtual threads?

Implementacja JDK opiera się na virtual threads (JEP 485) — tanie I/O concurrency.

39. gather po infinite stream + windowFixed?

Działa lazy, ale downstream musi konsumować; infinite okna — potencjalnie infinite output.

40. Kiedy NIE używać gathererów?

Proste map/filter wystarczy; bardzo duże dane z backpressure → reactive; CPU parallel → parallelStream/Executor.
