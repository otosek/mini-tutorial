Część 0 — Fundamenty

Spring Cloud Bus to cienka warstwa nad brokerem wiadomości (Kafka lub RabbitMQ), która rozgłasza zdarzenia do wszystkich instancji aplikacji w klastrze. Najczęstszy use case: po zmianie configu w Git jednym wywołaniem /actuator/busrefresh odświeżasz @RefreshScope beany na wszystkich replikach wszystkich serwisów — bez ręcznego POST na każdą instancję.

Admin / pipeline POST /actuator/busrefresh (jedna instancja order-service) │ ▼ topic: springCloudBus │ ┌─────────┼─────────┬─────────────┐ ▼ ▼ ▼ ▼ order-1 order-2 author-1 author-2 refresh refresh refresh refresh

Bus nie zastępuje Config Server — tylko propaguje sygnał „przeładuj config z serwera”. Bez Config Server Bus może nadal rozsyłać custom eventy (RemoteApplicationEvent), ale to rzadki przypadek.

Bus vs pojedynczy /actuator/refresh

refresh — tylko ta JVM. busrefresh — publikuje zdarzenie na bus; każdy subskrybent wykonuje refresh lokalnie. Przy 20 replikach × 5 serwisów = 100 wywołań ręcznie vs jeden busrefresh.

1. Kiedy używać / kiedy nie

Bierz BusOlej Bus
Wiele replik wielu serwisów + Config Server + częsty refresh bez redeploy K8s — zmiana ConfigMap + rolling restart (GitOps) wystarcza
Już masz Kafka/Rabbit na Stream — ten sam broker na bus Jedna instancja na serwis — zwykły /actuator/refresh
Chcesz webhook z Git → busrefresh po pushu do config repo Config tylko w env vars / Parameter Store przy starcie — brak refresh w runtime
Broadcast custom eventów między serwisami (rzadkie) Brak brokera — nie stawiaj Rabbita tylko dla Bus
Na K8s w 2025+ częściej: Argo CD / Flux redeploy przy zmianie Secret — prostsze mentalnie niż Bus + refresh scope. Bus ma sens w VM/ECS bez GitOps albo gdy refresh musi być bez restartu poda.

2. Konfiguracja

Starter (Kafka): spring-cloud-starter-bus-kafka. Rabbit: spring-cloud-starter-bus-amqp. Wymaga też Config Client jeśli chodzi o refresh configu.

spring:
  cloud:
    bus:
      enabled: true
      id: ${spring.application.name}:${server.port}  # unikalny per instancja
    stream:
      kafka:
        binder:
          brokers: localhost:9092

management:
  endpoints:
    web:
      exposure:
        include: health,refresh,busrefresh,bus-env

Każda aplikacja subskrybuje topic exchange (Rabbit) lub topic Kafka (domyślnie springCloudBus). Id instancji musi być unikalne — duplikat = dziwne zachowanie subskrypcji.

EndpointDziałanie
POST /actuator/busrefreshRefresh config + @RefreshScope na wszystkich nodach
POST /actuator/busrefresh?name=order-service&destination=**Tylko wybrane aplikacje (filtr)
POST /actuator/busenvPodobnie dla env (starsze / rzadziej)

Zabezpiecz endpointy Actuator — busrefresh na otwartym porcie = każdy przeładowuje config. Spring Security + rola ADMIN lub wyłącz exposure na publicznym interfejsie.

3. Integracja z Config Server

1. Push do Git (config-repo): feature.newCheckout=true 2. Config Server widzi nową wersję (webhook / polling) 3. POST /actuator/busrefresh na dowolnej instancji (lub webhook z GitHub Actions) 4. Wszystkie serwisy: pobierz config → odśwież @RefreshScope beany
@RefreshScope
@ConfigurationProperties(prefix = "feature")
public class FeatureFlags {
  private boolean newCheckout;
}

Bez @RefreshScope busrefresh przeładuje Environment, ale istniejące beany trzymają stare wartości — ten sam problem co przy pojedynczym refresh (patrz tutorial Config).

Webhook z GitLab/GitHub na Config Server lub na jedną aplikację z busrefresh — typowy pipeline. Alternatywa: Spring Cloud Config Monitor + /monitor na serwerze configu (publikuje na bus po pushu).

# config-server + bus
spring:
  cloud:
    config:
      server:
        monitor:
          github:
            enabled: true

4. Własne zdarzenia (zaawansowane)

Możesz publikować własne RemoteApplicationEvent — inne serwisy z Bus je odbierają. Użyteczne do rzadkich sygnałów administracyjnych; do domeny biznesowej używaj Spring Cloud Stream, nie Bus.

public class CacheInvalidateEvent extends RemoteApplicationEvent {
  public CacheInvalidateEvent(Object source, String originService, String destination) {
    super(source, originService, destination);
  }
}

Destination ** = broadcast. Konkretna nazwa serwisu = tylko ten konsument. Nie przeładowuj Bus dużymi payloadami — to sygnał, nie kolejka zadań.

Typowe błędy

  1. Bus bez brokera. Aplikacja startuje, ale zdarzenia nie docierają — sprawdź Kafka/Rabbit i topic springCloudBus.
  2. Duplikat spring.cloud.bus.id. Dwie instancje z tym samym id — tylko jedna dostaje eventy.
  3. busrefresh bez Config Client. Event leci, ale nie ma skąd pobrać nowego configu.
  4. Bean bez @RefreshScope. Bus zadziałał, wartość na ekranie stara — mylące przy debugowaniu.
  5. Actuator publiczny na internecie. Busrefresh bez auth — podatność operacyjna i bezpieczeństwa.
  6. Refresh DataSource przez Bus. Przeładowanie URL DB w locie — wyciek połączeń; rolling restart bezpieczniejszy.
  7. Bus + Stream ten sam broker, ten sam consumer group. Konflikt konfiguracji — osobne topici, osobne grupy.
  8. Oczekiwanie natychmiastowej spójności. Eventual delay brokera — kilka sekund do pełnego refreshu klastra.
  9. Bus na prod „bo było w tutorialu” przy GitOps K8s. Zbędna złożoność — YAGNI.
  10. Monitor webhook bez secreta. Każdy może triggerować refresh — weryfikuj podpis GitHub/GitLab.
