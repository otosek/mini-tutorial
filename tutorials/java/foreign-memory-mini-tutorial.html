Część 1 — Fundamenty

1.1 Co to jest Foreign Memory API

Foreign Function & Memory API (FFM, Project Panama) to standardowy sposób w Javie na pracę z pamięcią poza stertą JVM (off-heap) oraz wywoływanie kodu natywnego — bez ręcznego JNI. Część „memory” obejmuje alokację, layout i bezpieczny dostęp przez MemorySegment.

JEP 454 — finalizacja w Java 22 (wcześniej preview/incubator). Pakiet: java.lang.foreign.

1.2 Jaki problem rozwiązuje

  • ByteBuffer — ograniczony, 2 GB limit, brak deterministycznego scope
  • sun.misc.Unsafe — niebezpieczny, deprecated, use-after-free = crash JVM
  • JNI — dużo boilerplate C, łatwo o wyciek pamięci i błędy wątków

FFM daje: scoped memory (arena zamyka → segment unieważniony), wyjątki zamiast crashy, VarHandle do struktur.

Część 2 — MemorySegment i Arena

MemorySegment

Reprezentuje ciągły region pamięci (on-heap lub off-heap). Nie alokujesz segmentu „sam” — zwykle przez Arena.

Arena

Zarządza cyklem życia segmentów: alokacja + deterministyczne zwolnienie przy close(). Try-with-resources = automatyczne zamknięcie scope.

import java.lang.foreign.*;

try (Arena arena = Arena.ofConfined()) {
    MemorySegment segment = arena.allocate(64);
    segment.set(ValueLayout.JAVA_INT, 0, 42);
    int value = segment.get(ValueLayout.JAVA_INT, 0);
    // arena.close() → segment nieważny, pamięć zwolniona
}

Próba dostępu po zamknięciu areny → IllegalStateException (segment „not alive”), nie undefined behavior jak w C.

allocateFrom — kopiowanie z Javy

try (Arena arena = Arena.ofConfined()) {
    MemorySegment cString = arena.allocateFrom("Authors API");
    // UTF-8, null-terminated — gotowe pod wywołanie natywne
}

Część 4 — MemoryLayout i dostęp do danych

ValueLayout opisuje typ prymitywny (JAVA_INT, JAVA_LONG, ADDRESS…). StructLayout / SequenceLayout — struktury C-like z alignment.

StructLayout authorLayout = MemoryLayout.structLayout(
    ValueLayout.JAVA_LONG.withName("id"),
    ValueLayout.JAVA_INT.withName("titleCount"),
    ValueLayout.ADDRESS.withName("namePtr")
);

try (Arena arena = Arena.ofConfined()) {
    MemorySegment block = arena.allocate(authorLayout);
    block.set(authorLayout, "id", 1L);
    block.set(authorLayout, "titleCount", 5);
    long id = block.get(authorLayout, "id");
}

VarHandle z layout path — type-safe dostęp bez ręcznych offsetów:

VarHandle idHandle = authorLayout.varHandle(
    MemoryLayout.PathElement.groupElement("id"));
idHandle.set(block, 0L, 99L);

SegmentScope — każdy segment wie, czy jego arena żyje. segment.isAccessibleBy(Thread.currentThread()) sprawdza uprawnienia wątku.

Typowy use case w aplikacji Java (bez własnego C): biblioteki natywne (SQLite, compress, crypto), zero-copy I/O, integracja z istniejącymi .so/.dll przez FFM zamiast pisać JNI wrapper.

Część 6 — Foreign functions (skrót)

Ta sama FFM API obejmuje wywołania natywne — nie tylko pamięć:

Linker linker = Linker.nativeLinker();
SymbolLookup lookup = SymbolLookup.loaderLookup()
    .or(Linker.nativeLinker().defaultLookup());

MethodHandle strlen = linker.downcallHandle(
    lookup.find("strlen").orElseThrow(),
    FunctionDescriptor.of(ValueLayout.JAVA_LONG, ValueLayout.ADDRESS)
);

try (Arena arena = Arena.ofConfined()) {
    MemorySegment str = arena.allocateFrom("hello");
    long len = (long) strlen.invoke(str);
}

Kluczowe typy: Linker, FunctionDescriptor, SymbolLookup, MethodHandle (downcall). Up-call (C → Java) też możliwy przez Linker.upcallStub.

Typowe błędy

  1. Dostęp do segmentu po arena.close() — use-after-free; zawsze try-with-resources
  2. Confined arena z wielu wątków — użyj ofShared()
  3. Przekazanie segmentu do native code poza scope areny — native trzyma wskaźnik po free → crash; przedłuż życie areny
  4. Ręczne offsety bez layout — błędy alignment/padding; używaj StructLayout
  5. Myślenie, że ofAuto = natychmiast free — GC decyduje; dla determinizmu confined/shared
  6. Global arena „na wszystko” — wyciek natywnej pamięci jak w C
  7. Mylenie ADDRESS z long — na 64-bit ADDRESS to layout wskaźnika, nie zawsze long w C
  8. Brak --enable-native-access — moduły z FFM mogą wymagać flagi (JDK 22+)
  9. JNI + FFM mieszane bez planu — dwa modele zarządzania pamięcią
  10. Duży off-heap bez monitoringu — JVM heap mało pokaże; śledź native memory (NMT, JFR)

Pytania rekrutacyjne — krótkie odpowiedzi

Junior / Mid

1. Co to Foreign Memory API?

Część FFM API (Project Panama) do bezpiecznej alokacji i dostępu do pamięci off-heap przez MemorySegment i Arena.

2. Od której wersji Java jest standardem?

Java 22 — JEP 454 (Foreign Function & Memory API).

3. Co to MemorySegment?

Obiekt reprezentujący ciągły region pamięci (heap lub off-heap) z kontrolą scope i bounds.

4. Co robi Arena?

Alokuje segmenty i zarządza ich cyklem życia — przy close zwalnia natywną pamięć i unieważnia segmenty.

5. Co to confined arena?

Arena jednowątkowa (owner thread), deterministyczny scope do close — domyślny wybór wydajnościowy.

6. Co to shared arena?

Arena wielowątkowa — segmenty dostępne z wielu wątków do momentu close.

7. Co się stanie po close areny przy odczycie segmentu?

IllegalStateException — segment nie jest „alive”.

8. Co robi arena.allocateFrom(String)?

Alokuje segment i kopiuje string jako UTF-8 z null terminator (C string).

9. Jaki pakiet?

java.lang.foreign

10. FFM vs JNI — główna zaleta?

Mniej boilerplate, bezpieczniejszy model pamięci (scope), pure Java bez obowiązkowego C glue code.

11. Co to ValueLayout?

Opis layoutu wartości prymitywnej (np. JAVA_INT, ADDRESS) — rozmiar i alignment.

12. Czym różni się off-heap od heap?

Off-heap nie podlega GC JVM; alokacja/zwolnienie przez Arena; nie liczy się do -Xmx wprost.

13. Co to Project Panama?

Projekt OpenJDK: interoperacyjność Java ↔ native (FFM API zastępuje incubator/JNI w nowym kodzie).

14. Try-with-resources z Arena — po co?

Gwarantuje close() i zwolnienie natywnej pamięci nawet przy wyjątku.

15. Arena.global — kiedy?

Prawie nigdy w aplikacji — pamięć na całe życie procesu; close() nie działa.

Mid / Senior

16. ofAuto vs ofConfined?

ofAuto — scope do GC/cleaner, niedeterministyczne free. ofConfined — explicit close, deterministyczne, szybsze.

17. StructLayout — po co?

Mapowanie struktur C (padding, alignment) — get/set po nazwach pól zamiast ręcznych offsetów.

18. VarHandle z layout path?

Type-safe dostęp do pól struktury w segmencie — alternatywa dla segment.get(layout, "field").

19. Linker.downcallHandle — co zwraca?

MethodHandle do wywołania funkcji natywnej z Javy zgodnie z FunctionDescriptor.

20. FunctionDescriptor?

Opis sygnatury native: typ zwracany + typy argumentów jako MemoryLayout.

21. SymbolLookup?

Wyszukiwanie symboli (np. strlen) w załadowanej bibliotece natywnej.

22. Dlaczego FFM szybsze od JNI (orientacyjnie)?

Mniej warstw, MethodHandle, brak generowania stubów JNI per call w typowym użyciu.

23. SegmentAllocator — relacja do Arena?

Arena extends SegmentAllocator — arena alokuje i kontroluje lifetime segmentów.

24. MemorySegment z ByteBuffer?

Możliwa konwersja (heap/direct buffer) — most do legacy API.

25. JEP 472 — JNI?

Przygotowanie do ograniczenia JNI — nowy kod native interop powinien iść w FFM.

26. ADDRESS layout?

Reprezentuje wskaźnik natywny (size zależy od platformy) — argument do funkcji C przyjmujących pointer.

27. Native access restriction?

Moduły wywołujące FFM mogą wymagać --enable-native-access=modulename — kontrola bezpieczeństwa.

28. Kiedy off-heap w typowej aplikacji Spring?

Rzadko wprost — raczej przez bibliotekę (Netty direct buffers, driver DB, codec) migrującą na FFM.

29. sequenceLayout?

Layout tablicy elementów stałego rozmiaru — np. tablica 10 intów w strukturze C.

30. reinterpret na segmencie?

Nowy segment ten sam adres, inny rozmiar — resize po native call zwracającym bufor.

Pułapki

31. Segment przekazany do native async po close areny?

Use-after-free w C — JVM nie chroni; arena musi żyć przez cały czas użycia w native.

32. Confined arena + virtual thread inny niż owner?

Virtual thread = osobny Thread — dostęp z innego VT do confined segment → wyjątek.

33. Czy FFM zastępuje całkowicie DirectByteBuffer?

Stopniowo — wiele API nadal używa ByteBuffer; FFM to preferowany kierunek od Java 22.

34. Unsafe.allocateMemory vs Arena?

Unsafe — manual free, brak scope. Arena — structured, exceptions zamiast crash.

35. Global arena w connection pool?

Zły pomysł — wyciek off-heap; per-request confined arena lub pool segmentów ze znanym scope.

36. Alignment w StructLayout — dlaczego ważny?

C compiler dodaje padding — zły layout = złe odczyty pól struktury native.

37. Czy GC śledzi off-heap FFM?

Nie jak obiekty heap — native memory osobno (NMT); arena.close zwalnia natychmiast.

38. downcall z wrong FunctionDescriptor?

Undefined behavior po stronie native / crash — descriptor musi dokładnie matchować C ABI.

39. ofShared + close z innego wątku?

Dozwolone (w przeciwieństwie do confined) — współdzielone zamknięcie scope.

40. Kiedy NIE używać FFM?

Prosta aplikacja CRUD bez native — wystarczy heap. FFM gdy: biblioteka C, zero-copy, performance off-heap, zastąpienie JNI.
