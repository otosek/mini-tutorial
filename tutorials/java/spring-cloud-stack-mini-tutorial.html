Część 0 — Fundamenty

Spring Cloud to nie jeden framework — to zestaw projektów (gateway, config, stream, openfeign…) współdzielących wersje w BOM-ie (spring-cloud-dependencies). Każdy moduł rozwiązuje jeden problem rozproszonego systemu; razem dają spójny stack dla mikroserwisów na JVM.

Spring Boot = pojedyncza aplikacja. Spring Cloud = jak te aplikacje gadają ze sobą, jak wchodzi ruch z zewnątrz, skąd biorą config i jak testujesz kontrakty między zespołami.

Netflix → Spring

Eureka, Zuul, Ribbon, Hystrix — era Netflix OSS. Dziś: Gateway zamiast Zuul, LoadBalancer zamiast Ribbon, Resilience4j zamiast Hystrix. Eureka nadal spotykany w legacy; na K8s często DNS Service zamiast Eureka.

1. Warstwy i moduły

WarstwaModułRola w jednym zdaniu
Edge Gateway Jedno wejście HTTP(S), routing, auth na brzegu, CORS, rate limit
Sync OpenFeign Serwis A woła serwis B przez REST — interfejs zamiast RestClient w pętli
Sync LoadBalancer + Discovery lb://order-service — wybór instancji z Eureka/Consul/K8s
Async Stream Eventy przez Kafka/Rabbit — luźne sprzężenie, outbox, saga
Infra Config Centralny YAML w Git/Vault; refresh bez przebudowy JAR
Infra Contract Testy kontraktowe HTTP/messaging — producer vs consumer w CI
Infra AWS (io.awspring) S3, SQS, SNS, Parameter Store — Spring idiom nad SDK v2
Cross Resilience4j CB, retry, bulkhead — w serwisie i na Gateway

Nie musisz brać wszystkiego. Minimalny sensowny mikroserwis: Boot + (Feign lub Stream) + LB. Gateway gdy wiele serwisów na jednym hoście publicznym. Config gdy >3 serwisy i wspólne properties.

2. Przepływ synchroniczny (request-response)

1. Klient → GET https://api.example.com/api/orders/42
2. Gateway: walidacja JWT, StripPrefix, route → lb://order-service
3. LoadBalancer: wybór repliki order-service (K8s Endpoints)
4. order-service: logika; potrzebuje autora → AuthorClient (Feign)
5. Feign → lb://author-service/authors/7
6. Resilience4j: CB open? → fallback lub 503
7. Odpowiedź JSON w górę łańcucha

Łańcuch wywołań: każdy hop dodaje latency. Trzy synchroniczne Feigny pod rząd = suma timeoutów. Gdy >2 hopów — rozważ event (Stream) albo agregację w BFF na Gateway.

3. Przepływ asynchroniczny (event-driven)

1. order-service: zapis do DB + wpis outbox (ta sama transakcja)
2. scheduler / Debezium: publish OrderCreated → topic order-created
3. Stream Supplier/Consumer lub @KafkaListener
4. notification-service: Consumer → wysyłka maila (SES / Stream)
5. inventory-service: Consumer → rezerwacja stanu
6. Błąd → retry → DLQ order-created.dlq

Spring Cloud Stream abstrahuje brokera; kontrakty messaging testujesz SCC (ten sam koncept co HTTP). Saga choreograficzna = wiele consumerów na eventy; orkiestracja = osobny serwis + stan (Camunda, Temporal) — poza samym Stream.

Sync vs async — reguła

Sync (Feign): potrzebujesz odpowiedzi teraz, prosty query, mało zależności. Async (Stream): notyfikacje, integracja w tle, wiele subskrybentów, buforowanie szczytów, eventual consistency akceptowalna.

Na K8s częsty stack 2025+: ConfigMap/Secret + External Secrets, bez Config Server; DNS zamiast Eureka; Gateway jako Ingress backend; Stream na managed Kafka (MSK, Confluent Cloud).

5. Spring Cloud AWS w tym obrazku

io.awspring.cloud nie zastępuje Gateway ani Stream — uzupełnia:

  • SQS/SNS — kolejki managed zamiast self-hosted Rabbit (Stream ma binder Kafka; SQS przez listener SCA)
  • Parameter Store / Secrets Manager — config bez Config Server (spring.config.import)
  • S3 — załączniki w evencie (w Kafka tylko URL, nie plik)

RDS/Postgres — zwykły JDBC + Hibernate, bez startera SCA. Cognito — OAuth2 issuer dla Gateway Resource Server.

Typowe błędy architektury stacku

  1. Wszystko synchroniczne Feignem. Kaskada timeoutów i tight coupling — event tam, gdzie nie potrzebujesz odpowiedzi od razu.
  2. Gateway + Eureka + K8s naraz. Trzy źródła prawdy o instancjach — wybierz jeden model discovery.
  3. Config Server + Parameter Store + ConfigMap. Trzy miejsca na properties — jeden kanał configu per środowisko.
  4. Brak kontraktów przy niezależnym deployu. Zielony build, czerwony prod — SCC taniej niż E2E na stagingu.
  5. Logika biznesowa w filtrach Gateway. Gateway routuje i auth; domena zostaje w serwisach.
  6. Stream bez DLQ i idempotencji. At-least-once = duplikaty — consumer musi to obsłużyć.
  7. Resilience4j wszędzie bez metryk. CB bez obserwowalności — nie wiesz, kiedy open jest uzasadniony.
  8. Spring Cloud „bo korporacja” w 2-serwisowym systemie. Operacyjny koszt brokera, config servera, gateway — YAGNI.
  9. Testy tylko E2E na pełnym stacku. Wolne, flaky — piramida: unit → contract → kilka E2E.
  10. Wersje Boot i Cloud nie z jednego BOM. spring-cloud-dependencies w dependencyManagement — inaczej NoSuchMethodError w runtime.
