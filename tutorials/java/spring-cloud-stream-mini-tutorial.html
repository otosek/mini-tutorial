Część 0 — Fundamenty

Spring Cloud Stream (SCS) to abstrakcja nad brokerami wiadomości (Kafka, RabbitMQ, Pulsar…). Piszesz logikę w Springu (Supplier, Consumer, Function) — binder mapuje to na konkretny broker bez zmiany kodu przy wymianie Kafka → Rabbit.

OrderService Kafka topic: order-created @Bean Consumer<OrderCreated> ←── binder ──→ partition 0..N process(event) @Bean Supplier<OrderShipped> ── binder ──→ topic: order-shipped
PojęcieZnaczenie
BinderImplementacja dla brokera — spring-cloud-stream-binder-kafka
BindingPołączenie między beanem a destination (topic / exchange)
DestinationNazwa topicu (Kafka) lub exchange (Rabbit)
Consumer groupGrupa odbiorców — każda wiadomość raz na grupę (Kafka)
Message<T>Payload + nagłówki (correlation-id, tenant, typ)
SCS 3+ — model funkcyjny

Starszy model (@Input / @Output, @EnableBinding) jest deprecated. Nowe projekty: beany java.util.function.Supplier, Consumer, Function + konfiguracja YAML spring.cloud.stream.bindings.

1. Kiedy używać / kiedy nie

Bierz Spring Cloud StreamOlej — użyj innego
Event-driven między mikroserwisami Spring, możliwa zmiana brokera Tylko Kafka, zespół zna ją dobrze — @KafkaListener / Spring for Apache Kafka prostsze
Jednolity model publish/subscribe w całym klastrze Spring Wysoka przepustowość, niskie latency — czysty klient Kafka z ręcznym tuningiem
Testy z TestChannelBinder / embedded broker Strumienie Kinesis — osobny binder AWS (Spring Cloud AWS 4.x)
Kontrakty messaging (Spring Cloud Contract) Request-reply synchroniczny — Feign/REST wystarczy

Starter Kafka: spring-cloud-starter-stream-kafka. Rabbit: spring-cloud-starter-stream-rabbit. Jeden binder na aplikację — nie mieszaj Kafka i Rabbit w jednym procesie bez wyraźnej potrzeby.

2. Model funkcyjny — Supplier, Consumer, Function

@Bean
public Consumer<OrderCreated> handleOrderCreated() {
  return event -> orderProcessor.process(event);
}

@Bean
public Supplier<OrderShipped> publishShipped() {
  return () -> shipmentQueue.poll();  // lub Flux — patrz niżej
}

@Bean
public Function<OrderCreated, InvoiceGenerated> orderToInvoice() {
  return order -> invoiceService.generate(order);
}

Konfiguracja bindingów — nazwa beana = nazwa bindingu (domyślnie):

spring:
  cloud:
    stream:
      bindings:
        handleOrderCreated-in-0:
          destination: order-created
          group: order-service
        publishShipped-out-0:
          destination: order-shipped
        orderToInvoice-in-0:
          destination: order-created
        orderToInvoice-out-0:
          destination: invoice-generated

Konwencja: {beanName}-in-0 / -out-0 (indeks gdy wiele wejść/wyjść). group — consumer group Kafka; bez grupy każda instancja dostaje kopię (broadcast).

Reactive (Flux)

@Bean
public Function<Flux<OrderCreated>, Flux<OrderProcessed>> processOrders() {
  return flux -> flux
      .map(orderProcessor::process)
      .onErrorContinue((e, o) -> log.warn("skip {}", o, e));
}

Flux — backpressure i batching; wymaga reaktywnego bindera. Dla prostych eventów wystarczy Consumer<T>.

3. Binder Kafka — konfiguracja

spring:
  cloud:
    stream:
      kafka:
        binder:
          brokers: localhost:9092
          auto-create-topics: false   # prod: topic z góry (partycje, retention)
        bindings:
          handleOrderCreated-in-0:
            consumer:
              ack-mode: manual
              enable-dlq: true
              dlq-name: order-created.dlq
      bindings:
        handleOrderCreated-in-0:
          consumer:
            max-attempts: 3
            back-off-initial-interval: 1000
UstawienieEfekt

Pułapka: concurrency=10 na topic z 3 partycjami — 7 wątków bez pracy. Partycje = górny limit równoległości w jednej grupie.

4. Nagłówki, tenant, idempotencja

Payload w JSON + metadane w nagłówkach:

@Bean
Consumer<Message<OrderCreated>> handleWithHeaders() {
  return message -> {
    String tenant = message.getHeaders().get("X-Tenant-Id", String.class);
  String correlationId = message.getHeaders().get("correlationId", String.class);
    TenantContext.set(tenant);
    try {
      process(message.getPayload());
    } finally {
      TenantContext.clear();
    }
  };
}

Propagacja z HTTP → Kafka przy publikacji:

@Bean
Supplier<Message<OrderCreated>> emitOrder() {
  return () -> MessageBuilder
      .withPayload(buildOrder())
      .setHeader("X-Tenant-Id", TenantContext.get())
      .setHeader("correlationId", MDC.get("correlationId"))
      .build();
}

Idempotencja: consumer może dostać tę samą wiadomość ponownie (at-least-once). Sprawdź eventId w DB / Redis przed side-effectem. Nagłówek idempotency-key to konwencja, nie magia brokera.

Ordering: kolejność tylko w obrębie jednej partycji. Ten sam partition-key (np. orderId) → ta sama partycja.

5. Błędy, retry, DLQ

Domyślnie: wyjątek w Consumer → retry (wg max-attempts) → opcjonalnie DLQ (dead-letter topic).

spring.cloud.stream.kafka.bindings.handleOrderCreated-in-0.consumer:
  enable-dlq: true
  dlq-name: order-created.dlq
  auto-commit-on-error: false
Wiadomość → consumer (błąd) → retry 1..N → DLQ topic (order-created.dlq) → alert / ręczna analiza / osobny consumer naprawczy

Poison message — zawsze pada na deserializacji lub logice: bez DLQ blokuje partycję (lagi rosną). Włącz DLQ na prod.

Retry a idempotencja: retry + brak idempotencji = podwójne przetworzenie. Projektuj consumer jako idempotentny albo używaj transakcji outbox.

Ręczna obsługa:

@Bean
Consumer<OrderCreated> safeConsumer() {
  return event -> {
    try {
      process(event);
    } catch (TransientException e) {
      throw e;  // retry
    } catch (PermanentException e) {
      dlqPublisher.send(event);  // nie retry — logika biznesowa
    }
  };
}

Typowe błędy

  1. Brak group na consumerze. Każda instancja czyta wszystko — duplikaty i brak load balancingu.
  2. Więcej instancji niż partycji. Nadmiarowe konsumenty stoją bezczynnie — planuj partycje przy tworzeniu topicu.
  3. Stary model @EnableBinding. Deprecated — migracja na funkcje + YAML bindings.
  4. Deserializacja bez content-type. SerializationException — ustaw application/json i zgodne DTO.
  5. Duży payload w Kafka. Limit domyślnie ~1 MB — obrazy/PDF do S3, w evencie tylko referencja.
  6. Brak DLQ na prod. Jedna zła wiadomość = lag całej partycji.
  7. Retry na błąd permanentny. Nieskończone ponawianie — idź od razu do DLQ.
  8. Tenant tylko w payloadzie. Łatwo zapomnieć w publisherze — nagłówek + interceptor spójny z HTTP/Feign.
  9. Transakcja DB + publish bez outbox. Commit DB i send do Kafka nie są atomowe — wzorzec outbox lub transactional messaging.
  10. SCS „bo mikroserwisy” przy 2 wiadomościach dziennie. Overhead operacyjny brokera — czasem wystarczy tabela outbox + scheduler.
