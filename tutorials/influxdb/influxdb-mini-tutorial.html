Część 0 — Fundamenty TSDB

InfluxDB — baza szeregów czasowych (time-series database). Optymalizowana pod ciągły strumień punktów z timestampem: metryki serwerów, IoT, APM, logi liczbowe. Nie zastępuje Postgresa jako źródła prawdy o encjach biznesowych.

Kiedy InfluxDBKiedy coś innego
Wysoka częstotliwość zapisu metryk (tysiące punktów/s)Transakcje, relacje, ACID → Postgres
Agregacje w oknach czasowych (średnia/min/max per 5 min)Full-text search → Elasticsearch
Retencja z automatycznym wygaszaniem starych danychPull model + service discovery → Prometheus
Dashboardy operacyjne (Grafana)Jedna liczba „uptime” bez historii → cache / Redis
Seria czasowa (time series)

Unikalna kombinacja measurement + tagów — wszystkie punkty tej serii mają ten sam zestaw tagów. Wysoka cardinality tagów = wiele serii = większy koszt pamięci i indeksów.

Pułapka: InfluxDB nie jest „Postgres z timestampem”. Brak JOINów w stylu SQL (w 2.x Flux), brak transakcji wielowierszowych — projektuj pod write-heavy + time-range queries.

Część 2 — Model danych i line protocol

Wszystkie wersje przyjmują dane przez line protocol — tekstowy format, jeden punkt = jedna linia.

<measurement>,<tag_key>=<tag_value> <field_key>=<value> <timestamp>

cpu,host=server01,region=eu-west usage=0.64,idle=0.36 1704067200000000000
ElementRegułaPrzykład
MeasurementNazwa tabeli logicznejcpu, http_request
TagsMetadane indeksowane — string, niska cardinalityhost, region, status
FieldsWartości liczbowe / bool — nie indeksowaneusage=0.64, ok=true
TimestampDomyślnie nanosekundy; opcjonalny przy write APIUnix ns lub ms (zależy od API)
Tags vs fields — najważniejsza decyzja projektowa

Tag = kolumna, po której filtrowasz i grupujesz (host, service, env). Field = liczba, którą agregujesz (latency, bytes). User ID, request ID, URL → zwykle field lub osobny log store — nie tag.

Cardinality

Liczba unikalnych kombinacji tagów. 10 hostów × 5 regionów = 50 serii — OK. 1M user_id jako tag = katastrofa pamięciowa. Pułapka: „wrzucę wszystko w tagi, bo Grafana łatwo grupuje”.

Mapowanie na Flux / storage 2.x

W bucketu dane trafiają do tabeli _measurement z kolumnami tagów i _field / _value. Jeden punkt z dwoma fields w LP = dwie wiersze w storage.

Część 3 — Retention i downsampling

Retention policy — jak długo dane żyją w buckecie. Po TTL punkt jest usuwany (nie „archiwizowany” domyślnie). W 2.x ustawiasz przy tworzeniu bucketu lub przez API.

# Bucket z retencją 30 dni (CLI influx 2.x)
influx bucket create -n metrics_raw -o myorg -r 30d

# Bucket na dane zagregowane — 1 rok
influx bucket create -n metrics_1h -o myorg -r 365d

Downsampling (tasks)

Typowy wzorzec: raw 7d (pełna granularność) → agregat 5m/1h w drugim buckecie na rok. Task Flux uruchamiany co minutę:

option task = {
  name: "downsample_cpu_5m",
  every: 1m,
}

from(bucket: "metrics_raw")
  |> range(start: -task.every)
  |> filter(fn: (r) => r._measurement == "cpu")
  |> aggregateWindow(every: 5m, fn: mean, createEmpty: false)
  |> to(bucket: "metrics_5m", org: "myorg")

Pułapka: downsampling bez createEmpty: false może generować puste okna; agreguj tylko potrzebne measurements — task na cały bucket kosztuje CPU.

Część 4 — Zapis danych

CLI i HTTP API (2.x)

# Plik LP
cpu,host=a usage=0.5 1704067200000000000
cpu,host=b usage=0.8 1704067200000000000

influx write -b metrics_raw -o myorg -f points.lp --precision ns

# HTTP (curl)
curl -X POST "http://localhost:8086/api/v2/write?org=myorg&bucket=metrics_raw&precision=ns" \
  --header "Authorization: Token YOUR_TOKEN" \
  --data-binary "cpu,host=a usage=0.5"

Java — klient 2.x

// Maven: com.influxdb:influxdb-client-java (wersja ≈ serwer)
InfluxDBClient client = InfluxDBClientFactory.create(
    "http://localhost:8086",
  "YOUR_TOKEN",
  "myorg",
  "metrics_raw");

try (WriteApi writeApi = client.makeWriteApi()) {
  Point point = Point.measurement("cpu")
      .addTag("host", "server01")
      .addField("usage", 0.64)
      .time(Instant.now(), WritePrecision.NS);
  writeApi.writePoint(point);
}
client.close();

makeWriteApi() — batching asynchroniczny; przy shutdown zamknij klienta, żeby nie stracić bufora. Dla synchronicznego: client.getWriteApiBlocking().writePoint(...).

Batch write

List<Point> batch = List.of(
    Point.measurement("cpu").addTag("host", "a").addField("usage", 0.5),
    Point.measurement("cpu").addTag("host", "b").addField("usage", 0.8)
);
writeApi.writePoints(batch);

Część 5 — Odczyt i agregacje (Flux)

Flux — funkcjonalny pipeline (2.x). Każde zapytanie zaczyna od źródła i zakresu czasu. W UI: Data Explorer → skrypt Flux.

from(bucket: "metrics_raw")
  |> range(start: -1h)
  |> filter(fn: (r) => r._measurement == "cpu")
  |> filter(fn: (r) => r._field == "usage")
  |> filter(fn: (r) => r.host == "server01")
  |> aggregateWindow(every: 1m, fn: mean, createEmpty: false)
  |> yield(name: "mean")
Funkcja FluxCo robi
from(bucket:)Źródło danych
range(start:, stop:)Filtr czasu — zawsze wymagany w praktyce
filter(fn:)Warunek na kolumny (r.host, r._value)
aggregateWindowOkna czasowe: mean, sum, max, count
group(columns:)Grupowanie przed agregacją (per host)
last() / max()Redukcja w grupie
to(bucket:)Zapis wyniku (task / ETL)

InfluxQL (1.x i compat 2.x)

SELECT mean("usage") FROM "cpu"
WHERE time > now() - 1h AND "host" = 'server01'
GROUP BY time(1m) fill(none)

InfluxQL jest znajome z SQL, ale Flux daje pełną moc pipeline (join streamów, pivot). W 2.x preferuj Flux dla tasks i nowych kodów; InfluxQL tylko przy legacy.

Java — query Flux

String flux = """
  from(bucket: \"metrics_raw\")
    |> range(start: -1h)
    |> filter(fn: (r) => r._measurement == \"cpu\")
    |> last()
""";

List<FluxTable> tables = client.getQueryApi().query(flux, "myorg");
for (FluxTable table : tables) {
  for (FluxRecord record : table.getRecords()) {
    System.out.println(record.getTime() + " " + record.getValue());
  }
}

Część 6 — Telegraf · Grafana · alerting

Host / kontener / aplikacja → Telegraf (zbiera metryki, output influxdb_v2) → InfluxDB (bucket) → Grafana (datasource InfluxDB — Flux lub InfluxQL)

Telegraf — agent z pluginami (cpu, mem, disk, nginx, prometheus scrape). Konfiguracja outputs.influxdb_v2 z URL, token, bucket, org.

[[outputs.influxdb_v2]]
  urls = ["http://influxdb:8086"]
  token = "$INFLUX_TOKEN"
  organization = "myorg"
  bucket = "metrics_raw"

Grafana: datasource typu InfluxDB — w 2.x wybierz Flux, podaj org i token. Dashboardy: time series, stat, heatmap. Zapytania z $__interval dla auto-window.

Alerting (2.x): check Flux + notification endpoint (Slack, PagerDuty). Alternatywa: alerty w Grafana na datasource InfluxDB — jeden punkt prawdy dla dashboardów i alertów.

Typowe błędy

  • User ID / session ID jako tag — eksplozja cardinality; użyj field lub innego store.
  • Wysokie-cardinality tag „na wszystko” — każdy unikalny URL, order_id, trace_id w tagach.
  • Brak retention — bucket bez TTL → dysk rośnie bez końca; ustaw przy tworzeniu.
  • Query bez range() w Flux — skan całego bucketu, timeout lub OOM na prod.
  • Mieszanie precision timestamp — ns vs ms vs s w LP bez precision w API → złe daty na wykresach.
  • Field jako string z liczbą — LP nie ma typów jak SQL; konsekwentnie float/int dla agregacji.
  • Zapisywanie wszystkiego w jednym measurement — trudne filtrowanie; rozdziel domeny (cpu, http, queue).
  • Async WriteApi bez flush przy shutdown — utrata ostatniego batcha przy restart poda.
  • Token admin w aplikacji — token write-only na jeden bucket, rotacja w sekretach.
  • Downsampling na żywym raw bez drugiego bucketu — nadpisanie granularności bez kopii zapasowej.
