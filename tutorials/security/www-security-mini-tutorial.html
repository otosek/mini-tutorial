Mapa zagrożeń

Aplikacja WWW = przeglądarka + API + szablony + zewnętrzne URL. Atak trafia w **wejście użytkownika**, **nagłówki HTTP**, **politykę origin** albo **logikę serwera wykonującą requesty/szablony**.

AtakGdzieCel atakującego
XSSPrzeglądarka ofiaryWykonać JS w kontekście domeny (cookies, tokeny, DOM)
CSRFPrzeglądarka ofiaryWysłać niechciane żądanie z sesją/cookies ofiary
CORSPolityka przeglądarki(Źle skonfigurowany) udostępnić API innym originom

XSS — Cross-Site Scripting

Klient Wstrzyknięcie JavaScript wykonywanego w przeglądarce użytkownika w kontekście Twojej domeny.

TypMechanizmPrzykład
ReflectedPayload w URL/formularzu, natychmiast w odpowiedzi?q=<script>…</script>
StoredPayload zapisany w DB, widoczny dla innychKomentarz autora z JS w polu bio
DOM-basedJS aplikacji zapisuje niebezpieczne dane do DOMinnerHTML = location.hash

Obrona

  • Encoding przy output — HTML entity dla treści, JS escape w atrybutach
  • React domyślnie escapuje JSX — pułapka: dangerouslySetInnerHTML
  • CSP — ogranicza inline script (defense in depth)
  • HttpOnly cookies — JS nie odczyta session cookie (nie chroni przed akcjami w DOM)
// ŹLE — React authors: bio z API bez sanityzacji
<div dangerouslySetInnerHTML={{ __html: author.bio }} />

// DOBRZE — tekst jako children (auto-escape)
<p>{author.bio}</p>

// DOBRZE — jeśli HTML konieczny: DOMPurify przed renderem
<div dangerouslySetInnerHTML={{ __html: DOMPurify.sanitize(author.bio) }} />
Pułapka rekrutacyjna

XSS ≠ SQL injection. XSS działa w przeglądarce; nie wymaga dostępu do bazy — wystarczy, że aplikacja wyświetli niezaufane dane.

CSRF — Cross-Site Request Forgery

Klient Złośliwa strona wysyła żądanie do Twojego API **z przeglądarki zalogowanej ofiary** (cookies sesji lecą automatycznie).

<!-- evil.com — formularz auto-submit -->
<form action="https://api.authors.example/authors/1" method="POST">
  <input name="name" value="Hacked" />
</form>
<script>document.forms[0].submit()</script>

Obrona

  • CSRF token — synchronizer token w formularzu/nagłówku (X-CSRF-TOKEN); Spring Security domyślnie dla sesji
  • SameSite cookies — SameSite=Lax lub Strict ogranicza cross-site POST
  • Custom header — np. X-Requested-With lub Bearer token — proste POST z formularza HTML nie doda nagłówka
  • OAuth / Bearer w Authorization — nie leci automatycznie jak cookie (SPA z localStorage ma inne ryzyko XSS)
CSRF vs XSS

CSRF wykorzystuje zaufaną sesję bez znajomości tokenu. XSS może ukraść token CSRF i wtedy CSRF protection pada — stąd CSP + XSS prevention są kluczowe razem.

CORS — Cross-Origin Resource Sharing

Nagłówki Mechanizm **przeglądarki**, nie „firewall”. Serwer mówi, które **originy** mogą czytać odpowiedź JS z innej domeny.

NagłówekZnaczenie
Access-Control-Allow-OriginDozwolony origin (https://app.example) — unikaj * z credentials
Access-Control-Allow-Credentialstrue — cookies w cross-origin fetch
Access-Control-Allow-MethodsGET, POST, PUT…
Access-Control-Allow-HeadersAuthorization, Content-Type…

Preflight: żądania „nieproste” (PUT, custom headers) — przeglądarka wysyła OPTIONS przed właściwym requestem.

// React authors — fetch z innego portu (dev: localhost:5173 → :8080)
fetch("http://localhost:8080/api/authors", {
  credentials: "include",  // cookies — wymaga konkretnego ACAO, nie *
  headers: { Authorization: "Bearer …" }
});

// Spring — źle: Allow-Origin: * + credentials: true (przeglądarka odrzuci)
// Spring — dobrze: whitelist originów z konfiguracji
Pułapka

CORS **nie blokuje** requestu curl/Postman — tylko JS w przeglądarce. Brak CORS ≠ bezpieczeństwo API; autoryzacja musi być po stronie serwera.

CSP — Content Security Policy

Nagłówek Whitelist źródeł: skryptów, stylów, obrazków, ramek. Główna obrona przed inline XSS i ładowaniem złośliwych CDN.

Content-Security-Policy:
  default-src 'self';
  script-src 'self' https://cdn.trusted.com;
  style-src 'self' 'unsafe-inline';
  img-src 'self' data: https:;
  frame-ancestors 'none';
  base-uri 'self';
DyrektywaPo co
script-srcSkąd wolno JS — unikaj 'unsafe-inline' w produkcji
nonce-XYZ / hashDozwolony konkretny inline script (Vite/React build)
frame-ancestorsOchrona przed clickjacking (zamiast starego X-Frame-Options)
report-uri / report-toLogowanie naruszeń CSP

Wdrożenie: najpierw Content-Security-Policy-Report-Only, potem enforce. React dev często wymaga luźniejszej polityki — produkcja: strict.

SSRF — Server-Side Request Forgery

Serwer Atakujący podaje URL; **backend** wykonuje HTTP request — np. do 169.254.169.254 (metadata AWS), wewnętrznego admin panelu, Redis.

// Endpoint: "Pobierz okładkę książki z URL"
GET /api/fetch-cover?url=http://169.254.169.254/latest/meta-data/

// Atakujący czyta token IAM / skanuje sieć wewnętrzną

Obrona

  • Whitelist dozwolonych hostów/schematów (https tylko, bez IP prywatnych)
  • Blokada DNS rebinding — resolve + sprawdź IP przed requestem
  • Brak przekazywania surowego URL od użytkownika — proxy z katalogiem CDN
  • Segmentacja sieci — aplikacja bez routingu do metadanych chmury

SSTI — Server-Side Template Injection

Serwer User input trafia do **silnika szablonów** jako kod szablonu, nie jako dane — możliwe **RCE** (Remote Code Execution).

// Thymeleaf / Freemarker — źle: template z parametru
templateEngine.process(userSuppliedTemplate, context);

// Freemarker — payload (przykład):
${"freemarker.template.utility.Execute"?new()("id")}

// DOBRZE: szablon statyczny na dysku, user data tylko w zmiennych kontekstu
model.addAttribute("authorName", escapeHtml(input));

Dotyczy: Thymeleaf, Freemarker, Velocity, Jinja2, Twig. **Nigdy** nie kompiluj szablonu z inputu użytkownika. W React (authors) SSTI nie występuje — szablony to JSX po stronie builda; ryzyko to XSS, nie SSTI.

Typowe błędy

  1. Myślenie, że CORS chroni API przed atakami spoza przeglądarki
  2. Access-Control-Allow-Origin: * razem z credentials: include
  3. Poleganie wyłącznie na CSRF token bez SameSite i bez ochrony przed XSS
  4. dangerouslySetInnerHTML bez sanityzacji (stored XSS w bio autora)
  5. CSP z 'unsafe-inline' 'unsafe-eval' — prawie jak brak CSP
  6. Traktowanie HttpOnly jako ochrony przed XSS (chroni cookie, nie akcje w sesji)
  7. Endpoint „fetch URL” bez walidacji — klasyczny SSRF
  8. Renderowanie błędów stack trace z parametrami użytkownika (reflected XSS)
  9. Dynamiczne szablony e-mail/raportów z inputu użytkownika (SSTI)
  10. JWT w localStorage + brak CSP — jeden XSS = kradzież tokenu

Pytania rekrutacyjne — krótkie odpowiedzi

Junior / Mid — 1–15

1. Czym różni się XSS od SQL injection?

XSS wykonuje JS w przeglądarce ofiary w kontekście aplikacji. SQLi manipuluje zapytaniem do bazy po stronie serwera.

2. Co to reflected XSS?

Payload w żądaniu (URL, formularz) jest natychmiast odbijany w odpowiedzi HTML bez trwałego zapisu.

3. Co to stored XSS?

Złośliwy skrypt zapisany w bazie (np. komentarz) i serwowany innym użytkownikom.

4. Dlaczego React domyślnie łagodzi XSS?

JSX escapuje wartości wstawiane jako children — znaki specjalne HTML stają się tekstem, nie tagami.

5. Po co HttpOnly na cookie sesji?

JavaScript w przeglądarce nie może odczytać takiego cookie — utrudnia kradzież sesji przez XSS.

6. Czym jest CSRF?

Wymuszenie na przeglądarce ofiary wysłania autentykowanego żądania do aplikacji bez wiedzy użytkownika.

7. Jak działa CSRF token?

Serwer generuje tajny token powiązany z sesją; żądanie musi go zawierać — zewnętrzna strona go nie zna.

8. Co robi SameSite=Lax?

Cookie nie jest wysyłane przy cross-site POST (z wyjątkami nawigacji top-level GET) — ogranicza CSRF.

9. Czym jest CORS?

Mechanizm przeglądarki: serwer deklaruje nagłówkami, czy JS z danego origin może odczytać odpowiedź cross-origin.

10. Czy brak CORS blokuje curl?

Nie. CORS dotyczy tylko polityki same-origin w przeglądarce dla JavaScript.

11. Co to preflight OPTIONS?

Wstępne żądanie przeglądarki sprawdzające, czy serwer zezwala na metodę/nagłówki cross-origin.

12. Do czego służy CSP?

Nagłówek HTTP ograniczający źródła skryptów, stylów, ramek — ogranicza skutki XSS i supply-chain.

13. Czym jest SSRF?

Atak zmuszający serwer do wykonania HTTP requestu pod kontrolą atakującego — często do zasobów wewnętrznych.

14. Czym jest SSTI?

Wstrzyknięcie składni silnika szablonów w input użytkownika, co może prowadzić do wykonania kodu na serwerze.

15. XSS, CSRF czy oba — kradzież sesji cookie HttpOnly?

Bezpośredniej kradzieży HttpOnly cookie przez JS nie ma (XSS nie „czyta” cookie). XSS może jednak wykonywać akcje w imieniu użytkownika w tej samej sesji.

Mid / Senior — 16–30

16. DOM-based XSS — przykład?

document.getElementById('out').innerHTML = location.hash.slice(1) — payload w hash bez udziału serwera.

17. Dlaczego Bearer token w localStorage + XSS = game over?

XSS może odczytać localStorage i wysłać token atakującemu — brak HttpOnly. Alternatywa: cookie HttpOnly + BFF lub krótko żyjące tokeny.

18. CSRF przy REST API ze stateless JWT w Authorization?

Klasyczny CSRF na cookie nie dotyczy, jeśli token tylko w nagłówku (JS musi go dodać). Ryzyko wraca przy cookie-based session lub hybrid.

19. Dlaczego ACAO: * nie działa z credentials?

Specyfikacja CORS zabrania — przeglądarka wymaga jawnego origin przy Access-Control-Allow-Credentials: true.

20. CSP nonce — kiedy?

Gdy potrzebny inline script w HTML — serwer generuje losowy nonce per request i dodaje do script-src i tagu script.

21. frame-ancestors vs X-Frame-Options?

frame-ancestors w CSP jest nowsze, elastyczne (wiele originów); X-Frame-Options to legacy (DENY/SAMEORIGIN).

22. SSRF do 169.254.169.254 — co to?

Link-local metadata cloud (AWS/GCP/Azure) — często credentials/role; klasyczny cel SSRF w chmurze.

23. Jak bronić endpoint „import from URL”?

Whitelist hostów, blokada IP prywatnych/link-local, timeout, brak redirectów do wewnętrznych adresów, osobna sieć egress.

24. SSTI vs XSS — różnica?

SSTI: wykonanie w silniku szablonów na serwerze (RCE). XSS: wykonanie JS w przeglądarce ofiary.

25. Thymeleaf — bezpieczne vs niebezpieczne użycie inputu?

Bezpieczne: . Ryzykowne: parsowanie fragmentu szablonu z inputu użytkownika jako template source.

26. Double Submit Cookie — CSRF?

Token w cookie i w body/header — serwer porównuje. Wymaga, by atakujący nie mógł ustawić cookie (SameSite pomaga).

27. CORS misconfiguration — reflected origin?

Serwer odbija Origin requestu w ACAO bez walidacji — każda strona może czytać odpowiedzi z credentials.

28. Content-Type i CSRF na JSON API?

Form POST ma application/x-www-form-urlencoded — JSON wymaga fetch z JS; prosty CSRF formularzem nie wyśle JSON (choć nie polegaj tylko na tym).

29. CSP report-only — po co?

Monitorowanie naruszeń bez blokowania — migracja ze starych inline scriptów bez awarii produkcji.

30. Jak XSS obchodzi CSRF token?

Skrypt w domenie ofiary odczytuje token z DOM/meta/cookie (jeśli nie HttpOnly) i dołącza do fetch — stąd priorytet: zapobieganie XSS.

Pułapki — 31–40

31. „Mamy CORS wyłączony — API bezpieczne”?

Fałsz dla ataków poza przeglądarką i dla błędnej autoryzacji. CORS to nie autentykacja.

32. CSP unsafe-inline — kiedy akceptowalne?

Raczej dev/legacy; produkcja powinna iść w nonce/hash. unsafe-inline niweczy większość korzyści CSP.

33. CSRF na GET usuwającym zasób?

Tak — jeśli GET zmienia stan i cookie leci automatycznie. REST: mutacje tylko POST/PUT/DELETE + CSRF/token.

34. SSRF przez DNS rebinding?

Host najpierw resolve do publicznego IP, potem TTL=0 i resolve do 127.0.0.1 — obejście blacklist po hostname. Obrona: pin IP po resolve.

35. SSTI w PDF/email template z user data?

Tak — jeśli engine traktuje ${…} w treści od użytkownika jako kod. Używaj placeholderów danych, nie składni engine w input.

36. Angular/React — czy automatycznie chronią przed DOM XSS?

Domyślny binding tak; nie chroni: innerHTML, bypassSanitizer, href z javascript:, third-party widgets.

37. SameSite=None — kiedy i ryzyko?

Cross-site cookies (embedded, OAuth flows) — wymaga Secure. Zwiększa powierzchnię CSRF bez dodatkowych tokenów.

38. CORS preflight cache — Max-Age?

Przeglądarka cache'uje wynik OPTIONS — zła konfiguracja utrzymuje się do wygaśnięcia cache preflight.

39. Subresource Integrity (SRI) a CSP?

SRI weryfikuje hash CDN script — CSP ogranicza skąd wolno ładować. Razem: defense in depth przy zewnętrznych skryptach.

40. Jeden ranking: co wdrożyć pierwsze w greenfield SPA + API?

Autoryzacja server-side, walidacja input, output encoding, CSP + HttpOnly/SameSite cookies lub Bearer z krótkim TTL, CSRF jeśli cookie session, brak SSRF w integracjach URL, statyczne szablony serwerowe.
