0. Fundamenty — co to znaczy dla Ciebie

ISO/IEC 27001 to norma na system zarządzania bezpieczeństwem informacji (ISMS). Organizacja nie „certyfikuje kodu” — certyfikuje proces: polityki, role, ryzyko, dowody audytowe. Ty jako programista API dostarczasz implementację kontrolek i ślad w repozytorium / pipeline, który audytor może prześledzić.

Pojęcia, które usłyszysz na co dzień

SoA (Statement of Applicability) — lista kontrolek z Załącznika A: które obowiązują, jak są spełnione, uzasadnienie wyłączeń. Jeśli A.8.28 jest „Applicable”, secure coding nie jest opcjonalny.
Risk treatment — ticket z nowym endpointem powinien mieć ocenę ryzyka (dane osobowe? płatności? integracja zewnętrzna?).
Dowód (evidence) — zielony pipeline, log merge z approval, skan CVE, wpis w changelogu deployu.

Jedno zdanie: norma wymaga, żeby każda zmiana w API była przewidywalna, autoryzowana, przetestowana i audytowalna — a Ty implementujesz to w ticketach, PR-ach i jobach CI.

Załącznik A grupy A.8 — Rozwój to Twój główny „kontrakt” z security/compliance. Reszta normy (dostęp fizyczny, HR) dotyczy Ciebie pośrednio; poniższe — bezpośrednio.

Pułapka: „Mamy ISO, więc security robi zespół GRC” — audytor pyta Ciebie, skąd wiesz, że endpoint DELETE /users/{id} nie pozwala na BOLA. Kontrolka bez implementacji = finding.

2. Mapa SDLC — Twój tydzień w projekcie z ISO

Backlog / refinement
  → klasy danych, AC bezpieczeństwa, zależności (A.8.26)
Analiza / design API (OpenAPI)
  → auth, rate limit, model błędów (A.8.27)
Implementacja + unit/integration tests (A.8.28, A.8.29)
PR → CI (SAST, deps, testy) → code review (A.8.32)
Merge → artefakt (SBOM) → deploy stage → smoke / DAST
Change approval → prod (A.8.31, A.8.32)
Monitoring, logi, incydenty (dowód operacyjny ISMS)

Frontend schodzi na drugi plan: i tak walidujesz kontrakt API — to serwer musi egzekwować autoryzację, limity i spójność danych. UI może być złośliwy; API nie może ufać klientowi.

3. Analiza i wymagania — zanim napiszesz kod

3.1 Refinement ticketu

  • Jakie dane przetwarza endpoint (public / internal / confidential / special category)?
  • Kto może wywołać operację (rola, scope OAuth, tenant)?
  • Czy jest idempotencja / rate limiting / audyt (kto, kiedy, co)?
  • Czy integracja zewnętrzna wymaga allowlist URL (SSRF)?
  • Czy zmiana łamie kontrakt — wersjonowanie API (/v2, nagłówki)?

3.2 Threat modeling (lekki format STRIDE dla API)

STRIDEPytanie przy REST
SpoofingCzy token / mTLS jednoznacznie identyfikuje klienta?
TamperingCzy body i parametry są walidowane i podpisane tam, gdzie trzeba?
RepudiationCzy mutacje mają correlation-id i audit log?
Information disclosureCzy 404 vs 403 nie wycieka istnienia zasobu? Stack trace tylko w dev?
DoSLimity rozmiaru payload, timeout, pagination max?
ElevationCzy {id} w URL jest sprawdzany względem tożsamości (BOLA)?

Output analizy zapisz w ticketu lub ADR — to **evidence** dla A.8.25/A.8.26.

4. Kodowanie API — secure coding w praktyce

4.1 Wejście i wyjście

// DOBRZE — walidacja DTO + jawna polityka błędów (Spring)
@PostMapping("/orders")
public OrderResponse create(@Valid @RequestBody CreateOrderRequest req,
                            @AuthenticationPrincipal Jwt jwt) {
  var tenantId = tenantResolver.from(jwt);
  return orderService.create(tenantId, req); // serwis sprawdza ownership
}

// ŹLE — ID z URL bez sprawdzenia właściciela (BOLA / API1)
@GetMapping("/orders/{orderId}")
public Order get(@PathVariable UUID orderId) {
  return orderRepo.findById(orderId).orElseThrow(); // każdy zna UUID → cudze zamówienie
}

4.2 Sekrety i konfiguracja (ISO + Twelve-Factor III)

  • Zero kluczy API, connection stringów i JWT signing keys w Git — nawet w „tymczasowych” branchach.
  • Vault / Secrets Manager / sealed secrets w K8s; lokalnie .env w .gitignore.
  • Logi: maskowanie tokenów, numerów kart, PESEL; structured logging z trace_id.

4.3 Zależności (A.8.28 + supply chain)

Lockfile obowiązkowy (pom.xml + lock, Gradle lockfile). Każdy upgrade biblioteki = PR z wynikiem skanu CVE. Pułapka: „tylko patch Springa” bez uruchomienia testów integracyjnych auth.

4.4 OpenAPI jako kontrakt

Spec trzymany w repo, reviewowany jak kod. W CI: breaking-change detection (np. openapi-diff). Dokumentacja nie może obiecywać słabszego auth niż implementacja.

5. Code review, merge i zarządzanie zmianami

Kontrolka A.8.32 wymaga kontrolowanych zmian — w Git flow oznacza to **branch protection** i sensowny review, nie formalny „LGTM”.

5.1 Kolejność (spójna z code review w Java)

  1. CI zielone: build, testy, SAST, skan zależności, ewentualnie OpenAPI diff.
  2. Diff vs ticket / AC — czy scope nie wprowadza nieudokumentowanego API?
  3. Warstwa bezpieczeństwa: authZ na każdej ścieżce mutacji, walidacja, brak wrażliwych danych w odpowiedzi.
  4. Testy dowodzą zachowania (w tym negatywne: 401, 403, 422).

5.2 Merge

  • Preferuj squash/merge z numerem ticketu — łatwy audit trail.
  • Dwa approvals dla krytycznych obszarów (auth, płatności, eksport danych) — często zapisane w polityce projektu.
  • Brak merge mimo czerwonego CI „bo tylko mała zmiana” — naruszenie change management.

5.3 Checklist reviewera (API)

  • Czy każdy endpoint ma auth (oprócz jawnych publicznych health)?
  • Czy błędy nie ujawniają stack trace / wewnętrznych ID?
  • Czy mass assignment niemożliwy (DTO bez nadmiarowych setterów)?
  • Czy nowe pola PII mają retencję / pseudonimizację?
  • Czy webhook / callback waliduje podpis i replay?

@Test

Dane testowe: syntetyczne generatory (Faker) lub zanonimizowany dump — **A.8.33**. Kopiowanie prod na laptop bez zgody = poważne naruszenie.

8. Twelve-Factor App a wymagania ISO

12-Factor nie zastępuje ISO — ale **ułatwia dowodzenie** separacji środowisk, kontroli zmian i bezpiecznej konfiguracji. Skrót mapowania dla backendu:

FaktorISO / bezpieczeństwo
I CodebaseJeden źródłowy artefakt → audytowalna linia od commit do deploy (A.8.32)
II DependenciesSBOM, skan CVE — supply chain (A.8.28)
III ConfigSekrety poza repo (A.8.28, A.8.31)
IV Backing servicesProd DB ≠ dev; creds per env
V Build, release, runImmutability — ten sam JAR/image na stage i prod
VI ProcessesStateless API — sesja w Redis/JWT, nie na dysku poda
XI Logsstdout → central SIEM; retention zgodny z polityką
XII Admin processesMigracje DB jako joby z approval, nie ręczne SQL na prod

Szczegóły faktorów: tutorial twelve-factor/twelve-factor-mini-tutorial.html w tym repozytorium.

9. Pipeline CI/CD — brama zgodności

Bez automatyzacji ISO przy skali zespołu się rozpada. Minimalny **secure pipeline** dla serwisu API:

commit → lint/format → unit tests → build artefaktu
      → SAST (Semgrep, CodeQL, Sonar)
      → dependency scan (OWASP DC, Trivy, Snyk)
      → SBOM (CycloneDX / Syft)
      → deploy STAGE (osobne creds)
      → integration + contract tests
      → DAST/API scan (ZAP, schemat OpenAPI)
      → manual / automated approval → PROD
      → smoke + monitoring alert

9.1 Joby, które audytor lubi zobaczyć

  • Branch protection — wymagany status check, brak push na main.
  • Podpis artefaktu (cosign, Sigstore) — integralność supply chain.
  • Infrastructure as Code — Terraform/K8s manifesty w PR z review.
  • Environment secrets — GitHub Environments z approverami na prod.
  • Retention logów pipeline — zgodnie z polityką (np. 1 rok).
# Fragment GitHub Actions — gate na CVE (przykład)
- name: Dependency check
  run: mvn org.owasp:dependency-check-maven:check -DfailBuildOnCVSS=7

9.2 Deploy a A.8.31

Ten sam pipeline promuje build; **różni się tylko config** (factor III). Zakaz: ręczna podmiana pliku JAR na serwerze bez ticketu. Rollback = poprzedni immutable image z rejestru, nie „hotfix na serwerze”.

10. Typowe błędy (ISO + API)

  1. Security jako osobny sprint — bez DoD w każdym tickecie; audyt znajduje luki w rutynowych feature’ach.
  2. AuthN bez AuthZ — „jest JWT” ale brak sprawdzenia właściciela zasobu (API1).
  3. Prod data na dev — naruszenie A.8.33 i RODO naraz.
  4. Sekrety w historii Git — rotacja klucza bez usunięcia z historii = finding do zamknięcia dowodem.
  5. CI tylko „compile” — brak testów auth i skanu zależności; change management bez technicznej bramki.
  6. Logging wszystkiego — body requestu z hasłem w Kibanie; sprzeczne z minimalizacją danych.
  7. OpenAPI nieaktualne — dokumentacja obiecuje publiczny endpoint; implementacja inna (API9).
  8. Wyłączanie testów „tymczasowo” na release — brak dowodu regresji.
  9. Microservice bez centralnego policy — każdy zespół inaczej interpretuje role (API5).
  10. Ignorowanie rate limitów na kosztownych operacjach (raporty, export CSV) — API4 i incydent DoS.
