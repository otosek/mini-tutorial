Część 1 — Fundamenty

1.1 Co to jest Hibernate

Hibernate to implementacja JPA — mapuje klasy Java na tabele SQL i odwrotnie. Ty pracujesz na obiektach; Hibernate generuje SQL, śledzi zmiany i synchronizuje stan z bazą. W Spring Boot zwykle używasz EntityManager (JPA) lub repozytoriów Spring Data, które pod spodem wołają Hibernate.

1.2 Minimalna encja

Encja to klasa oznaczona @Entity z @Id. Hibernate wie, którą tabelę reprezentuje (@Table) i jak mapować pola na kolumny. @GeneratedValue mówi, skąd wziąć id (auto-increment, sekwencja, UUID). To fundament — bez poprawnej encji reszta nie zadziała.

Przykład: Author z id, firstName, lastName.

Część 2 — Stany encji

2.1 Cztery stany

Obiekt w Hibernate nie jest „zwykłym POJO” — ma stan w kontekście persystencji. To klucz do zrozumienia, kiedy idzie INSERT vs UPDATE i dlaczego zmiany „znikają”.

StanZnaczenie
TransientNowy, Hibernate go nie zna — new Author()
ManagedW Persistence Context — Hibernate śledzi zmiany
DetachedBył managed, sesja się zamknęła — zmiany nie synchronizują się same
RemovedOznaczony do usunięcia przy następnym flush

2.2 Operacje zmieniające stan

  • persist() — transient → managed, przy flush: INSERT
  • merge() — detached → managed (kopia), UPDATE jeśli coś się zmieniło
  • remove() — managed → removed, przy flush: DELETE
  • flush() — wymusza wysłanie SQL do bazy (w ramach transakcji)

Pułapka: edytujesz detached encję poza kontekstem — bez merge() zmiany nie trafią do bazy.

2.3 Persistence Context

To „pierwszy poziom cache” w ramach jednej sesji. Drugi find(id) może nie iść do bazy — Hibernate zwraca obiekt z pamięci. Dirty checking: przy flush Hibernate porównuje stan obiektu z momentem załadowania i generuje UPDATE tylko dla zmienionych pól.

Część 3 — Relacje i właściciel

3.1 Typy relacji

@OneToOne, @OneToMany, @ManyToOne, @ManyToMany — opisują relację między tabelami. Unidirectional — tylko jedna strona ma pole. Bidirectional — obie strony mają referencje; wygodniejsze w kodzie, ale wymaga synchronizacji obu stron.

3.2 Właściciel relacji (mappedBy vs @JoinColumn)

Właściciel to strona, która trzyma klucz obcy w bazie — ma @JoinColumn. Druga strona ma @OneToMany(mappedBy = "author") — mówi: „FK jest po tamtej stronie, ja tylko odzwierciedlam relację”.

Przykład: Title ma @ManyToOne Author + @JoinColumn — właściciel. Author.titles ma mappedBy = "author".

@Entity
public class Title {
    @ManyToOne
    @JoinColumn(name = "author_id")  // właściciel — FK w tabeli titles
    private Author author;
}

@Entity
public class Author {
    @OneToMany(mappedBy = "author")  // odwrócona strona
    private List<Title> titles;
}

3.3 Dlaczego @OneToMany bez mappedBy to pułapka

Bez mappedBy Hibernate zakłada relację przez tabelę pośrednią (join table), a nie FK w tabeli „wielu”. Dla Author → Title chcesz kolumnę author_id w titles, więc FK musi być na @ManyToOne w Title.

Cascade — operacja na rodzicu propaguje się na dzieci (PERSIST, MERGE, REMOVE…). orphanRemoval — usunięcie dziecka z kolekcji = DELETE w bazie (silniejsze niż sam cascade).

3.4 Lazy vs Eager

LAZY — dane powiązane ładują się dopiero przy pierwszym dostępie (domyślnie @OneToMany, @ManyToMany). EAGER — ładują się od razu z rodzicem (domyślnie @ManyToOne, @OneToOne). EAGER na kolekcjach często prowadzi do N+1 lub ogromnych JOIN-ów — zwykle wymuszaj LAZY i fetch explicite tam, gdzie potrzebujesz.

Część 4 — Problem N+1

4.1 Co to jest

Jedno zapytanie pobiera N rekordów rodzica, potem przy każdym dostępie do relacji lazy Hibernate robi osobne SELECT — łącznie 1 + N zapytań. Przy 100 autorach i ich tytułach: 101 query zamiast 1–2.

// N+1 w praktyce:
List<Author> authors = em.createQuery("SELECT a FROM Author a", Author.class).getResultList();
// 1 SELECT

for (Author a : authors) {
    a.getTitles().size();  // +1 SELECT na każdego autora
}
// razem: 1 + N

4.2 Jak wykryć

Włącz logi SQL (spring.jpa.show-sql lub logger Hibernate). Policz SELECT-y przy jednym requestcie. Narzędzia: p6spy, datasource-proxy, Hibernate statistics.

4.3 Jak naprawić

Cztery główne strategie — wybór zależy od tego, czy potrzebujesz pełnych encji, ile relacji ładujesz naraz i czy wystawiasz dane na API.

RozwiązanieKiedy użyćOpis
JOIN FETCH Jedna relacja (@OneToMany / @ManyToOne), lista lub pojedynczy rekord, potrzebujesz pełnych encji w serwisie Jeden SELECT z JOIN — rodzic i dzieci w jednym query. Proste i przewidywalne. Nie łącz wielu kolekcji — iloczyn kartezjański. Uważaj na paginację (setFirstResult) — duplikaty wierszy zawyżają liczbę rekordów.
@EntityGraph Spring Data JPA, powtarzalny fetch plan w wielu metodach repo, złożone grafy relacji (@NamedEntityGraph), łączenie z własnym @Query Standard JPA — deklarujesz co załadować (atrybuty/relacje), Hibernate/Spring generuje JOIN FETCH lub batch load. Czytelniejsze niż JPQL w stringu; ten sam graf na wielu metodach. Typ FETCH (domyślnie) nadpisuje lazy na eager dla wskazanych ścieżek.
@BatchSize Wiele encji rodzica (np. 100 autorów), lazy relacja OK, druga kolekcja do załadowania osobnym query, unikasz wielkiego JOIN Zamiast N osobnych SELECTów Hibernate robi partiami: WHERE author_id IN (?, ?, … 20 id). Przy 100 autorach: ~1 + 5 query zamiast 101. Encje nadal managed — wygodne w serwisie.
DTO / projection REST API, raport, tabela w UI — nie potrzebujesz encji, tylko kilka pól; chcesz zerowego ryzyka lazy i N+1 JPQL wybiera wyłącznie pola (interface, record, konstruktor). Brak proxy, brak Persistence Context poza transakcją. Najstabilniejsza granica warstwy API.

4.3.1 JOIN FETCH — mikro-przykład

Scenariusz: endpoint zwraca autora z listą tytułów — jeden autor, jedna relacja.

// ❌ N+1 — 2 query (author + titles)
Author a = em.find(Author.class, 1L);
a.getTitles().size();

// ✅ 1 query — author + titles razem
Author a = em.createQuery(
    "SELECT a FROM Author a JOIN FETCH a.titles WHERE a.id = :id", Author.class)
  .setParameter("id", 1L)
  .getSingleResult();
a.getTitles().size(); // bez dodatkowego SELECT

Lista autorów z tytułami — ten sam wzorzec, ale DISTINCT przy wielu tytułach na autora:

SELECT DISTINCT a FROM Author a JOIN FETCH a.titles

4.3.2 @EntityGraph — rozszerzenie

@EntityGraph to standard JPA (nie tylko Hibernate) — mówisz encji które relacje mają być załadowane w danym query, zamiast pisać JOIN FETCH ręcznie. Spring Data przekazuje graf do Hibernate, który generuje odpowiedni SQL.

Co to robi pod spodem?

Dla wskazanych atrybutów Hibernate zwykle robi to samo co JOIN FETCH — jeden SELECT z JOIN. Dla relacji, których nie da się sensownie joinować w jednym query, może użyć batch load. Efekt: brak N+1 przy dostępie do wymienionych pól w tej samej transakcji.

ElementZnaczenie
attributePathsLista ścieżek do załadowania, np. "titles", "publisher.address" (zagnieżdżone)
type = FETCHDomyślny. Wskazane relacje ładowane JOIN-em w tym query — lazy na chwilę staje się eager
type = LOADGłówne query bez JOIN; wskazane relacje ładowane osobnymi SELECT-ami (batch jeśli możliwe). Rzadziej używany
@NamedEntityGraphGraf zdefiniowany na encji — reuse w wielu metodach repo i w EntityManager
subgraphZagnieżdżony fetch — np. tytuły i wydawca każdego tytułu

Podstawowy przykład — attributePaths

Scenariusz: endpoint zwraca autora z listą tytułów — jeden autor, jedna relacja.

public interface AuthorRepository extends JpaRepository<Author, Long> {

    @EntityGraph(attributePaths = "titles")
    Optional<Author> findWithTitlesById(Long id);
}

// serwis — 1 query, encja gotowa w @Transactional
Author author = repo.findWithTitlesById(1L).orElseThrow();
author.getTitles().forEach(t -> ...); // bez dodatkowego SELECT

Nazwany graf na encji — reuse

Gdy ten sam fetch plan powtarza się w wielu miejscach, definiujesz go raz na klasie encji:

@NamedEntityGraph(
    name = "Author.withTitles",
    attributeNodes = @NamedAttributeNode("titles")
)
@Entity
public class Author {
    @OneToMany(mappedBy = "author")
    private List<Title> titles;
}

// repo — odwołanie po nazwie
@EntityGraph("Author.withTitles")
Optional<Author> findById(Long id);

@EntityGraph("Author.withTitles")
List<Author> findByLastName(String lastName);

Korzyść: zmiana fetch planu w jednym miejscu (@NamedEntityGraph) — wszystkie metody repo korzystają z aktualnej wersji.

Zagnieżdżony graf (subgraph)

Scenariusz: autor → tytuły → wydawca (Title.publisher). Ścieżka z kropką w attributePaths albo jawny subgraph:

@NamedEntityGraph(
    name = "Author.full",
    attributeNodes = {
        @NamedAttributeNode(value = "titles", subgraph = "title-publisher")
    },
    subgraphs = @NamedSubgraph(
        name = "title-publisher",
        attributeNodes = @NamedAttributeNode("publisher")
    )
)
@Entity
public class Author { ... }

@EntityGraph("Author.full")
Optional<Author> findFullById(Long id);

// skrót w Spring Data — kropka = zagnieżdżona ścieżka:
@EntityGraph(attributePaths = {"titles", "titles.publisher"})
Optional<Author> findWithTitlesAndPublishers(Long id);

Uwaga: im głębszy graf, tym większy JOIN — przy wielu kolekcjach na tym samym poziomie wraca problem iloczynu kartezjańskiego.

EntityGraph + własny @Query

Graf mówi co załadować; JPQL mówi skąd i z jakim filtrem. Spring Data łączy oba:

@EntityGraph(attributePaths = "titles")
@Query("SELECT a FROM Author a WHERE a.lastName = :name")
List<Author> findByLastNameWithTitles(@Param("name") String name);

// paginacja — EntityGraph na Page:
@EntityGraph("Author.withTitles")
Page<Author> findByCountry(Country country, Pageable pageable);

Hibernate do query z JPQL dokleja JOIN-y dla atrybutów z grafu. Filtrowanie zostaje w JPQL — nie musisz powtarzać JOIN FETCH w stringu.

FETCH vs LOAD

// FETCH (domyślny) — JOIN w tym samym query
@EntityGraph(attributePaths = "titles", type = EntityGraph.EntityGraphType.FETCH)

// LOAD — główne query bez JOIN; relacje osobno (batch SELECT)
@EntityGraph(attributePaths = "titles", type = EntityGraph.EntityGraphType.LOAD)

W praktyce prawie zawsze używasz FETCH. LOAD ma sens, gdy chcesz uniknąć dużego JOIN-u, ale i tak załadować relację przed zamknięciem sesji — Hibernate może zbatchować osobne SELECT-y.

Bez Spring Data — EntityManager

EntityGraph działa też w czystym JPA:

EntityGraph<Author> graph = em.createEntityGraph(Author.class);
graph.addAttributeNodes("titles");

Map<String, Object> hints = Map.of("jakarta.persistence.fetchgraph", graph);
Author author = em.find(Author.class, 1L, hints);
// alternatywa: em.createEntityGraph("Author.withTitles") — nazwany graf z encji

Hint fetchgraph — tylko wskazane atrybuty jako eager; reszta lazy. Hint loadgraph — wskazane eager + reszta według domyślnego fetch type encji.

EntityGraph vs JOIN FETCH

@EntityGraphJOIN FETCH w JPQL
SkładniaDeklaratywna, na repo / encjiImperatywna, w stringu JPQL
Reuse@NamedEntityGraph — jedna definicja, wiele metodKopiujesz JOIN w każdym query
Dynamiczne filtryJPQL w @Query + graf osobnoWszystko w jednym JPQL
SQL pod spodemZwykle ten sam JOIN FETCHJawna kontrola nad JOIN
PułapkiTe same: kartezjański iloczyn, paginacjaTe same

Typowe pułapki EntityGraph

  • Wiele kolekcji w jednym grafie — attributePaths = {"titles", "reviews"} → iloczyn kartezjański. Rozwiązanie: osobne metody repo albo @BatchSize na drugiej kolekcji
  • Paginacja + FETCH — Page<Author> z grafem kolekcji może zwrócić mniej/m więcej rekordów niż pageSize (duplikaty w JOIN). Rozwiązanie: query count osobno; fetch kolekcji w drugim kroku albo DTO
  • Graf poza transakcją — załadowane w grafie pola są OK; pola poza grafem nadal lazy → LazyInitializationException
  • Myślenie, że graf = cache — działa tylko dla tego jednego query; kolejne findById bez grafu znów lazy

Praktyczna reguła: EntityGraph wybieraj, gdy fetch plan jest stały i powtarzalny (szczegóły encji, kilka metod repo). JOIN FETCH w JPQL — gdy query jest jednorazowe, bardzo specyficzne albo potrzebujesz pełnej kontroli nad JOIN (np. DISTINCT, warunki na joinowanej tabeli).

4.3.3 @BatchSize — mikro-przykład

Scenariusz: lista 50 autorów — każdy ma lazy titles; nie chcesz JOIN FETCH na całej liście.

@Entity
public class Author {
    @OneToMany(mappedBy = "author")
    @BatchSize(size = 20)  // lub globalnie: hibernate.default_batch_fetch_size=20
    private List<Title> titles;
}

// 1 SELECT — wszyscy autorzy
List<Author> authors = em.createQuery("SELECT a FROM Author a", Author.class)
    .getResultList();

// Hibernate ładuje titles partiami po 20 autorów (np. 3 query zamiast 50)
authors.forEach(a -> a.getTitles().size());

Efekt: 50 autorów → 1 + 3 = 4 query (przy batch_size=20), nie 51.

4.3.4 DTO / projection — mikro-przykład

Scenariusz: REST zwraca tylko id, imię autora i liczbę tytułów — encja w ogóle nie wychodzi z warstwy persistence.

// record + JPQL constructor expression — 1 query, zero lazy
public record AuthorSummary(Long id, String fullName, long titleCount) {}

@Query("""
    SELECT new com.example.AuthorSummary(a.id, CONCAT(a.firstName, ' ', a.lastName), COUNT(t))
    FROM Author a LEFT JOIN a.titles t
    GROUP BY a.id, a.firstName, a.lastName
    """)
List<AuthorSummary> findAllSummaries();

// interface projection — Spring Data generuje query z pól getterów
public interface AuthorRow {
    Long getId();
    String getFirstName();
    String getLastName();
}

List<AuthorRow> findAllBy();  // SELECT id, first_name, last_name — bez titles

Efekt: JSON w kontrolerze bez N+1, bez LazyInitializationException, bez przypadkowego serializowania całego grafu encji.

4.4 Typowe pułapki

  • N+1 w pętli po encjach
  • N+1 przy serializacji do JSON (REST zwraca @OneToMany → każdy element triggeruje lazy load)
  • JOIN FETCH wielu kolekcji naraz → iloczyn kartezjański w wyniku — rozwiązanie: osobne query albo @BatchSize zamiast wielu JOIN FETCH

Część 5 — LazyInitializationException

Gdy sesja jest zamknięta, a kod próbuje odczytać lazy kolekcję lub proxy — Hibernate rzuca LazyInitializationException.

  1. Trzymaj dostęp do relacji wewnątrz @Transactional
  2. Załaduj wcześniej: JOIN FETCH / @EntityGraph
  3. Zwróć DTO zamiast encji na zewnątrz warstwy persistence
  4. Unikaj Open Session In View jako plastra — maskuje N+1 i ukrywa błędy architektury

Pułapka getReference(): zwraca proxy bez SELECT — OK jako wskaźnik FK (order.setAuthor(em.getReference(Author.class, 1L))), ale odczyt lazy pola poza transakcją kończy się wyjątkiem.

Część 6 — Najczęstsze błędy na początku

  1. Bidirectional bez synchronizacji — ustawiasz tylko author.titles.add(title), nie ustawiasz title.setAuthor(author) → FK null
  2. Equals/hashCode na id — transient encje mają id = null, trafiają do tego samego bucketu w HashSet
  3. cascade = ALL wszędzie — przypadkowe skasowanie całego drzewa
  4. @OneToMany bez mappedBy — niechciana join table zamiast FK
  5. Modyfikacja detached bez merge — zmiany nie zapisują się
  6. Encja jako DTO w API — wystawiasz lazy graf, dostajesz N+1 albo LazyInitException
  7. Logika w getterze encji — side effect + nieoczekiwane query
  8. Brak indeksu na FK — wolne JOIN-y w produkcji
  9. Eager na kolekcjach — wolna aplikacja od pierwszego dnia
  10. find() vs getReference() — getReference() zwraca proxy bez SELECT; potem LazyInit jeśli sesja zamknięta

Część 7 — Zapytania (skrót)

JPQL — obiekty i pola encji, nie nazwy tabel. Criteria API — type-safe, dynamiczne filtry. Native SQL — gdy JPQL nie wystarcza.

persist tworzy nowy rekord; merge scala detached z kontekstem. Paginacja: setFirstResult / setMaxResults — uważaj na COUNT z JOIN FETCH (duplikaty).

Część 8 — Rozwiązania praktyczne (Senior)

Na rozmowie Senior oczekuje nie tylko definicji, ale diagnozy → narzędzia → decyzji. Poniżej typowe problemy z gotowymi poprawkami.

8.1 N+1 — kiedy którego sposobu

SposóbKiedyKrótko
JOIN FETCHJedna relacja, mała listaJeden query z JOIN
@BatchSize(n=20)Wiele encji, lazy OKHibernate grupuje SELECTy po N id
DTO / projectionAPI, raportyW ogóle nie ładujesz encji
@EntityGraphSpring DataJawny fetch plan na metodzie repo

Odpowiedź na rozmowie: „W logach widzę 1 + N SELECTów. Diagnozuję przez SQL log / p6spy / Hibernate statistics. Naprawiam fetch join albo batch size albo DTO — przy wielu kolekcjach unikam wielu JOIN FETCH (iloczyn kartezjański).”

8.2 merge() — detached encja

Edycja detached poza kontekstem nie zapisze się sama. merge() zwraca inną managed instancję — pracuj na zwróconej referencji.

Order managed = em.merge(detached);
managed.setStatus(SHIPPED); // dirty checking przy flush/commit

8.3 Kasowanie rodzica z dziećmi

Bez propagacji: FK constraint albo osierocone rekordy.

@OneToMany(mappedBy = "author", cascade = CascadeType.REMOVE, orphanRemoval = true)
private List<Title> titles;
  • cascade = REMOVE — kasuje dzieci z rodzicem
  • orphanRemoval = true — kasuje dziecko usunięte z kolekcji

8.4 Optimistic vs pessimistic locking

Optimistic — mała contention, konflikt przy commit:

@Version
private Long version;
// OptimisticLockException → retry lub komunikat użytkownikowi

Pessimistic — rezerwacja, stock, płatność:

@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("SELECT a FROM Account a WHERE a.id = :id")
Optional<Account> findForUpdate(@Param("id") Long id);

8.5 GenerationType.IDENTITY psuje batch insert

DB generuje id dopiero po INSERT — Hibernate nie może batchować. Rozwiązanie: SEQUENCE z allocationSize:

@Id
@GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "author_seq")
@SequenceGenerator(name = "author_seq", sequenceName = "author_seq", allocationSize = 50)
private Long id;

8.6 equals / hashCode z @GeneratedValue

hashCode() na id — przy transient id == null, po persist hash się zmienia → błędy w Set/Map. Użyj natural key:

@Override
public boolean equals(Object o) {
    if (!(o instanceof Author a)) return false;
    return email != null && email.equals(a.email);
}

8.7 @ManyToMany → encja pośrednia

Join table bez dodatkowych pól, słaba kontrola, wolne przy skali. Zamiast Student ↔ Course wprowadź Enrollment z @ManyToOne do obu stron + pola (enrolledAt, grade).

8.8 Masowy import (miliony rekordów)

Zwykła sesja — rosnący L1, dirty checking, ryzyko OOM. StatelessSession + commit co N rekordów; przy ekstremalnej skali JDBC batch / COPY (Postgres).

statelessSession.insert(entity);
if (++i % 500 == 0) {
    tx.commit();
    tx.begin();
}

8.9 Soft delete

@SQLDelete(sql = "UPDATE author SET deleted = true WHERE id = ?")
@Where(clause = "deleted = false")
@Entity
public class Author { ... }

Pułapka: unique na email — skasowany rekord blokuje email. Rozwiązanie: partial unique index w DB (WHERE deleted = false).

8.10 Second-level cache — kiedy ma sens

  • Tak: rzadko zmieniane słowniki (kategorie, kraje)
  • Nie: dane użytkownika w czasie rzeczywistym, listy z filtrami, query bez cacheable

L2 cache'uje encje po id — nie zastępuje dobrego fetch planu. Query cache to osobna warstwa, domyślnie wyłączona.

8.11 Diagnoza w produkcji

  1. Logi SQL / datasource proxy (p6spy, Hibernate statistics)
  2. Policz query na request — wzorzec 1 + N = N+1
  3. Wybierz: fetch join / batch / DTO
  4. Test integracyjny @DataJpaTest + assert liczby query

Pytania rekrutacyjne — krótkie odpowiedzi

Junior / Mid

1. Jakie są stany encji w JPA?

Transient, managed (persistent), detached, removed.

2. Czym różni się persist() od merge()?

persist() — nowa encja → managed, INSERT. merge() — detached → managed (kopia w kontekście), UPDATE.

3. Co to jest N+1?

1 query na listę + N query na relacje lazy — np. 100 autorów = 101 SELECT.

4. Jak rozwiązać N+1?

JOIN FETCH, @EntityGraph, @BatchSize, DTO zamiast encji.

5. Kto jest właścicielem relacji 1:N?

Strona @ManyToOne z @JoinColumn — tam jest FK w bazie.

6. Co robi mappedBy?

Wskazuje właściciela — ta strona nie zarządza FK, tylko odzwierciedla relację.

7. LAZY vs EAGER?

LAZY — ładuje przy pierwszym dostępie. EAGER — ładuje od razu z rodzicem.

8. Co to jest LazyInitializationException?

Dostęp do lazy relacji po zamknięciu sesji — brak proxy do załadowania danych.

9. Czym różni się cascade od orphanRemoval?

Cascade propaguje operacje z rodzica na dzieci. OrphanRemoval kasuje dziecko usunięte z kolekcji.

10. Dlaczego @OneToMany bez mappedBy to problem?

Hibernate tworzy join table zamiast FK w tabeli „wielu”.

11. Co to jest Persistence Context?

Cache pierwszego poziomu w sesji — śledzi managed encje i dirty checking.

12. Czy trzeba wołać save() po zmianie pola managed encji?

Nie — dirty checking zapisze zmiany przy flush/commit.

13. Co robi flush()?

Wymusza wysłanie pending SQL do bazy (w tej samej transakcji).

14. @Embeddable vs @Entity?

@Embeddable — wartość w tej samej tabeli (kompozycja). @Entity — osobna tabela.

15. Co to jest proxy w Hibernate?

Lazy placeholder — prawdziwe dane ładuje dopiero przy pierwszym użyciu.

Mid / Senior

16. First-level vs second-level cache?

L1 — per sesja (Persistence Context), zawsze włączony. L2 — współdzielony między sesjami, opcjonalny (EHCache, Infinispan).

Rozwiązanie: L2 tylko dla rzadko zmienianych słowników; invalidacja przy write. Nie zastępuje fetch planu.

17. Kiedy find() nie idzie do bazy?

Gdy encja jest już w Persistence Context (L1 cache).

Pułapka: inna sesja = zawsze SELECT (albo L2, jeśli włączony).

18. getReference() vs find()?

getReference() — proxy bez SELECT (lazy). find() — od razu SELECT (lub z L1).

Rozwiązanie: getReference() tylko jako wskaźnik FK — bez odczytu lazy pól poza transakcją.

19. Optimistic vs pessimistic locking?

Optimistic — @Version, konflikt przy commit. Pessimistic — SELECT FOR UPDATE, blokada w bazie.

Rozwiązanie: mała contention → optimistic; rezerwacja/stock → pessimistic (@Lock(PESSIMISTIC_WRITE)).

20. Co to jest dirty checking?

Hibernate porównuje stan managed encji z snapshotem — generuje UPDATE tylko dla zmienionych pól.

Powiązane: @DynamicUpdate — UPDATE tylko zmienionych kolumn w SQL.

21. Dlaczego JOIN FETCH wielu kolekcji to problem?

Iloczyn kartezjański — duplikaty wierszy, ogromny wynik, wolne query.

Rozwiązanie: osobne query, @BatchSize, DTO — nie łącz wielu kolekcji jednym JOIN FETCH.

22. Jak zaprojektować equals/hashCode z @GeneratedValue?

Na polach biznesowych (natural key) albo stałym polu — nie na id (null u transient).

Rozwiązanie: np. equals po email — stabilne w Set/Map przed i po persist.

23. Problemy z @ManyToMany?

Join table, brak dodatkowych kolumn, wolne przy dużych zbiorach — często lepsza encja pośrednia.

Rozwiązanie: encja pośrednia z @ManyToOne + pola relacji (enrolledAt, grade).

24. @Formula / @Where / @Filter?

@Formula — computed column. @Where — stały warunek SQL. @Filter — dynamiczny filtr sesji.

Rozwiązanie soft delete: @SQLDelete + @Where(deleted = false); partial unique index na email.

25. StatelessSession — kiedy?

Masowe operacje bez cache i dirty checking — import, batch update milionów rekordów.

Rozwiązanie: commit co 500 rekordów; przy ekstremalnej skali JDBC batch / COPY.

26. Problemy z GenerationType.IDENTITY?

Hibernate nie zna id przed INSERT — psuje batch insert, kolejność operacji w sesji.

Rozwiązanie: SEQUENCE + allocationSize = 50 — mniej round-tripów, działający batch.

27. @DynamicUpdate — po co?

UPDATE tylko zmienionych kolumn — mniejszy SQL, mniej konfliktów przy concurrent update.

28. Jak testować repozytoria?

@DataJpaTest + H2/Testcontainers — prawdziwy SQL, izolowane testy JPA.

Senior: assert liczby query — wykrywasz N+1 w CI, nie w produkcji.

29. DTO projection vs encja w serwisie?

DTO — brak lazy, brak N+1, stabilne API. Encja — wygodna w transakcji, ryzyko poza nią.

Rozwiązanie: encja w warstwie persistence; DTO na granicy API — nigdy lazy graf w REST.

30. Co to jest fetch plan?

Strategia ładowania relacji — lazy/eager + explicite fetch (join, batch, subselect).

Pułapka: LAZY samo w sobie N+1 nie rozwiązuje — tylko opóźnia do momentu iteracji.

Pułapki / tricky

31. Czy każdy find(id) to SELECT?

Nie — jeśli encja jest w L1 cache, Hibernate zwraca ją z pamięci.

32. Czy remove() od razu kasuje w bazie?

Nie — dopiero przy flush/commit (chyba że flush() explicite).

33. Dlaczego delete(parent) nie kasuje dzieci?

Bez cascade = REMOVE lub orphanRemoval — FK constraint albo osierocone rekordy.

34. Czy ustawienie LAZY wystarczy, żeby nie było N+1?

Nie — LAZY tylko opóźnia problem; N+1 wystąpi przy iteracji i dostępie do relacji.

Rozwiązanie: JOIN FETCH, @BatchSize lub DTO — patrz Część 8.

35. Dwa obiekty z tym samym id w jednej sesji?

Ten sam obiekt (identity) — Persistence Context gwarantuje jedną instancję na id.

36. merge() zmienia moją referencję?

Tak — zwraca inną managed instancję; oryginalny detached zostaje detached.

Rozwiązanie: Order managed = em.merge(detached); — dalsze zmiany na managed.

37. @OneToOne — gdzie FK?

Po stronie z @JoinColumn; druga strona mappedBy.

38. Czy Hibernate cache'uje query (JPQL)?

Osobno — query cache (L2) to inna warstwa niż encje; domyślnie wyłączony.

39. Enum w JPA — ORDINAL vs STRING?

STRING — czytelne, odporne na zmianę kolejności. ORDINAL — kruche, łamie się po reorder enum.

40. Co robi @OrderColumn vs @OrderBy?

@OrderColumn — osobna kolumna z indeksem w join table (rzadko). @OrderBy — sortowanie po polu encji w SQL.
