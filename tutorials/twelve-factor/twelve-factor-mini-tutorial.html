Część 1 — Fundamenty

1.1 Co to jest Twelve-Factor App

Metodologia 12 zasad opisujących, jak budować nowoczesne aplikacje webowe (SaaS) — skalowalne, przenośne między środowiskami, gotowe na deploy w chmurze. Nie jest to framework ani narzędzie — to zbiór praktyk architektonicznych i operacyjnych.

1.2 Dla kogo i po co

Powstało przy Heroku, ale dziś dotyczy każdej aplikacji deployowanej na AWS, GCP, Azure, Kubernetes. Cel: ten sam kod idzie przez dev → staging → prod bez ręcznych poprawek; skalowanie i rollback są przewidywalne; zespół nie walczy ze środowiskiem.

1.3 Jedno zdanie na start

Aplikacja to jeden artefakt konfigurowany środowiskiem, uruchamiany jako stateless proces, skalowany horyzontalnie, z logami na stdout i zależnościami jawnie zadeklarowanymi.

Część 2 — 12 faktorów

I Codebase — Jedna baza kodu

Jeden repozytorium → wiele deployów. Jeden app = jeden repo Git. Wiele aplikacji = wiele rep. Wspólny kod wydziel do bibliotek (npm, Maven), nie kopiuj między repo.

Przykład: react-authors na GitHubie — ten sam commit idzie na staging i prod. Osobne repo na frontend i backend = dwie aplikacje (OK), nie „dwie wersje tej samej”.

Pułapka: monorepo z wieloma niezależnymi appami — każda musi mieć własną ścieżkę deployu.

II Dependencies — Jawne zależności

Nigdy nie polegaj na tym, co „już jest w systemie”. Deklaruj zależności w pliku manifestu (package.json, pom.xml, requirements.txt) i izoluj (node_modules, venv, JAR z Maven).

Przykład: npm install odtwarza identyczne drzewo na każdej maszynie. Nie instalujesz Node globalnie „bo tak zawsze było”.

Pułapka: brak lockfile (package-lock.json) — build niedeterministyczny.

III Config — Konfiguracja w środowisku

Config ≠ kod. Wszystko, co może się różnić między deployami (DB URL, klucze API, feature flags), trzymaj w zmiennych środowiskowych — nie w repo, nie w hardcoded plikach per env.

# DOBRZE — env
DATABASE_URL=postgres://...
API_KEY=${SECRET_FROM_VAULT}

# ŹLE — w repo
config-prod.properties  # z hasłem

Wyjątek: pliki konfiguracyjne bez sekretów (np. domyślny port) — OK, jeśli nie zawierają danych wrażliwych.

IV Backing services — Usługi jako zasoby

Traktuj DB, cache, queue, storage jak „attached resources” — podłączane przez URL/credentials z env. Aplikacja nie wie, czy Postgres jest lokalny czy w AWS RDS — widzi tylko connection string.

Przykład: dev: Postgres w Dockerze. Prod: RDS. Kod identyczny — zmienia się tylko DATABASE_URL.

Pułapka: hardcoded localhost:5432 w kodzie serwisu.

V Build, release, run — Rozdziel etapy

Trzy fazy muszą być ściśle oddzielone:

EtapCo robiKto
BuildKompilacja, bundling, artefakt (JAR, Docker image layer)CI
ReleaseBuild + config (immutable snapshot)Platforma deploy
RunUruchomienie procesów release w środowiskuRuntime (K8s, Heroku)

Pułapka: edycja plików na serwerze prod po deployu — następny deploy nadpisze zmiany.

VI Processes — Procesy bezstanowe

Aplikacja wykonuje się jako jeden lub więcej procesów stateless. Żadnego trzymania sesji w pamięci procesu, plików uploadowanych na dysk lokalny, cache in-memory jako źródła prawdy.

Stan trzymaj w backing service (Redis, DB, S3). Każdy request może trafić na dowolny proces — load balancer nie gwarantuje sticky session (chyba że świadomie).

Przykład: sesja użytkownika w Redis, nie w HashMap w JVM.

VII Port binding — Eksport przez port

Aplikacja jest samowystarczalna — sama nasłuchuje na porcie HTTP (np. 8080) i eksportuje usługę. Nie wymaga embedowanego serwera aplikacji z zewnątrz (Apache + mod_php to antywzorzec 12-factor).

Przykład: Spring Boot JAR, Node Express, Vite preview — proces binduje port. Reverse proxy (nginx) opcjonalnie przed nim.

VIII Concurrency — Skaluj przez procesy

Skaluj przez uruchamianie większej liczby procesów, nie przez wewnętrzne wątki jako model skalowania. Każdy proces to kopia app; orchestrator (K8s, Heroku) rozkłada je na maszynach.

Model: web=4, worker=2 — typy procesów w Procfile / K8s deployments. CPU-bound → więcej procesów; I/O-bound → też więcej procesów (lub virtual threads wewnątrz).

Pułapka: jeden gigantyczny JVM z 500 wątkami zamiast 4 procesów × 125 — trudniejszy deploy i mniejsza odporność.

IX Disposability — Szybki start i graceful shutdown

Procesy muszą szybko startować (sekundy) i gracyjnie kończyć (SIGTERM → dokończ requesty → wyjdź). Elastyczne skalowanie i deploy bez downtime wymagają krótkiego życia procesów.

// Spring Boot — graceful shutdown
server.shutdown=graceful
spring.lifecycle.timeout-per-shutdown-phase=30s

Pułapka: 5-minutowy warmup przy starcie — autoscaler nie nadąża; kill -9 bez drain — utracone requesty.

X Dev/prod parity — Parzystość środowisk

Dev, staging i prod jak najbardziej podobne — ten sam typ DB, ten sam backing services (choć mniejsza skala), ten sam artefakt deploy. Gap czasowy (dev opóźniony o miesiące) i narzędziowy (SQLite dev vs Postgres prod) to źródło bugów „u mnie działa”.

Praktyka: Docker Compose lokalnie z Postgres + Redis; CI deployuje ten sam image co prod.

XI Logs — Logi jako strumień zdarzeń

App pisze logi na stdout/stderr — nie zarządza plikami logów, rotacją, archiwizacją. Platforma (K8s, CloudWatch, Datadog) zbiera, przechowuje i indeksuje strumień.

Log = linia zdarzenia z timestampem. Strukturalne logi (JSON) ułatwiają parsowanie.

Pułapka: log4j → /var/log/app.log na dysku kontenera — znika przy restarcie poda.

XII Admin processes — Zadania admina one-off

Migracje DB, seed, one-time script — uruchamiaj jako osobny proces one-off, w tym samym release co app, ale nie w długo działającym serwerze web.

# Przykład
kubectl run migrate --image=myapp:v1.2 --command -- java -jar app.jar migrate
# lub w CI przed deployem
flyway migrate

Pułapka: endpoint HTTP /admin/migrate w produkcji — ryzyko bezpieczeństwa.

Część 3 — Jak faktory się łączą

Git repo (I)
  → CI build artefaktu (II, V)
    → Release = artefakt + env config (III, V)
      → Procesy stateless na porcie (VI, VII)
        → Skaluj liczbą procesów (VIII)
          → Backing services przez URL (IV)
            → Logi na stdout (XI)
              → Admin/migrate one-off (XII)

Łamanie jednego factoru zwykle psuje inne: brak config w env (III) → brak dev/prod parity (X); stan w pamięci (VI) → problem ze skalowaniem (VIII).

Część 4 — 12-Factor a dziś (K8s, serverless)

Temat12-Factor mówiDziś
DeployRelease jako immutable unitDocker image + K8s Deployment / Helm
ConfigEnv vars+ ConfigMaps, Secrets, Vault (nadal inject do env)
ProcesyStateless processesPods; sidecars dla proxy/logging
ConcurrencyScale processesHPA, KEDA; serverless = extreme case
LogsstdoutFluent Bit → ELK / Loki / CloudWatch

12-factor nie jest przestarzały — K8s i serverless to implementacje tych samych idei. „Beyond 12-factor”: distributed tracing, health checks (/health, /ready), infrastructure as code.

Część 5 — Najczęstsze błędy

  1. Sekrety w repo — hasła w Git (łamanie III)
  2. Brak lockfile — niedeterministyczny build (II)
  3. Stan sesji w pamięci — nie skaluje się (VI)
  4. Upload na lokalny dysk kontenera — ginie przy restarcie (VI, IV → S3)
  5. SQLite dev, Postgres prod — inne SQL, inne zachowanie (X)
  6. Logi do pliku w kontenerze — brak centralizacji (XI)
  7. Edycja prod ręcznie — drift, niepowtarzalny release (V)
  8. Jeden repo, dwa deploye bez jasności — chaos w codebase (I)
  9. Brak graceful shutdown — 502 przy deployu (IX)
  10. Migracje przez endpoint web — security + coupling (XII)

Pytania rekrutacyjne — krótkie odpowiedzi

Junior / Mid

1. Co to jest Twelve-Factor App?

12 zasad budowy skalowalnych aplikacji SaaS — od codebase po logi i admin tasks.

2. Wymień 12 faktorów.

Codebase, Dependencies, Config, Backing services, Build/release/run, Processes, Port binding, Concurrency, Disposability, Dev/prod parity, Logs, Admin processes.

3. Factor I — Codebase?

Jeden repo Git = jedna app; wiele deployów (staging, prod) z tego samego kodu.

4. Factor II — Dependencies?

Jawna deklaracja w manifeście + izolacja — bez polegania na systemowych pakietach.

5. Factor III — Config?

Konfiguracja (w tym sekrety) w env, nie w kodzie/repo.

6. Factor IV — Backing services?

DB, queue, cache jako attached resources — podłączane URL z env, wymienialne bez zmiany kodu.

7. Factor V — Build, release, run?

Build = kompilacja; Release = build + config (immutable); Run = uruchomienie procesów.

8. Factor VI — Processes / stateless?

Brak stanu w pamięci procesu — stan w DB/Redis/S3; każdy request może iść na dowolny proces.

9. Factor VII — Port binding?

App sama nasłuchuje na porcie HTTP — samowystarczalny proces, nie embed w zewnętrznym serwerze.

10. Factor VIII — Concurrency?

Skaluj przez więcej procesów (horizontal), nie przez „grubszy” jeden proces.

11. Factor IX — Disposability?

Szybki start, graceful shutdown (SIGTERM), odporne na kill.

12. Factor X — Dev/prod parity?

Dev i prod jak najbardziej podobne — ten sam stack, ten sam artefakt, mały gap czasowy.

13. Factor XI — Logs?

Logi na stdout/stderr jako strumień — app nie zarządza plikami logów.

14. Factor XII — Admin processes?

Migracje i skrypty admina jako one-off proces, nie w długo działającym serwerze.

15. Gdzie trzymać hasło do DB?

W env / Secrets (K8s, Vault) — nigdy w repo.

Mid / Senior

16. Config w pliku vs env — kiedy plik OK?

Plik bez sekretów, ten sam we wszystkich env; wrażliwe zawsze z env/secret store.

17. Jak 12-factor mapuje się na Docker?

Image = build; tag + env = release; container run = run. Stateless container, port expose.

18. Procfile — co to?

Deklaracja typów procesów (web, worker) — pochodzi z Heroku, idea z factor VIII.

19. Stateless vs sticky session?

12-factor preferuje stateless; sticky session to kompromis — utrudnia skalowanie i deploy.

20. Gdzie trzymać upload plików?

Backing service (S3, GCS) — nie lokalny dysk kontenera (IV, VI).

21. Graceful shutdown w K8s?

SIGTERM → preStop hook → drain connections → exit; terminationGracePeriodSeconds.

22. Immutable infrastructure — związek z factor V?

Release nie mutuje się — nowy deploy = nowy release, rollback = poprzedni release.

23. Feature flags — config czy kod?

Config (env / flag service) — factor III; włączanie bez rebuildu.

24. Monorepo a factor I?

OK jeśli każda app ma własną ścieżkę deploy; jeden repo może mieć wiele apps.

25. 12-factor vs microservices?

12-factor opisuje pojedynczą app; microservices = wiele 12-factor apps + komunikacja między nimi.

26. Health check — czy jest w 12-factor?

Nie explicite — „beyond 12-factor”; dziś standard (/health, /ready) dla K8s probes.

27. Structured logging (JSON) a factor XI?

Zgodne — stdout JSON ułatwia agregację; factor mówi „event stream”, nie format.

28. Flyway/Liquibase — factor XII?

Tak — migracja jako one-off job w pipeline, ten sam release co app.

29. Serverless a factor VIII?

Ekstremalna wersja — platforma skaluje procesy/funkcje; nadal stateless handlers.

30. Co łamie dev/prod parity najczęściej?

Inna baza (SQLite vs Postgres), brak Dockera lokalnie, ręczne configi prod-only.

Pułapki / tricky

31. Czy .env w repo jest OK?

.env.example bez sekretów — OK. .env z hasłami — łamanie III (nigdy commit).

32. Czy factor VI zabrania cache?

Nie — cache read-only/Redis jako backing service OK; in-memory jako source of truth — nie.

33. nginx przed app — łamie port binding?

Nie — app nadal binduje port; nginx to reverse proxy, opcjonalna warstwa.

34. Czy 12-factor wymaga chmury?

Nie — to praktyki przenośne; działają on-prem z Docker/K8s.

35. Jeden JAR, wiele env — ile release?

Ten sam build (artefakt), wiele release (build + różny config per env).

36. WebSocket + stateless?

Trudniejsze — stan połączenia; rozwiązania: sticky, Redis pub/sub, external broker.

37. Cron w app vs osobny worker?

Factor VIII — osobny worker process lepszy niż cron w każdym web procesie.

38. ConfigMaps vs env w K8s?

ConfigMap/Secret inject do env — nadal factor III (config poza kodem).

39. 12-factor a GDPR / audit logs?

Factor XI — logi na stdout; retention i compliance na poziomie platformy agregującej.

40. Najważniejszy factor na rozmowie?

Subiektywnie: III (config) + VI (stateless) — bo łamią się najczęściej i psują skalowanie.
