Część 1 — Fundamenty

1.1 OAuth 2 — autoryzacja, nie logowanie

OAuth 2 odpowiada na pytanie: „Czy aplikacja X może działać w moim imieniu na zasobie Y?” — bez podawania hasła aplikacji. To framework delegacji dostępu (authorization), nie protokół uwierzytelniania użytkownika.

1.2 OIDC — tożsamość na OAuth 2

OpenID Connect (OIDC) to warstwa na OAuth 2 — odpowiada: „Kim jest użytkownik?” Dodaje ID Token (JWT z claims o użytkowniku) i standardowe endpointy (/userinfo, discovery).

OAuth 2OIDC
CelDostęp do API (access token)Logowanie + profil użytkownika
TokenAccess token (często opaque/JWT)+ ID Token (JWT)
Typowy use case„App czyta moje maile”„Zaloguj przez Google”
Scope OIDC—openid (wymagany)

1.3 Jedno zdanie

OAuth 2 = pozwolenie na dostęp. OIDC = OAuth 2 + standard logowania i tożsamości.

Client ID vs Client Secret

Client ID — publiczny identyfikator aplikacji (może być w SPA). Client Secret — tajny klucz — tylko backend (server-side), nigdy w przeglądarce ani mobile app.

Część 3 — Tokeny

Access Token

Poświadczenie dostępu do Resource Server. W nagłówku: Authorization: Bearer <token>. API weryfikuje (podpis JWT, introspection, lub własna baza). Krótki TTL (minuty–godzina).

Refresh Token

Długowieczny token do pobrania nowego access token bez ponownego logowania. Tylko confidential client (backend) lub bezpieczne storage (mobile). Rotacja refresh token — best practice.

ID Token (OIDC only)

JWT o tożsamości użytkownika — dla klienta, nie do wołania API. Claims: sub, email, name, iss, aud, exp, nonce.

// Fragment payload ID Token (JWT)
{
  "iss": "https://auth.example.com/realms/authors",
  "sub": "f843a72e-...",
  "aud": "authors-spa",
  "exp": 1710000000,
  "iat": 1709996400,
  "email": "user@example.com",
  "name": "Anna Kowalska"
}

JWT — struktura

header.payload.signature — Base64URL. Podpis weryfujesz kluczem publicznym z JWKS (iss musi się zgadzać). Nigdy nie ufaj payload bez weryfikacji podpisu.

Część 4 — Authorization Code + PKCE

Standard dla SPA i mobile. Implicit flow i password grant — deprecated.

Kroki (SPA z PKCE)

1. App generuje code_verifier (random) i code_challenge = BASE64URL(SHA256(verifier))
2. Redirect na /authorize z response_type=code, client_id, redirect_uri, scope=openid profile email, code_challenge, code_challenge_method=S256, state, nonce
3. User loguje się u Authorization Server + consent
4. Redirect z powrotem: ?code=AUTH_CODE&state=...
5. App wymienia code na tokeny — POST /token z code_verifier (PKCE), code, redirect_uri
6. Odpowiedź: access_token, id_token, opcjonalnie refresh_token
7. App weryfikuje ID Token (podpis, aud, exp, nonce). API woła z access_token.
// Przykład authorize URL (uproszczony)
GET https://auth.example.com/authorize?
  response_type=code
  &client_id=authors-spa
  &redirect_uri=https://app.example.com/callback
  &scope=openid%20profile%20email
  &code_challenge=E9Melhoa2OwvFrEMT...
  &code_challenge_method=S256
  &state=random-state
  &nonce=random-nonce

Po co PKCE?

Public client (SPA) nie ma client secret. Bez PKCE — kto przechwyci code z redirect URL, wymieni na tokeny. PKCE wiąże code z weryfikatorem znaným tylko oryginalnej app.

state i nonce

ParametrChroni przed
stateCSRF — musisz porównać z wartością w session przed wymianą code
nonce (OIDC)Replay ID Token — musi być w claim nonce JWT

Część 6 — OIDC szczegóły

Scope openid

Bez openid w scope — to czysty OAuth 2 (brak ID Token). Z openid — OIDC. Dodatkowe: profile, email, offline_access (refresh token).

Claims

Atrybuty o użytkowniku — w ID Token i/lub UserInfo. Standardowe: sub (stable user id), email, email_verified, name, preferred_username. Custom claims — realm/client specific.

Discovery

GET https://auth.example.com/realms/authors/.well-known/openid-configuration

// Zwraca m.in.:
// authorization_endpoint, token_endpoint, userinfo_endpoint,
// jwks_uri, scopes_supported, response_types_supported

Klient nie hardcoduje URL-i — pobiera z discovery (issuer musi się zgadzać).

UserInfo endpoint

GET /userinfo
Authorization: Bearer <access_token>

Dodatkowe claims poza ID Token — gdy scope wymaga lub token ma scope userinfo.

Session vs token

Logowanie OIDC tworzy sesję u IdP (cookie na domenie auth) + tokeny dla klienta. Logout — wylogowanie z app ≠ wylogowanie z IdP (SSO session może zostać).

Backend (Spring / Node) — weryfikacja JWT

  1. Pobierz JWKS z iss
  2. Zweryfikuj podpis, exp, iss, aud
  3. Sprawdź scope/role dla endpointu

Typowe providery

Keycloak (self-hosted), Auth0, Azure AD / Entra ID, Google, Okta — wszyscy implementują OIDC + discovery.

BFF pattern (Backend for Frontend)

SPA → własny backend → wymiana code, tokeny w HttpOnly cookie. Secret nigdy w przeglądarce. Popularne w enterprise SPA.

Część 8 — Najczęstsze błędy

  1. OAuth 2 = logowanie — sam OAuth nie mówi kim jest user; OIDC tak
  2. ID Token w API — API oczekuje access token, nie id_token
  3. Client secret w SPA — wyciek; użyj PKCE
  4. Implicit flow w 2024+ — deprecated, token w URL
  5. Brak weryfikacji state/nonce — CSRF / replay
  6. Brak weryfikacji JWT (podpis, aud, iss) — akceptujesz sfałszowany token
  7. Access token w localStorage — XSS = kradzież sesji
  8. redirect_uri mismatch — dokładne dopasowanie z rejestracją klienta
  9. Mylenie scope z rolą aplikacji — scope w token ≠ automatycznie RBAC w DB
  10. Brak rotacji refresh token — skradziony refresh = długi dostęp

Pytania rekrutacyjne — krótkie odpowiedzi

Junior / Mid

1. Co to OAuth 2?

Framework delegacji dostępu — aplikacja działa w imieniu użytkownika bez hasła do API.

2. Co to OIDC?

Warstwa tożsamości na OAuth 2 — logowanie, ID Token, standardowe claims.

3. OAuth vs OIDC — różnica?

OAuth = autoryzacja (dostęp). OIDC = uwierzytelnianie (kim jest user) + OAuth.

4. Cztery role OAuth?

Resource Owner, Client, Authorization Server, Resource Server.

5. Co to access token?

Poświadczenie dostępu do API — Bearer w nagłówku Authorization.

6. Co to ID Token?

JWT o tożsamości użytkownika — dla klienta (OIDC), nie do API.

7. Co to refresh token?

Token do pobrania nowego access token bez ponownego logowania.

8. Authorization Code flow — idea?

Redirect → code → wymiana code na tokeny po stronie klienta (backend/BFF).

9. Po co PKCE?

Ochrona public client (SPA) — code bez verifiera nie da się wymienić.

10. Co to scope openid?

Włącza OIDC — odpowiedź zawiera ID Token.

11. Co to state?

Parametr anty-CSRF — porównujesz po redirect z wartością sprzed authorize.

12. Co to nonce (OIDC)?

Anty-replay — musi być w claim nonce ID Token.

13. Client ID vs Client Secret?

ID publiczny. Secret tajny — tylko confidential client (backend).

14. Implicit flow — używać?

Nie — deprecated; token w URL, brak PKCE.

15. Claim sub?

Subject — stabilny identyfikator użytkownika u tego iss.

Mid / Senior

16. Access token vs ID Token — komu?

Access → Resource Server. ID Token → Client (informacja o userze).

17. Client Credentials flow?

M2M — client_id + secret → access token, bez użytkownika i ID Token.

18. Jak API weryfikuje JWT?

JWKS, podpis, exp, iss, aud — potem scope/role.

19. Discovery endpoint?

/.well-known/openid-configuration — metadata IdP, endpointy, scopes.

20. UserInfo vs ID Token?

ID Token przy logowaniu. UserInfo — dodatkowe claims na żądanie z access token.

21. BFF pattern — po co?

Tokeny poza przeglądarką — HttpOnly cookie, secret na serwerze.

22. Token introspection?

POST do IdP — opaque token → active, scope, sub (gdy token nie JWT).

23. Rotacja refresh token?

Nowy refresh przy każdym użyciu — stary unieważniony; ogranicza kradzież.

24. SSO vs token w app?

SSO = sesja cookie u IdP. App ma własne tokeny — logout z app ≠ SSO logout.

25. aud vs azp w JWT?

aud — odbiorca tokena. azp — authorized party (kto poprosił — klient).

26. Scope vs Role w aplikacji?

Scope w tokenie (OAuth). Role — logika RBAC w app (może mapować z claims).

27. offline_access scope?

Żądanie refresh token — dostęp gdy user offline od IdP UI.

28. Device Authorization Grant?

User loguje na innym urządzeniu — TV/CLI dostaje token po poll.

29. Keycloak vs Auth0?

Keycloak — open source, self-host. Auth0 — SaaS, managed IdP. Oba OIDC.

30. Resource Owner Password — dlaczego źle?

App zbiera hasło — omija IdP UX, MFA, consent; deprecated.

Pułapki / tricky

31. Czy OAuth sam w sobie uwierzytelnia?

Nie w pełni — OIDC dodaje uwierzytelnianie użytkownika (ID Token).

32. JWT = bezpieczny?

Podpis integrity OK; ale każdy z tokenem może użyć — krótki TTL, HTTPS, nie w URL.

33. Dekodować JWT w JS wystarczy?

Nie — decode ≠ verify; bez weryfikacji podpisu można sfałszować payload.

34. PKCE tylko dla mobile?

Nie — wymagane/rekomendowane dla wszystkich public clients (SPA too).

35. redirect_uri wildcard w prod?

Ryzyko — token redirect do ataku; dokładne URI per env.

36. CORS a OAuth?

/authorize to redirect (nie XHR). /token z SPA — CORS musi być skonfigurowany u IdP.

37. Długi access token TTL?

Złe — przy kradzieży długi dostęp; krótki access + refresh.

38. Logout — co czyści?

App session, refresh token revoke, opcjonalnie IdP end_session (SSO).

39. Multi-tenant — iss claim?

iss identyfikuje IdP/realm — weryfikuj zawsze; inny iss = inny tenant.

40. Najważniejszy flow na rozmowie?

Authorization Code + PKCE — SPA/mobile; umieć krok po kroku i role tokenów.
