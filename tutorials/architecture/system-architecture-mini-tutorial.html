Architektura Style i podział

Monolit

Jeden deployable — prosty start, wspólna baza, łatwy debug. Skala przez większą maszynę lub repliki całości. Pułapka: coupling rośnie z czasem.

Modularny monolit

Monolit z wyraźnymi modułami (np. authors, titles) — granice w kodzie, jeden proces. Często lepszy start niż microservices.

Mikroserwisy

Osobne serwisy, deploy, baza (database per service). Skala niezależna, technologie mix. Koszt: sieć, spójność, DevOps, obserwowalność.

SOA vs mikroserwisy

SOA — większe serwisy, często ESB. Mikroserwisy — mniejsze, smart endpoints / dumb pipes (API + events, bez centralnego ESB).

Event-Driven Architecture (EDA)

Serwisy komunikują się zdarzeniami (AuthorCreated). Luźne powiązanie, skalowanie async. Trudniejsze: debug, spójność końcowa, ordering.

Serverless / FaaS

Funkcje na żądanie — zero ops serwerów, płatność per invocation. Cold start, limity czasu, vendor lock-in.

Layered / Hexagonal / Clean

Podział warstw wewnątrz aplikacji — domain w środku, adaptery na zewnątrz. Nie zastępuje podziału na serwisy.

Sync vs async — kiedy co

Sync — potrzebujesz odpowiedzi od razu (UI czeka). Async — możesz odłożyć (email, indeks, raport), wyższa odporność na awarie downstream.

Rozproszone Fundamenty

CAP theorem

W partition (P) wybierasz między Consistency (C) a Availability (A). W praktyce P zawsze możliwy — trade-off C vs A + opóźnienie (latency).

PACELC

Rozszerzenie CAP: przy Partition → A lub C; Else (normalnie) → Latency vs Consistency.

Eventual consistency (spójność końcowa)

Repliki z czasem się zgodzą — akceptowalne w wielu systemach rozproszonych; UI musi to uwzględniać.

Network partition

Sieć dzieli węzły — split-brain bez quorum. Rozwiązania: majority quorum, fencing tokens.

Quorum

Decyzja wymaga większości węzłów (N/2+1) — unika split-brain przy partition.

Consensus (Raft, Paxos)

Protokoły uzgodnienia wartości w klastrze — etcd (K8s), leader election, replicated log.

Leader / follower

Jeden leader przyjmuje zapisy, reszta replikuje — failover przy awarii leadera (election).

Clock skew

Zegary w węzłach nie są identyczne — nie polegaj na timestamp jako jedynym porządku (użyj logical clocks / version vectors).

At-least-once / at-most-once / exactly-once

Dostawa wiadomości: retry → at-least-once; exactly-once drogie — idempotency + dedup w praktyce.

WzorzecCo robi

Circuit breakerPo N błędach — przerwij wołania, daj serwisowi odpocząć (open → half-open → closed)
BulkheadIzolacja pul (wątki, connections) — awaria jednej części nie zabija całości

Graceful degradationRekomendacje wyłączone, cache stale — partial response lepszy niż 500
Health check/health (alive), /ready (może przyjąć ruch) — LB i K8s probes

Fail fast — szybko zwróć błąd zamiast blokować wątki. Design for failure — zakładaj, że sieć, DB i downstream padną.

Typowe błędy

  1. Microservices day one — złożoność bez potrzeby
  2. Wspólna baza między serwisami — coupling, brak niezależnego deployu
  3. Sync chain A→B→C→D — latency sumuje się, jeden fail = cascade
  4. Brak timeoutów i retry bez idempotency — duplikaty i zawieszone wątki
  5. Ignorowanie eventual consistency w UI — „zapisałem, czemu nie widać w index?”
  6. Cache bez strategii invalidacji — stale data forever
  7. Brak observability — „działa u mnie”, prod to czarna skrzynka
  8. Distributed monolith — wiele serwisów, ale wszystkie muszą deploy razem
