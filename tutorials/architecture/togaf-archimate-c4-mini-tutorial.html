Co to jest TOGAF

TOGAF (The Open Group Architecture Framework) to otwarty framework do projektowania, planowania, wdrażania i zarządzania architekturą przedsiębiorstwa (Enterprise Architecture, EA). Nie jest narzędziem ani notacją graficzną — to metoda pracy, zbiór artefaktów i rekomendacji, które porządkują decyzje architektoniczne od strategii biznesowej po infrastrukturę IT.

W organizacji TOGAF pełni rolę wspólnego języka i procesu między biznesem, architektami, bezpieczeństwem i zespołami delivery. Umożliwia: spójne planowanie transformacji, zarządzanie portfelem inicjatyw, traceability od celów strategicznych do rozwiązań technicznych oraz governance architektury (Architecture Board, compliance, wyjątki).

TOGAF obejmuje m.in. ADM (Architecture Development Method), Architecture Content Framework (struktura artefaktów), Enterprise Continuum (od wzorców referencyjnych po rozwiązania wdrożone) oraz Capability-Based Planning. Wersja TOGAF Standard, 10th Edition (2022) rozszerza ADM o Agile, DevOps i digital product delivery — metoda pozostaje iteracyjna, nie waterfallowa.

Cykl ADM — praktycznie

Architecture Development Method (ADM) to serce TOGAF: cykl 9 faz (plus wymaganie) opisujący, jak budować i ewoluować architekturę. W praktyce ADM to nie sztywny waterfall — fazy mogą być wykonywane równolegle, w iteracjach lub tylko częściowo (np. sam Phase B + C dla jednej inicjatywy).

Praktyczna zasada: ADM odpowiada na pytania dlaczego (A), co biznes robi (B), jakie systemy i dane (C), na czym to stoi (D), jak to dostarczyć (E–F) i czy wdrożenie jest zgodne (G–H).

Integracja TOGAF, ArchiMate i C4 Model

Te trzy standardy operują na różnych poziomach abstrakcji, ale adresują ten sam problem: jak opisać architekturę tak, by decydenci i zespoły techniczne mówili o tym samym systemie.

StandardRolaAdresatTypowy artefakt
TOGAF Proces i governance — kiedy, dlaczego, w jakiej kolejności EA, CIO, Architecture Board Roadmapa, principles, compliance
ArchiMate Notacja enterprise — warstwy, relacje, viewpoints Architekci EA, analitycy biznesowi Modele warstwowe w repozytorium EA
C4 Model Widoki software — kontekst, kontenery, komponenty, kod Dev team, tech lead, solution architect Diagramy Context + Containers (często w Structurizr/PlantUML)
TOGAF mówi „co i kiedy”

Definiuje fazy ADM, artefakty (np. Application Architecture w Phase C), zasady i roadmapę transformacji. Nie narzuca składni diagramów.

ArchiMate mówi „jak modelować EA”

Warstwy Business, Application, Technology + Motivation, Strategy, Implementation & Migration. Relacje typu serving, realization, assignment łączą elementy między warstwami. Viewpoints (np. Layered, Service Realization) filtrują widok dla stakeholdera.

C4 mówi „jak opisać software dla programistów”

Upraszcza jeden system (lub jego fragment) do 4 poziomów zoom. Idealny jako zoom-in z ArchiMate Application Component lub TOGAF Application Architecture.

Synergia: TOGAF Phase B–D produkuje modele, które naturalnie mapują się na warstwy ArchiMate. Wybrane elementy Application Layer (np. Loyalty Platform) rozwijasz w C4 Context i Containers dla zespołu delivery. Traceability: Capability biznesowa → Application Service (ArchiMate) → Container (C4) → repozytorium kodu.

Zasady architektoniczne TOGAF

Architecture Principles to ogólne reguły decyzyjne — krótkie, testowalne, zatwierdzone przez Architecture Board w Phase Preliminary. Poniżej 5 kluczowych zasad rekomendowanych przez TOGAF (nazwy mogą być dostosowane do organizacji, sens pozostaje zgodny ze standardem).

1. Business Continuity First (Pierwszeństwo biznesu)

Architektura służy celom biznesowym, nie odwrotnie. Każda decyzja techniczna musi być uzasadniona wpływem na value stream, revenue lub ryzyko operacyjne. Test: „Jaki capability biznesowy wspieramy tym wyborem?”

2. Information is Shared (Wspólne dane / Information Sharing)

Dane są zasobem korporacyjnym — preferuj single source of truth, unikaj silosów i duplikacji master data. Integracje przez udostępnione usługi/API, nie kopiowanie plików ad hoc. Zgodne z Phase C (Data Architecture).

3. Technology Independence (Niezależność od dostawcy)

Decyzje nie mogą nieuzasadnionie wiązać organizacji z jednym vendorem. Preferuj otwarte standardy, warstwy abstrakcji, możliwość wymiany komponentu. Wyjątki wymagają formalnego Architecture Exception.

4. Interoperability (Interoperacyjność)

Systemy muszą współpracować przez zdefiniowane interfejsy (API, events, pliki według standardu). Nowe rozwiązania integrują się z istniejącym landscape — nie budujemy „wyspy”. ArchiMate serving / flow; C4 Context pokazuje sąsiadów.

5. Security by Design (Bezpieczeństwo od początku)

Security, privacy i compliance są wbudowane w ADM od Phase A, nie dokładane na końcu. Identity, autoryzacja, szyfrowanie, audyt — zgodnie z politykami organizacji i regulacjami (RODO itd.).

TOGAF zaleca też m.in. Reuse Before Buy Before Build, Responsive Change Management i Common Use Applications — wybór zależy od dojrzałości EA w organizacji (zwykle 10–20 principles, nie 50).

Case study: program lojalnościowy klientów

Scenariusz: sieć retail wdraża Customer Loyalty Platform — punkty za zakupy, poziomy członkostwa, personalizowane oferty w aplikacji mobilnej i na kasie. Integracja z ERP (zamówienia), CRM (profil klienta), POS (naliczanie punktów przy transakcji).

TOGAF — fazy i uzasadnienie biznesowe

  • Phase A (Vision): Cel — zwiększenie retention o 15%, LTV klienta; scope: loyalty + integracje; stakeholderzy: Marketing, Store Ops, IT, Legal (RODO).
  • Phase B (Business): Capability Customer Engagement; procesy: rejestracja, naliczanie punktów, wymiana nagród, segmentacja; role: klient, kasjer, marketer.
  • Phase C (IS): Nowa aplikacja Loyalty Platform; współdzielone dane: Customer Golden Record w CRM; eventy transakcyjne z POS.
  • Phase D (Technology): Cloud (K8s), API Gateway, PostgreSQL + Redis, standard OAuth2/OIDC z corporate IdP.
  • Phase E–F: Work packages: (1) core loyalty API, (2) integracja POS, (3) mobile app; roadmap Q1–Q3; migracja istniejących kart papierowych.
  • Phase G: Review — czy POS wysyła eventy w formacie zatwierdzonym przez Data Architecture.

ArchiMate — mapowanie warstw

Business Layer

  • Business Actor: Klient, Kasjer
  • Business Process: Nalicz punkty przy zakupie, Wymień nagrodę
  • Business Service: Program lojalnościowy — realizowany przez warstwę aplikacji

Application Layer

  • Application Component: Loyalty Platform, CRM, POS Middleware, Mobile App
  • Application Service: PointsAccrualService, RewardsCatalogService
  • Data Object: CustomerProfile, PointsBalance, TransactionEvent
  • Relacje: Mobile App uses Loyalty Platform; Loyalty serves Business Service; POS flows TransactionEvent → Loyalty

Technology Layer

  • Node: K8s Cluster (prod); Device: POS terminal, smartphone
  • System Software: API Gateway, PostgreSQL, Redis, Kafka (opcjonalnie event bus)
  • Relacja: Loyalty Platform assigned to K8s Node

Typowe błędy

  1. TOGAF jako papierologia — pełne ADM dla każdej małej zmiany; brak tailoringu metody do skali inicjatywy.
  2. Jeden diagram „na wszystko” — mieszanie strategii biznesowej z klasami Java na jednym slajdzie; utrata odbiorcy.
  3. ArchiMate bez viewpoints — model 500 elementów bez filtrów; nikt go nie czyta. Stosuj Layered View, Service Realization View per stakeholder.
  4. C4 zamiast EA — tylko diagramy kontenerów bez powiązania z capabilities i roadmapą TOGAF; brak governance.
  5. Brak Architecture Principles — spór SQL vs NoSQL rozstrzygany ad hoc zamiast przez zatwierdzone zasady (np. Technology Independence).
  6. Duplikacja master data — loyalty trzyma własną kopię klienta zamiast CRM jako source of truth (łamanie Information Sharing).
  7. Phase G pomijane — wdrożenie bez compliance review; produkcja odbiega od target architecture bez śladu decyzji.
  8. Niespójne nazewnictwo — ten sam system jako „Loyalty”, „Points Engine” i „CRM Extension” w różnych artefaktach.
  9. Zbyt głęboki C4 za wcześnie — Components/Code przed ustaleniem granic kontenerów i kontraktów API.
  10. Brak Requirements Management — wymagania biznesowe nie są trace’owane do elementów ArchiMate ani user stories w backlogu.
