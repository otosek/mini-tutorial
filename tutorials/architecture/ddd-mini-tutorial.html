Co to jest DDD

Domain-Driven Design to podejście do budowy oprogramowania, w którym model domeny biznesowej jest sercem systemu. Kod, nazwy klas i rozmowy zespołu mówią tym samym językiem co eksperci domenowi.

DDD nie jest frameworkiem — to zestaw wzorców, heurystyk i podziału pracy. Sens ma przy złożonej domenie, nie przy CRUD bez reguł.

Zasada: Domain nie zna bazy ani Reacta. Zależności idą do wewnątrz — infrastructure implementuje interfejsy z domain.

Strategiczne — najważniejsze hasła

Domain (domena)

Obszar wiedzy i działalności biznesowej — „zarządzanie autorami i tytułami”, nie „React” ani „PostgreSQL”.

Ubiquitous Language (wspólny język)

Ten sam słownik w rozmowach z biznesem, w kodzie i dokumentacji. Author, nie UserRecord. Hasło ≠ login w kontekście księgarstwa.

Bounded Context (ograniczony kontekst)

Granica, w której model ma jedno znaczenie. Ten sam termin może znaczyć co innego w innym kontekście. Kontekst = granica spójności modelu i zespołu.

Context Map (mapa kontekstów)

Diagram relacji między kontekstami — kto od kogo zależy, jak się integrują (upstream/downstream).

Core Domain

To, co daje przewagę konkurencyjną — tu inwestujesz najlepszych ludzi i najwięcej uwagi.

Supporting Subdomain

Ważne, ale nie unikalne — można kupić/zlecić (np. wysyłka maili).

Generic Subdomain

Commodity — auth, logowanie, płatności standardowe. Nie wymyślaj od zera.

Anti-Corruption Layer (ACL)

Warstwa tłumacząca między Twoim modelem a cudzym API — chroni domenę przed obcym językiem i strukturą.

Taktyczne — najważniejsze hasła

Entity (encja)

Obiekt z tożsamością trwającą w czasie — Author z id. Dwa autory z tym samym id = ten sam autor.

Value Object (obiekt wartości)

Bez własnej tożsamości — definiowany atrybutami. Email, Money, Address. Immutable, porównanie po wartościach.

Aggregate (agregat)

Klaster encji + VO traktowany jako jedna jednostka spójności. Zmiany przez korzeń. Spójność transakcyjna w granicach agregatu.

Aggregate Root (korzeń agregatu)

Jedyny punkt wejścia do agregatu — z zewnątrz referencje tylko do root. Np. Order jako root, OrderLine wewnątrz.

Repository

Abstrakcja persystencji agregatu — „jak kolekcja w pamięci”. AuthorRepository.save(), findById(). Domain nie zna SQL.

Domain Service

Operacja domenowa, która nie pasuje do jednej encji — np. „przenieś autora do innego wydawnictwa” wymagające kilku obiektów. Bez stanu.

Application Service

Orkiestracja use case — transakcja, wywołanie repo, domain service, publikacja eventu. Cienka warstwa, mało logiki biznesowej.

Domain Event (zdarzenie domenowe)

Coś ważnego, co już się stało w domenie — AuthorCreated, TitlePublished. Inne agregaty reagują asynchronicznie.

Factory

Tworzenie skomplikowanych agregatów z zachowaniem invariantów — gdy konstruktor to za mało.

Invariant (invariant)

Reguła zawsze prawdziwa w agregacie — „email unikalny”, „suma pozycji = total zamówienia”. Chroni korzeń agregatu.

Specification

Obiekt opisujący regułę selekcji/walidacji wielokrotnego użytku — „autor kwalifikujący się do promocji”.

Przykład — projekt authors

Bounded Contexts (katalogi src/):

  authors/     → Author, reguły autorów, CRUD
  titles/      → Title, powiązanie z autorem (inny model „autora” — tylko id/ref?)
  index/       → wyszukiwanie, read model (może inny język: Document, Entry)

Relacje:
  titles  ──Customer/Supplier──►  authors
  index   ──ACL / Conformist──►   authors + titles (odczyt)
KontekstAggregate Root?Warstwa dziś w projekcie
authorsAuthorPresentation + Application (useAuthors) + Infrastructure (authorList)
titlesTitle (?)Do zbudowania — osobny model, nie kopiuj Author 1:1
index— (query)Often read-only / CQRS projection

Uwaga: W monolicie foldery src/authors to początek podziału na konteksty — nie muszą od razu być osobnymi serwisami (microservices).

Typowe błędy

  1. Anemic Domain Model — encje tylko getter/setter, logika w serwisach „proceduralnych”
  2. Jeden wielki model — brak bounded contexts, wszystko w jednej bazie encji
  3. Agregat za duży — cała baza w jednym root → konflikty, wolne transakcje
  4. Referencje między agregatami po obiekcie — tylko ID, nie Author wewnątrz Title jako encja
  5. Repository dla każdej encji — repo tylko dla aggregate root
  6. DDD wszędzie — overkill przy prostym CRUD; DDD gdy reguły i złożoność rosną
  7. Ubiquitous Language tylko w kodzie — bez udziału ekspertów domeny słowa się rozjeżdżają
