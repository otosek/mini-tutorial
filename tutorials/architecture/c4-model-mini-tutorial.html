Co to jest C4

C4 Model to lekki sposób opisywania architektury oprogramowania w czterech poziomach przybliżenia (jak mapa: kraj → miasto → ulica → plan mieszkania). Autor: Simon Brown. Nie jest standardem ISO ani metodą EA — to konwencja diagramów + słownik elementów, która działa w dokumentacji, ADR i rozmowach z zespołem.

Jeden diagram = jeden poziom zoom na jeden software system (granica odpowiedzialności zespołu). Relacje między elementami opisujesz krótkimi zdaniami („Wysyła zdarzenia do…”, „Czyta dane z…”). Szczegóły implementacji (framework, wersja JDK) należą do opisów kontenerów lub kodu, nie do każdego prostokąta na Context.

C4 dobrze łączy się z EA (TOGAF, ArchiMate) jako zoom-in z warstwy aplikacji — szerszy kontekst opisuje tutorial TOGAF · ArchiMate · C4.

Context: maks. ~10–15 elementów. Jeśli nie mieści się — podziel na dwa systemy lub dwa widoki (np. integracje wewnętrzne vs zewnętrzne).

Opis relacji obowiązkowy

Strzałka bez etykiety („REST”) to najczęstszy błąd. C4 wymaga: co płynie i po co (sync/async, format).

Narzędzia: Structurizr (DSL + eksport do PlantUML/Mermaid), PlantUML C4, draw.io z biblioteką C4, IcePanel. Diagramy trzymaj w repo obok kodu (np. docs/architecture/).

Kiedy stosować C4

SytuacjaStosujPoziom
Onboarding nowego deva / opis domeny produktuTakContext (+ krótki opis systemu)
Projekt nowego serwisu, podział na mikroserwisy vs monolitTakContext → Containers
Review integracji (API, eventy) przed sprintemTakContext lub Containers
Refactoring wewnątrz jednej aplikacjiTakComponents (czasem Code)
Cała mapa 500 systemów korporacjiRaczej nie sam C4ArchiMate / asset catalog; C4 per wybrany system
Diagram sieci VLAN, racków, firewalliNieDiagram infrastruktury / cloud (osobna notacja)
User journey / ekrany UINieWireframe, mapa ekranów
Algorytm sortowania w jednej funkcjiNieKod + test, bez C4

Heurystyka: jeśli rozmowa dotyczy granicy odpowiedzialności lub kontraktu między deployable units — narysuj Containers. Jeśli dotyczy całego produktu na rynku — Context. Components rysuj, gdy zespół utknął w jednym repo i trzeba ustalić moduły bez przedwczesnego microservices split.

Kiedy aktualizować: przy zmianie integracji zewnętrznej (Context), wydzieleniu bazy/kolejki (Containers), wyciągnięciu modułu (Components). Context rzadziej niż Containers.

Przykład 1: biurowiec — ta sama logika co C4

Poniżej nie jest to diagram BMS w notacji C4 dla inwestora — to analogia, która uczy poziomów bez żargonu IT. Potem ten sam schemat myślenia przenosisz na software (przykład 2).

Obiekt analogii: „System” = biurowiec Smart Tower

Funkcja: bezpieczna praca i komfort najemców. Granica systemu: działka + budynek (nie całe miasto).

3 · Components — wnętrze jednego kontenera (np. HVAC)

  • Controller stref — regulacja per piętro
  • Sensor network — temperatura, CO₂, wilgotność
  • Schedule engine — tryb dzień/noc, święta
  • Alarm handler — awaria filtra → BMS

Relacje: czujniki → controller (odczyt co 30 s); controller → aktuatory (PWM); schedule → controller (setpoint).

4 · Code — pojedynczy sterownik

Na tym poziomie analogii: schemat PLC, mapa rejestrów Modbus, firmware czujnika — odpowiednik diagramu klas w Java. W projekcie IT Level 4 często pomijasz ręcznie — wystarczy link do pakietu w repo.

Wniosek z analogii: gość na recepcji (Person) nie musi znać PID w kotłowni (Code). Context wystarczy dla najemcy; serwis HVAC zna Components.

4 · Code

Przykład: interfejs AvailabilityService + implementacja DefaultAvailabilityService w pakiecie com.smarttower.booking.domain — generuj z IDE lub pomiń w wiki, jeśli repo jest źródłem prawdy.

Mapowanie analogia → IT: Najemca = Person; HVAC = osobny container (tu: Calendar Sync); BMS = Booking API agregujące logikę; recepcja = Web App + reguły gości (tu: role z IdP).

Structurizr DSL — szkic

DSL trzyma diagramy jako tekst w repo; jeden model, wiele widoków (Context, Containers).

workspace {
    model {
        employee = person "Pracownik"
        booking = softwareSystem "Room Booking Platform" {
            web = container "Web App" "React"
            api = container "Booking API" "Spring Boot"
            db = container "Booking DB" "PostgreSQL"
        }
        m365 = softwareSystem "MS 365 Calendar"
        employee -> web "Rezerwuje sale" "HTTPS"
        web -> api "API" "JSON/HTTPS"
        api -> db "Czyta/zapisuje" "JDBC"
        api -> m365 "Sync wydarzeń" "Graph API"
    }
    views {
        systemContext booking { include * }
        container booking { include * }
    }
}

Typowe błędy

  1. Jeden diagram na wszystkie poziomy — klasy Java obok CRM i kasjer na jednym slajdzie; odbiorca traci kontekst.
  2. Brak etykiet na strzałkach — nie wiadomo, czy to sync REST, event, czy batch nocny.
  3. „Container” = VM lub Kubernetes pod — w C4 container to aplikacja/baza/kolejka, nie node K8s (infrastruktura to osobny diagram).
  4. Rozwijanie systemu sąsiedniego w Containers — CRM na Context zostaje czarną skrzynką; jego wnętrze to osobny model C4 innego zespołu.
  5. Components przed ustaleniem granic API — najpierw Containers i kontrakty, potem moduły w API.
  6. Diagram bez opisu systemu — prostokąt „Platforma X” bez 2 zdań o wartości biznesowej.
  7. Level 4 ręcznie dla całego monolitu — szybko się starzeje; lepiej odnośnik do modułu w repo.
  8. Mylenie C4 z modelem danych ERD — tabele mogą być kontenerem (DB), ale relacje FK to nie diagram architektury.
  9. Brak decyzji, co jest „systemem” — Mobile App czasem jest kontenerem, czasem osobnym systemem; ustal z zespołem i trzymaj konsekwencję.
  10. Diagramy tylko na kickoff — po zmianie integracji z MS 365 Context/Containers muszą być zaktualizowane, inaczej ADR i kod się rozjeżdżają.
