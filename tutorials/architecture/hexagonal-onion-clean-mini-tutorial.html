Fundament — po co te trzy nazwy

Hexagonal (Ports & Adapters), Onion i Clean Architecture to nie trzy konkurencyjne frameworki, lecz trzy sposoby opisania tego samego celu: reguły biznesowe w centrum, zależności skierowane do środka, technologia (HTTP, JPA, Kafka) na obwodzie. Różnią się metaforą i słownictwem — w projekcie Spring Boot często łączysz je w jedną strukturę pakietów.

Jedno zdanie na zapamiętanie: port to kontrakt, adapter to implementacja, use case to scenariusz, agregat to prawo domeny.

1. Teoretyczny opis architektur

a) Architektura heksagonalna (Ports & Adapters)

Metafora Inside / Outside: w środku aplikacji siedzi logika domenowa i scenariusze aplikacyjne; na zewnątrz — „świat” (użytkownik, baza, kolejka, inny serwis). Port to interfejs w języku domeny („potrzebuję zapisać zamówienie”), adapter to konkretna technologia (REST controller, repozytorium JPA, klient HTTP).

Cel: wymienność infrastruktury bez dotykania reguł. Testujesz use case z adapterem w pamięci; produkcja podpina PostgreSQL — ten sam port, inna implementacja.

Cecha wyróżniająca: symetria wejścia i wyjścia. Sterownik HTTP i repozytorium bazy to oba adaptery; oba wołają porty zdefiniowane przez aplikację/domenę. Nie ma „górnej warstwy ważniejszej od dolnej” — obie są równorzędnymi wejściami/wyjściami do heksagonu.

b) Onion Architecture

Metafora koncentrycznych pierścieni: im głębiej w cebuli, tym mniej zależności od szczegółów technicznych i tym stabilniejszy kod. Jądro to model domeny; kolejne pierścienie to serwisy aplikacyjne, interfejsy infrastruktury, na zewnątrz implementacje.

Cel: chronić jądro przed „przeciekaniem” frameworków — encje JPA, adnotacje Springa i DTO HTTP nie powinny definiować modelu biznesowego.

Cecha wyróżniająca: reguła zależności według promienia — warstwa zewnętrzna może znać wewnętrzną (adapter implementuje interfejs zdefiniowany bliżej centrum), nigdy odwrotnie. Stabilność rośnie w kierunku jądra.

c) Clean Architecture (Robert C. Martin)

Metafora rygorystycznego podziału ról: Entities (reguły enterprise), Use Cases (reguły aplikacji), Interface Adapters (prezentacja, persistence, mapowanie), Frameworks & Drivers (Spring, Hibernate, baza). Nazwy są sztywne, ale mapują się 1:1 na hex/onion.

Cel: niezależność od UI, bazy i frameworków — biznes może działać w konsoli, a potem dostać REST bez przepisywania use case’ów.

Cecha wyróżniająca: Dependency Rule — źródła zależności wskazują wyłącznie do wewnątrz. Use case nie importuje JpaRepository; gateway (port wyjściowy) jest interfejsem w pierścieniu use case, implementacja (np. OrderRepositoryJpaAdapter) żyje na zewnątrz.

2. Anatomia obiektów i zmiana warstw (mapowanie)

Te same słowa („Order”) pojawiają się w wielu warstwach — to różne typy obiektów. Mapowanie między nimi robi adapter lub mapper w infrastrustrukturze, nie agregat.

TypWarstwaRolaFramework
DTO / Request–Response Presentation (adapter wej.) Kształt JSON/API; walidacja techniczna (@NotNull, format). Nie niesie reguł biznesowych. Often records + Bean Validation w adapterze
Command / Query Application Intencja use case’a: CreateOrderCommand, GetOrderQuery. Proste, niemutowalne. Czyste record, bez Springa
Domain model / VO Domain Agregaty, value objects, reguły i invarianty. Metody biznesowe zmieniają stan. POJO / records — zero adnotacji
DB Entity / JPA bean Infrastructure (persistence adapter) Mapa tabeli: kolumny, relacje ORM. Nie wychodzi poza adapter. @Entity, @Table, Spring Data tylko tutaj
Przepływ przy tworzeniu zamówienia

CreateOrderRequest (DTO) → controller mapuje na CreateOrderCommand → CreateOrderUseCase buduje/wywołuje Order (domena) → OrderRepository.save(order) (port) → adapter mapuje Order → OrderJpaEntity → baza.

Pułapka: jeden wspólny „OrderDTO” używany od kontrolera do Hibernate — łamie izolację i prowadzi do anemicznego modelu albo reguł w adnotacjach JPA.

3. Struktura pakietów w Javie (moduł order)

Poniżej wzorcowe drzewo dla bounded context / modułu order w monolicie Maven. Pakiety odzwierciedlają warstwy; Spring skanuje tylko ...adapter... i ...config....

com.example.shop.order/

│       └── GetOrderService.java

    ├── in/
    │   └── web/
    │       ├── OrderController.java     # @RestController — ADAPTER IN
    │       ├── CreateOrderRequest.java  # record + @Valid
    │       └── OrderResponse.java       # record
    ├── out/
    │   └── persistence/
    │       ├── OrderJpaEntity.java      # @Entity — tylko persistence
    │       ├── OrderLineJpaEmbeddable.java
    │       ├── SpringDataOrderJpaRepository.java  # extends JpaRepository
    │       ├── OrderRepositoryAdapter.java        # ADAPTER OUT — implements OrderRepository
    │       └── OrderPersistenceMapper.java        # Order ↔ OrderJpaEntity
    └── out/
        └── catalog/
            └── HttpProductCatalogAdapter.java     # ADAPTER OUT — implements ProductCatalogPort
│
└── config/                              # składanie beanów Springa
    └── OrderModuleConfiguration.java    # @Configuration — rejestruje use case + adaptery

W wariancie Clean nazwy port/in ≈ Input Boundary, port/out ≈ Gateway. W Onion folder domain to jądro, application pierścień, adapter skórka.

4. Przykład w kodzie Java — utworzenie zamówienia

Minimalny, spójny przekrój: agregat z regułą, port wyjściowy, use case, adapter JPA i konfiguracja Springa poza domeną.

Domain — agregat i port (tylko w application/port/out)

// domain/model/OrderId.java
public record OrderId(UUID value) {
    public OrderId {
        Objects.requireNonNull(value);
    }
}

// domain/model/OrderLine.java
public record OrderLine(String sku, int quantity, Money unitPrice) {
    public OrderLine {
        if (quantity <= 0) throw new OrderDomainException("quantity must be positive");
        Objects.requireNonNull(sku);
        Objects.requireNonNull(unitPrice);
    }
    Money lineTotal() { return unitPrice.multiply(quantity); }
}

// domain/model/Order.java — rich model, bez setterów
public final class Order {
    private final OrderId id;
    private final List<OrderLine> lines;
    private OrderStatus status;

    private Order(OrderId id, List<OrderLine> lines) {
        this.id = id;
        this.lines = List.copyOf(lines);
        this.status = OrderStatus.DRAFT;
    }

    public static Order createDraft(OrderId id, List<OrderLine> lines) {
        if (lines.isEmpty()) throw new OrderDomainException("order needs at least one line");
        return new Order(id, lines);
    }

    public void confirm() {
        if (status != OrderStatus.DRAFT)
            throw new OrderDomainException("only draft can be confirmed");
        status = OrderStatus.CONFIRMED;
    }

    public OrderId id() { return id; }
    public OrderStatus status() { return status; }
    public List<OrderLine> lines() { return lines; }
}

// application/port/out/OrderRepository.java — PORT wyjściowy
public interface OrderRepository {
    void save(Order order);
    Optional<Order> findById(OrderId id);
}

Application — command i use case

// application/command/CreateOrderCommand.java
public record CreateOrderCommand(UUID orderId, List<Line> lines) {
    public record Line(String sku, int quantity, BigDecimal unitPrice, String currency) {}
}

// application/port/in/CreateOrderUseCase.java
public interface CreateOrderUseCase {
    OrderId handle(CreateOrderCommand command);
}

// application/service/CreateOrderService.java — czysta Java
public final class CreateOrderService implements CreateOrderUseCase {
    private final OrderRepository orders;
    private final ProductCatalogPort catalog;

    public CreateOrderService(OrderRepository orders, ProductCatalogPort catalog) {
        this.orders = orders;
        this.catalog = catalog;
    }

    @Override
    public OrderId handle(CreateOrderCommand command) {
        var lines = command.lines().stream()
            .map(l -> {
                var price = catalog.priceFor(l.sku())
                    .orElseThrow(() -> new OrderDomainException("unknown sku: " + l.sku()));
                return new OrderLine(l.sku(), l.quantity(), price);
            })
            .toList();
        var order = Order.createDraft(new OrderId(command.orderId()), lines);
        order.confirm();
        orders.save(order);
        return order.id();
    }
}

Infrastructure — encja JPA, mapper, adapter

// adapter/out/persistence/OrderJpaEntity.java
@Entity
@Table(name = "orders")
class OrderJpaEntity {
    @Id UUID id;
    @Enumerated(EnumType.STRING) OrderStatus status;
    @ElementCollection
    @CollectionTable(name = "order_lines")
    List<OrderLineEmbeddable> lines;
}

// adapter/out/persistence/OrderRepositoryAdapter.java — ADAPTER
class OrderRepositoryAdapter implements OrderRepository {
    private final SpringDataOrderJpaRepository jpa;
    private final OrderPersistenceMapper mapper;

    OrderRepositoryAdapter(SpringDataOrderJpaRepository jpa, OrderPersistenceMapper mapper) {
        this.jpa = jpa;
        this.mapper = mapper;
    }

    @Override
    public void save(Order order) {
        jpa.save(mapper.toEntity(order));
    }

    @Override
    public Optional<Order> findById(OrderId id) {
        return jpa.findById(id.value()).map(mapper::toDomain);
    }
}

// config/OrderModuleConfiguration.java — Spring tylko tutaj
@Configuration
class OrderModuleConfiguration {
    @Bean
    CreateOrderUseCase createOrderUseCase(OrderRepository repo, ProductCatalogPort catalog) {
        return new CreateOrderService(repo, catalog);
    }

    @Bean
    OrderRepository orderRepository(SpringDataOrderJpaRepository jpa, OrderPersistenceMapper mapper) {
        return new OrderRepositoryAdapter(jpa, mapper);
    }
}

Adapter wejściowy (skrót)

// adapter/in/web/OrderController.java
@RestController
@RequestMapping("/orders")
class OrderController {
    private final CreateOrderUseCase createOrder;

    OrderController(CreateOrderUseCase createOrder) { this.createOrder = createOrder; }

    @PostMapping
    ResponseEntity<OrderResponse> create(@Valid @RequestBody CreateOrderRequest body) {
        var id = createOrder.handle(new CreateOrderCommand(
            body.orderId(),
            body.lines().stream()
                .map(l -> new CreateOrderCommand.Line(l.sku(), l.quantity(), l.unitPrice(), l.currency()))
                .toList()
        ));
        return ResponseEntity.status(HttpStatus.CREATED)
            .body(new OrderResponse(id.value(), "CONFIRMED"));
    }
}

5. Dobre praktyki i decyzje architektoniczne

Kiedy pełne warstwy, a kiedy uprościć?

  • Pełny hex/onion/clean — nietrywialne reguły (stany, promocje, limity), wiele adapterów (REST + batch + events), wysoka potrzeba testów bez Springa, długi żywot modułu.
  • Uproszczenie — prosty CRUD bez invariantów: wystarczy controller → service → repository z encją JPA; nie twórz trzech klas Order „dla zasady”.
  • Kompromis — port na repozytorium + cienka domena (kilka metod) często daje 80% korzyści przy umiarkowanej złożoności.

Jeden mikroserwis, 2–3 domeny obok siebie

Nie mieszaj modeli w jednym pakiecie service. Trzymaj osobne korzenie modułów (order, inventory, billing) z własnym domain/application/adapter. Komunikacja między kontekstami:

  • Port wyjściowy + adapter w tym samym procesie (wywołanie use case innego modułu przez interfejs — jak port driven).
  • Anti-Corruption Layer — adapter tłumaczy obcy model (np. DTO innego modułu) na lokalny command/VO.
  • Domain events (opcjonalnie) — moduł A publikuje fakt, moduł B ma własny handler w adapter/in/messaging; brak importu encji A w B.

Granica modułu = granica pakietów + brak publicznych klas domenowych poza modułem (Java module system lub konwencja + ArchUnit).

Czego kategorycznie unikać

  • Import jakarta.persistence, org.springframework w domain i application.
  • Encja JPA jako agregat domenowy „bo szybciej”.
  • Use case wywołujący EntityManager lub RestTemplate bezpośrednio.
  • Transakcje i polityki retry w klasach domenowych — to cross-cutting adaptera lub fasady aplikacyjnej.
  • Współdzielenie mutowalnych DTO między warstwami.
  • Porty z metodami w stylu CRUD tabeli (saveOrderEntity) zamiast języka domeny (save(Order)).

Typowe błędy

  1. „Clean Architecture folder” bez reguł w domenie — piękne pakiety, puste encje, logika w 500-liniowym serwisie.
  2. Port = interfejs JpaRepository — port należy do application, nie do Spring Data.
  3. Mapowanie tylko w jedną stronę — brak odtwarzania agregatu z bazy (lazy, brak VO).
  4. Use case z logiką biznesową — if-y statusów powinny być w agregacie; use case tylko orkiestruje.
  5. Jeden moduł na cały monolit — brak podziału na bounded context przy wielu domenach.
  6. Testy tylko @SpringBootTest — brak szybkich testów use case z fake adapterami.
  7. DTO w warstwie application — command/query to nie JSON; trzymaj kształt API w adapterze web.
  8. Odwrotne zależności przez events „globalne” — wspólny bus bez kontraktu i wersjonowania psuje granice.
  9. Over-engineering CRUD — trzy mapery i sześć klas Order na listę rekordów bez reguł.
  10. Wspólny „kernel” encji — jedna współdzielona encja JPA używana przez wiele serwisów łamie autonomię kontekstów.
