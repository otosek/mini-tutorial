0. Fundamenty i słownik

Multi-tenancy to jedna instancja aplikacji obsługująca wielu odizolowanych klientów (tenantów). Tenant to organizacja, nie użytkownik — jeden tenant ma wielu userów. Tenant ID to identyfikator, który musi towarzyszyć każdemu żądaniu, zapytaniu SQL, wiadomości w kolejce, wpisowi w logu i kluczowi w cache.

Cała trudność multi-tenancy sprowadza się do jednego zdania: tenant ID musi być ustalony raz, w miejscu godnym zaufania, i propagowany automatycznie — bo każde miejsce, gdzie programista musi o nim pamiętać ręcznie, jest przyszłym wyciekiem danych.

3. Warstwa prezentacji frontend

Odpowiedź na pytanie „czy trzeba coś robić po stronie frontendu”: tak, ale nie w celu bezpieczeństwa. Frontend odpowiada za rozpoznanie tenanta dla UX (branding, routing, cache), nigdy za autoryzację.

Co konkretnie zrobić w React / TypeScript

TenantProvider (React Context)

Jedno miejsce z tenantId, logo, kolorami, feature flagami — pobrane z /api/tenant-config. Motyw najprościej przez CSS variables, nie przez warunki w komponentach.

TanStack Query — tenant w queryKey

Bez tego po przełączeniu tenanta użytkownik zobaczy dane poprzedniego z cache. Dodatkowo queryClient.clear() przy zmianie tenanta i przy logout.

Interceptor HTTP (axios / fetch wrapper)

Dokłada token i opcjonalnie X-Tenant-Id dla logów/telemetrii. Backend traktuje ten nagłówek jako podpowiedź, nigdy jako uprawnienie.

Namespacing storage

localStorage, sessionStorage, IndexedDB i Service Worker cache muszą mieć klucze z tenantem i być czyszczone przy przełączeniu — inaczej dane wyciekają między kontami na tym samym urządzeniu.

// TanStack Query — klucz zawiera tenanta
const { data } = useQuery({
  queryKey: ['orders', tenantId, page],
  queryFn: () => api.get(`/orders?page=${page}`).then(r => r.data),
  enabled: Boolean(tenantId),
});

// Przełączenie tenanta = twardy reset cache
function switchTenant(next: string) {
  queryClient.clear();
  setTenantId(next);
}
Pułapka: pole „wybierz tenanta” wysyłane jako parametr do API bez weryfikacji po stronie serwera. To najczęstsza podatność multi-tenant (IDOR na poziomie tenanta) — backend musi sprawdzić, czy zalogowany user ma prawo do wskazanego tenanta, na podstawie tokenu, nie żądania.

4. Warstwa orkiestracji edge / gateway

Tu tenant zostaje ustalony i znormalizowany, żeby dalsze warstwy nie musiały parsować hostów.

// Spring Cloud Gateway — normalizacja i ochrona nagłówka
@Bean
GlobalFilter tenantFilter() {
  return (exchange, chain) -> {
    String host = exchange.getRequest().getURI().getHost();
    String tenant = host.split("\\.")[0];              // acme.app.com → acme
    var request = exchange.getRequest().mutate()
        .headers(h -> h.remove("X-Tenant-Id"))          // zawsze wyczyść wejście
        .header("X-Tenant-Id", tenant)
        .build();
    return chain.filter(exchange.mutate().request(request).build());
  };
}

5. Warstwa logiki biznesowej Spring / Java

Zadanie tej warstwy: przechować tenanta w kontekście i przenieść go wszędzie tam, gdzie ucieka wątek — do async, schedulerów, konsumentów kolejek i wywołań HTTP w dół.

Ustawienie kontekstu

@Component
public class TenantFilter extends OncePerRequestFilter {

  @Override
  protected void doFilterInternal(HttpServletRequest req,
                                  HttpServletResponse res,
                                  FilterChain chain) throws IOException, ServletException {
    var jwt = (Jwt) SecurityContextHolder.getContext()
        .getAuthentication().getPrincipal();
    String tenantId = jwt.getClaimAsString("tid");     // źródło prawdy = token

    TenantContext.set(tenantId);
    MDC.put("tenantId", tenantId);                      // logi
    try {
      chain.doFilter(req, res);
    } finally {
      TenantContext.clear();                            // BEZ TEGO wyciek na pulę wątków
      MDC.remove("tenantId");
    }
  }
}

Pułapka: @Scheduled i joby nie mają żądania HTTP, więc nie mają tenanta. Job musi iterować po liście tenantów z control plane i dla każdego jawnie ustawić kontekst. Uruchomienie zapytania bez kontekstu w modelu „wspólne tabele” zwróci albo nic, albo — bez RLS — wszystko.

PostgreSQL — Row Level Security jako siatka bezpieczeństwa

Filtrowanie w aplikacji zawiedzie w dniu, w którym ktoś napisze findAll() albo native query bez warunku. RLS przenosi izolację do bazy — nawet zapomniane zapytanie zwróci tylko dane bieżącego tenanta.

-- 1. Włącz RLS (FORCE działa też na właściciela tabeli!)
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;
ALTER TABLE orders FORCE ROW LEVEL SECURITY;

-- 2. Polityka: czytanie i zapis tylko w obrębie tenanta
CREATE POLICY tenant_isolation ON orders
  USING      (tenant_id = current_setting('app.tenant_id')::uuid)
  WITH CHECK (tenant_id = current_setting('app.tenant_id')::uuid);

-- 3. Aplikacja ustawia zmienną NA TRANSAKCJĘ (SET LOCAL, nie SET!)
BEGIN;
  SELECT set_config('app.tenant_id', '3f1c...-acme', true);  -- true = local
  SELECT * FROM orders;      -- widzi tylko swojego tenanta
COMMIT;
Trzy pułapki RLS naraz: (1) SET bez LOCAL zostaje na połączeniu i po zwrocie do puli HikariCP obsłuży innego tenanta; (2) bez FORCE ROW LEVEL SECURITY właściciel tabeli — a często aplikacja łączy się właśnie jako właściciel — całkowicie pomija polityki; (3) rola z atrybutem BYPASSRLS (albo superuser) ignoruje RLS, więc migracje uruchamiaj inną rolą niż runtime.

Indeksy, klucze i partycjonowanie

  • tenant_id jako pierwsza kolumna indeksu złożonego — (tenant_id, created_at). Indeks tylko po created_at zmusi bazę do czytania wierszy wszystkich tenantów.
  • Każdy unique musi zawierać tenanta — UNIQUE (tenant_id, email), nie UNIQUE (email). Inaczej rejestracja u jednego klienta zablokuje ten sam e-mail u innego.
  • Klucze obce w obrębie tenanta — rozważ FK złożone (tenant_id, order_id), żeby baza nie pozwoliła połączyć rekordów dwóch tenantów.
  • Partycjonowanie (PARTITION BY LIST/HASH (tenant_id)) przy bardzo dużych tabelach — szybsze usuwanie tenanta i lepsze plany, ale rośnie złożoność.
  • Statystyki — jeden gigantyczny tenant obok tysiąca małych psuje selektywność; czasem trzeba ANALYZE i osobne plany lub silo dla giganta.

Cache

// Spring Cache — tenant w kluczu, zawsze
@Cacheable(cacheNames = "productList",
           key = "T(com.app.TenantContext).get() + ':' + #categoryId")
public List<Product> findByCategory(Long categoryId) { ... }

W Redis użyj CacheKeyPrefix lub osobnej bazy/klucza z prefiksem tenant:{id}:. Cache drugiego poziomu Hibernate jest tenant-aware tylko w trybach DATABASE/SCHEMA — przy wspólnych tabelach klucz musi zawierać tenanta jawnie.

@SqsListener("orders-queue")
public void handle(OrderEvent event,
                   @Header("tenantId") String tenantId) {
  TenantContext.set(tenantId);
  MDC.put("tenantId", tenantId);
  try {
    orderService.process(event);      // reszta kodu nie wie o multi-tenancy
  } finally {
    TenantContext.clear();
    MDC.remove("tenantId");
  }
}

Kolejka wspólna czy per tenant? Wspólna jest domyślna — prostsza i tańsza. Osobna kolejka (lub osobna grupa konsumentów) ma sens, gdy jeden tenant potrafi zapchać przetwarzanie na godziny albo ma inne SLA. Kompromis: wspólna kolejka + limit równoległości per tenant i osobna kolejka dla planu enterprise.

Pułapka: DLQ bez tenanta w metadanych. Po incydencie nie wiesz, których klientów dotyczyła awaria i komu trzeba odtworzyć dane.

8. Usługi AWS ze wsparciem dla multi-tenancy

Cognito — tożsamość i claim z tenantem

Dwa modele: wspólny User Pool z atrybutem custom:tenantId (skalowalny, tanie onboardingi) albo pool per tenant (mocniejsza izolacja, ale limit pooli na konto i trudniejsze zarządzanie). Trigger Pre Token Generation wstrzykuje claim tid do tokenu — dzięki temu backend nie musi pytać bazy o przypisanie użytkownika.

IAM + STS session tags — izolacja na poziomie chmury

Wzorzec „token vending machine”: aplikacja robi AssumeRole z tagiem sesji tenantId, a polityka używa ${aws:PrincipalTag/tenantId}. Wtedy nawet błąd w kodzie nie pozwoli sięgnąć po dane innego tenanta w S3 czy DynamoDB — izolacja jest wymuszona przez AWS, nie przez if.

S3 — prefiks per tenant

s3://bucket/{tenantId}/... plus warunek IAM na prefiks. Bucket per tenant tylko dla nielicznych dużych klientów — limity kont i zarządzanie polityk rosną szybciej niż korzyść.

DynamoDB — dynamodb:LeadingKeys

tenantId jako partition key (lub jej prefiks) + warunek IAM LeadingKeys z tagiem sesji — twarda izolacja bez osobnych tabel. On-demand rozwiązuje problem nierównego ruchu między tenantami.

RDS / Aurora PostgreSQL

Schemat per tenant lub wspólne tabele z RLS. RDS Proxy jest praktycznie obowiązkowy przy schemacie per tenant — inaczej pule połączeń mnożą się przez liczbę tenantów. Aurora Serverless v2 amortyzuje nierówne obciążenie.

API Gateway — throttling i plany

Usage plan i klucz API per tenant dają limity bez kodu. Lambda authorizer może zwrócić kontekst z tenantem, który trafi dalej jako nagłówek.

CloudWatch, X-Ray, EMF

tenantId jako pole strukturalnego logu i adnotacja w trace — pozwala zdebugować zgłoszenie jednego klienta. Jako wymiar metryki używaj ostrożnie: wysoka kardynalność to realny koszt; zwykle wystarczy wymiar dla planu (tier), a szczegóły w logach.

KMS i Secrets Manager

Klucz CMK per tenant, gdy klient wymaga własnego klucza (BYOK) — spełnia audyty i umożliwia „kryptograficzne usunięcie” danych przez zniszczenie klucza.

Warto znać materiały AWS SaaS Factory i SaaS Builder Toolkit — opisują dokładnie ten podział na control plane i application plane oraz gotowe wzorce izolacji.

9. Onboarding, offboarding, koszty

  • Rejestr tenantów w control plane: id, nazwa, plan, model izolacji, status, mapowanie domen. To on jest źródłem listy dla migracji i jobów.
  • Provisioning jako proces (Step Functions albo serwis): utwórz schemat/bazę, uruchom migracje, założ konto admina, wyślij zaproszenie, zarejestruj domenę.
  • Offboarding zaprojektuj razem z onboardingiem — RODO wymaga usunięcia danych, a przy wspólnych tabelach to kaskada po dziesiątkach tabel plus backupy i logi.
  • Metering kosztów: tagi AWS nie działają wewnątrz współdzielonego zasobu. Koszt per tenant trzeba mierzyć w aplikacji (liczba żądań, GB w S3, czas CPU) i łączyć z rachunkiem.
  • Testy izolacji: test integracyjny, który loguje się jako tenant A i próbuje pobrać zasób tenanta B, oczekując 403/404. Ten jeden test wyłapuje większość regresji.

10. Must-know — najistotniejsze

  1. Tenant ID pochodzi z tokenu, nigdy z parametru czy nagłówka od klienta.
  2. Kontekst, nie parametr — TenantContext / ScopedValue, a nie tenantId w każdej sygnaturze metody.
  3. Obrona wielowarstwowa — filtr Hibernate i RLS w PostgreSQL. Aplikacja da wydajność, baza da gwarancję.
  4. SET LOCAL w transakcji — jedyny bezpieczny sposób ustawienia tenanta przy puli połączeń.
  5. FORCE ROW LEVEL SECURITY plus osobna rola dla migracji, inaczej polityki są ozdobą.
  6. tenant_id pierwszy w indeksach i obecny w każdym UNIQUE.
  7. Zawsze clear() w finally — pula wątków przenosi kontekst na kolejne żądanie.
  8. Propagacja do async, schedulerów i konsumentów kolejek — TaskDecorator, nagłówki wiadomości.
  9. Tenant w każdym kluczu cache — Redis, Spring Cache, TanStack Query.
  10. Limity per tenant od początku — inaczej jeden klient położy wszystkich.
  11. Model izolacji to decyzja per tier, nie na zawsze dla całego systemu.
  12. Test, który próbuje wykraść dane innego tenanta — obowiązkowy element pipeline'u.

Typowe błędy

  • Zaufanie nagłówkowi X-Tenant-Id z internetu. Podmiana wartości = dostęp do danych obcej firmy. Gateway musi ten nagłówek usuwać na wejściu.
  • Brak clear() w finally. Tomcat i pule wątków recyklingują wątki — następne żądanie dziedziczy tenanta poprzedniego.
  • SET app.tenant_id zamiast SET LOCAL. Zmienna zostaje na połączeniu w HikariCP i wycieka do innego tenanta.
  • RLS bez FORCE, aplikacja jako właściciel tabeli. Polityki istnieją, ale nie działają — najgorszy możliwy wariant, bo daje fałszywe poczucie bezpieczeństwa.
  • UNIQUE (email) bez tenanta. Jeden klient blokuje rejestrację u drugiego; naprawa po wdrożeniu wymaga migracji danych.
  • Indeksy bez tenant_id na początku. Zapytania małego tenanta skanują dane wszystkich — wydajność spada z liczbą klientów.
  • Klucze cache bez tenanta. Redis albo queryKey w TanStack Query pokazuje dane obcej organizacji — wyciek widoczny dla użytkownika.
  • @Async, @Scheduled i konsument kolejki bez propagacji kontekstu. Albo NullPointerException na produkcji, albo operacja wykonana na danych złego tenanta.
  • Pula połączeń per tenant. 500 tenantów × 10 połączeń wyczerpuje limit PostgreSQL; potrzebny wspólny pool z search_path albo RDS Proxy.
  • Migracje tylko na domyślnym schemacie. Nowe schematy tenantów zostają w starej wersji i aplikacja sypie błędami dla części klientów.
  • tenantId jako wymiar metryki dla tysięcy tenantów. Rachunek CloudWatch rośnie liniowo z liczbą klientów — wymiar per tier, szczegóły w logach.
  • Brak limitów per tenant. Jeden import CSV od dużego klienta zapycha kolejkę i psuje SLA wszystkim (noisy neighbour).
  • Poleganie wyłącznie na filtrowaniu w kodzie. Jedno findAll(), native query albo raport napisany „na szybko” i masz incydent bezpieczeństwa.
  • Brak zaprojektowanego usuwania tenanta. Przy wspólnych tabelach żądanie RODO staje się projektem na tygodnie.
  • Testy tylko z jednym tenantem. Izolacja nigdy nie jest sprawdzana, więc regresja wychodzi u klienta, nie w CI.
