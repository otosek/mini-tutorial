Co to jest REST

REST (Representational State Transfer) to styl architektoniczny opisany przez Roya Fieldinga w dysertacji z 2000 r. Nie jest protokołem ani standardem — to zestaw ograniczeń. API spełniające je nazywa się „RESTful"; w praktyce większość tzw. REST API to po prostu HTTP + JSON na poziomie 2 skali Richardsona.

OgraniczenieZnaczenie
Client–ServerSeparacja klienta (UI) od serwera (dane) — rozwijają się niezależnie
StatelessKażde żądanie zawiera wszystko, co potrzebne; serwer nie trzyma sesji — token w nagłówku, nie w pamięci serwera
CacheableOdpowiedzi oznaczone jako cache'owalne (ETag, Cache-Control) — klient i proxy mogą je przechowywać
Uniform InterfaceJednolity interfejs: zasoby adresowane URI, manipulacja przez reprezentacje, standardowe metody HTTP, HATEOAS
Layered SystemPośrednicy (proxy, gateway, load balancer) przezroczysti dla klienta
Code on DemandOpcjonalne: serwer może wysłać kod do wykonania (np. JS) — jedynie nieobowiązkowe ograniczenie

Zasoby i URI

Zasób (resource) to rzeczownik, nie czasownik. URI identyfikuje co, metoda HTTP mówi co z tym zrobić.

DOBRZE                          ŹLE
/authors                        /getAuthors
/authors/42                     /getAuthor?id=42
POST /authors                   /createAuthor
/authors/42/titles              /getTitlesForAuthor
DELETE /authors/42              /deleteAuthor?id=42
  • Kolekcja vs element: /authors (lista) vs /authors/42 (jeden zasób)
  • Zagnieżdżanie płytkie — max 2 poziomy: /authors/42/titles, głębiej lepiej /titles?authorId=42
  • Liczba mnoga dla kolekcji, spójnie w całym API
  • Query string na filtry i paginację, nie na akcje: ?status=active&page=2&size=20&sort=name

Bezpieczna (safe)

Nie zmienia stanu serwera — można ją wołać bez skutków. Crawlery i prefetch klika GET bez obaw.

Idempotentna

Powtórzenie żądania N razy daje ten sam efekt co 1 raz. DELETE /authors/42 dwa razy → autor nadal nie istnieje. Kluczowe przy retry po timeoutach.

Pułapka: PUT zastępuje całą reprezentację — pominięte pola mogą zostać wyzerowane. Częściowa aktualizacja to PATCH (format JSON Merge Patch lub JSON Patch).

Format błędów: standard RFC 9457 Problem Details — Content-Type: application/problem+json z polami type, title, status, detail, instance. Spring Boot 3 wspiera z pudełka (spring.mvc.problemdetails.enabled=true).

Pułapka: 401 vs 403 są odwrotnie niż sugerują nazwy — „Unauthorized" znaczy „nieuwierzytelniony", nie „nieautoryzowany".

Richardson Maturity Model i HATEOAS

Skala dojrzałości API — Leonard Richardson (2008). Większość produkcyjnych „REST API" stoi na poziomie 2 i to wystarcza.

Poziom 3  HATEOAS          zasoby + metody + kody + linki w odpowiedziach
Poziom 2  HTTP verbs       zasoby + poprawne metody i kody statusów   ← typowe API
Poziom 1  Resources        wiele URI, ale wszystko POST-em
Poziom 0  The Swamp of POX jeden URI, jeden POST (SOAP, XML-RPC)

HATEOAS (Hypermedia as the Engine of Application State): odpowiedź zawiera linki do dozwolonych akcji — klient nie zna URI na sztywno, tylko „nawiguje" po API:

{
  "id": 42,
  "name": "Andrzej Sapkowski",
  "_links": {
    "self":   { "href": "/authors/42" },
    "titles": { "href": "/authors/42/titles" },
    "update": { "href": "/authors/42", "method": "PUT" }
  }
}

Pułapka: nazywanie poziomu 2 „pełnym REST-em" — bez hypermediów to „HTTP API". HATEOAS w praktyce jest rzadki: klienci i tak piszą ścieżki na sztywno, a kontrakt opisuje OpenAPI.

OpenAPI — specyfikacja

OpenAPI Specification (OAS) to standardowy, maszynowo czytelny opis HTTP API w YAML lub JSON. Wywodzi się ze Swagger Specification (2011); w 2015 przekazana pod Linux Foundation jako OpenAPI Initiative. Wersje: 2.0 (= Swagger), 3.0, 3.1 (pełna zgodność z JSON Schema 2020-12).

Jeden dokument = kontrakt API. Z niego generujesz dokumentację, klientów, mocki i testy — bez czytania kodu serwera.

Struktura dokumentu

openapi: 3.1.0
info:        # tytuł, wersja, opis, kontakt
servers:     # URL-e środowisk (dev, prod)
paths:       # /authors/{id}: → get / put / delete → parameters, requestBody, responses
components:  # schemas, securitySchemes, responses — re-użycie przez $ref
security:    # globalnie lub per operacja
tags:        # grupowanie operacji w dokumentacji

Przykład — Authors API

openapi: 3.1.0
info:
  title: Authors API
  version: 1.0.0
paths:
  /authors:
    get:
      summary: Lista autorów
      parameters:
        - name: page
          in: query
          schema: { type: integer, default: 0 }
      responses:
        '200':
          description: Strona autorów
          content:
            application/json:
              schema:
                type: array
                items: { $ref: '#/components/schemas/Author' }
    post:
      summary: Utwórz autora
      requestBody:
        required: true
        content:
          application/json:
            schema: { $ref: '#/components/schemas/AuthorInput' }
      responses:
        '201': { description: Utworzono, headers: { Location: { schema: { type: string } } } }
        '422': { description: Błąd walidacji }
  /authors/{id}:
    get:
      parameters:
        - name: id
          in: path
          required: true
          schema: { type: integer }
      responses:
        '200':
          description: Autor
          content:
            application/json:
              schema: { $ref: '#/components/schemas/Author' }
        '404': { description: Nie znaleziono }
components:
  schemas:
    Author:
      type: object
      required: [id, name]
      properties:
        id:   { type: integer, format: int64 }
        name: { type: string, minLength: 1 }
    AuthorInput:
      type: object
      required: [name]
      properties:
        name: { type: string, minLength: 1 }
  securitySchemes:
    bearerAuth:
      type: http
      scheme: bearer
security:
  - bearerAuth: []

Typowe błędy

  1. Czasowniki w URI — /getAuthors, /createAuthor zamiast zasobów i metod HTTP
  2. POST do wszystkiego — tracisz semantykę GET/PUT/DELETE, idempotencję i cache
  3. Zawsze 200 + błąd w body — kody statusów istnieją; klient nie powinien parsować body, by poznać wynik
  4. 500 na błąd walidacji — błąd klienta to 4xx; 500 to bug po Twojej stronie
  5. Mylenie 401 i 403 — 401: nie wiem, kim jesteś; 403: wiem i odmawiam
  6. Eksponowanie encji JPA jako API 1:1 — wyciek modelu wewnętrznego, over-posting, cykle w JSON; używaj DTO
  7. Zmiana łamiąca kontrakt bez wersji — usunięcie/zmiana pola wymaga nowej wersji API; dodanie pola jest bezpieczne
  8. Endpoint bez paginacji — GET /authors zwracające 100 tys. rekordów; domyślny page/size od początku
  9. Spec rozjechany z kodem — dokumentacja kłamie; pilnuj contract-first albo testów kontraktowych w CI
  10. Brak idempotencji przy POST płatności — retry klienta po timeout = podwójne obciążenie; rozwiązuje Idempotency-Key
