Co to jest wzorzec

Wzorzec projektowy (design pattern) to sprawdzone rozwiązanie typowego problemu w projektowaniu obiektowym. Nie jest biblioteką ani snippetem do wklejenia — to nazwa + struktura klas + intencja.

Kanon Gang of Four (Gamma, Helm, Johnson, Vlissides, 1994) dzieli 23 wzorce na trzy grupy: creational (tworzenie obiektów), structural (składanie struktur), behavioral (komunikacja i algorytmy).

Kreacyjny Singleton

Gwarantuje jedną instancję klasy i globalny punkt dostępu. W Javie często enum albo holder z lazy init — unikaj „podwójnego checkingu” bez volatile.

Kiedy: konfiguracja, cache współdzielony, logger — gdy naprawdę potrzebujesz jednej instancji. Unikaj jako „globalnej zmiennej” na wszystko.

public enum AppConfig {
  INSTANCE;
  private final String env = System.getenv().getOrDefault("APP_ENV", "dev");
  public String env() { return env; }
}
// AppConfig.INSTANCE.env()

Kreacyjny Factory Method

Tworzenie obiektu przez metodę/interfejs zamiast new Concrete w kliencie. Klient zna produkt (interfejs), nie konkretną klasę.

Kiedy: typ obiektu zależy od konfiguracji, środowiska lub parametru; chcesz otworzyć kod na nowe warianty bez zmiany call-site’ów.

interface Notifier { void send(String msg); }

class NotifierFactory {
  static Notifier create(String channel) {
    return switch (channel) {
      case "email" -> new EmailNotifier();
      case "sms"   -> new SmsNotifier();
      default      -> throw new IllegalArgumentException(channel);
    };
  }
}

Kreacyjny Builder

Buduje obiekt krok po kroku (fluent API), zamiast konstruktora z 8+ parametrami. Dobry do obiektów niemutowalnych i opcjonalnych pól.

Kiedy: wiele opcjonalnych pól, czytelność wywołań, walidacja dopiero na build(). W Javie: ręczny builder, Lombok @Builder, records + withery.

var order = Order.builder()
    .customerId(42)
    .item("SKU-1", 2)
    .discount(10)
    .build();

Strukturalny Adapter

Opakowuje obce API tak, by pasowało do Twojego interfejsu. Nie zmienia zachowania — tłumaczy wywołania.

Kiedy: integracja biblioteki zewnętrznej, legacy SOAP → Twój port, inny format daty/DTO bez przepisywania klientów.

interface PaymentPort { void charge(Money amount); }

class StripeAdapter implements PaymentPort {
  private final StripeClient client;
  public void charge(Money amount) {
    client.createCharge(amount.cents(), "PLN");
  }
}

Strukturalny Decorator

Dokłada odpowiedzialność do obiektu w runtime, zachowując ten sam interfejs. Klasyczny przykład: InputStream / BufferedInputStream.

Kiedy: logowanie, cache, retry, kompresja — warstwy wokół tej samej operacji bez eksplozji podklas.

interface Repo { User find(long id); }

class CachingRepo implements Repo {
  private final Repo inner;
  private final Map<Long, User> cache = new HashMap<>();
  public User find(long id) {
    return cache.computeIfAbsent(id, inner::find);
  }
}

Strukturalny Facade

Jeden prosty interfejs nad kilkoma klasami podsystemu. Ukrywa kolejność wywołań i szczegóły.

Kiedy: use-case warstwy aplikacji, uproszczenie startu biblioteki, API dla UI/REST bez eksponowania 5 serwisów naraz.

class CheckoutFacade {
  void placeOrder(Cart cart) {
    inventory.reserve(cart);
    payment.charge(cart.total());
    shipping.schedule(cart);
    orders.save(cart);
  }
}

Strukturalny Proxy

Zastępca obiektu z tym samym interfejsem: lazy load, kontrola dostępu, remote stub. W Hibernate lazy proxy to właśnie Proxy.

Kiedy: kosztowna inicjalizacja, ACL przed wywołaniem, wywołanie zdalne (RMI/HTTP). Różnica vs Decorator: Proxy kontroluje dostęp do realnego obiektu; Decorator dokłada funkcje.

class LazyImage implements Image {
  private Image real;
  public void draw() {
    if (real == null) real = new HeavyImage(path);
    real.draw();
  }
}

Behawioralny Strategy

Rodzina wymiennych algorytmów za wspólnym interfejsem. Klient wybiera strategię (lub dostaje ją z DI) bez if/switch w środku logiki biznesowej.

Kiedy: różne polityki cen, sortowanie, walidacja, płatności — ten sam kontekst, inny algorytm. W Springu: wiele beanów jednego interfejsu + mapa/qualifier.

interface Pricing { Money price(Cart cart); }

class RegularPricing implements Pricing { ... }
class VipPricing implements Pricing { ... }

Money total = pricing.price(cart); // wstrzyknięta strategia

Behawioralny Observer

Podmiot powiadamia listę obserwatorów o zmianie stanu. Luźne powiązanie: publisher nie zna konkretnych listenerów.

Kiedy: eventy domenowe, UI (Listener), Spring ApplicationEventPublisher, reactive streams. Unikaj cykli powiadomień i ciężkiej pracy synchronicznie w listenerze.

class OrderService {
  private final List<Consumer<Order>> listeners = new ArrayList<>();
  void onPlaced(Consumer<Order> l) { listeners.add(l); }
  void place(Order o) {
    save(o);
    listeners.forEach(l -> l.accept(o));
  }
}

Behawioralny Command

Żądanie jako obiekt: parametry + execute() (+ opcjonalnie undo()). Można kolejkować, logować, retry’ować.

Kiedy: undo/redo, joby w kolejce, makrokomendy, oddzielenie UI („przycisk”) od akcji. Blisko CQRS command, ale GoF Command to obiekt z zachowaniem.

interface Command { void execute(); }

class TransferCmd implements Command {
  public void execute() { account.debit(from); account.credit(to); }
}
queue.offer(new TransferCmd(from, to, amount));

Behawioralny Template Method

Abstrakcyjna klasa definiuje szkielet algorytmu; podklasy nadpisują kroki (haki). Odwrócenie Strategy: tu dziedziczenie, nie kompozycja.

Kiedy: wspólny pipeline (np. import pliku: parse → validate → save), różnice tylko w środkowych krokach. Preferuj Strategy, gdy warianty rosną lub nie chcesz hierarchii klas.

abstract class ImportJob {
  final void run(Path file) {
    var rows = parse(file);
    validate(rows);
    save(rows);
  }
  abstract List<Row> parse(Path file);
  void validate(List<Row> rows) { /* default */ }
  abstract void save(List<Row> rows);
}

Behawioralny Chain of Responsibility

Request idzie przez łańcuch handlerów; każdy może obsłużyć, przekazać dalej albo przerwać. Servlet filters, Spring Security filter chain, middleware.

Kiedy: walidacja wieloetapowa, autoryzacja, logging/metrics przed handlerem, support tickets (poziomy eskalacji). Pilnuj kolejności i tego, by łańcuch zawsze kończył się sensownie.

interface Handler {
  void setNext(Handler n);
  void handle(Request r);
}

// AuthHandler → RateLimitHandler → BusinessHandler
auth.setNext(rateLimit);
rateLimit.setNext(business);
auth.handle(request);

Typowe błędy

  • Singleton na wszystko — ukryty global state, trudne testy, ukryte zależności.
  • Wzorzec „bo brzmi seniorowo” — bez problemu do rozwiązania to szum w kodzie.
  • Mylenie Adapter / Decorator / Proxy — podobna struktura, inna intencja.
  • God Object zamiast Facade — facade upraszcza API, nie zbiera całej logiki świata.
  • Strategy z jednym wariantem „na zapas” — YAGNI; dodaj gdy pojawi się drugi algorytm.
  • Observer synchroniczny z ciężką I/O — blokuje publishera; rozważ async / kolejkę.
  • Template Method + głębokie dziedziczenie zamiast kompozycji Strategy.
  • Factory zwracająca konkret zamiast interfejsu — klient i tak sprzężony z implementacją.
  • Builder bez walidacji na build() — niespójne obiekty pół-zbudowane.
  • Łańcuch bez końca / bez „fallback” — request ginie po drodze w ciszy.
