Część 1 — Fundamenty

1.1 Co to jest TypeScript

TypeScript to nadzbiór JavaScriptu z systemem typów statycznych. Kod TS kompiluje się do JS (tsc lub bundler — Vite, esbuild). Typy istnieją tylko w czasie kompilacji — w runtime zostaje czysty JavaScript.

1.2 Po co TypeScript

Łapie błędy przed uruchomieniem (null, zła sygnatura, literówka w polu). Lepsze IDE — autouzupełnianie, refaktoryzacja, nawigacja. Dokumentacja w kodzie — typy mówią, co funkcja przyjmuje i zwraca. W projektach React + API (np. authors) typy modeli domeny (Author, CreateAuthorInput) trzymają frontend spójny.

1.3 Jak działa kompilacja

// author.ts — TypeScript
export function greet(name: string): string {
  return `Hello, ${name}`
}

// author.js — output (typy usunięte)
export function greet(name) {
  return `Hello, ${name}`
}

tsc sprawdza typy → emituje JS. Bundler (Vite) robi to w locie podczas dev/build. Błąd typu = build fail (przy strict: true).

Część 2 — Typy podstawowe i strukturalne

2.1 Typy prymitywne

let count: number = 0
let name: string = 'Anna'
let active: boolean = true
let nothing: null = null
let notDefined: undefined = undefined
let id: bigint = 1n
let unique: symbol = Symbol('id')

2.2 Typy strukturalne (shape, nie nazwa klasy)

TS używa structural typing — liczy się kształt obiektu, nie czy implementuje interfejs explicite.

type Point = { x: number; y: number }

function print(p: Point) {
  console.log(p.x, p.y)
}

print({ x: 1, y: 2 })  // OK — ma wymagany kształt

2.3 Tablice, tuple, readonly

const ids: number[] = [1, 2, 3]
const pair: [string, number] = ['age', 30]  // tuple — stała długość i typy

type Author = {
  readonly id: string   // nie można nadpisać
  firstName: string
  lastName: string
}

2.4 Inferencja — nie pisz typów wszędzie

const title = 'Dune'           // inferred: string
const authors = ['A', 'B']     // inferred: string[]

function double(n: number) {   // return inferred: number
  return n * 2
}

Pisz typy explicite przy parametrach funkcji publicznych i API — resztę TS wywnioskuje.

Część 3 — strict i bezpieczeństwo typów

3.1 strict: true

Włącza pakiet restrykcyjnych opcji — w Twoim projekcie authors to standard. Najważniejsze pod opcje:

OpcjaCo robi
strictNullChecksnull / undefined to osobne typy — musisz obsłużyć explicite
noImplicitAnyZakaz domyślnego any
strictFunctionTypesŚcisłe sprawdzanie parametrów funkcji
strictPropertyInitializationPola klasy muszą być zainicjalizowane

3.2 any vs unknown vs never

TypZnaczenie
anyWyłącza sprawdzanie — uciekajka, unikaj
unknown„Nie wiem co to” — musisz zawęzić przed użyciem
neverWartość, która nigdy nie wystąpi — throw, nieskończona pętla, exhaustive check
 
function parseJson(raw: string): unknown {
  return JSON.parse(raw)
}

const data = parseJson('{"id":1}')
// data.id  // błąd — unknown

if (typeof data === 'object' && data !== null && 'id' in data) {
  // teraz można zawęzić dalej
}

Część 4 — Unie, intersection, literal types

4.1 Union (|)

Wartość może być jednym z typów.

type AuthorId = string
type Status = 'draft' | 'published' | 'archived'  // literal union

function formatId(id: string | number): string {
  return typeof id === 'number' ? id.toString() : id
}

4.2 Intersection (&)

Połączenie kształtów — musi spełniać oba.

type Named = { name: string }
type Aged = { age: number }
type Person = Named & Aged   // { name: string; age: number }

4.3 Discriminated unions — wzorzec MUST KNOW

type ApiResult =
  | { status: 'ok'; data: Author[] }
  | { status: 'error'; message: string }

function handle(result: ApiResult) {
  if (result.status === 'ok') {
    return result.data   // TS wie: data istnieje
  }
  return result.message  // TS wie: message istnieje
}

Wspólne pole (status) = dyskryminator — TS zawęża typ w switch / if.

Część 5 — Type narrowing

Narrowing — zawężanie typu w gałęzi kodu, żeby TS wiedział, z czym pracujesz.

TechnikaPrzykład
typeoftypeof x === 'string'
instanceofx instanceof Date
in'email' in author
Equalityx === null, x !== undefined
Type predicatefunction isAuthor(x: unknown): x is Author
Discriminated unionif (r.status === 'ok')
Exhaustive checkdefault: const _exhaustive: never = action
 
function isAuthor(value: unknown): value is Author {
  return (
    typeof value === 'object' &&
    value !== null &&
    'id' in value &&
    'firstName' in value
  )
}

Część 6 — Generics

Generics — parametry typu. Jedna funkcja/komponent, wiele typów — bez any.

function first<T>(items: T[]): T | undefined {
  return items[0]
}

first<string>(['a', 'b'])   // string | undefined
first([1, 2])                // inferred: number | undefined

// React Query w projekcie authors — generyczne hooki
function useQuery<T>(options: { queryFn: () => Promise<T> }): T { ... }

Ograniczenia (extends)

function getId<T extends { id: string }>(item: T): string {
  return item.id
}

keyof i indeksowany access

type Author = { id: string; firstName: string; lastName: string }
type AuthorKey = keyof Author   // 'id' | 'firstName' | 'lastName'

function getField<K extends keyof Author>(author: Author, key: K): Author[K] {
  return author[key]
}

type Author = { id: string; firstName: string; lastName: string; email: string }
type CreateAuthorInput = Omit<Author, 'id'>

// Mapped type — własny wzorzec
type Nullable<T> = { [K in keyof T]: T[K] | null }

Część 8 — interface vs type, moduły, tsconfig

8.1 interface vs type

interfacetype
Rozszerzanieextends, declaration merging& intersection, brak merging
Unie, tuple, mappedNieTak
KiedyKształty obiektów, API publiczneUnie, utility, aliasy złożone

W praktyce oba działają dla obiektów — wybierz konwencję zespołu i trzymaj się jej.

8.2 Moduły i import typów

import type { Author } from './models'     // tylko typ — usunięty w emit
import { type Author, authorSchema } from './models'  // inline type import

8.3 tsconfig — essentials

{
  "compilerOptions": {
    "strict": true,
    "target": "ES2022",
    "module": "ESNext",
    "moduleResolution": "bundler",
    "jsx": "react-jsx",
    "noUnusedLocals": true,
    "skipLibCheck": true
  }
}

skipLibCheck: true — szybsza kompilacja, pomija błędy w .d.ts z node_modules. erasableSyntaxOnly (TS 6 / Vite 8) — blokuje enum, namespace — preferuj union literals.

8.4 Zod + TypeScript (Twój projekt)

import { z } from 'zod'

const authorSchema = z.object({
  firstName: z.string().min(1),
  lastName: z.string().min(1),
  email: z.string().email(),
})

type CreateAuthorInput = z.infer<typeof authorSchema>  // typ z runtime schema

z.infer — jedno źródło prawdy: walidacja runtime + typ compile-time.

Część 9 — Najczęstsze błędy

  1. Nadużywanie any — tracisz sens TS; użyj unknown
  2. Brak strictNullChecks — undefined w runtime mimo „pewności” typów
  3. Type assertion (as) bez walidacji — kłamstwo dla kompilatora
  4. Duplikacja typów zamiast z.infer / wspólnego modelu
  5. Enum zamiast union literals — problemy z tree-shaking, erasableSyntaxOnly
  6. Ignorowanie błędów @ts-ignore — dług techniczny
  7. Mutowanie readonly / props React — błąd logiczny + typowy
  8. Zbyt szeroki typ zwracany — object, Record<string, unknown> bez potrzeby
  9. Brak exhaustive check w switch na union — nowy wariant union = cicha dziura
  10. Import typu bez import type — czasem circular dependency w bundlerze

Pytania rekrutacyjne — krótkie odpowiedzi

Junior / Mid

1. Co to jest TypeScript?

Nadzbiór JS ze statycznym typowaniem — kompiluje się do JavaScript.

2. Czy typy istnieją w runtime?

Nie — są usuwane przy kompilacji (erasure).

3. Co robi strict: true?

Włącza pakiet restrykcyjnych opcji — m.in. strictNullChecks, noImplicitAny.

4. any vs unknown?

any — wyłącza sprawdzanie. unknown — bezpieczny „nie wiem”, wymaga narrowing.

5. Co to union type?

Wartość może być jednym z typów: string | number.

6. Co to intersection type?

Połączenie kształtów: A & B — musi spełniać oba.

7. interface vs type?

Interface — extends, declaration merging. Type — unie, tuple, mapped types.

8. Co to type narrowing?

Zawężanie typu w gałęzi kodu (if, switch, typeof, instanceof).

9. Co to generics?

Parametry typu — funkcja/typ działający na wielu typach bez any.

10. Co robi Partial<T>?

Wszystkie pola T stają się opcjonalne.

11. Co robi Omit<T, K>?

Typ T bez pól K.

12. Co to literal type?

Konkretna wartość jako typ: 'draft' | 'published'.

13. Co to never?

Typ bez wartości — unreachable code, exhaustive checks.

14. Structural vs nominal typing?

TS — structural (kształt). Java — nominal (nazwa klasy/interfejsu).

15. Co to readonly?

Pole/tablica nie do mutacji po przypisaniu.

Mid / Senior

16. Discriminated union — po co?

Wspólne pole (status/tag) umożliwia bezpieczne zawężenie w switch/if.

17. Type predicate — co to?

value is Author — funkcja mówi kompilatorowi, jaki typ zwraca po true.

18. Exhaustive check z never?

W default switch: const _: never = x — błąd kompilacji gdy union ma nowy wariant.

19. keyof i T[K]?

keyof — union kluczy. Indeksowany access — typ pola K w T.

20. Covariance / contravariance parametrów?

strictFunctionTypes — parametry funkcji są contravariant (ściślejsze przypisanie).

21. as const — po co?

Literalny, readonly typ — ['a','b'] as const → readonly tuple, nie string[].

22. Declaration merging?

Interface o tej samej nazwie łączy się — używane w typach globalnych, rozszerzaniu modułów.

23. import type — po co?

Import tylko typu — usunięty w emit, unika circular deps i runtime importów.

24. satisfies — po co?

Sprawdza zgodność z typem, zachowuje węższą inferencję (TS 4.9+).

25. Mapped types — przykład?

{ [K in keyof T]: T[K] | null } — transformacja każdego pola.

26. Conditional types — T extends U ? X : Y?

Typ zależny od warunku — używane w utility types (Exclude, Extract).

27. infer w conditional type?

Wyciąga typ z wnętrza — np. ReturnType<F> inferuje typ zwracany.

28. Distributive conditional types?

Conditional na union rozkłada się na union wyników — T extends U ? X : Y per member.

29. z.infer<typeof schema>?

Typ TypeScript wywnioskowany z schematu Zod — runtime + compile-time z jednego źródła.

30. skipLibCheck — plusy/minusy?

Szybszy build, mniej szumu z .d.ts; minus — ukryte błędy w typach bibliotek.

Pułapki / tricky

31. Czy {} akceptuje wszystko?

Prawie — akceptuje any oprócz null/undefined (przy strictNullChecks).

32. Czy as Author robi walidację?

Nie — tylko mówi kompilatorowi „ufaj mi”; runtime bez zmian.

33. Enum vs union literals?

Union — prostszy, tree-shakeable, zgodny z erasableSyntaxOnly. Enum — runtime object, większy bundle.

34. Czy Array.isArray to type guard?

Tak — wbudowany guard: unknown[] po true.

35. Double assertion as unknown as T?

Wymuszenie konwersji przez unknown — code smell, omija bezpieczeństwo typów.

36. Czy interface jest dziedziczony w runtime?

Nie — tylko typ; w JS nic nie zostaje.

37. void vs undefined jako return?

void — funkcja nic użytecznego nie zwraca; może return undefined. Semantyka intentu.

38. Tuple vs array?

Tuple — stała długość, typy per index. Array — dowolna długość, jeden typ elementu.

39. noUncheckedIndexedAccess?

Indeks tablicy/obiektu zwraca T | undefined — bezpieczniejsze, więcej null-checków.

40. TS vs JSDoc w czystym JS?

TS — pliki .ts, pełny system typów. JSDoc + checkJs — typowanie w .js bez kompilacji.
