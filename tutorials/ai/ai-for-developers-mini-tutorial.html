Gdzie jesteśmy (2025–2026)

AI w programowaniu przeszło z „autouzupełniania linii” do całych sesji w IDE: chat z kontekstem repo, edycja wielu plików, terminal, reguły projektu, subagenci. To nie zastępuje inżyniera — zmienia tempo pisania boilerplate, eksploracji i debugowania.

FazaCo byłoCo jest
2021–22Copilot = sugestia następnej liniiMało kontekstu projektu
2023–24Chat w IDE, @-mentions plikówRefactor w wielu plikach
2025–26Agenci, reguły, MCP, cloud agentsDłuższe zadania autonomiczne (z nadzorem)
Must know ★

Model nie „wie” Twojego projektu — widzi to, co dasz w kontekście (otwarte pliki, rules, grep, indeks repo). Im lepszy kontekst, tym mniej halucynacji.

Modele (stan 2026): Claude, GPT, Gemini — rotacja „najlepszego” co kwartał. W praktyce: wybierz model dostępny w Twoim IDE + polityce firmy; nie uzależniaj procesu od jednego vendora bez fallbacku.

Workflow z AI — co działa

  1. Małe zadania — jeden plik, jeden bug, jeden test → szybki zysk
  2. Reguły projektu — .cursor/rules, AGENTS.md: stack, konwencje, czego nie dotykać
  3. Review diff — AI generuje, człowiek akceptuje linia po linii (jak junior)
  4. Exploration — „gdzie jest X?”, „jak działa flow Y?” — szybsze niż solo grep
  5. Testy i edge cases — AI dobry w wypisywaniu przypadków, które pominąłeś
  6. Dokumentacja / tutorial HTML — szablony, spójność; weryfikuj fakty
Opinia: Największy ROI to nie „napisz mi całą aplikację”, tylko skrócenie pętli read → write → test → fix o 30–50% na znanym stacku.

Agenci i automatyzacja

Agent = model + narzędzia (pliki, shell, grep, MCP) + pętla aż do „done”. Trend: Cloud Agents (PR z issue), Bugbot na CI, background tasks w IDE.

PlusMinus
Refactor 10 plików overnightMoże zepsuć więcej niż człowiek w pośpiechu
CI fix loopKoszt tokenów + czas review
MCP — baza, Jira, Slack w kontekścieNowy attack surface / wycieki

MCP (Model Context Protocol) — standard podpinania zewnętrznych źródeł do agenta. Praktycznie: czytaj dokumentację wewnętrzną, tickety — bez kopiowania do chatu ręcznie.

Halucynacja

Model podaje pewnie brzmiącą bibliotekę/metodę, której nie ma. Lekarstwo: uruchom kod, test, linter — nie ufaj samemu chatowi.

Enterprise i compliance

  • Polityka danych — czy kod źródłowy może iść do chmury modelu? (on-prem / VPC / zero retention)
  • Secrets — AI wklei klucz do promptu; hooki i .gitignore obowiązkowe
  • Audit — kto zaakceptował diff od agenta? Ten sam proces co PR od człowieka
  • Licencje — output AI a copyright (szara strefa; polityka prawna firmy)
  • SOC2 / ISO — vendor AI w due diligence

Opinie — za i przeciw

Za

  • Demokratyzacja boilerplate — mniej czasu na szukanie składni
  • Onboarding w obcym repo — szybsze „gdzie co jest”
  • Dokumentacja i tutoriale — pierwszy szkic w minuty
  • Dostępność — junior z dobrym procesem review nie stoi w miejscu
  • Automatyzacja nudnych refaktorów (rename, migracja API)

Przeciw / ryzyka

  • Atrofia umiejętności — „nie czytam kodu, tylko akceptuję”
  • Jednolity „AI smell” — ten sam styl, te same błędy w całej branży
  • Fałszywe poczucie bezpieczeństwa na security-critical code
  • Koszt subskrypcji × zespół vs realny zysk (mierz, nie wierz na słowo)
  • Vendor lock-in na workflow IDE
Opinia: AI to super-charged Stack Overflow, nie architekt. Decyzje (bounded context, transakcje, auth) nadal Twoje. Model nie poniesie odpowiedzialności za prod incident.
Opinia: Zespoły, które wygrywają, traktują AI jak bardzo szybkiego stażystę — zawsze z review, testami i regułami repo. Zespoły, które przegrają — „ship without reading”.

Typowe błędy

  1. Brak reguł projektu — AI generuje inny styl w każdym pliku
  2. Akceptacja diffu bez uruchomienia testów
  3. Wklejanie secrets / PII do chatu
  4. „Napisz cały mikroserwis” bez iteracji i granic
  5. Ufanie wersjom API z pamięci modelu (stare Java/Spring/React)
  6. Ignorowanie polityki firmy — shadow IT z własnym ChatGPT
  7. Brak pomiaru — „czujemy, że szybciej” bez metryk cycle time
  8. Rezygnacja z code review „bo AI sprawdziło”
