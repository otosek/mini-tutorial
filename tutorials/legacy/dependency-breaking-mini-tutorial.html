Fundament: seams i zależności

Legacy code to kod bez testów (Feathers) — nie wiek pliku. Zanim przepiszesz monolit na moduły lub mikroserwisy, musisz przełamać zależności: baza, pliki, new w środku metody, statyki, sieć. Każda technika poniżej tworzy seam (szew): miejsce, gdzie w teście podstawiasz inną implementację bez zmiany zachowania produkcyjnego.

Workflow: (1) napisz test charakterystyczny lub docelowy, (2) wybierz technikę zależnie od rodzaju coupling, (3) minimalna refaktoryzacja pod seam, (4) dopiero potem większa architektura (Extract Interface → moduł Maven, itd.).

Techniki 1–8

1. Adapt Parameter (Dostosuj parametr)

Co to jest (krótki opis)
Zmieniasz sygnaturę wywoływanej metody (dodajesz parametr), żeby przekazać zależność z zewnątrz zamiast tworzyć ją wewnątrz callee.
Kiedy i po co stosować
Gdy nie możesz zmienić klasy testowanej, ale możesz zmienić metodę pomocniczą lub legacy util, z którego korzysta — typowy przypadek w starym pakiecie *.util.*.
Przed (legacy) 
public final class LegacyPricingUtil {
  public static Money discount(Order order) {
    TaxService tax = new TaxService(); // JDBC + cache Redis
    return order.subtotal().minus(tax.rateFor(order.region()));
  }
}
Po (refaktoryzacja / test) 
public final class LegacyPricingUtil {
  public static Money discount(Order order, TaxService tax) {
    return order.subtotal().minus(tax.rateFor(order.region()));
  }
}

// test
@Test void discount_uses_injected_tax() {
  TaxService fake = region -> new BigDecimal("0.08");
  Money result = LegacyPricingUtil.discount(orderPl(), fake);
  assertThat(result).isEqualTo(Money.of("92.00"));
}

2. Break Out Method Object (Wydziel obiekt-metodę)

Co to jest (krótki opis)
Długa metoda z wieloma polami tymczasowymi staje się klasą (Method Object); zależności wchodzą przez konstruktor obiektu-metody.
Kiedy i po co stosować
Metoda 200+ linii w serwisie monolitu — nie da się sensownie nadpisać fragmentu; wydzielenie daje jeden punkt wstrzykiwania mocków.
Przed 
class SettlementService {
  void settleBatch(List<Invoice> invoices) {
    Connection c = DbPool.get(); // static
    // ... 80 linii SQL, pętle, warunki ...
  }
}
Po 
class BatchSettlement {
  private final Connection conn;
  BatchSettlement(Connection conn) { this.conn = conn; }
  void run(List<Invoice> invoices) { /* ta sama logika */ }
}

class SettlementService {
  void settleBatch(List<Invoice> invoices) {
    new BatchSettlement(DbPool.get()).run(invoices);
  }
}

// test: BatchSettlement z H2 in-memory Connection

3. Definition Text Replacement (Zamiana tekstu definicji)

Co to jest (krótki opis)
W C/C++ Feathers podmienia makra/preprocesor; w Javie odpowiednik to testowe definicje (properties, stałe kompilacji w osobnym module) zamiast hardcoded stringów w kodzie.
Kiedy i po co stosować
Legacy czyta ścieżki, URL-e lub nazwy tabel z literałów w kodzie — bez możliwości uruchomienia produkcyjnej bazy w teście.
Przed 
class ReportExporter {
  void export() {
    Path out = Path.of("/var/monolith/reports/daily.csv");
    Files.writeString(out, buildCsv());
  }
}
Po 
class ReportExporter {
  private static final String OUT =
      System.getProperty("report.dir", "/var/monolith/reports") + "/daily.csv";

  void export() {
    Files.writeString(Path.of(OUT), buildCsv());
  }
}

// test JVM: -Dreport.dir=/tmp/test-reports
// lub @BeforeAll System.setProperty + @AfterAll clear

4. Encapsulate Global References (Enkapsuluj odwołania globalne)

Co to jest (krótki opis)
Bezpośredni dostęp do singletonów/statyków owijasz cienką klasą fasady, którą można zastąpić w teście.
Kiedy i po co stosować
ApplicationContextHolder.getBean(), SecurityContextHolder, własne Registry.getInstance() — rozproszone po setkach klas.
Przed 
class OrderNotifier {
  void send(Order o) {
    MailSender mail = ApplicationContextHolder.getBean(MailSender.class);
    mail.send(o.customerEmail(), "OK", body(o));
  }
}
Po 
interface BeanLookup { <T> T get(Class<T> type); }

class SpringBeanLookup implements BeanLookup {
  public <T> T get(Class<T> type) {
    return ApplicationContextHolder.getBean(type);
  }
}

class OrderNotifier {
  private final BeanLookup beans;
  OrderNotifier(BeanLookup beans) { this.beans = beans; }
  void send(Order o) {
    beans.get(MailSender.class).send(o.customerEmail(), "OK", body(o));
  }
}

5. Expose Static Method (Ujawnij metodę statyczną)

Co to jest (krótki opis)
Logika ukryta w prywatnej metodie instancyjnej staje się public static (lub package-private static), żeby testować ją bez całego obiektu i jego zależności.
Kiedy i po co stosować
Czysta funkcja (walidacja, kalkulacja) w środku klasy z 15 zależnościami w konstruktorze.
Przed 
class PolicyEngine {
  private final RuleRepository rules;
  Decision evaluate(Application app) {
    return applyRules(app, rules.loadFor(app.product()));
  }
  private Decision applyRules(Application app, List<Rule> rs) { /* ... */ }
}
Po 
class PolicyEngine {
  static Decision applyRules(Application app, List<Rule> rs) { /* ... */ }
  Decision evaluate(Application app) {
    return applyRules(app, rules.loadFor(app.product()));
  }
}

@Test void applyRules_rejects_underage() {
  assertThat(PolicyEngine.applyRules(minorApp(), rules))
      .isEqualTo(Decision.REJECT);
}

6. Extract and Override Factory Method (Wydziel i nadpisz metodę fabryki)

Co to jest (krótki opis)
new ProblematicType() ląduje w protected metodzie fabrykującej; w teście podklasa nadpisuje fabrykę i zwraca stub.
Kiedy i po co stosować
Klasa sama tworzy collaboratorów (parser pliku, klient HTTP) i nie możesz jeszcze wstrzyknąć konstruktora w całym monolicie.
Przed 
class ImportJob {
  void run(Path file) {
    CsvParser parser = new CsvParser();
    parser.parse(file, this::handleRow);
  }
}
Po 
class ImportJob {
  void run(Path file) { createParser().parse(file, this::handleRow); }
  protected CsvParser createParser() { return new CsvParser(); }
}

class ImportJobTest extends ImportJob {
  CsvParser fake;
  @Override protected CsvParser createParser() { return fake; }
}

7. Extract and Override Getter (Wydziel i nadpisz getter)

Co to jest (krótki opis)
Dostęp do pola-zależności przechodzi przez protected getter; testowa podklasa zwraca mock.
Kiedy i po co stosować
Pole inicjalizowane inline (private Mailer mailer = new SmtpMailer()) — konstruktor używany w 400 miejscach.
Przed 
class BillingFacade {
  private final PaymentGateway gateway = new BraintreeGateway();
  Receipt charge(Invoice i) { return gateway.charge(i); }
}
Po 
class BillingFacade {
  Receipt charge(Invoice i) { return getGateway().charge(i); }
  protected PaymentGateway getGateway() { return new BraintreeGateway(); }
}

class BillingFacadeTest extends BillingFacade {
  PaymentGateway mock = mock(PaymentGateway.class);
  @Override protected PaymentGateway getGateway() { return mock; }
}

8. Extract and Override Call (Wydziel i nadpisz wywołanie)

Co to jest (krótki opis)
Pojedyncze „niemożliwe” wywołanie (np. System.currentTimeMillis(), wysyłka) wydzielasz do protected metody i nadpisujesz w teście.
Kiedy i po co stosować
Determinizm czasu, losowości lub I/O w środku algorytmu — bez pełnej parametryzacji całej metody publicznej.
Przed 
class TokenIssuer {
  String issue(User u) {
    long exp = System.currentTimeMillis() + 3600_000;
    return sign(u.id(), exp);
  }
}
Po 
class TokenIssuer {
  String issue(User u) { return sign(u.id(), nowMillis() + 3600_000); }
  protected long nowMillis() { return System.currentTimeMillis(); }
}

class FixedClockIssuer extends TokenIssuer {
  @Override protected long nowMillis() { return 1_700_000_000_000L; }
}

Techniki 9–16

9. Extract Interface (Wydziel interfejs)

Co to jest (krótki opis)
Wycinasz interfejs z konkretnej klasy legacy i typujesz pole lub parametr interfejsem — produkcja zostaje przy starej implementacji.
Kiedy i po co stosować
Pierwszy krok przed modularyzacją monolitu: port w domenie, adapter w infrastrukturze (hexagonal).
Przed 
class ShipmentService {
  private final LegacyFedExClient fedEx = new LegacyFedExClient();
  void ship(Package p) { fedEx.book(p); }
}
Po 
interface CarrierClient { void book(Package p); }

class LegacyFedExClient implements CarrierClient { /* SOAP */ }

class ShipmentService {
  private final CarrierClient carrier;
  ShipmentService(CarrierClient carrier) { this.carrier = carrier; }
  void ship(Package p) { carrier.book(p); }
}

10. Introduce Implementer (Wprowadź implementatora)

Co to jest (krótki opis)
Interfejs już istnieje, ale klasa nadal sama wybiera implementację; wydzielasz osobną klasę-producenta (implementer), którą podmieniasz w teście.
Kiedy i po co stosować
Switch if (env.equals("PROD")) wybierający adapter — coupling do środowiska w jednym miejscu.
Przed 
class AuditWriter {
  void write(Event e) {
    AuditStore store = "PROD".equals(env())
        ? new DbAuditStore() : new NoOpAuditStore();
    store.append(e);
  }
}
Po 
interface AuditStoreImplementer { AuditStore create(); }

class AuditWriter {
  private final AuditStoreImplementer implementer;
  AuditWriter(AuditStoreImplementer impl) { this.implementer = impl; }
  void write(Event e) { implementer.create().append(e); }
}

// test: () -> mockStore

11. Introduce Instance Estimator (Wprowadź estymator instancji)

Co to jest (krótki opis)
Dodajesz metodę (lub hook), która szacuje lub zlicza ile obiektów danego typu powstanie przy wywołaniu — bez pełnego wykonania side effectów.
Kiedy i po co stosować
Charakteryzacja legacy: „czy ta metoda tworzy po cichu 500 obiektów DAO?” zanim podłączysz prawdziwą bazę.
Przed 
class CatalogSync {
  void refresh(List<Sku> skus) {
    for (Sku s : skus) {
      new ProductDao().upsert(s); // każde upsert = nowe DAO
    }
  }
}
Po 
class CatalogSync {
  int estimateDaoCreations(List<Sku> skus) {
    return skus.size(); // po refaktorze: jeden dao, tu tylko model
  }
  void refresh(List<Sku> skus, ProductDao dao) {
    for (Sku s : skus) dao.upsert(s);
  }
}

@Test void refresh_does_not_create_dao_per_row() {
  assertThat(sync.estimateDaoCreations(listOf(100))).isEqualTo(1);
}

12. Pass Mock Object (Przekaż obiekt-mock)

Co to jest (krótki opis)
Metoda publiczna przyjmuje collaboratora jako argument; produkcja przekazuje prawdziwy obiekt, test — mock/fake (Feathers: najprostszy seam).
Kiedy i po co stosować
Nowy kod obok legacy lub metoda już ma zbyt długą listę parametrów — akceptujesz jawne przekazanie zależności zamiast lookupu.
Przed 
class CommissionCalculator {
  Money forSalesperson(String id, YearMonth ym) {
    SalesLedger ledger = new SalesLedger(); // JDBC
    return ledger.total(id, ym).multiply(rate(id));
  }
}
Po 
class CommissionCalculator {
  Money forSalesperson(String id, YearMonth ym, SalesLedger ledger) {
    return ledger.total(id, ym).multiply(rate(id));
  }
}

@Test void commission() {
  SalesLedger ledger = mock(SalesLedger.class);
  when(ledger.total("A", ym)).thenReturn(Money.of("1000"));
  assertThat(calc.forSalesperson("A", ym, ledger)).isEqualTo(Money.of("50"));
}

13. Link Substitution (Podstawienie linku)

Co to jest (krótki opis)
Referencja (link) do obiektu w polu lub rejestrze jest podmieniana na inny obiekt tego samego typu (lub podtypu) w teście — bez zmiany kodu wywołującego.
Kiedy i po co stosować
Service locator z setterem, mapa handlerów, łańcuch odpowiedzialności — jeden element wymieniasz na fake.
Przed 
class Pipeline {
  private Handler head = new ValidateHandler(new PersistHandler(null));
  void process(Request r) { head.handle(r); }
}
Po 
class Pipeline {
  Handler head = new ValidateHandler(new PersistHandler(null));
  void setHead(Handler h) { this.head = h; } // seam testowy
  void process(Request r) { head.handle(r); }
}

@Test void process() {
  Pipeline p = new Pipeline();
  Handler spy = spy(new ValidateHandler(mock(PersistHandler.class)));
  p.setHead(spy);
  p.process(req);
  verify(spy).handle(req);
}

14. Parameterize Constructor (Parametryzuj konstruktor)

Co to jest (krótki opis)
Zależności wchodzą przez konstruktor zamiast new wewnątrz klasy — klasyczne DI umożliwiające test jednostkowy.
Kiedy i po co stosować
Refaktoryzacja modułu monolitu pod Spring / ręczny composition root; każde new Repository() w serwisie.
Przed 
class CustomerService {
  Customer find(UUID id) {
    return new JdbcCustomerRepository().findById(id);
  }
}
Po 
class CustomerService {
  private final CustomerRepository repo;
  CustomerService(CustomerRepository repo) { this.repo = repo; }
  Customer find(UUID id) { return repo.findById(id); }
}

@Test void find() {
  var repo = mock(CustomerRepository.class);
  when(repo.findById(id)).thenReturn(customer);
  assertThat(new CustomerService(repo).find(id)).isSameAs(customer);
}

15. Parameterize Method (Parametryzuj metodę)

Co to jest (krótki opis)
Zależność przekazujesz jako argument metody biznesowej (nie konstruktora), gdy tylko część wywołań potrzebuje innej implementacji.
Kiedy i po co stosować
Publiczne API już stabilne; nie chcesz ruszać fabryk Springa, ale jedna metoda musi być testowalna.
Przed 
class StatementGenerator {
  Pdf generate(Account a) {
    ExchangeRates rates = new EcbRatesClient().fetch();
    return render(a, rates);
  }
}
Po 
class StatementGenerator {
  Pdf generate(Account a, ExchangeRates rates) {
    return render(a, rates);
  }
  Pdf generate(Account a) {
    return generate(a, new EcbRatesClient().fetch());
  }
}

@Test void generate_uses_passed_rates() {
  ExchangeRates fixed = (from, to) -> BigDecimal.ONE;
  assertThat(gen.generate(account, fixed).pages()).isEqualTo(1);
}

16. Prick Create („Ukłucie” tworzenia)

Co to jest (krótki opis)
Celowo „pękasz” punkt tworzenia obiektu (np. wyjątek w konstruktorze testowym), żeby zobaczyć skąd w stack trace leci new — mapa coupling przed refaktoryzacją.
Kiedy i po co stosować
Nie wiesz, ile miejsc tworzy dany typ w gigantycznym module; przygotowujesz Parameterize Constructor / Extract Interface.
Przed 
// rozproszone: new SmsGateway() w 12 klasach
class AlertService {
  void ping(User u) { new SmsGateway().send(u.phone(), "ALERT"); }
}
Po (test diagnostyczny + seam) 
class PrickSmsGateway extends SmsGateway {
  PrickSmsGateway() { throw new IllegalStateException("PRICK: creation site"); }
}

// tymczasowo w kodzie prod (branch): new PrickSmsGateway() → uruchom test integracyjny
// stack trace wskaże wszystkie ścieżki; potem:
class AlertService {
  AlertService(SmsGateway sms) { this.sms = sms; }
}

Techniki 17–24

17. Pull Up Dependency (Podciągnij zależność)

Co to jest (krótki opis)
Wspólną zależność z podklas przenosisz do klasy bazowej (pole + konstruktor protected), żeby testowa podklasa bazowa miała jeden punkt podstawienia.
Kiedy i po co stosować
Hierarchia AbstractBatchJob z duplikowanym new JobRepository() w każdej podklasie.
Przed 
class NightlyJob extends Job {
  void run() { new JobRepository().markDone("nightly"); }
}
class HourlyJob extends Job {
  void run() { new JobRepository().markDone("hourly"); }
}
Po 
abstract class Job {
  protected final JobRepository repo;
  protected Job(JobRepository repo) { this.repo = repo; }
}
class NightlyJob extends Job {
  void run() { repo.markDone("nightly"); }
}

@Test void nightly() { new NightlyJob(fakeRepo).run(); /* ... */ }

18. Push Down Dependency (Spchnij zależność)

Co to jest (krótki opis)
Zależność używana tylko w jednej podklasie zostaje usunięta z klasy bazowej i trafia do tej podklasy — mniejszy coupling reszty hierarchii.
Kiedy i po co stosować
Baza w monolicie ma pole PaymentGateway, ale tylko OnlineCheckout z niego korzysta — testy innych podklas nie powinny go mockować.
Przed 
abstract class Checkout {
  protected PaymentGateway gateway = new BraintreeGateway();
}
class OnlineCheckout extends Checkout { /* używa gateway */ }
class InvoiceCheckout extends Checkout { /* gateway martwy */ }
Po 
abstract class Checkout { /* brak gateway */ }
class OnlineCheckout extends Checkout {
  private final PaymentGateway gateway;
  OnlineCheckout(PaymentGateway g) { this.gateway = g; }
}
class InvoiceCheckout extends Checkout { /* czyste testy */ }

19. Replace Function with Function Pointer (Zamień funkcję na wskaźnik funkcji)

Co to jest (krótki opis)
W Javie: zamiast sztywnego wywołania metody wstawiasz FunctionalInterface (Supplier, Function, własny callback), który można podmienić.
Kiedy i po co stosować
Legacy woła statyczną funkcję pomocniczą (IdGenerator.next(), hash) — trudna do stubowania bez PowerMock.
Przed 
class IdempotencyGuard {
  String key(Request r) {
    return r.path() + ":" + UUID.randomUUID();
  }
}
Po 
class IdempotencyGuard {
  private final Supplier<UUID> uuid;
  IdempotencyGuard(Supplier<UUID> uuid) { this.uuid = uuid; }
  String key(Request r) { return r.path() + ":" + uuid.get(); }
}

@Test void stable_key() {
  var guard = new IdempotencyGuard(() -> UUID.fromString("00000000-0000-0000-0000-000000000001"));
  assertThat(guard.key(req)).endsWith("00000000-0000-0000-0000-000000000001");
}

20. Replace Global Reference with Getter (Zamień odwołanie globalne getterem)

Co to jest (krótki opis)
Bezpośredni odczyt pola statycznego/globalnego zastępujesz metodą-instancją (lub statyczną) gettera, którą nadpisujesz w teście.
Kiedy i po co stosować
Config.FEATURE_X, public static DbConnection connection — globalny stan blokujący równoległe testy.
Przed 
class FeatureRouter {
  Handler route(Request r) {
    if (Config.FEATURE_NEW_FLOW) return new NewFlowHandler();
    return new LegacyHandler();
  }
}
Po 
class FeatureRouter {
  boolean newFlowEnabled() { return Config.FEATURE_NEW_FLOW; }
  Handler route(Request r) {
    return newFlowEnabled() ? new NewFlowHandler() : new LegacyHandler();
  }
}

class TestRouter extends FeatureRouter {
  boolean flag;
  @Override boolean newFlowEnabled() { return flag; }
}

21. Subclass and Override Method (Podklasa i nadpisanie metody)

Co to jest (krótki opis)
Testowa podklasa nadpisuje metodę produkcyjną, żeby wyłączyć side effect lub zwrócić stałą — bez modyfikacji kodu produkcyjnego poza protected widocznością.
Kiedy i po co stosować
Klasa final nie jest — szybki test przed większą refaktoryzacją; współgra z Extract and Override Call.
Przed 
class ReportJob {
  void execute() {
    List<Row> data = loadFromWarehouse();
    email(data);
  }
  private void email(List<Row> data) { /* SMTP */ }
}
Po 
class ReportJob {
  void execute() { email(loadFromWarehouse()); }
  protected void email(List<Row> data) { /* SMTP */ }
}

class ReportJobTest extends ReportJob {
  List<Row> captured;
  @Override protected void email(List<Row> data) { captured = data; }
}

22. Supersede Instance Variable (Zastąp pole instancji)

Co to jest (krótki opis)
Po wydzieleniu interfejsu zamieniasz typ pola z klasy konkretnej na abstrakcję i przypisujesz implementację w konstruktorze lub setterze testowym.
Kiedy i po co stosować
Po Extract Interface — pole nadal ma typ LegacyHttpClient zamiast HttpClient.
Przed 
class CrmSync {
  private LegacyHttpClient client = new LegacyHttpClient();
  void push(Contact c) { client.post("/contacts", c); }
}
Po 
interface HttpClient { void post(String path, Object body); }

class CrmSync {
  private HttpClient client;
  CrmSync(HttpClient client) { this.client = client; }
  void push(Contact c) { client.post("/contacts", c); }
}

@Test void push() {
  HttpClient mock = mock(HttpClient.class);
  new CrmSync(mock).push(contact);
  verify(mock).post("/contacts", contact);
}

23. Template Method (Metoda szablonowa)

Co to jest (krótki opis)
Szkielet algorytmu zostaje w klasie bazowej; warianty (kroki zmienne) w metodach protected abstract / hookach — testujesz krok bez całego workflow.
Kiedy i po co stosować
Duplikacja sekwencji „pobierz → waliduj → zapisz” w wielu serwisach monolitu z różnym tylko „zapisz”.
Przed 
class ImportCsvService {
  void importFile(Path p) {
    List<Row> rows = parse(p);
    validate(rows);
    jdbcBatchInsert(rows);
  }
}
Po 
abstract class ImportTemplate {
  final void importFile(Path p) {
    List<Row> rows = parse(p);
    validate(rows);
    persist(rows);
  }
  protected abstract void persist(List<Row> rows);
}

class ImportCsvService extends ImportTemplate {
  @Override protected void persist(List<Row> rows) { jdbcBatchInsert(rows); }
}

@Test void validate_only() {
  var t = new ImportTemplate() {
    @Override protected void persist(List<Row> r) { }
  };
  assertThrows(ValidationException.class, () -> t.importFile(badFile));
}

24. Text Redirection (Przekierowanie tekstu)

Co to jest (krótki opis)
Wejście/wyjście tekstowe (pliki konfiguracyjne, SQL skrypt, stdin/stdout) przekierowujesz na zasób testowy — odpowiednik Feathersa dla I/O tekstowego.
Kiedy i po co stosować
Legacy ładuje reguły z pliku na dysku lub wypisuje raport na System.out — bez mockowania całego frameworka.
Przed 
class RuleLoader {
  List<Rule> load() throws IOException {
    return parse(Files.readString(Path.of("/etc/monolith/rules.yaml")));
  }
}
Po 
class RuleLoader {
  List<Rule> load(Path rulesFile) throws IOException {
    return parse(Files.readString(rulesFile));
  }
  List<Rule> load() throws IOException {
    return load(Path.of("/etc/monolith/rules.yaml"));
  }
}

@Test void load() throws Exception {
  Path tmp = Files.writeString(tempFile, "rules: []\n");
  assertThat(new RuleLoader().load(tmp)).isEmpty();
}

Mapa: kiedy którą technikę

Problem w monolicieTechniki (kolejność prób)
new w metodzieExtract and Override Factory, Parameterize Constructor/Method, Pass Mock
Static / singletonEncapsulate Global, Replace Global with Getter, Expose Static
Pliki / config / stdoutText Redirection, Definition Text Replacement
Metoda-gigantBreak Out Method Object, Template Method
Hierarchia klasPull Up / Push Down Dependency, Subclass and Override
Przed modułami MavenExtract Interface → Supersede Instance Variable → Introduce Implementer
Nie wiesz skąd couplingPrick Create, Introduce Instance Estimator
Los / czas / IDExtract and Override Call, Replace Function with Function Pointer

Typowe błędy

  • Big Bang DI — parametryzacja całego monolitu zamiast jednego seamu pod jeden test.
  • PowerMock jako pierwszy wybór — maskuje design; preferuj Extract Interface lub override getter.
  • Testy integracyjne zamiast unit — uruchamianie pełnego Springa + Oracle „bo tak było” nie zastępuje przełamania zależności.
  • Public settery tylko dla testów — w produkcji każdy może podmienić zależność; lepszy konstruktor package-private + test w tym samym pakiecie lub seam protected.
  • Extract Interface bez Supersede — interfejs istnieje, pole nadal trzyma klasę legacy.
  • Subclass and Override na klasach final — w Javie wymaga usunięcia final (świadoma decyzja) lub innej techniki.
  • Prick Create na produkcji — wyłącznie krótkotrwały branch diagnostyczny, nigdy deploy.
  • Definition Text Replacement bez dokumentacji — magiczne -D w CI bez opisu w README zespołu (u was: w composition root / Helm values).
  • Method Object bez limitu — wydzielasz cały serwis zamiast jednej metody; seam ginie w nowym bogactwie.
  • Ignorowanie characterization tests — przed refaktoryzacją brak testu „zapisującego obecne zachowanie”; regresja przy migracji do nowej architektury.
