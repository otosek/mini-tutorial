Część 0 — Fundamenty

Struktury probabilistyczne w Redis to kompaktowe struktury, które świadomie rezygnują z pełnej dokładności na rzecz stałego (lub logarytmicznego) zużycia pamięci i wysokiej przepustowości. W Redis Stack większość z nich dostarcza moduł RedisBloom (Bloom, Cuckoo, CMS, Top-K, t-digest); wyjątkiem jest HyperLogLog — wbudowany w rdzeń Redis od lat (prefiks PF*).

Jedno zdanie podsumowujące: wybierasz strukturę według pytania biznesowego („czy element był już widziany?”, „ile unikalnych?”, „ile razy klucz?”, „kto w topie?”, „jaki percentyl latencji?”), a nie według nazwy modułu.

Redis Stack vs open-source Redis

RedisBloom i pozostałe moduły Stack wymagają obrazu redis/redis-stack (lub managed Redis Enterprise / Cloud ze Stack). Czysty redis:7 bez modułów obsługuje tylko HyperLogLog i klasyczne typy (string, set, hash…).

Bloom Filter i Cuckoo Filter

Oba odpowiadają na pytanie membership: „czy ten klucz (URL, ID użytkownika, hash pliku) był już dodany?”. Odpowiedź nie ma jest wiarygodna; odpowiedź może być wymaga weryfikacji w źródle prawdy (DB, object storage).

1. Bloom Filter

  • Co jest pewne: Jeśli BF.EXISTS zwraca 0, element na pewno nie był dodany do tego filtra (przy braku resetu struktury i poprawnej semantyce klucza). Nie ma false negatives — negatywny wynik testu membership jest deterministyczny.
  • Co jest niepewne (Błąd): Wynik 1 oznacza „prawdopodobnie jest” — możliwy false positive z prawdopodobieństwem zależnym od parametrów BF.RESERVE (error_rate, capacity). Po przekroczeniu założonej pojemności FP rośnie; Bloom nie obsługuje usuwania pojedynczych elementów bez rebuild całej struktury.
  • Najczęstsze zastosowania: (1) Cache aside / deduplikacja zdarzeń — przed kosztownym odczytem z DB sprawdzasz Bloom „czy ten event_id już przetworzyliśmy”. (2) Anti-spam i rate limiting wstępny — szybki filtr „czy ten fingerprint IP+UA widzieliśmy w oknie” przed pełnym licznikiem token bucket. (3) Web crawler / CDN — unikanie wielokrotnego pobierania tych samych URL-i już odwiedzonych w shardzie.

1b. Cuckoo Filter (wariant membership z delete)

  • Co jest pewne: Tak jak Bloom: CF.EXISTS = 0 ⇒ element definitywnie nie występuje w filtrze. Dodatkowo CF.DEL usuwa wcześniej wstawiony element — operacja poprawna w sensie struktury (w Bloom delete bez rebuild jest niemożliwe).
  • Co jest niepewne (Błąd): Nadal występują false positives (parametry CF.RESERVE: capacity, bucket size, max iterations). Przy przepełnieniu (CF.ADD zwraca błąd insert) musisz zwiększyć capacity lub shardować filtry — inaczej tracisz gwarancję „brak FP” tylko wtedy, gdy insert się powiódł.
  • Najczęstsze zastosowania: (1) Sliding window dedup — elementy wypadają z okna przez CF.DEL lub rotację kluczy Redis bez pełnego rebuild Bloom. (2) Graph / recommendation prefetch — „czy już proponowaliśmy parę (user, item)” z możliwością cofnięcia po expire sesji. (3) Stream processing — exactly-once logiczne przez membership z TTL na poziomie aplikacji (rotacja CF per partition).
# Bloom — rezerwacja i insert (RedisBloom)
BF.RESERVE urls_seen 0.001 10000000
BF.ADD urls_seen "https://example.com/a"
BF.EXISTS urls_seen "https://example.com/b"   # 0 = na pewno nie było

# Cuckoo — delete
CF.RESERVE sessions 1000000
CF.ADD sessions "sess:abc"
CF.DEL sessions "sess:abc"

Pułapka: false positive w filtrze membership zawsze wymaga drugiego etapu (DB, set Redis) — projektuj ścieżkę „BF miss → tani odczyt”, „BF hit → drogi confirm”.

HyperLogLog

2. HyperLogLog

  • Co jest pewne: Struktura nigdy nie zwraca dokładnej liczby unikalnych — zawsze estymacja. Pewne jest natomiast ograniczenie pamięci: ~12 KB na klucz HLL przy standardowej precyzji (domyślnie sparse/dense w Redis), niezależnie od liczby obserwowanych elementów (miliardy hashy nadal ~stały rozmiar).
  • Co jest niepewne (Błąd): Błąd względny cardinality jest statystyczny, typowo ~0.81% (standard error dla domyślnej precyzji Redis). Merge (PFMERGE) sumuje estymacje zbiorów rozłącznych; przy dużym overlap merge daje zawyżoną cardinality — to błąd modelu użycia, nie „bug Redis”.
  • Najczęstsze zastosowania: (1) UV / DAU / unikalni użytkownicy — PFADD stats:2025-10-04 userId bez trzymania setu milionów ID. (2) Metryki SRE — unikalne IP, unikalne trace_id na minutę w pipeline observability. (3) A/B i analityka produktowa — przybliżona liczba unikalnych viewerów kampanii per shard z PFMERGE na agregatorze.
PFADD uv:daily:20251004 "user:8812" "user:9910"
PFCOUNT uv:daily:20251004
PFMERGE uv:week41 uv:daily:20251004 uv:daily:20251005

Dla dokładnej cardinality (np. rozliczenia finansowe) użyj SET / DB — HLL to świadomy kompromis operacyjny.

Count-Min Sketch

3. Count-Min Sketch (CMS)

  • Co jest pewne: Zapytanie CMS.QUERY zwraca licznik, który jest ≥ rzeczywistej liczby wystąpień danego klucza (w modelu increment-only bez resetu). Count-Min Sketch to estymator górny — nigdy nie zaniża countu przez kolizje hashy w macierzy depth×width.
  • Co jest niepewne (Błąd): Wartość może być zawyżona (overestimate) przez kolizje innych kluczy w tych samych komórkach; wielkość błędu zależy od width i depth (CMS.INITBYPROB / INITBYDIM). Nie rozróżniasz „hot key” z count 1M od sąsiada z count 10 — obaj mogą „pompować” wspólne komórki.
  • Najczęstsze zastosowania: (1) Heavy hitter detection — identyfikacja kluczy API przekraczających próg zapytań bez trzymania hashmapy wszystkich klientów. (2) CDN / edge — popularność obiektów — przybliżone county URI do decyzji prefetch vs eviction. (3) Network security — licznik pakietów per flow (5-tuple skrócony) w anty-DDoS przed pełnym DPI.
CMS.INITBYPROB traffic 0.001 0.01
CMS.INCRBY traffic "client:42" 1
CMS.INCRBY traffic "client:42" 1
CMS.QUERY traffic "client:42"    # >= 2

Top-K

4. Top-K

  • Co jest pewne: Struktura utrzymuje co najwyżej K kandydatów na „najczęstsze” klucze w fixed memory. Element, który konsekwentnie dominuje countami, zostanie w strukturze; elementy o countach poniżej progu detekcji mogą w ogóle nie trafić do listy — to pewna właściwość algorytmu (HeavyKeeper / Space-Saving), nie pełny ranking.
  • Co jest niepewne (Błąd): W liście top-K mogą pojawić się false positives (klucz chwilowo „wskoczył” przez fluktuację). Raportowane TOPK.COUNT to estymaty — mogą odbiegać od prawdziwego countu w strumieniu; kolejność miejsc 4–K bywa niestabilna przy podobnych countach.
  • Najczęstsze zastosowania: (1) Realtime leaderboard / trending — hashtag, produkt, endpoint REST w oknie czasu bez sortowania milionów wierszy. (2) Observability — top slow endpoints — w parze z CMS lub metrykami aplikacji: Top-K na kluczu „route+status”. (3) Fraud / abuse — bieżąca lista top kont wysyłających transakcje w streamie Kafka konsumowanym przez Redis.
TOPK.RESERVE trending 50 2000 8 0.9
TOPK.ADD trending "item:7" "item:3" "item:7"
TOPK.LIST trending
TOPK.COUNT trending "item:7"

t-digest

5. t-digest

  • Co jest pewne: Po dodaniu próbek (TDIGEST.ADD) struktura daje stabilne estymaty quantili w „ciężkim centrum” rozkładu (mediana, p50, p90 przy typowych rozkładach latencji) przy bounded memory (parametr compression). Merge digestów (TDIGEST.MERGE) jest asocjatywny — sensowny dla agregacji per-node → global w observability.
  • Co jest niepewne (Błąd): W ogonach rozkładu (p99.9, p99.99, min/max ekstremalne) błąd względny rośnie — t-digest świadomie alokuje mniej „rozdzielczości” na tails. Pojedyncze outliery mogą być zbyt mocno „ściśnięte” przy niskim compression; dla SLA strict tail lepszy bywa HDR Histogram / raw sample w krótkim oknie.
  • Najczęstsze zastosowania: (1) SLO latencji API — p95/p99 czasu odpowiedzi z milionów requestów/dzień w jednym kluczu Redis per service. (2) FinOps / billing usage — percentyle wielkości payloadu, czasu jobów batch bez exportu do TSDB. (3) Capacity planning — rozkład rozmiaru koszyka, czasu sesji — decyzje o shardingu i limitach.
TDIGEST.CREATE latency:checkout 100
TDIGEST.ADD latency:checkout 12 45 38 1200 41
TDIGEST.QUANTILE latency:checkout 0.95
TDIGEST.CDF latency:checkout 100

W Redis Cluster klucz probabilistyczny musi być w tym samym hash slot co powiązane dane albo stanowić samodzielny klucz globalny — unikaj wielu struktur rozproszonych po slotach bez merge na aplikacji.

Wzorzec architektoniczny

Request / event → (1) Bloom/CF membership — odrzut duplikatów → (2) CMS / Top-K — hot keys w strumieniu → (3) HLL — unikalni per dzień → (4) t-digest — percentyle latencji per service → Źródło prawdy (Postgres, S3, TSDB) tylko gdy filtr lub SLA tego wymaga

Warstwa probabilistyczna siedzi przed drogimi systemami: Redis nie zastępuje ledgera ani dokładnego analytics warehouse — redukuje koszt I/O i pamięć na ścieżce gorącej.

Typowe błędy

  • Traktowanie Bloom/Cuckoo „1” jako pewnego membership — zawsze confirm w źródle prawdy; FP to feature, nie bug.
  • Przekroczenie capacity Bloom bez resize — rosnące FP; monitoruj fill i planuj nowy klucz / sharding.
  • Delete w Bloom — niemożliwe poprawnie; użyj Cuckoo lub rotacji kluczy czasowych.
  • HLL jako dokładny UV do rozliczeń — błąd ~1% może być niedopuszczalny prawnie/finansowo.
  • PFMERGE na zbiorach z dużym overlap — zawyżona cardinality; deduplikuj na poziomie kluczy dziennych.
  • CMS jako licznik „dokładny” — overestimate; progi decyzyjne ustaw z zapasem.
  • Top-K jako kompletny ranking — elementy poniżej progu znikają na zawsze z perspektywy struktury.
  • t-digest p99.99 do alertów bez kalibracji — tails wymagają wyższego compression lub innego pipeline.
  • Brak modułu RedisBloom na prod — komendy BF.* / TDIGEST.* fail; tylko HLL działa na vanilla Redis.
  • Jeden wielki klucz probabilistyczny w Cluster — hot spot; sharduj po prefiksie (np. bf:{hash%256}).
